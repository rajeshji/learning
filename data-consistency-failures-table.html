Why Data Consistency Failures Are the Most Dangerous

Data consistency failures affect: correctness + trust + financial accuracy + user state Unlike infra failures, consistency failures are dangerous because: system may appear completely healthy while data is silently wrong 7 root causes of consistency failures: missing data | duplicate data | stale data | out-of-order data partial state | concurrent conflicts | replica divergence

1 — Missing and Lost Data Failures
Lost WriteMust Know Write acknowledged to client but not actually persisted (async flush, pre-commit ack) Audit mismatch, reconciliation gaps, missing records Replay from WAL or event log Durable writes — ack only after commit to disk Missing state propagates — downstream services act on absent data Strong durability increases write latency
Message / Event LossMust Know Broker crash, network failure, consumer ack before processing Sequence gap detection, consumer lag anomaly Replay events from durable log (Kafka, WAL) Persistent queues, acks-after-processing, replication Missing workflow steps — order never fulfilled, payment not triggered Persistent brokers cost more; replication adds latency
Dropped Transaction Transaction silently aborted — timeout, deadlock, infra failure mid-commit Reconciliation mismatch, expected record not found Retry or reprocess the transaction Atomic commits, proper timeout handling, dead-letter queues Financial or state inconsistency — one side updated, other not Retries without idempotency may create duplicates
Checkpoint Loss Process crashes before checkpoint is flushed to durable storage Recovery inconsistency, replay starts from wrong offset Restore from previous valid snapshot Synchronous checkpoint flush, frequent checkpointing Recovery rolls back too far — re-processes old events → duplicates More frequent checkpoints increase IO and latency
2 — Duplicate Data and Double Processing Failures
Duplicate ProcessingMust Know At-least-once delivery retries the same message Duplicate record IDs, repeated side effects in logs Deduplication store, idempotency key lookup Idempotent consumers, exactly-once semantics where critical Double payment, double order, double notification Deduplication store adds storage and lookup overhead
Duplicate Events Producer retries after uncertain acknowledgement Duplicate event IDs detected at consumer Ignore/drop duplicates by event ID Exactly-once producer semantics (Kafka idempotent producer) Multiple downstream side effects — charges, records, notifications Exactly-once semantics add implementation complexity
Double Spend / Double BookingMust Know Concurrent requests race to reserve same resource DB constraint violation, reconciliation anomaly Rollback one request, compensating action Serializable isolation, pessimistic locking, inventory reservation Financial loss, oversold inventory, customer trust damage Strong locking reduces concurrent throughput significantly
Repeated Workflow Execution Orchestrator retries a workflow that already ran Duplicate workflow states, repeated output records Workflow deduplication by workflow ID Unique workflow IDs, check-before-execute pattern Duplicate notifications, payments, or external API calls Stateful orchestration adds operational overhead
3 — Stale and Outdated Data Failures
Stale ReadMust Know Read routed to replica lagging behind leader Replica lag metrics, user-visible data mismatch Route critical reads to primary/leader Quorum reads, session consistency, bounded staleness User sees old data → acts on it → business state corruption Reading from primary reduces read scalability
Read-After-Write Inconsistency User writes then reads — read routed to stale replica User-visible mismatch immediately after update Sticky session routing — read from primary after write Read-your-writes consistency, session tokens User makes wrong business decision based on stale own write Sticky sessions reduce load balancing effectiveness
Cache InconsistencyMust Know Cache not invalidated after DB update Cache value differs from DB value, user complaints Invalidate cache on write, force cache refresh Write-through cache, TTL-based expiry, cache-aside with short TTL Stale data served at scale — wrong prices, balances, inventory Aggressive invalidation increases cache miss rate and DB load
Outdated Materialized View Async aggregation pipeline lags behind source events View-to-source lag metrics, wrong analytics results Refresh/rebuild the materialized view Faster stream processing, CDC-based view updates Incorrect analytics, recommendations, dashboards used for decisions Faster refresh increases compute cost significantly
4 — Ordering and Sequencing Failures
Out-of-Order Event ProcessingMust Know Distributed consumers process events in wrong sequence Sequence mismatch in output, invalid state transitions Reorder and replay events using sequence numbers Per-key ordered queues (Kafka partitioning by entity key) Invalid workflow state — cancel processed before create Strict ordering reduces consumer parallelism
Reordered Writes Async replication or network delay causes writes to arrive out of order Timestamp or version mismatch between replicas Conflict resolution — LWW, version vectors Single-writer model per entity, monotonic write ordering Inconsistent replicas — different nodes show different history Single writer per entity limits write throughput
Clock Skew Ordering Error Nodes have different wall-clock times — NTP drift Timestamp-based ordering anomalies, wrong TTL behaviour Use logical clocks (Lamport) or vector clocks for ordering Reliable NTP sync, avoid wall-clock-based ordering Wrong TTL expiry, wrong event ordering, wrong data freshness decisions Logical clocks add complexity; vector clocks scale poorly
Late Event Arrival Network delay or broker backlog delivers event long after event time Event-time vs processing-time lag metrics Watermark-based window buffering, late event reprocessing Proper event-time handling in stream processor (Flink, Spark) Incorrect aggregates, metrics, and analytics outputs Wider watermark windows increase processing latency
5 — Partial State and Transaction Failures
Partial Transaction CommitMust Know Multi-service operation — one step succeeds, another fails Cross-service reconciliation mismatch Saga compensating transactions to undo completed steps Avoid 2PC; design idempotent, retryable saga steps Payment deducted but order not created — financial harm to user 2PC hurts availability; Saga adds design and testing complexity
Saga Compensation Failure Compensating transaction also fails — cannot undo the partial work Workflow stuck in compensating state, no resolution Retry compensation with backoff; manual intervention fallback Idempotent compensation actions, retry with persistent tracking Permanent inconsistent state — requires manual reconciliation Saga orchestration complexity grows with step count
Half-Processed Workflow Worker crashes mid-process, state not saved Workflow stuck with no progress, orphaned partial records Resume or retry workflow from last durable checkpoint Durable workflow state (Temporal, step functions), checkpointing Downstream services waiting on result never get it Durable workflow state adds infrastructure and operational overhead
Cross-Service State Mismatch Async update propagates slowly — services temporarily out of sync Reconciliation job finds mismatched entities across services Re-sync via event replay or reconciliation job Event-driven consistency, outbox pattern, CDC Business logic acts on stale state → incorrect downstream decisions Eventual consistency means window of inconsistency always exists
6 — Replica and Replication Failures
Replica DivergenceMust Know Replication gap or network error leaves replica with different data Checksum mismatch, version comparison between replicas Read repair, anti-entropy sync from leader Quorum replication, synchronous replication on critical paths Different users reading different replicas see different data More replication traffic increases bandwidth cost
Replication LagMust Know Follower falls behind leader — slow network, large write burst Replica lag metrics (seconds behind leader) Route critical reads to leader, bounded staleness Tune replication pipeline, use synchronous replication where needed Stale reads cascade — users and downstream see old data at scale Synchronous replication increases write latency significantly
Split Brain Replication Network partition + multiple leaders both accept writes Multiple leaders detected, write divergence alerts Reconcile conflicting writes after partition heals Consensus-based systems (Raft/Paxos), fencing tokens Massive inconsistency — both sides have different truth Strong consistency during partition reduces availability
Failed Replica Repair Repair process interrupted — replica partially rebuilt Persistent divergence after repair attempt Full replica rebuild from primary Better repair scheduling, incremental repair strategies Long-term inconsistency if undetected — reads from bad replica Full rebuild increases network and disk IO significantly
7 — Concurrency and Conflict Failures
Race Condition (Data)Must Know Two concurrent operations read-modify-write same record Inconsistent or incorrect final state, anomalous data Locking, compare-and-swap, version field check Atomic operations, serializable isolation, immutable records Corrupted shared state propagates to all readers Locks reduce concurrent throughput
Lost UpdateMust Know Concurrent writers — last write silently overwrites earlier write Version mismatch, missing intermediate values Optimistic locking — check version before commit Serializable transactions, CAS operations Silent data corruption — no error, just wrong data Strong isolation levels hurt concurrent write throughput
Write Conflict Multiple writers updating same entity in distributed system Conflict detected at merge or commit time Merge with LWW / CRDT / application-level logic Single-writer ownership per entity Replica inconsistency — merged state may be wrong Merge logic adds significant design complexity
8 — Schema and Serialization Consistency Failures
Schema MismatchMust Know Producer and consumer use incompatible schema versions Serialization/deserialization failures in consumer Fallback parsing, schema version routing Schema registry (Confluent), backward-compatible evolution Entire processing pipeline fails — all consumers error out Multi-schema support adds complexity to producer and consumer
Backward Compatibility Failure Old client receives new message it cannot decode API decode errors, unexpected null fields, parse failures Version routing, support multiple schema versions Expand-contract migration, never remove fields without deprecation Cross-service breakage — all old clients fail simultaneously Slower expand-contract migrations delay feature delivery
Serialization Corruption Encoding/decoding bug — partial write, bit flip, format mismatch Parse failures, garbled records, checksum mismatch Replay/reprocess from raw durable source Strict schema validation, checksums, CRC on records Event processing pipeline halts entirely Validation and checksums add per-record overhead

Staff-Level Data Consistency Thinking — 7 Questions to Ask Always

1. Can data be LOST? → durable writes, acks after commit, persistent queues 2. Can data be DUPLICATED? → idempotency keys, exactly-once semantics, dedup store 3. Can reads become STALE? → quorum reads, read from primary, bounded staleness 4. Can ORDERING break? → per-key partitioning, sequence numbers, vector clocks 5. Can workflows PARTIALLY COMPLETE? → Saga + compensating actions, outbox pattern 6. Can REPLICAS DIVERGE? → quorum replication, read repair, consensus 7. Can CONCURRENT WRITES CONFLICT? → optimistic locking, CAS, serializable isolation

Silent vs Loud Failures — Why Silent Is Most Dangerous

Loud Failure (Obvious)

  • Service crashes — error is visible
  • Alerts fire immediately
  • Rollback is clear and quick
  • Impact scope is obvious

Silent Inconsistency (Most Dangerous)

  • System appears fully healthy
  • No errors in logs or alerts
  • Corruption spreads slowly
  • Users lose trust gradually
  • Reconciliation is costly and slow
  • May not be found until audit

Final Mental Model — All Data Consistency Failures Reduce to 6 States

1. Missing → data was never written or was lost 2. Duplicate → same data written more than once 3. Stale → old version served instead of current 4. Partial → workflow or transaction only half-completed 5. Conflicting → two versions exist with no clear winner 6. Out-of-order → events processed in wrong sequence Hardest failures = silent inconsistencies system healthy → data wrong → trust damaged → reconciliation required
