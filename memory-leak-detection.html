Memory Leak Detection

valgrind, jmap, pmap, top — Staff Engineer level

The Big Picture

When memory is never released, the application grows continuously until performance drops, GC pauses increase, swapping begins, OOM occurs, or Kubernetes kills the container.

Memory leak detection identifies where memory is retained and why it cannot be reclaimed.

Allocate Memory → Use Memory → Object No Longer Needed ↓ Reference Still Exists → GC Cannot Free → Memory Grows → OOM

What is a Memory Leak?

Native (C/C++)

Memory allocated via malloc()/new is never released. Memory permanently leaks.

Managed (Java/Go/.NET)

Objects remain reachable via references — GC cannot free them. More accurately called Memory Retention.

Memory Growth vs Memory Leak

Not every growing process has a leak. Staff Engineers distinguish normal growth first.

SituationMemory Leak?
Growing Page Cache❌ No
jemalloc Arena Growth❌ Usually No
JVM Heap Growth with Stable Live Set❌ Normal
Cache Without Eviction✅ Yes
Static Map Continuously Growing✅ Yes
malloc() Without free()✅ Yes

Investigation Flow — Outside to Inside

System Metrics (top/RSS) ↓ Process Memory (pmap) ↓ Heap Growth (jstat / pprof) ↓ Heap Snapshot (jmap / heapdump) ↓ Object Retention (Dominator Tree) ↓ Allocation Site (GC Root Path) ↓ Root Cause → Fix → Validate

Never start by reading code. Start with measurements.

OS-Level Detection — top, pmap, /proc

First confirm whether process memory is actually growing.

MetricMeaning
RSSActual physical memory in use
VIRTVirtual address space size
%MEMProcess memory as % of total
SWAPSwapped-out memory
# Live process overview top / htop # Memory mappings per segment pmap -x <PID> # Detailed mappings /proc/<PID>/smaps # System-wide memory /proc/meminfo

A continuously increasing RSS often indicates a leak or memory retention.

Valgrind — Native C/C++ Leak Detection

Gold standard for native memory leaks. Intercepts malloc(), calloc(), realloc(), and free().

valgrind --leak-check=full ./my-app

Leak categories reported

CategoryMeaning
Definitely lostNo pointer exists — true leak
Indirectly lostLost via another lost block
Possibly lostInterior pointer — may be lost
ReachableStill referenced at exit

Trade-off: 20–50× slower execution. Use in testing/CI, not production.

Modern Native Alternatives

ToolBest For
HeaptrackAllocation profiling — much faster than Valgrind

LeakSanitizer (LSan)Fast leak detection standalone

JVM — jmap, jcmd, jstat

# Capture heap dump jmap -dump:live,file=heap.hprof <PID> # Live heap histogram jmap -histo:live <PID> # GC stats over time jstat -gcutil <PID> 1000 # Heap dump via jcmd jcmd <PID> GC.heap_dump /tmp/heap.hprof

Heap Dump Analysis — Key Concepts

ConceptMeaning
Shallow SizeMemory of the object itself
Retained SizeAll memory freed if this object were collected
Dominator TreeObjects responsible for largest retained memory
GC Root PathWhy the object is still alive
Example: GC Root Path Static Map → Cache → User Objects → Memory Never Released Removing the static reference frees thousands of objects.

The Dominator Tree is usually the fastest path to identifying the leak source.

Real-World Examples

Spring Boot — Cache Without Eviction

RSS grows hourly → jmap heap dump → Eclipse MAT Dominator Tree → ConcurrentHashMap (unbounded cache) → Add size limit / LRU eviction

C++ Service — Missing free()

RSS continuously grows (no GC) → Valgrind --leak-check=full → "Definitely Lost" reported → Missing free() in request handler → Fix: RAII / smart pointers

Go Service — Global Variable

Heap grows after traffic spikes → pprof heap profile → Large slice in global variable → Remove global reference → GC collects

Staff Engineer Thinking

Junior

Memory keeps increasing.

Senior

Is there a heap leak?

Staff asks

  • Is RSS increasing or only heap?
  • Is this Page Cache or application memory?
  • Is the leak native or managed?
  • Is memory retained intentionally?
  • Are GC roots preventing reclamation?
  • Is allocator fragmentation involved?
  • Is the container close to its memory limit?
  • Is this expected growth under load?

Production Failure Scenarios

RSS Continuously Growing

Cause: Native memory leak or allocator growth  ·  Fix: Inspect pmap, heap dump, allocator stats

JVM Heap Never Shrinks

Cause: Retained objects  ·  Fix: Analyze heap dump with Eclipse MAT Dominator Tree

High RSS but Stable Heap

Cause: Native memory leak or allocator fragmentation  ·  Fix: Check DirectByteBuffers, malloc arenas, jemalloc stats

Kubernetes OOMKilled

Cause: Container exceeds memory limit  ·  Fix: Capture heap dump before restart; review off-heap usage

Production Debugging Checklist

  • ✅ Check RSS using top
  • ✅ Compare RSS vs Heap usage
  • ✅ Inspect memory maps (pmap, smaps)
  • ✅ Capture heap dump or allocation profile
  • ✅ Analyze retained objects (Dominator Tree)
  • ✅ Follow GC Root paths to allocation site
  • ✅ Identify and fix root cause
  • ✅ Verify memory stabilizes after deploy
  • ✅ Monitor long-running memory trends

Key Takeaways

Memory Leaks • Native: malloc() without free() → permanent loss. • Managed: objects reachable → GC cannot collect. • Not every growth is a leak (page cache, arenas). Investigation Order • OS level (top/pmap) → Runtime (jmap/pprof) → Analysis. • Never start with code. Start with measurements. Key Techniques • Dominator Tree → fastest path to leak source. • GC Root Path → explains why object is alive. • Retained Size → total memory freed if object removed. Tools • Native: Valgrind, Heaptrack, ASan. • JVM: jmap, jcmd, Eclipse MAT. • Go: pprof (/debug/pprof/heap). • .NET: PerfView, dotnet-counters. Staff workflow • Measure → Capture → Analyze → Identify → Fix → Validate.
