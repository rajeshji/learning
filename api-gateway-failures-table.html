1 — API Gateway Availability Failures
Gateway CrashMust Know Runtime failure, OOM kill, unhandled exception crashes gateway process Health check failures, all API requests failing immediately Failover to standby gateway instance Active-active HA gateway deployment, no single instance takes all traffic Entire API surface unavailable — all clients see connection refused Active-active HA doubles gateway infrastructure cost
Single Gateway SPOFMust Know Only one gateway deployed — it fails and entire API is gone Complete traffic outage, zero successful API calls Emergency failover, direct client to secondary if available Multiple gateway replicas behind a load balancer, no SPOF Global outage — entire API surface unreachable for duration of recovery Multi-replica gateway adds operational complexity and cost
Ingress Controller Failure Kubernetes ingress controller crashes — gateway routing lost Traffic routing failure, all services behind ingress unreachable Restart ingress controller, failover to backup ingress HA ingress setup (multiple replicas), ingress health monitoring Cluster-wide API outage — all services behind ingress fail simultaneously HA ingress adds pod resource overhead and control-plane complexity
Gateway Startup Failure Bad config pushed, cert error, or dependency unavailable on startup CrashLoopBackOff, restart loop, no new requests being served Rollback deployment, restore last known-good config Config validation in CI/CD, blue-green gateway deployment API unavailable until rollback completes — duration depends on deploy speed Config validation and blue-green deployment slow release velocity
2 — Traffic Overload and Resource Failures
Gateway CPU SaturationMust Know High request volume combined with TLS termination and auth validation Gateway CPU >90%, latency increasing, request queue growing Scale gateway horizontally, shed low-priority traffic Capacity planning, horizontal autoscaling, CDN for cacheable responses Latency spike → clients retry → gateway further overloaded → collapse More gateway replicas cost more; autoscaling has scale-out lag
Thread Pool ExhaustionMust Know Slow backend services hold threads — all gateway threads blocking on upstream Request queue buildup, thread pool saturation metrics Timeout blocked requests aggressively, reject new requests Non-blocking async IO (Netty/reactive), aggressive backend timeouts All API requests timeout — slow backend failure cascades to entire gateway Async programming models are more complex to develop and debug
Connection Exhaustion Massive concurrent clients — gateway hits connection limit Connection limit reached, new requests rejected with connection error Increase connection limit, enable HTTP/2 multiplexing Connection reuse (keepalive), HTTP/2 multiplexing, connection pooling New client requests rejected — appears as API unavailability More connections consume more memory; keepalive delays cleanup
TLS Handshake Overload Mass reconnects or new clients — TLS setup is CPU-intensive at high scale TLS handshake latency spike, gateway CPU at 100% TLS session resumption, TLS offloading to dedicated hardware TLS 1.3 (faster), ECDSA certs, session ticket reuse All HTTPS connections slow or dropped — clients see SSL errors TLS offloading removes end-to-end encryption — security trade-off
Memory Exhaustion Large request/response buffering, memory leak, or oversized payloads Heap growth, OOM alerts, gateway process killed by OS Restart/rebalance, impose strict request size limits Request size limits, streaming responses (avoid full buffering) Gateway crash → cold start surge → retry storm from all clients Strict size limits may reject legitimate large payloads
3 — Routing and Request Forwarding Failures
Incorrect Route MappingMust Know Bad routing config pushed — request reaches wrong backend service Unexpected errors from wrong service, requests hitting wrong endpoints Rollback routing rules immediately Route validation in CI, canary routing before full rollout Wrong service behavior at scale — could trigger data mutations on wrong service Canary routing slows config deployment velocity
Traffic BlackholingMust Know Requests silently dropped — misconfigured ACL, wrong VPC, broken rule Timeout spike from client side, gateway shows no errors internally Reroute via alternate path, rollback config Redundant routing paths, active synthetic probes from client perspective Silent failure — retry storm from clients amplifies gateway load More redundant paths add routing complexity and cost
Stale Service Discovery Backend service scaled or redeployed — gateway still routes to old endpoint Requests to dead instances, connection refused errors from gateway Refresh service registry, retry to a healthy endpoint Fast service discovery propagation, health-check-driven routing Increased failure rate — requests routed to terminated instances More frequent discovery refresh increases discovery service load
Protocol Translation Failure Mismatch between what gateway expects and what backend speaks (HTTP/gRPC/WS) Encoding/decoding errors, unexpected protocol errors in logs Fallback to compatible protocol, apply protocol adapter Compatibility testing for all gateway-backend protocol pairs Service communication failure — entire endpoint broken for affected clients Multi-protocol support adds significant gateway complexity
4 — Authentication and Authorization Failures
Auth Service UnavailableMust Know OAuth server / JWT validator / identity provider goes down Login and token validation failures spike, all auth-protected APIs fail Cached token validation (short TTL), fail-open for low-risk endpoints HA auth service, cached token signatures with clock skew tolerance Entire API inaccessible — every authenticated request rejected Cached token validation risks using revoked tokens until cache expires
JWT Validation FailureMust Know Signing key rotated without updating gateway, or expired key used Auth error spike, all JWT validations failing Refresh signing keys in gateway config, deploy key update Automated key rotation with key overlap period (both keys valid briefly) Global auth outage — all JWT-protected APIs reject every request Key overlap period means old compromised keys remain valid temporarily
Authorization Rule Failure Incorrect RBAC/policy deployed — wrong access control applied Unexpected access patterns, either too much access or too many 403s Rollback policy config immediately Policy testing in staging, canary rollout for policy changes Security exposure (too permissive) or service lockout (too restrictive) Canary policy rollout slows experimentation and feature release velocity
Token Introspection Latency External auth server is slow — every request waits for token validation Increased P99 latency on all authenticated endpoints Switch to local JWT validation, cache introspection results Prefer self-contained JWTs over remote introspection for scalability Gateway-wide slowdown — every single request pays the auth latency penalty Cached introspection may return stale permissions until cache expires
Rate-Limit Bypass Auth/routing misconfiguration allows requests to skip rate limiting Traffic anomaly — specific paths show unconstrained traffic Block abusive traffic via WAF, enforce limits at multiple layers Defence-in-depth rate limiting (gateway + service + DB levels) Backend overload — unlimited traffic from bypassing clients hammers backends Multiple rate limit layers add latency overhead per request
5 — Aggregation and Backend Dependency Failures
Backend Service TimeoutMust Know Downstream service slow or unavailable — gateway waits, holding thread Gateway timeout metrics, P99 latency spike on specific routes Timeout aggressively, return fallback or partial response Circuit breakers per backend, aggressive timeout configuration Thread pool exhaustion — all gateway threads blocked on slow backend Aggressive timeout may fail valid slow-but-correct operations
Aggregation FailureMust Know One backend fails during BFF aggregation — partial data from other backends Partial API response failures, aggregation error metrics Return partial/degraded response, mark failed section as absent Resilient aggregation with per-backend fallbacks, circuit breakers Entire API endpoint fails if aggregation is not resilient to partial failure Partial responses may confuse clients expecting complete data
N+1 Backend Explosion Gateway makes one downstream call per item in list — fan-out multiplies Request fan-out spike, backend QPS much higher than gateway QPS Batch downstream calls, parallelise with bounded concurrency Better aggregation design, DataLoader pattern, precomputed responses Backend overload — N downstream calls for every 1 gateway request Batching and caching add complexity to the aggregation layer
Retry Storm to Backends Gateway retries aggressively on backend failure — amplifying already-failing backend Retry traffic spike in backend metrics Exponential backoff, circuit breaker to stop retrying failing backend Retry budgets per backend, circuit breaker with half-open probe Backend collapse — retry amplification buries the already-slow service Circuit breaker open means some valid requests are rejected during recovery
6 — Rate Limiting and Throttling Failures
Rate Limiter Failure OpenMust Know Distributed rate limiter (Redis) unavailable — all limits bypassed silently Sudden traffic surge, rate limiter health check failing Fail-closed local limiter, emergency throttle at gateway HA rate limiter (Redis Sentinel/Cluster), local fallback limiter Backend overload — unlimited traffic floods through to all downstream services Local fallback limiter may throttle unfairly without global state
Rate Limiter Failure Closed Rate limiter bug causes it to block all traffic — returns 429 universally Massive 429 spike affecting all clients uniformly Disable rate limiter temporarily, route around it Circuit breaker on rate limiter itself, safe fallback to allow-all mode API service unavailable for all clients — entire API surface returns 429 Disabling limiter exposes backends to unconstrained traffic
Distributed Counter Inconsistency Multi-node rate limiter has desync — some nodes allow more, some fewer Uneven throttling across gateway nodes, inconsistent client experience Re-sync rate limiter counters, use consistent hash routing Stronger consistency for rate limit counters, centralised counter service Unfair traffic handling — some clients bypassed, others incorrectly throttled Strongly consistent counters add coordination latency to every request
Burst Traffic Bypass Traffic burst exceeds rate limiter window — spike slips through before limit fires Backend saturation despite rate limiter showing within limits Token bucket / leaky bucket algorithms to smooth bursts Sliding window rate limiting, burst protection at multiple layers Cascading overload — burst reaches backends unfiltered, causes spikes Strict burst limiting may reject legitimate traffic during valid peaks
7 — Network and Connectivity Failures
DNS Failure to GatewayMust Know DNS outage or misconfiguration — clients cannot resolve gateway hostname DNS lookup failures before any request reaches gateway Secondary DNS resolver, reduce TTL for fast propagation Multi-provider DNS, DNS monitoring, low TTL on critical records Entire API unreachable — all clients fail at DNS resolution stage Multi-provider DNS adds cost; low TTL increases DNS query volume
Gateway Network Partition Network cut between gateway and backend tier — cannot forward requests Backend unreachable errors, all routes returning 502/503 Route to alternate gateway with network connectivity Multi-network redundancy between gateway and backend tiers Partial or total API outage depending on partition scope Redundant network paths add infrastructure cost
WebSocket Disconnect Storm Gateway restarts or network blip — all long-lived WebSocket connections drop Massive simultaneous reconnect attempts, connection exhaustion Gradual reconnect with jitter, sticky sessions for WebSocket clients Graceful gateway drain before restart, WebSocket connection affinity Reconnect storm — all dropped clients retry at once → connection exhaustion Graceful drain slows deployments; sticky sessions reduce balancing flexibility
Packet Loss to Backend Network congestion or instability between gateway and backend nodes Retransmission spike, intermittent request failures on specific routes Retry with backoff, reroute to healthy backend instances Redundant backend network paths, better network capacity planning Timeout amplification — packet loss triggers retries → more traffic on degraded path More retries add latency and can amplify load on already-degraded path
8 — Configuration and Deployment Failures
Bad Gateway ConfigMust Know Wrong routing rules, policies, or timeouts pushed to production Traffic anomalies, error rate spike immediately after config change Rollback config immediately Config validation in pipeline, blue-green gateway config deployment Global outage — all traffic misrouted or blocked by bad config Blue-green config deployment slows change velocity
Certificate Misconfiguration TLS cert expired, wrong domain, or key mismatch TLS handshake errors, browser and client SSL errors Emergency cert rotation, rollback to previous cert Automated cert rotation (ACM/Let's Encrypt), cert expiry monitoring All HTTPS traffic fails — clients see certificate error, cannot reach API Automated rotation adds operational complexity; rotation itself can briefly break traffic
Canary Routing Failure Wrong traffic split — canary gets too much or wrong traffic Traffic imbalance metrics, error rate spike on canary route Disable canary, restore 100% to stable version Gradual traffic shift with validation gates before each increment Partial outage if bad canary handles significant traffic before detected Slow canary ramp reduces speed of new feature delivery
Schema / Contract Mismatch Gateway and backend disagree on API schema — new version breaks old gateway Serialization errors, unexpected null fields, protocol decode failures Apply version fallback, deploy schema-compatible gateway version Backward-compatible schema changes, contract testing in CI All requests to affected endpoint fail — serialization errors for all clients Backward compatibility constraints slow schema evolution
9 — Multi-Region and Global Gateway Failures
Global Gateway Failover FailureMust Know Primary region outage — traffic not redirected to secondary region Traffic stuck in failed region, global API error rate spike Manual failover via DNS or global load balancer Active-active multi-region, automated global failover with health checks Global API outage — all clients stuck hitting failed region Active-active multi-region doubles gateway cost and adds data sync complexity
Geo-Routing Failure Wrong region selected — user routed to far-away gateway region Latency spike, users in specific geographies report slow APIs Override geo-routing rules manually Latency-based geo-DNS, regular geo-routing tests from all regions Regional overload if one gateway absorbs all global traffic incorrectly Latency-based routing is more complex and harder to reason about than static geo
Traffic Spillover Overload Failed region's traffic spills to secondary — secondary lacks capacity Secondary region saturation, error rate spike in secondary Rate limit spillover traffic, shed non-critical requests Active-active with 50%+ headroom per region for full failover absorption Multi-region cascade — secondary overloads and fails too 50% headroom means over-provisioning each region during normal operation
Global Config Drift Regions deployed different gateway config versions — inconsistent API behaviour Different API responses from different regions, region-specific errors Force config sync from authoritative source Centralised config management, GitOps config propagation with validation Inconsistent user experience — behaviour differs by region silently Centralised config propagation adds synchronisation latency per change

Slow Backend Amplification — Most Dangerous Gateway Pattern

Dead backend: circuit breaker opens → fail fast → gateway threads freed Slow backend: threads block waiting → pool fills → ALL requests slow → clients retry → more threads blocked → complete gateway failure Mitigation: 1. Aggressive per-backend timeout (much shorter than client timeout) 2. Circuit breaker (open after N failures in window) 3. Bulkhead (separate thread pools per backend) 4. Async IO (never block threads on IO) Rule: design gateway assuming every backend will be slow, not just dead

Final Mental Model — All Gateway Failures Reduce to 5 States

1. Traffic not routed → crash / SPOF / DNS / blackholing 2. Traffic misrouted → bad config / stale discovery / protocol fail 3. Gateway overloaded → CPU / threads / TLS / connections 4. Backend dependency → timeout / aggregation fail / retry storm / auth down 5. Rate limiting broken → fail open / fail closed / counter desync Most dangerous: slow backend → gateway thread exhaustion because it affects ALL APIs, not just the slow backend's routes
