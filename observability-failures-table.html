Observability Failure Scenarios

Staff-level · 9 categories · 36 scenarios · detect / mitigate / prevent / cascading / trade-off

Why Observability Failures Are Uniquely Dangerous

Observability provides: metrics + logs + traces + alerting + debugging + visibility Without it: systems fail silently — MTTR explodes, cascading failures spread undetected 9 root failure classes: metrics | logging | tracing | alerting | monitoring infra cardinality/scale | correlation | time/ordering | security observability

1 — Metrics Collection and Monitoring Failures
Metrics Pipeline FailureMust Know Prometheus scraper, agent, or collector network fails — metrics stop flowing Dashboards show gaps, "No data" panels, stale last-seen timestamps Fall back to CLI/raw metric endpoints, restart collectors Redundant collectors, HA Prometheus (Thanos/Cortex), watchdog supervision Blind system operation — operators cannot see CPU, error rates, or latency Redundant collectors add infra cost and coordination complexity
Missing Critical MetricsMust Know Metrics never instrumented — incident occurs with zero telemetry for that system Post-incident: no data available for root cause analysis Add instrumentation immediately to affected service Observability standards checklist (RED / USE / golden signals) for every service Extended MTTR — operators debug blind, guessing at root cause Comprehensive instrumentation adds engineering effort per service
Stale / Incorrect MetricsMust Know Buggy instrumentation, counter reset on restart, or metric name collision Impossible values (negative latency), metrics never changing, logic doesn't match Validate metrics pipeline, compare against source-of-truth (logs) Metrics schema testing in CI, canary validation of new instrumentation Misleading debugging — operators act on wrong data, worsen the incident Schema validation adds CI pipeline complexity per service
Metrics Aggregation Failure Aggregator node overloaded — federated or global aggregate stops computing Missing global dashboards, aggregated panels show "no data" Fall back to per-node local dashboards, bypass aggregator Hierarchical aggregation, shard aggregators by service domain Partial operational blindness — fleet-level view unavailable during incident Hierarchical aggregation adds complexity and coordination overhead
2 — Logging Failures
Log Pipeline FailureMust Know Fluentd / Logstash / Kafka log shipper crashes or network fails Missing logs in Elasticsearch/Loki, service generates logs but none arrive Buffer logs locally, retry pipeline, route via secondary shipper HA log pipeline (multiple shippers), local disk buffer with durability guarantee Debugging impossible — no log evidence for ongoing or past incidents HA log pipeline adds significant infra complexity and cost
Log LossMust Know Log buffer overflows or disk fills — logs dropped silently at source or shipper Sequence gaps in log index, known events absent from log search Replay from service-side buffer if available, check disk space Durable log queues (persistent Kafka topics), log backpressure to service Missing incident evidence — audit trail incomplete, root cause unprovable Durable log queues add storage overhead and end-to-end latency
Excessive Log StormMust Know Error retry loop or misconfigured verbose logging floods the pipeline Log volume spike, logging infra CPU/disk at 100%, other logs crowded out Rate-limit logs at source, suppress repeated identical messages Structured logging with per-error deduplication, log rate limits per service Logging infra collapse — storm drowns out critical error signals from other services Rate limiting may suppress genuine high-frequency error events
Sensitive Data in Logs Token, password, or PII accidentally included in a log statement Secret scanning alert in log pipeline, SIEM rule triggers on credential pattern Redact affected log records, rotate exposed credentials immediately Safe logging framework (no raw request/response logging), secret scanner in CI Security breach — anyone with log access has valid credentials Masking sensitive fields reduces debug detail available in logs
3 — Distributed Tracing Failures
Missing Trace PropagationMust Know Service fails to forward trace context header — trace chain breaks at that hop Broken trace chains in Jaeger/Zipkin, orphan spans with no parent Inject fallback trace ID at missing hop, patch missing propagation Standardised propagation (W3C TraceContext), propagation integration tests Request tracking impossible — cannot reconstruct full request path for any incident Propagation adds per-request overhead and requires changes in every service
Partial Trace LossMust Know Trace collector overloaded — spans dropped before storage Missing spans in completed traces, gaps in latency breakdown Buffer spans locally, increase collector capacity Scalable tracing infra, tail-based sampling (sample on completion, not start) Incomplete root cause analysis — latency spike attributed to wrong service Tail-based sampling requires holding span buffers in memory during request lifetime
Trace Cardinality Explosion Too many unique span/operation names — TSDB indexing explodes Storage and query latency growing, tracing backend OOM or slow Reduce span cardinality, apply sampling, drop high-cardinality labels Cardinality governance — no user IDs or request IDs in span operation names Observability platform crash — tracing backend OOM kills entire trace system Cardinality limits reduce per-user trace granularity
Trace Storage Exhaustion Long trace retention or high request volume — trace storage disk fills Trace ingestion failures, "storage full" errors in tracing backend Reduce retention window, archive old traces to cold storage Tiered trace storage, retention policies, storage capacity monitoring All new traces lost — historical debugging unavailable for post-incident review Shorter retention reduces post-incident debugging window
4 — Alerting and Incident Detection Failures
Missing AlertMust Know Threshold never configured, or alert condition not covering the failure mode Incident detected manually by a user report — not by alerting system Emergency dashboards to detect manually, add alert retroactively Alert coverage reviews against SLO, alerting-as-code with coverage checks Long undetected outage — every minute without alert = longer MTTR Comprehensive alert coverage requires ongoing tuning as systems change
False Positive Alert StormMust Know Noisy thresholds or flapping metric — hundreds of non-actionable alerts fire Massive alert volume, on-call engineer overwhelmed by noise Suppress / group alerts, apply alert deduplication immediately Smarter alerting (multi-window burn rate), SLO-based alerts over raw thresholds Alert fatigue — real critical alert buried in storm, response delayed Fewer, smarter alerts may miss some edge-case failure modes
False Negative AlertsMust Know Threshold too loose — actual outage occurs but alert condition never met Silent failure: users experience degradation, alerting system shows green Add anomaly detection, tighten thresholds, add SLO burn rate alerts SLO-based burn rate alerting, error budget exhaustion alerts Major outages go completely unnoticed — no one is paged Tighter thresholds increase false positive rate
Alert Routing FailureMust Know PagerDuty, Slack, or email integration fails — alerts fire but nobody receives them Alert history shows fired alerts, but no engineer received notification Activate secondary notification channel (phone call, SMS, backup Slack) Multi-channel alerting, alert delivery confirmation, routing health checks Delayed incident response — alert fires but nobody acts for hours Multi-channel routing adds notification complexity and possible duplicate pages
5 — Monitoring Infrastructure Failures
Prometheus Server FailureMust Know Monitoring server crashes, OOM, or storage fills — scraping stops Monitoring itself unavailable — dashboards inaccessible or stale Failover to standby Prometheus instance HA Prometheus (Thanos/Cortex), monitoring of monitoring (meta-monitoring) Complete visibility loss — operators cannot see any system metrics HA monitoring cluster doubles cost; Thanos adds operational complexity
Collector Agent Failure Node exporter, OpenTelemetry agent, or Datadog agent crashes on a host Missing host-level metrics (CPU, memory, disk) for specific nodes Restart collector agent, watchdog supervision Watchdog process for collector, systemd restart policy Partial blind spots — certain hosts invisible during fleet-wide incident Watchdog monitoring adds another operational component to manage
Monitoring Network Partition Monitoring node isolated from services — cannot scrape or receive telemetry All metrics flat-line simultaneously — looks like a major outage Push-based telemetry as fallback, local buffering Multi-path networking for monitoring, push + pull hybrid telemetry model Visibility gap looks like outage — operators may take unnecessary action Push-based telemetry changes the model significantly — more complex
Centralised Monitoring Bottleneck Single Prometheus/Grafana handles too many metrics — query latency explodes Dashboard load times degrade, query timeouts, monitoring UI unresponsive Federated monitoring, reduce query complexity Hierarchical/federated monitoring architecture, pre-aggregate heavy queries Observability collapse during high-load incident — when you need it most, it fails Federated monitoring adds coordination complexity and consistency challenges
6 — Cardinality and Scale Failures
High Cardinality ExplosionMust Know Metric labels include user IDs, request IDs, or unbounded values — TSDB explodes Prometheus memory growing rapidly, query latency spike, OOM crash Drop high-cardinality labels immediately, apply recording rules Cardinality governance policy — no unbounded values as metric labels Monitoring crash — Prometheus OOM kills entire observability platform Low cardinality metrics reduce per-instance debugging granularity
Metric Storage Explosion Long retention policy with high metric volume — storage grows faster than capacity Storage growth spike, disk usage alerts on monitoring nodes Compress/archive old metrics, reduce retention window Tiered metric storage (Thanos), retention policies, storage capacity planning Disk exhaustion kills monitoring node — complete visibility loss Shorter retention reduces historical debugging and capacity planning ability
Query Fanout Explosion Dashboard query spans thousands of series — each query fans out to many nodes Dashboard panels timing out, "context deadline exceeded" errors Pre-aggregate with recording rules, reduce query scope Recording rules for expensive queries, query cost limits Dashboard unusable during incident — cannot see the metrics you need Recording rules must be maintained as metrics change — operational burden
Observability DDoS Traffic spike generates massive telemetry volume — collectors and storage overwhelmed Collector CPU/memory spike, telemetry ingestion failures, data loss Throttle telemetry at source, increase sampling ratio Adaptive sampling, rate limiting on telemetry ingestion Metrics/trace loss at peak load — observability fails when you need it most Aggressive sampling reduces visibility into edge-case failures
7 — Correlation and Context Failures
Logs Cannot Correlate to TracesMust Know Logs missing trace ID — cannot link a log line to the distributed trace it belongs to Fragmented debugging — log search and trace view cannot be joined Add trace ID injection middleware to logging framework Unified observability standard (OpenTelemetry), trace ID in all log statements Slow root cause analysis — operator must manually correlate by timestamp Trace ID injection requires changes in every service's logging setup
Metrics Detached from Business ContextMust Know Only infra metrics collected — no business KPIs (orders/sec, checkout success rate) Infra shows green but customers report broken functionality Add business metric queries against DB or event stream Golden signals + business metrics, SLI/SLO defined on customer-facing behaviour Missed customer impact — outage only detected via user complaints, not alerting Business metrics add engineering effort and ownership questions per domain
Cross-Service Visibility Gap Downstream dependency has no telemetry — cannot see whether it is the root cause Broken service chain — you can see your service is slow but not why Synthetic monitoring to probe downstream, dependency dashboards End-to-end distributed tracing, observability requirements for all dependencies Hidden dependency failures — root cause attribution impossible Requiring observability from dependencies creates political/org friction
Version / Deployment Blindness Metrics not tagged with deployment version — cannot tell which version caused regression Latency spike after deploy but cannot isolate to specific version Add version label to all metrics, compare before/after deploy Deployment-aware telemetry, version tags in all metric labels Slow rollback — cannot confidently identify bad version without version tagging Version labels add cardinality to all metrics
8 — Time Synchronization and Ordering Failures
Clock Skew Between NodesMust Know NTP misconfigured — nodes have diverged wall-clock times Timestamp mismatch in correlated logs, events appear out of order Use logical timestamps for correlation, fix NTP immediately Reliable NTP/PTP, clock skew monitoring alert Incorrect event ordering — root cause analysis leads to wrong conclusions Monotonic/logical clocks add metadata complexity to telemetry
Out-of-Order Logs / Events Async buffering or network delay — log events arrive in wrong order Log timestamps inconsistent with event sequence Reorder events by ingestion timestamp, flag out-of-order logs Ordered delivery pipelines, sequence numbers in log records Misleading debugging — operator reads log sequence as causal when it is not Strict ordering reduces log pipeline parallelism and throughput
Delayed Telemetry DeliveryMust Know Network congestion or queue lag — telemetry arrives minutes after the event Metric timestamps significantly behind wall clock, old alerts firing late Prioritise telemetry traffic, bypass congested path Separate observability network plane, QoS prioritisation for telemetry Slow incident detection — alert fires 10 minutes after failure, MTTR extends Dedicated observability network plane adds significant infra cost
Telemetry Replay Duplication Pipeline retry or recovery replays telemetry — metrics/logs counted twice Duplicate log entries, metric counters jump unexpectedly Idempotent ingestion using event ID deduplication Deduplication logic in ingestion pipeline, event ID on each telemetry record Wrong dashboard values — operators act on doubled metrics, make bad decisions Deduplication adds ingestion latency and storage overhead
9 — Security and Compliance Observability Failures
Audit Logging FailureMust Know Audit log pipeline crashes, disk fills, or misconfiguration drops audit events Missing audit trail entries, compliance scan finds gaps in audit log Emergency fallback logging, restore pipeline immediately Immutable audit log storage, redundant audit pipeline, gap-detection monitoring Compliance violation — breach undetectable, regulatory fines possible Immutable audit log storage adds cost; redundant pipeline adds complexity
Security Event BlindnessMust Know Intrusion, credential stuffing, or privilege escalation not generating telemetry Attack discovered via external report or post-breach forensics Enable security telemetry retroactively, triage recent activity SIEM integration, security-specific metrics (failed auth rate, privilege changes) Long attacker dwell time — attack spreads undetected across multiple systems Security telemetry adds log volume and storage cost
Telemetry Tampering Attacker modifies logs or metrics to hide their activity Log integrity check failure, hash mismatch on audit records Restore from immutable backup, treat system as compromised Signed/immutable logs, write-once audit storage, log integrity monitoring Hidden compromise — attacker erases evidence and continues undetected Log signing and immutability add storage and compute overhead per record
Observability Access Leak Dashboards, log queries, or trace data exposed to unauthorised users Unexpected data access in audit log, user accessing other team's dashboards Restrict access immediately, rotate exposed credentials RBAC for observability tools, data isolation per team/tenant in Grafana Data leakage — metric data may reveal business logic or traffic patterns Fine-grained RBAC in observability adds operational overhead

Staff-Level Observability Thinking — 9 Questions to Ask Always

1. Failures become invisible? → golden signals + alert coverage + SLO alerting 2. Alerts noisy/useless? → burn rate + multi-window + grouping + SLO-based 3. Telemetry overloads infra? → cardinality governance + sampling + tiered storage 4. Correlate logs/traces? → OpenTelemetry + trace ID in logs + unified standard 5. Monitoring itself fails? → meta-monitoring + HA + watchdog + multi-collector 6. Obs scales with traffic? → adaptive sampling + federated + recording rules 7. Business impact measurable? → business KPIs + customer-facing SLI/SLO 8. Incidents detected quickly? → alert routing + multi-channel + delivery confirmation 9. Telemetry trustworthy? → immutable logs + signed records + integrity checks

Final Mental Model — All Observability Failures Reduce to 4 States

1. Missing visibility → no metrics / no logs / no traces / no alerts 2. Wrong visibility → stale / incorrect metrics / misleading alerts / bad clocks 3. Delayed visibility → telemetry lag / pipeline delay / slow alert routing 4. Overloaded obs → cardinality explosion / log storm / monitoring crash Most dangerous: missing visibility + missing alert system degrades silently → no one is paged → cascading failure spreads → MTTR measured in hours not minutes The four golden signals (Google SRE): Latency | Traffic | Errors | Saturation Monitor these for EVERY service and you catch 90% of failures
