Write Ordering, Barriers & Durability Semantics

How data safely reaches persistent storage — Staff Engineer level

The Big Picture

write() does not save your data. It only copies data into the kernel page cache. Without proper ordering, a crash can corrupt data even after write() returned success.

write() fsync() Barrier Flush FUA Page Cache Journal COW WAL PLP
Application → write() → Page Cache → Filesystem → Block Layer → Device Cache → Flush → Persistent Media Each layer buffers, reorders, and batches writes for performance. Each layer is a potential crash point.

Write Lifecycle — Layer by Layer

LayerPurposeDurable?
Application BufferTemporary in-process memory❌ No
Page CacheOS-managed buffered I/O❌ No
Filesystem JournalCrash recovery log⚠ Partially
Device Cache (DRAM)Performance buffer in SSD/HDD❌ No (unless PLP)
Persistent MediaFlash / magnetic platters✅ Yes

Only persistent media is truly durable. Everything above it is volatile until flushed.

Why Write Ordering Matters

Wrong order → corruption

Write Metadata ↓ Power Failure ↓ Data never written On reboot: metadata points to garbage data.

Correct order → safe

Write Data ↓ Flush ↓ Write Metadata ↓ Commit Metadata only references fully-written data.

Barriers & Flush Commands

A barrier ensures Write B cannot become durable before Write A.

Write A ↓ Barrier ← storage cannot reorder past this ↓ Write B Without barrier: controller may write B before A → corruption on crash.

Hardware flush commands

CommandPurpose
ATA FLUSH CACHEHDD: write volatile cache to platters
NVMe FLUSHSSD: commit controller cache to flash
REQ_FLUSHLinux block layer flush request
REQ_FUAWrite directly to media, skip volatile cache

Write Ordering by Filesystem

ext4 — Ordered Mode (default)

Data Blocks → Flush → Journal Commit → Metadata Update Guarantee: metadata never references unwritten data blocks.

XFS — Metadata Log

Metadata Changes → Intent Log → Flush → Commit → FS Updated Log ensures recovery after crash; data ordering via barriers.

ZFS — Copy-on-Write

Allocate New Blocks → Write Data → Checksum → Atomic Pointer Update → Commit (TXG) Old data valid until new version safely committed. No journal replay required.

COW vs Journaling

Device Cache & Power Loss Protection

Most storage devices buffer writes in volatile DRAM. Without protection, power loss destroys buffered data even after fsync().

HardwareBehavior
Consumer HDDVolatile write cache — risky without barriers
Consumer SSDFTL cache in DRAM — vulnerable to power loss
Enterprise SSD (PLP)Supercapacitor flushes cache on power loss ✅
RAID ControllerDRAM cache — safe only with battery backup (BBU)

Durability depends on hardware as much as software. A PLP SSD + correct fsync() = true durability.

Database Perspective

PostgreSQL

BEGIN ↓ Write WAL ↓ fdatasync() ↓ Commit ↓ Update data pages

Kafka

Append to log ↓ Flush (acks=all) ↓ Ack producer Different ack policies trade durability for throughput.

Elasticsearch

Write to Translog ↓ fsync() ↓ Segment commit Ensures index consistency on crash.

Performance vs Durability Trade-offs

Production Failure Scenarios

Data Lost After Crash

Cause: Application relied only on write()  ·  Fix: Use fsync() or synchronous commit

Filesystem Corruption on Reboot

Cause: Write reordering with barriers disabled  ·  Fix: Enable barriers, use ordered journaling

High fsync Latency

Cause: Frequent device cache flushes on consumer SSD  ·  Fix: PLP-enabled SSD or batch/group commits

Slow Database Writes

Cause: Every transaction calls fsync() individually  ·  Fix: Group commits or tune commit interval

Unsafe Performance Optimization

Cause: Write barriers disabled on cheap hardware  ·  Fix: Only disable with battery-backed RAID or PLP SSD

Production Debugging Checklist

  • ✅ Verify write ordering (ordered vs writeback journal)
  • ✅ Confirm barriers are enabled: mount | grep barrier
  • ✅ Inspect device write cache: hdparm -I /dev/sda
  • ✅ Verify Power Loss Protection (check SSD spec)
  • ✅ Measure fsync() latency: fio --fsync=1
  • ✅ Check database WAL configuration
  • ✅ Benchmark with fio before changing durability settings
  • ✅ Validate crash recovery behavior in staging
  • ✅ Never disable barriers without hardware-level guarantees

Key Takeaways

write() only copies to page cache — NOT durable. Durability chain: write() → fsync() → device flush → persistent media Write Ordering • Data must be durable before metadata references it • Barriers prevent storage controllers from reordering • Journaling (ext4/XFS) replays intent log after crash • COW (ZFS) commits atomically — no replay needed Key APIs • fsync() → data + metadata to disk • fdatasync() → data only (faster for DBs) • O_SYNC → synchronous every write • FUA → skip volatile cache on write Hardware matters • Consumer SSD: vulnerable to power loss • Enterprise SSD + PLP: safe even without fsync barriers • RAID + BBU: safe cache Staff picks: group commits + PLP SSD + ordered FS = best balance of throughput, latency, durability
