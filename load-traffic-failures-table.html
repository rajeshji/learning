Load & Traffic Failure Scenarios

Staff-level · 7 categories · 29 scenarios · detect / mitigate / prevent / cascading / trade-off

Why Load Failures Are the Most Common Cause of Large-Scale Outages

Systems fail when: incoming traffic > processing capacity Unlike hard crashes, load failures start as slow degradation: slow response → caller retries → load amplifies → thread exhaustion → cascade 7 root sources: too much traffic | uneven traffic | sudden spikes | slow processing retry amplification | resource exhaustion | traffic misrouting

1 — Traffic Spike and Overload Failures
Sudden Traffic SpikeMust Know Viral event, flash sale, breaking news, scheduled launch RPS surge alert, latency spike, error rate increase Autoscaling, CDN for static content, load shedding Capacity planning, pre-scaling for known events Retries from slow responses overload downstream services Over-provisioning for rare spikes is expensive
Sustained High Load Continuous traffic growth exceeds current capacity CPU/memory consistently above safe threshold Horizontal scaling, async offload, read replicas Better partitioning, async processing, capacity growth plan Resource exhaustion cascades across cluster gradually More nodes increase infra cost linearly
Burst Traffic (Spiky Load) Traffic arrives in short bursts — cron jobs, batch triggers High traffic variance metrics, short P99 spikes Queue buffering to smooth bursts Token bucket rate limiting, request smoothing Queue explosion during burst → memory exhaustion Buffering adds end-to-end latency
Traffic Surge After DowntimeMust Know Service recovers — millions of users reconnect simultaneously Massive reconnect/request spike immediately after recovery Gradual traffic ramp-up, connection throttling during recovery Recovery traffic shaping, circuit breaker on reconnect Connection storm overloads LB and DB during recovery Slower ramp-up delays full service restoration
2 — Retry and Amplification Failures
Retry StormMust Know Clients retry failed/slow requests without backoff Retry traffic spike, outgoing request count 2-10× normal Exponential backoff + jitter, circuit breaker Proper retry policy with cap, backoff, and jitter Dependency receives multiplied traffic → collapses Fewer retries reduce resilience for transient failures
Thundering Herd ProblemMust Know Many clients wake or retry at the same instant Sudden synchronized spike — DB/cache hit in one burst Request coalescing (single-flight), staggered retry Jittered TTLs, randomised reconnect delays DB/cache overload from synchronized surge Coordination overhead adds per-request complexity
Reconnect Storm Millions of clients reconnect after network blip or service restart Connection rate spikes orders of magnitude above normal Connection rate limiting at LB, exponential backoff clients Persistent sessions, client-side jittered reconnect LB thread/connection exhaustion → service unavailable again Slower reconnect means longer user-visible outage
Cache StampedeMust Know Frequently-read cache key expires under high load DB QPS spike coinciding with cache miss rate spike Cache locking / single-flight (only one thread rebuilds) Staggered TTLs, probabilistic refresh, cache pre-warming DB overwhelmed → slow → callers timeout → retry → worse Cache coordination adds implementation complexity
3 — Uneven Traffic and Hotspot Failures
Hot Key / Hot PartitionMust Know One entity (user, video, product) attracts disproportionate traffic One shard/node at 100% CPU/throughput, others idle Replicate hot key to multiple nodes, local caching Better shard key selection, virtual nodes, consistent hashing Single shard saturates → requests fail → retries → collapse Replication of hot data increases storage and coordination
Skewed Load Distribution Hash function or LB sends disproportionate traffic to one node Uneven node CPU/memory metrics across cluster Rebalance traffic, dynamic routing adjustments Consistent hashing with virtual nodes, power-of-two-choices LB Overloaded node saturates → retry storm on that node Rebalancing adds routing overhead and latency
Celebrity / Fan-out Problem One popular entity's action triggers massive fan-out reads/writes Feed/read amplification spike for one account Hybrid fanout: push for normal users, pull for celebrities Tiered caching, read-optimised materialized feeds Feed generation service collapses from amplified reads Higher read latency for celebrity-tier users
Regional Traffic Imbalance One region absorbs abnormal share of global traffic Region-specific CPU/error rate spikes vs others Geo-routing failover, shift traffic to underloaded region Multi-region active-active with capacity planning per region Overloaded region degrades → cross-region latency spikes Cross-region traffic adds latency and egress cost
4 — Queue and Backpressure Failures
Queue BacklogMust Know Producers enqueue faster than consumers process — lag grows Queue lag metrics growing unboundedly Scale consumers, prioritise critical jobs, DLQ for overflow Backpressure on producers, consumer autoscaling Growing lag → delayed workflows → callers timeout → retries More consumers increase cost; larger queues consume memory
Consumer Lag (Kafka/Queue) Consumers fall behind producers — slow processing, small batch Consumer group lag metrics increasing over time Autoscale consumers, increase batch size Efficient consumer logic, parallelism, batching Delayed event propagation → stale downstream state Larger batches increase per-message processing latency
Infinite Queue Growth Incoming load permanently exceeds processing capacity Queue size continuously growing with no plateau Drop low-priority requests, traffic shaping Load shedding, backpressure, bounded queues with rejection Storage exhaustion → broker crash → full pipeline failure Dropping requests impacts user experience
Backpressure Failure Producers ignore downstream capacity signals — keep sending Queue overflow, consumer error rate spike Throttle producers, implement bounded queues with rejection Flow-control protocols, producer rate limiting Entire pipeline collapses — broker, consumer, and producer all fail Throttling producers reduces overall throughput
5 — Resource Exhaustion Under Load
Thread Pool ExhaustionMust Know Blocking operations hold threads; too many concurrent requests Queue wait time spike, task rejection errors Backpressure, async processing, rate limiting Non-blocking IO, right-sized thread pools, bulkheads All new requests queue/fail → timeout → retry storm Async systems are harder to reason about and debug
Connection Pool ExhaustionMust Know More concurrent requests than available DB/network connections Pool wait time maxed, connection refused errors Queue/rate-limit requests, increase pool size cautiously Connection reuse, async IO, proper pool sizing DB overwhelmed with concurrent connections → collapse Larger pools can overwhelm downstream DB with connections
CPU Saturation Under Load Heavy computation under high traffic — no headroom left CPU >90%, latency spike, run queue depth increase Horizontal scaling, caching, load shedding Precomputation, caching, algorithmic optimisation Latency increase → callers timeout → retry → worse saturation Over-provisioning for peak is expensive
Memory Exhaustion Under Load Too many active sessions, requests buffered in memory Heap growth trending upward, OOM kill events Load shedding, reduce in-memory buffering Bounded queues and caches, memory limits OOM kill → restart → traffic lost during restart Smaller memory limits may reject valid in-flight requests
File Descriptor Exhaustion Massive open connections under load — sockets not released "Too many open files" errors, failed socket accepts Increase OS FD limits, cleanup idle connections Connection pooling, idle timeout cleanup, keepalive tuning All new connections fail → service appears down to new users Higher FD limits increase kernel memory overhead
6 — Load Balancing and Routing Failures
Load Balancer OverloadMust Know LB tier becomes the bottleneck — exceeds its connection/CPU capacity LB CPU/connection count maxed, dropped connections Scale LBs horizontally, anycast / DNS-based distribution Multi-tier load balancing, LB capacity planning Entire service inaccessible — traffic never reaches backends More LBs add cost and routing complexity
Misrouted Traffic Bad routing rules, stale backend list, misconfiguration Uneven backend traffic, error spike on specific routes Re-route traffic, rollback routing config Config validation in CI/CD, gradual routing changes Hotspot overload on misrouted backend More routing logic adds configuration complexity
Sticky Session Imbalance Session affinity routes too much to one node Session-heavy nodes at high CPU/memory, others idle Session redistribution, drain-and-redirect sessions Stateless services (store session in Redis/DB not local) One node overloaded → slow → all its users affected Stateless design adds external session storage complexity
DNS Traffic Surge DNS resolver overloaded by massive lookup volume Slow DNS lookup times, request latency increase DNS caching at client and resolver, TTL tuning Multi-provider DNS, dedicated DNS infrastructure Global request latency spike as every connection waits on DNS Cached DNS can serve stale records after failover
7 — Cascading and Systemic Load Failures
Cascading FailureMust Know One overloaded service slows others — failure propagates Multi-service latency and error rate spikes simultaneously Circuit breakers + bulkheads to contain blast radius Service isolation, timeouts, async decoupling Entire system collapses starting from one overloaded node Partial degradation may result — non-critical features fail first
Slow Dependency AmplificationMust Know Slow DB or API causes callers to hold threads open waiting Latency spike + thread pool queue depth growing Timeout/fail fast, async processing, circuit breaker Timeouts on every network call, async processing Thread pool exhaustion → all requests fail for all users Faster failures may abort valid slow-but-correct operations
Retry Amplification Cascade Retries multiply load across multiple service tiers Retry traffic explosion, multi-tier error rate spike Retry budget, circuit breaker, load shedding Smarter retry logic — cap, backoff, jitter, idempotency Multi-tier collapse — each tier amplifies load on tier below Reduced retries reduce resilience against transient failures
Control Plane Overload Autoscaling API or service discovery overloaded during incident Infra API failures, autoscaling stops responding Prioritise critical control-plane operations, manual scaling Separate control-plane capacity, rate-limit infra API calls Autoscaling stops during outage — system cannot heal itself Extra dedicated control-plane infra increases cost

Staff-Level Load Thinking — 7 Questions to Ask Always

1. Is load TEMPORARY or SUSTAINED? → temporary: autoscale + CDN + shed load → sustained: horizontal scale + async + partitioning 2. Is traffic EVENLY DISTRIBUTED? → hotspot: virtual nodes, replicate hot key, local cache 3. Will RETRIES AMPLIFY load? → circuit breaker? jitter? retry cap? idempotency? 4. Can the system DEGRADE GRACEFULLY? → load shedding: drop non-critical, serve cached, 503 fast 5. Is PROCESSING SLOWER than arrival rate? → queue: scale consumers + backpressure + batching 6. Can ONE HOTSPOT collapse the system? → bulkhead: isolate hot resource, replicate hot key 7. Is BACKPRESSURE WORKING? → bounded queues + producer throttling + flow control

Slow Degradation vs Sudden Crash — Load Failures Are Insidious

Hard Failure (Obvious)

  • Process crashes → alert fires
  • LB removes node immediately
  • Error clearly visible in logs
  • Recovery is straightforward

Load Degradation (More Dangerous)

  • Service alive — just slow
  • Health checks still pass
  • Clients retry → amplify load
  • Thread pool fills silently
  • System collapses gradually
  • Recovery re-triggers surge

Final Mental Model — All Load Failures Reduce to 5 States

1. Too much traffic → spike / overload / celebrity problem 2. Uneven traffic → hotspot / skew / regional imbalance 3. Sudden traffic → thundering herd / reconnect storm / post-downtime surge 4. Slow processing → queue backlog / consumer lag / dependency slowness 5. Retry amplification → retry storm / cascading failure / death spiral Cascading failures are most dangerous: failure spreads → amplifies → overwhelms healthy systems → harder to stop
