Filesystem Design

Inode tables, journaling — ext4, XFS, ZFS — Staff Engineer level

The Big Picture

Applications never write directly to disks. Data flows through the filesystem, which determines data organization, crash recovery, metadata speed, allocation efficiency, fragmentation, and scalability.

Inode Journaling ext4 XFS ZFS COW Extents Superblock
Application → System Calls → Filesystem → Block Layer → SSD/HDD Disks only understand blocks. Filesystems map files → physical disk blocks.

Filesystem Architecture

Superblock ← master record (type, block size, free count) ↓ Free Space Bitmap ← tracks allocated/free blocks ↓ Inode Table ← per-file metadata + block pointers ↓ Directories ← filename → inode number mapping ↓ Data Blocks ← actual file contents ↓ Journal / Log ← crash consistency guarantee

Inode — File Metadata Container

Every file has one inode. The inode stores metadata — not the filename.

Inode contains

  • Owner & Group
  • Permissions
  • File size
  • Timestamps (atime, mtime, ctime)
  • Link count
  • Extents / block pointers
  • Extended attributes

Lookup chain

Filename ↓ Directory Entry ↓ Inode Number ↓ Inode (metadata) ↓ Data Blocks

Multiple filenames (hard links) can point to the same inode.

Data Blocks & Extents

File contents live in data blocks. Modern filesystems use extents instead of individual block pointers.

Block pointers (old)

Inode → Block 128 → Block 129 → Block 130 → Block 131 (1 pointer per block)

Extents (modern)

Inode → Start: 128 Length: 4 (covers blocks 128–131) Less metadata overhead, better sequential perf.

Crash Consistency Problem

Write Data → Update Metadata → Power Failure Metadata may now point to incomplete data. Without protection → filesystem inconsistent.

Two solutions:

Journaling (ext4, XFS)

Write Journal Entry ↓ Commit Journal ↓ Update Metadata ↓ Mark Complete On crash → replay journal → fast recovery

Copy-on-Write (ZFS)

Write new block ↓ Update pointer atomically ↓ Old block freed later On crash → old blocks still valid → consistent

Three Filesystem Architectures

ext4 — Block Groups

Block Group ├── Superblock Copy ├── Block Bitmap ├── Inode Bitmap ├── Inode Table └── Data Blocks

Journaling via JBD2, extents, delayed allocation. Mature, low overhead, general-purpose.

XFS — Allocation Groups

Filesystem ├── Allocation Group 1 (own free space + inodes) ├── Allocation Group 2 ├── Allocation Group 3 └── Allocation Group 4

B+Trees for extents, directories, free space. Parallel allocations, minimal contention — scales to petabytes.

ZFS — Storage Pool + COW

Application → Dataset → Storage Pool → VDEVs → Disks Combines: Filesystem + Volume Manager + RAID + Cache + Snapshots + Checksums

Every block has a checksum. Detects bit rot, silent corruption. Snapshots are native and instant.

Production Failure Scenarios

Long fsck Time

Cause: Large ext4 filesystem, dirty journal  ·  Fix: Use journaling correctly, monitor filesystem health

Metadata Bottleneck

Cause: Millions of parallel file creates on ext4  ·  Fix: Switch to XFS with multiple Allocation Groups

Silent Data Corruption

Cause: Disk bit rot on ext4/XFS  ·  Fix: Use ZFS with checksumming + periodic scrubs

Slow Snapshot Operations

Cause: LVM snapshots on ext4/XFS  ·  Fix: Use native ZFS snapshots

High Memory Usage

Cause: ZFS ARC consuming all RAM  ·  Fix: Tune zfs_arc_max based on available memory

Production Debugging Checklist

  • ✅ Measure disk latency: iostat -x 1
  • ✅ Check inode usage: df -i
  • ✅ Monitor free space fragmentation
  • ✅ Review journal/log activity
  • ✅ Check filesystem health: fsck / xfs_repair / zpool status
  • ✅ Monitor snapshot growth
  • ✅ Schedule periodic ZFS scrubs
  • ✅ Benchmark before changing filesystem type

Key Takeaways

Inodes • Store file metadata + block mappings • Directories just map filenames → inode numbers • Hard links: multiple names, one inode Journaling (ext4, XFS) • Log metadata intent before applying changes • Fast crash recovery via journal replay • ext4 default: ordered mode (data before metadata) Copy-on-Write (ZFS) • New blocks written, pointer atomically switched • Crash consistency built in — no journal needed • Enables free, instant snapshots ext4 → General-purpose, low overhead, stable XFS → Parallel allocations, B+Tree, large-scale ZFS → End-to-end checksums, native snapshots, self-healing, built-in RAID + volume mgmt Staff picks filesystem based on: • Latency, concurrency, integrity, snapshots, memory budget, operational simplicity
