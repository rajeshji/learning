Block vs Object vs File Storage

Choosing the right storage abstraction — Staff Engineer level

The Big Picture

Not every workload has the same storage requirements. Choosing the wrong storage type causes high latency, poor scalability, increased cost, and consistency issues.

Block File Object POSIX IOPS Latency Scalability Consistency
All storage ultimately resides on disks, but the abstraction determines performance and usability. Application → Storage API → Block | File | Object → SSD/HDD

Three Storage Abstractions

Block Storage

App ↓ File System ↓ Raw Blocks ↓ SSD/HDD

OS builds filesystem on top. Storage knows nothing about files.

File Storage

App ↓ POSIX Calls ↓ File System ↓ Shared Storage

Files, directories, permissions. Shared across clients.

Object Storage

App ↓ REST API ↓ Metadata Svc ↓ Dist. Nodes

PUT / GET / DELETE. Flat key-value namespace.

Data Organization & Access

Block → Fixed-size blocks Logical Block Address (LBA) e.g., sector 4096 on /dev/sdb File → Hierarchical directories /data/reports/q4.pdf Object → Flat key-value namespace bucket/photos/img001.jpg (+ rich metadata + version)

Block Storage — Deep Dive

Strengths

  • Lowest latency
  • Highest IOPS
  • Strong consistency
  • Random read/write optimized
  • Mountable as a disk

Trade-offs

  • Not easily shared
  • Limited horizontal scalability
  • Minimal metadata support

Best for: MySQL, PostgreSQL, Kafka logs, VM disks, WAL, transaction logs.

File Storage — Deep Dive

Strengths

  • Human-friendly paths
  • Shared across multiple clients
  • POSIX compliant
  • Built-in permissions & ownership

Trade-offs

  • Metadata bottlenecks at scale
  • Higher latency than block
  • Limited horizontal scalability

Best for: Shared team files, AI/ML datasets, CI/CD workspaces, enterprise file shares.

Object Storage — Deep Dive

Strengths

  • Infinite scalability
  • Rich metadata + versioning
  • HTTP / REST access
  • Built-in replication
  • Lifecycle policies
  • Low cost at scale

Trade-offs

  • Higher latency (20–200 ms)
  • No POSIX interface
  • Not suitable for databases
  • Eventual consistency (often)

Best for: Images, videos, data lakes, backups, archival, analytics.

Hybrid Architecture — Production Reality

Most production systems combine all three storage types, each serving a different data lifecycle stage.

Hot Database → Block Storage (NVMe SSD, EBS) Shared Models/Code → File Storage (EFS, NFS, Lustre) Backups / Data Lake → Object Storage (S3, GCS, Blob) └─ Each tier: different latency, cost, and durability tradeoff

Hot data on NVMe Block → Warm data on File → Cold data on Object = best price/performance ratio.

Storage Selection Workflow

Need Persistent Storage ↓ Low latency + high IOPS? YES → Block Storage (databases, VMs, logs) ↓ Need shared POSIX access? YES → File Storage (AI datasets, CI/CD, teams) ↓ Need massive scale + cloud-native? YES → Object Storage (media, backups, data lake)

Ask: latency SLA, access pattern (random vs sequential), sharing needs, consistency, growth over 5 years.

Production Failure Scenarios

Slow Database Queries

Cause: Database stored on file/object storage  ·  Fix: Move to Block Storage

Expensive Infrastructure

Cause: Cold backups stored on SSD Block  ·  Fix: Move to Object Storage

ML Training Jobs Waiting

Cause: Multiple nodes downloading data repeatedly from object storage  ·  Fix: Use shared File Storage (EFS/Lustre)

Media Platform Scaling Issues

Cause: Images stored on local disks  ·  Fix: Move to Object Storage + CDN

Key Takeaways

Block Storage • Raw, low-latency, high-IOPS access • Ideal for: databases, VMs, transaction logs • Strong consistency, single client mount File Storage • POSIX-compliant, shared multi-client access • Ideal for: AI/ML datasets, CI/CD, file shares • Medium latency, standard metadata Object Storage • Massive scalability, rich metadata, HTTP access • Ideal for: media, backups, data lakes, archives • Higher latency, eventual consistency Production Reality • Most large systems use all three (hybrid) • Block = hot transactional data • File = shared working datasets • Object = warm/cold data + archival • Selection driven by: latency, access pattern, consistency, scalability, cost
