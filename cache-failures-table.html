Cache Failure Scenarios

Staff-level · 8 categories · 37 scenarios · detect / mitigate / prevent / cascading / trade-off

Why Cache Failures Are the Most Deceptive

Cache is designed to: reduce latency + reduce DB load + improve scalability But when cache fails: cache traffic → database traffic → backend collapse 7 root failure classes: unavailable | inconsistency | overload | invalidation issues eviction | hot key | distributed coordination
Failure Scenario When It Occurs How To Detect How To Mitigate How To Prevent Cascading Failure Risk Trade-off
1 — Cache Availability Failures
Cache Node CrashMust Know Redis/Memcached node OOM, process kill, hardware failure Cache health check failure, hit ratio drops to zero Failover to replica cache node immediately Cache replication (Redis Sentinel/Cluster), multi-node setup All requests hit DB simultaneously — DB traffic spikes 10-100× Replication doubles memory cost and adds coordination overhead
Complete Cache Cluster OutageMust Know Cluster-wide failure — power, network, multi-node crash Massive cache miss spike, DB connection exhaustion Fallback to DB with rate limiting to protect it Multi-AZ cache cluster, cross-zone replication DB overload cascade — entire backend collapses under uncached load Larger multi-AZ clusters cost significantly more
Cache Connection Failure Network partition, connection pool exhausted, proxy down Connection timeout/refused errors, cache latency spike Retry with backoff, fallback to DB Connection pooling, keepalive, multi-path network App latency spike → callers timeout → retry storm Larger connection pools increase memory and FD usage
Cache Startup Failure Corrupted persistence file (AOF/RDB), bad config on restart Cache restart loop, startup error logs Restore from clean snapshot, rebuild cache from DB Config validation before start, snapshot integrity checks Cold cache storm — all requests hit DB until cache fully warmed Warm-up increases startup time and adds DB load during recovery
Distributed Cache Partition Network partition splits cache cluster — some nodes unreachable Missing cache nodes in cluster view, inconsistent routing Route to healthy cache nodes, fall back on misses Multi-AZ deployment, redundant network paths Inconsistent cached data — different app servers get different values Cross-zone traffic adds latency and egress cost
2 — Cache Performance and Latency Failures
Slow Cache Response CPU/network saturation, large values, heavy serialization Cache latency spike, P99 increase on cache calls Scale horizontally, reduce value size, local L1 cache Better key/value partitioning, compression App timeout → fallback to DB → DB overload More cache shards add operational complexity
Cache CPU Saturation Heavy concurrent read/write traffic, complex data structures Cache CPU >90%, latency increase Add cache shards, reduce complex operations (SORT, LRANGE) Better key distribution, avoid CPU-heavy Redis commands Increased latency → callers retry → cache load amplifies More shards add management overhead
Memory Pressure / Thrashing Cache size exceeds memory limit — aggressive eviction begins Eviction rate spike, cache hit ratio dropping Increase memory allocation, tune eviction policy Proper TTL policies, memory monitoring with headroom alert Cache churn → hit ratio collapses → DB sees all traffic More RAM is expensive; smaller caches reduce hit ratio
Disk Persistence Slowdown Redis AOF/RDB heavy IO — persistence writes compete with reads Write latency increase, fsync wait time metrics Tune persistence frequency, use async AOF Faster NVMe disks, separate persistence from read IO Write latency increase propagates to all callers Less persistence risks losing cache data on crash
Cache Query Storm Traffic spike — too many cache requests hit simultaneously Cache QPS spike, latency increase Rate limiting, CDN for cacheable responses upstream Better caching strategy, multi-tier caching (L1+L2) DB fallback activated for overflowing requests → DB overload Multi-tier caching adds complexity and memory cost
3 — Cache Miss and Stampede Failures
Cache StampedeMust Know Popular cache key expires — many threads race to rebuild from DB DB QPS spike coinciding with cache miss rate spike Single-flight pattern (one thread rebuilds, others wait) Staggered TTLs, probabilistic refresh before expiry, pre-warming DB overwhelmed by simultaneous queries → slowdown → timeout cascade Cache locking adds per-request coordination overhead
Cold Cache StormMust Know Cache restart or full flush — all data evicted simultaneously Hit ratio drops to near zero, DB QPS spikes dramatically Warm cache gradually using background jobs Cache pre-warming on startup, avoid flushing in production Massive DB spike — all requests bypass cold cache and hit DB Warm-up adds startup complexity and initial DB load
Cache AvalancheMust Know Many cache keys expire simultaneously — set with same TTL Large-scale miss spike affecting many endpoints at once Randomized TTL jitter, staggered expiration windows Add random jitter to all TTL values at write time Entire DB overloaded — avalanche of misses from all cache tiers Harder to predict exact cache expiry time for debugging
Cache Penetration Requests for keys that never exist — cache always misses, hits DB Repeated DB misses for same non-existent keys Bloom filter to block invalid keys, null value caching Input validation, cache null results with short TTL DB overloaded by repeated invalid lookups Bloom filter consumes memory; null caching can mislead
Cache Breakdown (Hot Key Miss) Single hot key expires — millions of requests race to DB for it One DB query spiking to massive QPS instantly Never-expire strategy for hottest keys, or mutex rebuild Hot key replication to multiple cache nodes, local process cache Hotspot DB collapse — single query pattern overwhelms DB Never-expire means stale data unless invalidated explicitly
4 — Cache Consistency Failures
Stale Cache DataMust Know Cache not invalidated after DB update — old value served Cache/DB value mismatch, user complaints about wrong data Invalidate cache entry on write, force refresh Write-through cache, short TTL, CDC-based invalidation Wrong prices, balances, or inventory shown at scale Aggressive invalidation increases miss rate and DB load
Lost Cache Invalidation Invalidation event dropped — message failure, network issue Persistent stale reads despite DB update Force cache refresh, TTL-based expiry as safety net Reliable invalidation pipeline (transactional outbox + CDC) Inconsistent user state spreads until TTL expiry More reliable pipeline adds coordination overhead
Read-After-Write Inconsistency User writes data — reads from stale cache before invalidation arrives User sees old data immediately after their own write Bypass cache temporarily for read after write (session routing) Read-your-writes consistency, write-through cache User confusion → repeat actions → duplicate data Bypassing cache reduces its hit ratio temporarily
Write-Behind Data Loss Cache crashes before async write-behind flushes to DB Missing DB updates after cache restart Replay from durable write log Durable write queue (WAL for write-behind), synchronous writes on critical data Permanent data loss if write-behind log not durable Durable write log adds IO overhead, reducing write-behind benefit
Distributed Cache Inconsistency Replication lag between cache nodes — different nodes return different values Different cache values on different nodes for same key Re-sync cache nodes, read from primary cache Stronger consistency mode, shorter replication lag Different users see different data — inconsistent UX at scale Synchronous cache replication adds write latency
5 — Cache Eviction and Memory Failures
Aggressive Eviction Memory limit reached — LRU/LFU evicts data faster than written Eviction metrics spike, cache hit ratio drops steadily Increase memory allocation, tune eviction policy Proper cache sizing, eviction policy matching access patterns Hit ratio collapse → all traffic falls through to DB More memory is expensive; wrong eviction policy wastes it
Critical Data Evicted Frequently-needed data evicted due to poor eviction policy Frequent cache misses for important objects Pin critical keys (no eviction), use dedicated cache namespace LFU eviction, separate cache pools for hot vs cold data DB load spikes for most important queries repeatedly Pinned keys reduce usable cache space for other data
Memory Fragmentation Long-running cache with many small writes creates fragmented memory mem_fragmentation_ratio > 1.5 in Redis INFO, OOM with free memory Restart cache (accept cold start), or use MEMORY PURGE jemalloc tuning, active defragmentation (Redis 4+) OOM crash from fragmentation → cold cache storm Active defrag adds CPU overhead during normal operation
Cache OOM Crash Unbounded cache growth — no max memory configured Memory alerts, Redis OOM error, process killed Restart, enforce maxmemory immediately Always set maxmemory + eviction policy in config Cold cache DB storm immediately after crash Smaller maxmemory reduces hit ratio
Large Object Domination Few very large values consume most cache memory, evicting many small ones Uneven memory usage per key, high eviction on small keys Split large objects into smaller chunks, compress values Object size limits, evict large objects first Eviction cascade for small high-traffic keys → miss storm Compression adds CPU overhead per read/write
6 — Hot Key and Partition Failures
Hot Key OverloadMust Know Viral content/popular item — one key gets millions of requests per second Single cache node CPU at 100% while others are idle Replicate hot key to multiple cache nodes, serve from local cache Local in-process L1 cache, CDN for truly hot content Single cache shard overloads → node unavailable → full miss cascade Hot key replication increases memory and invalidation complexity
Hot Partition / Shard Bad sharding — one shard receives most of the traffic Uneven shard metrics — one node at capacity, others idle Rebalance shards, add virtual nodes Better shard key selection, consistent hashing with virtual nodes Cache shard collapse → miss storm for all keys on that shard Rebalancing triggers key migration — transient miss storm
Celebrity / Fan-out Problem Popular entity triggers read amplification — millions hit same cache key Read amplification spike, single key dominates cache traffic Multi-layer caching (process cache + distributed cache + CDN) Tiered caching, pre-compute and cache celebrity-tier content Cache cluster overload → cascades to DB for celebrity-tier objects More cache layers add complexity and increase total memory cost
Skewed Key Distribution Hash function distributes keys unevenly across shards One cache node overloaded, others under-utilised Rehash with better function, add virtual nodes Consistent hashing, rendezvous hashing, virtual node count tuning Overloaded shard becomes bottleneck — cascades on miss More virtual nodes add metadata management overhead
7 — Distributed Cache Coordination Failures
Cache Replication Lag Slow network sync between primary and replica cache node Replica returns stale value while primary has updated value Read from primary cache for consistency-sensitive requests Faster replication pipeline, co-located cache nodes Stale cache reads at scale — wrong data served from replicas Reading from primary only removes replica read scalability benefit
Distributed Lock Failure Cache rebuild lock expires or fails — multiple threads rebuild same key Duplicate cache rebuilds, DB QPS spikes for same query Retry lock acquisition, use Redlock for distributed locking Reliable lock service, conservative lock TTL Stampede returns — lock failure defeats the single-flight protection Distributed lock coordination adds per-request overhead
Cache Rebalancing Storm Node added/removed — consistent hashing triggers massive key migration Network saturation during rebalance, miss rate spike Gradual rebalance, virtual node count to reduce migration scope Stable cluster size, virtual nodes to minimize migration on change Network saturation → cache misses during migration → DB load spike Slower rebalancing extends migration window and inconsistency
Split Brain Cache Network partition — both cache sides think they are primary Inconsistent cache state, different values returned from each side Reconcile cache after partition heals, invalidate diverged keys Consensus-based coordination (Redis Sentinel), fencing Different users get different cached responses — data divergence Consensus failover reduces availability during partition
8 — Persistence and Durability Failures
AOF Corruption (Redis) Crash during AOF write — partial entry corrupts log Redis fails to start, AOF loading error Use redis-check-aof to repair, restore from RDB snapshot AOF checksums (Redis 7+), RDB + AOF hybrid persistence Cache rebuild storm — full cold start after restoration Hybrid persistence uses more storage and has higher IO overhead
Snapshot Failure RDB snapshot interrupted — forked process killed, disk full Missing snapshot file, snapshotting error in Redis logs Retry snapshot, switch to AOF-only if snapshots unstable Monitor snapshot completion, enough disk for fork + data Recovery impossible without snapshot — must rebuild from DB Snapshot IO can slow Redis during fork — latency spikes
Durability Misconfiguration Cache configured with no persistence — loses all data on restart Unexpected cold cache after restart, all data missing Reconfigure persistence immediately, document config Infrastructure-as-code for cache config, config validation in CI Cold cache DB storm — all traffic hits DB until cache rebuilt Stronger persistence (fsync always) significantly slows writes
Cache Recovery Slowdown Large AOF file — cache takes too long to replay and start accepting connections Long startup time, service unavailable during replay Restore from RDB snapshot to reduce replay length Hybrid RDB+AOF, regular snapshots to truncate AOF length Extended service startup delay — cold cache DB storm on completion More frequent snapshots add snapshot IO overhead

10 Must-Know Cache Failures for Interviews

1. Cache stampede → single-flight + staggered TTL + pre-warming 2. Cache avalanche → TTL jitter on all keys at write time 3. Hot key overload → replicate key + local L1 cache + CDN 4. Stale cache → write-through + short TTL + CDC invalidation 5. Cold cache storm → pre-warming + gradual ramp + avoid flush in prod 6. Cluster outage → multi-AZ cluster + DB rate limit on fallback 7. Cache penetration → bloom filter + null-value caching + input validation 8. Eviction storm → proper cache sizing + LFU + separate hot/cold pools 9. Write-behind loss → durable write-behind queue + fallback to sync write 10. Distributed inconsistency → read-your-writes routing + write-through

Staff-Level Cache Thinking — 8 Questions to Ask Always

1. What if cache disappears? → DB must survive the full miss storm 2. DB survive miss storm? → rate limit + circuit breaker on fallback 3. Stale cache break correctness? → write-through + TTL + CDC invalidation 4. Hot key overload cluster? → local L1 + replicate key + CDN upstream 5. Can invalidation fail? → TTL as safety net + reliable event pipeline 6. Cache rebuild overload backend? → single-flight + gradual warm-up 7. Consistency required or eventual? → sync write-through vs async write-behind 8. Scaling creates instability? → virtual nodes to limit key migration scope

Cache Failure vs DB Failure — Which Is More Dangerous?

DB Down (Predictable)

  • Clear failure — no writes accepted
  • Alerting fires immediately
  • Everyone knows DB is the bottleneck
  • Failover path is well understood

Cache Down (More Dangerous)

  • Service still responds — just slower
  • DB absorbs cache traffic silently
  • DB overloads before alert fires
  • Both cache AND DB fail together
  • Recovery itself triggers another surge

Final Mental Model — All Cache Failures Reduce to 4 Core Problems

1. Cache unavailable → cache traffic → DB traffic → backend collapse 2. Cache stale → wrong data served → incorrect business logic at scale 3. Cache overloaded → hot key + stampede + avalanche → all roads to DB collapse 4. Cache inconsistent → distributed lag + invalidation failure → divergent state Key insight: cache failures are DB failures in disguise → always design DB to survive cache disappearing completely
