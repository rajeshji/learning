fsync() & Performance Impact

Durability vs throughput trade-offs — Staff Engineer level

The Big Picture

write() does not save your data. It only copies data into the kernel page cache. fsync() forces all pending writes to become durable — but it is often 100–10,000× slower than write().

write() fsync() fdatasync() Page Cache Group Commit WAL Device Flush PLP
write() → Page Cache (RAM) → [crash? data lost] write() + fsync() → Page Cache → Journal → Device Flush → Persistent Media → crash safe ✓

Why fsync() Is Expensive

Unlike write(), fsync() blocks synchronously through every storage layer:

Dirty Pages ↓ Write file data to filesystem ↓ Commit filesystem journal (ext4/XFS) ↓ Issue FLUSH to storage device (ATA/NVMe) ↓ Wait for hardware acknowledgment ↓ Return to application Every step adds latency. Hardware ACK is the bottleneck.

Latency Comparison

OperationTypical Latency
Memory copy<1 µs
write()1–10 µs
Page cache flush100–500 µs
fsync() — NVMe SSD0.05–0.5 ms
fsync() — SATA SSD0.5–2 ms
fsync() — HDD5–50 ms

fsync() on HDD is up to 50,000× slower than a memory copy. Hardware choice is the biggest lever.

fsync() Internals by Filesystem

ext4

Write data ↓ Journal metadata ↓ Flush journal (JBD2) ↓ Commit + device ACK

XFS

Write data ↓ Intent log ↓ Flush ↓ Commit + device ACK

ZFS

Write new blocks ↓ ZIL (intent log) ↓ Atomic TXG commit (COW — no overwrite)

fsync() vs fdatasync()

File Data✅✅

Use fdatasync() for WALs, logs, and append-only files — it avoids unnecessary metadata I/O while still guaranteeing data durability.

Batching & Group Commit — The Key Optimization

Worst: one fsync per write

Write → fsync() Write → fsync() Write → fsync() (3 flushes, blocks each time)

Better: group commit

Txn 1 ─┐ Txn 2 ─┤→ single fsync() Txn 3 ─┘ (1 flush, all commit)

Group commit is used by PostgreSQL, MySQL InnoDB, Kafka, and RocksDB — single flush covers many transactions.

Device Cache & Hardware Impact

DeviceTypical fsync LatencyPLP?
HDD10–50 ms❌ No
SATA SSD0.5–2 ms❌ Usually not
NVMe SSD0.05–0.5 ms⚠ Varies
Enterprise SSD (PLP)0.02–0.2 ms✅ Yes

PLP (Power Loss Protection) with supercapacitors lets the SSD flush its cache on power loss — fsync() can be faster because hardware guarantees durability.

Production Failure Scenarios

Lost Transactions After Crash

Cause: Application used only write()  ·  Fix: Call fsync() before acknowledging commit

Low TPS on Database

Cause: One fsync() per transaction  ·  Fix: Enable group commit

High fsync Latency

Cause: WAL on consumer HDD or SATA SSD  ·  Fix: Move WAL to dedicated NVMe SSD

Double Journaling Overhead

Cause: DB WAL + ext4 journaling on same data  ·  Fix: Tune filesystem or use O_DIRECT for WAL

Power Failure Data Loss on SSD

Cause: Consumer SSD volatile cache  ·  Fix: Enterprise SSD with PLP supercapacitor

Production Debugging Checklist

  • ✅ Measure fsync() latency: fio --fsync=1 --rw=write
  • ✅ Check storage hardware type (HDD / SATA / NVMe)
  • ✅ Verify PLP support in SSD spec sheet
  • ✅ Monitor page cache dirty ratio: /proc/meminfo
  • ✅ Check filesystem journaling mode (tune2fs -l)
  • ✅ Look for double journaling (DB WAL + FS journal on same path)
  • ✅ Monitor device queue depth: iostat -x 1
  • ✅ Confirm group commit is enabled in DB config
