Concurrency and Race Condition Failure Scenarios

Staff-level · 9 categories · 36 scenarios · detect / mitigate / prevent / cascading / trade-off

Why Concurrency Failures Are the Hardest Bugs to Find

Concurrency bugs are non-deterministic — they appear under load, not in unit tests. They depend on exact thread scheduling, CPU caching, and network timing. By the time you investigate, the interleaving that caused the bug is gone. Root causes reduce to one thing: Multiple agents (threads / processes / services) sharing mutable state without sufficient coordination

1 — Classic Race Conditions
Check-Then-Act RaceMust Know Thread A reads state (check), Thread B modifies it, Thread A acts on stale read — decision wrong Intermittent wrong outcomes under concurrent load; hard to reproduce in tests Replace check-then-act with atomic compare-and-swap (CAS) or lock the check and act together Atomic operations, optimistic locking, database-level constraints as last guard Data corruption — two threads believe they have exclusive access simultaneously CAS loops under high contention spin and waste CPU; locks serialise throughput
Read-Modify-Write RaceMust Know Two threads: both read value X, both compute X+1, both write X+1 — one increment lost Counter or balance drifting lower than expected under load Use atomic increment (AtomicInteger, Redis INCR, DB UPDATE with +1) Atomic read-modify-write primitives; never read-then-write for increments Inventory or balance undercounting — lost updates accumulate silently Atomic RMW on a hot key becomes a serialisation bottleneck at very high concurrency
TOCTOU — Time of Check to Time of UseMust Know Validation happens at T1, action happens at T2 — state changes between T1 and T2 Actions succeed that should have been rejected (e.g. overdraft after balance check) Perform validation and action in a single atomic transaction or under a lock Optimistic locking with version check at write, database-level constraint enforcement Security bypass — attacker exploits window between check and use to slip invalid state Atomic validation+action in DB transactions adds latency vs split read-write paths
ABA Problem in Lock-Free Structures CAS sees value A, assumes state unchanged — but state went A→B→A — CAS succeeds on wrong state Subtle wrong results in lock-free data structure under high concurrency Use tagged CAS (version counter alongside value) to detect the A→B→A sequence Tagged pointers or version stamps in all CAS operations on mutable structures Silent data structure corruption — wrong node removed or linked in lock-free list Version stamps add memory overhead per node; tagged CAS requires wider atomic operations
2 — Lost Update and Write Skew
Lost UpdateMust Know Two transactions read the same row, both compute new value, second commit overwrites first — first change lost Update appears to succeed but prior change missing; balance or count wrong Retry with fresh read; use optimistic locking (version field check on write) Optimistic locking (version field), pessimistic locking (SELECT FOR UPDATE), atomic SQL UPDATE Data integrity violation — financial, inventory, or state data silently incorrect SELECT FOR UPDATE serialises all writers; optimistic locking causes retries under contention
Write SkewMust Know Two transactions each read overlapping data and write non-overlapping rows — combined result violates constraint Database constraint not violated per-row but business invariant broken (e.g. two doctors both go off-call) Serialisable isolation level or explicit application-level lock on the shared read set SERIALIZABLE isolation, SELECT FOR UPDATE on all rows read that influence the write decision Business logic violation that database constraints cannot catch — silent corrupt state SERIALIZABLE isolation significantly reduces concurrency throughput
Phantom Read Leading to Wrong Decision Transaction T1 reads a range — T2 inserts row in that range — T1 re-reads, sees different count Business logic acting on stale aggregate count; result depends on read timing REPEATABLE READ or SERIALIZABLE isolation; predicate lock on range SERIALIZABLE isolation; COUNT with explicit locks; avoid range-based decisions in concurrent paths Wrong allocation decisions — over-issuing limited resources based on stale count Predicate locking reduces write throughput for all inserts into locked range
Dirty Write Overwrite Transaction A starts writing a row — Transaction B also writes same row before A commits — B overwritten by A commit B's change silently gone; race only detectable by comparing before/after values Ensure all engines use write locking (never allow uncommitted write to be overwritten) Database-level write locking (all ACID-compliant DBs prevent this by default — watch for NoSQL) Silent data loss — B's committed value replaced without trace Write locks add contention; in NoSQL systems you must implement this yourself
3 — Deadlocks and Livelocks
Classic Deadlock — Circular Lock WaitMust Know Transaction A holds lock on row 1, waits for row 2; Transaction B holds row 2, waits for row 1 Deadlock detection log entry; both transactions aborted and retried Abort one transaction (database auto-detects), retry with backoff Consistent global lock ordering — always acquire locks in the same order across all code paths Throughput drops as deadlock frequency increases under load — repeated abort-retry cycles Global lock ordering constrains code structure; may require refactoring query access patterns
Distributed DeadlockMust Know Service A holds resource X waiting for Y on Service B; B holds Y waiting for X — across service boundaries Both services stuck indefinitely — no timeout fires because timeout set too long Timeout on all cross-service lock waits, abort and retry with backoff Timeout on every distributed lock acquisition, avoid holding locks while calling external services Both services completely frozen — no requests on either complete until timeout fires Short lock timeouts abort valid slow operations; long timeouts allow deadlock to persist
Livelock — Infinite Courtesy Loop Thread A detects conflict, backs off; Thread B also backs off; both retry at same time — repeat forever High CPU with no forward progress; lock acquisition attempts firing but never succeeding Add randomised jitter to retry interval to break synchronisation Full jitter on all lock retry intervals, exponential backoff with random seed CPU exhaustion without any work completing — threads busy but useless Jitter makes worst-case retry latency less predictable
Lock Ordering Violation Introducing Deadlock Two code paths acquire the same locks in different order — deadlock possible whenever both run concurrently Intermittent deadlock errors under concurrent load at specific code paths Enforce consistent lock ordering between both code paths Static analysis for lock ordering, documented lock hierarchy, code review for lock acquisition order Production deadlock frequency grows as traffic increases — problem hidden at low load Enforcing lock ordering may require restructuring queries or request handling logic
4 — Double Spending and Financial Race Conditions
Payment Double-Spend RaceMust Know User submits payment twice quickly — both requests check balance simultaneously, both see sufficient funds, both deduct Account balance below expected, double debit in transaction history Idempotency key on payment endpoint — second request returns cached first result Idempotency key + deduplication store, SELECT FOR UPDATE on balance row, database constraint Financial loss — both payments processed, account overdrafted or double-charged Idempotency key store adds storage overhead; SELECT FOR UPDATE serialises all payments
Inventory OversellMust Know 100 users simultaneously buy last item — all see stock=1, all decrement to 0, all succeed — 100 orders for 1 item Orders exceed available stock; fulfilment failures; negative inventory count Reserve stock with atomic decrement and check (UPDATE ... WHERE stock > 0 RETURNING stock) Atomic SQL UPDATE with WHERE stock > 0, database CHECK constraint on stock >= 0, optimistic locking Customer fulfilment failures at scale — all 100 users must be notified and refunded Serialised stock update limits purchase throughput for high-demand items
Coupon or Voucher Double-Use User submits coupon redemption twice simultaneously — both requests see coupon as unused, both mark used Coupon applied multiple times in audit log, discount given twice Idempotency key + single atomic mark-as-used with unique constraint Unique constraint on redemption record, atomic check-and-mark, idempotency key per redemption Financial loss from repeated discount application across concurrent redemption paths Unique constraint causes second request to fail rather than return graceful response
Rate Limit Race Condition — Token Bucket Two concurrent requests both read token count as 1, both pass rate limit check, both consume the token More requests succeeding than rate limit allows under concurrent load Atomic token decrement (Redis DECR then check, not check then DECR) Redis atomic DECR+check, distributed rate limiter with atomic operations, per-node local limit Backend overloaded by requests that should have been rate-limited Atomic distributed rate limiting adds latency; local-only limiting cannot enforce global quotas
5 — Duplicate Processing and Idempotency Failures
At-Least-Once Delivery Without IdempotencyMust Know Message queue delivers same message twice (retry after timeout) — consumer processes it twice Duplicate records, double-applied side effects, duplicate emails or charges Detect duplicate by message ID at consumer, skip if already processed Idempotent consumer design with deduplication store keyed on message ID Double charges, duplicate notifications, double-applied inventory changes at scale Deduplication store adds storage and lookup overhead per message
Retry Without Idempotency KeyMust Know Client retries API call after network timeout — server processed original, retry creates second action Duplicate operations in audit log, user sees two of same action Detect duplicate by request ID, return cached result of first execution Idempotency key on all mutating endpoints, request deduplication at API layer Double payment, double order, double state change on every retry Idempotency key TTL determines how long dedup cache must be retained
Event Replay Causing Duplicate State Event stream replayed for recovery — event handlers not idempotent — state applied twice State values doubled, duplicate records, business metrics showing 2× expected Reset state to snapshot before replay, use idempotent apply functions Event sourcing with idempotent apply, sequence number tracking per aggregate Corrupt aggregate state — all business operations on affected entities return wrong results Idempotent event apply is harder to implement for operations with side effects
Cache Population Race — Multiple Writers Multiple threads all miss cache simultaneously — all fetch from DB and all write to cache — last write wins Multiple DB queries for same key at cache miss; no data loss but extra DB load Single-flight (only one thread fetches; others wait for result) Single-flight / request coalescing pattern, probabilistic early expiry to stagger misses DB thundering herd on cache miss — each additional concurrent thread adds one DB query Single-flight increases latency for all waiters; timeout on the fetching thread blocks them all
6 — Lock Contention and Starvation
Hot Lock — Serialised ThroughputMust Know All threads must acquire lock on a single hot resource — parallelism collapses to single-threaded Throughput ceiling despite adding threads; CPU low, lock wait metrics high Partition the resource so locks are held on shards, not the whole resource Striped locking (lock striping), sharded counters, CRDTs for commutative updates Throughput limit reached — adding concurrency makes performance worse via contention Striped locking requires aggregating across stripes for global counts
Reader-Writer Starvation Continuous stream of readers or writers starves the other side — starvation under sustained load Writers waiting indefinitely (reader starvation) or reads timing out under heavy write load Use fair read-write lock with queue, apply rate limiting to dominant side Fair RWLock with FIFO acquisition queue, reader-writer balance monitoring One side of workload stalled — writes backed up or reads timing out completely Fair locks have higher overhead than unfair locks; fairness reduces throughput slightly
Lock Convoy One thread holds lock for long time — all other threads queue up — when released, one acquires, rest wait again High average lock wait time, threads piling up in lock queue, throughput much lower than expected Reduce critical section duration, move work outside lock scope Minimise lock scope, avoid I/O inside locks, lock-free alternatives where possible Throughput collapses to rate of slowest critical section execution Extracting work outside locks adds code complexity and potential state inconsistency windows
Priority Inversion Via Lock Low-priority thread holds lock needed by high-priority thread — high-priority blocked behind low-priority High-priority tasks unexpectedly delayed; SLA violation despite low system load Priority inheritance — boost low-priority holder to priority of waiter Priority inheritance protocol in scheduler, avoid locks shared between different priority levels SLA violation — high-priority work delayed by low-priority background work Priority inheritance adds scheduler complexity; avoiding shared locks limits design flexibility
7 — Memory Visibility Failures
Visibility Failure — Stale Cache LineMust Know Thread A writes value — Thread B running on different CPU core reads stale value from its cache Non-deterministic stale reads in shared memory; value appears unwritten to other threads Use volatile / memory fence / atomic operations to force cache coherence volatile keyword (Java), atomic variables, memory barriers at write and read sites Silent wrong behaviour — threads computing on stale state, producing incorrect results Memory fences prevent CPU reordering optimisations, reducing instruction throughput
Instruction Reordering by CPU or Compiler CPU or compiler reorders instructions for performance — dependent code sees inconsistent state Non-deterministic wrong results under load, only on specific hardware architectures Insert appropriate memory barriers (acquire/release semantics) Use language-level synchronisation primitives that include barriers, do not hand-roll Subtle correctness violations — state appears initialised to one thread but not another Barriers are architecture-specific; over-use of barriers harms CPU pipeline efficiency
Double-Checked Locking Bug Singleton pattern checks null without lock, then locks, then checks again — reordering causes partially-initialised object to be seen NullPointerException or corrupted singleton state under race Use volatile on instance field, or use language-guaranteed lazy init (Holder pattern) volatile singleton field (Java), Initialization-on-Demand Holder idiom, or enum singleton Corrupted singleton used by all callers — system-wide incorrect behaviour from one race Holder pattern adds indirection; volatile prevents some CPU optimisations on hot path
False Sharing — Cache Line Contention Two unrelated variables in same CPU cache line — writes to one invalidate the other thread's cache for both Unexpected cache miss storm despite seemingly independent data; performance degrades with more cores Pad variables to separate cache lines (64-byte alignment) Align hot variables to cache line boundaries, use @Contended (Java), structure padding Performance degrades as core count increases — the opposite of expected scaling Cache line padding wastes memory proportional to number of hot variables padded
8 — Distributed Concurrency Failures
Distributed Lock Not Acquired — Split Brain WriteMust Know Two services both fail to see each other's lock — both acquire "exclusive" lock and write simultaneously Conflicting writes on same resource, data divergence detected on read Fence with epoch/fencing token — only holder of highest token can write Fencing tokens in all write paths, storage layer validates token before accepting write Silent data corruption — both writes succeed, final state is undefined Fencing token validation requires storage layer cooperation — cannot add after the fact
CAS Loop Spinning Under High ContentionMust Know Many threads/services compete on same CAS — losers spin and retry — CPU saturated with failed CAS attempts CPU high with low useful throughput, CAS failure rate metric high Add backoff + jitter between CAS retries, consider lock-based approach for high contention Exponential backoff on CAS failure, partition the contested resource to reduce contention CPU saturation — most CPU cycles wasted on failed CAS with no work done Backoff reduces throughput under low contention; partitioning adds coordination overhead
Distributed TOCTOU — Validate Then Modify Service A validates a distributed resource at T1, service B modifies it at T2, service A acts at T3 on now-invalid state Action succeeds that should have been rejected; business constraint violated Re-validate inside atomic transaction with the modify step Optimistic locking across distributed boundary, saga compensation if post-write validation fails Invalid state committed that cannot be easily undone without compensating transaction Re-validation inside transaction increases transaction scope and DB contention
Optimistic Lock Contention Thrash High write concurrency on same record — all writers optimistically lock, all but one fail — retry storm High version conflict rate in metrics, latency growing with concurrency Reduce write concurrency on hot record, switch to pessimistic lock for known hot paths Pre-partition hot records, limit concurrent writers per record, apply backoff on conflict Retry storm — every failed optimistic write immediately retries, amplifying contention Pessimistic lock on hot record serialises all writers — single-threaded throughput
9 — Database Transaction Anomalies
Serialisation Failure Under Concurrent WritesMust Know SERIALIZABLE isolation detects that concurrent execution is not equivalent to any serial order — aborts Serialisation error returned to application; transaction abort rate high under load Retry aborted transaction with backoff Idempotent transaction design, retry with exponential backoff, reduce transaction scope Retry storm — high abort rate causes all writers to retry simultaneously SERIALIZABLE isolation has highest abort rate under concurrency vs weaker isolation levels
Long Transaction Blocking OthersMust Know Transaction holds locks for seconds (user-interactive or slow query) — all concurrent writers queue behind it Lock wait spike, high query latency for all concurrent writers Kill long-running transaction, apply statement timeout Statement timeout, short transaction design, avoid user input inside transaction boundary All writers on affected rows stalled — throughput collapses for duration of long transaction Aggressive statement timeout aborts valid slow analytical queries
Select-For-Update Deadlock Pattern Two transactions use SELECT FOR UPDATE on multiple rows in different order — deadlock Deadlock detection error in DB log, one transaction aborted Retry aborted transaction, rewrite to acquire locks in consistent order Consistent row locking order (order by primary key), minimise rows locked per transaction Frequent deadlocks under load cause high retry rate and latency increase Ordering locks by PK constrains query structure — may require additional sort steps
Read-Committed Gap Allowing Double Booking READ COMMITTED isolation allows phantom inserts between reads — concurrent bookings both see availability Two bookings for same slot both succeed; duplicate reservation detected post-commit Unique constraint on (resource, time_slot) catches duplicate at commit Unique constraint as last-resort guard, SERIALIZABLE isolation, application-level advisory lock Double-booked resources, customer dissatisfaction, manual remediation required SERIALIZABLE isolation significantly reduces booking throughput under concurrency

Staff-Level Concurrency Thinking — 9 Questions to Ask Always

1. Is any check-then-act non-atomic? → attacker or race will exploit the gap 2. Can two writers update the same row? → need optimistic or pessimistic lock 3. Are all mutating endpoints idempotent? → retries and at-least-once delivery cause duplicates 4. Do lock acquisitions have a consistent order? → inconsistent order = eventual deadlock 5. Is any shared counter incremented non-atomically? → read-modify-write loses updates 6. Can a transaction hold locks while waiting on user? → all other writers stall 7. Does the DB isolation level match the invariant? → READ COMMITTED allows write skew 8. Are all financial operations protected by constraints? → DB constraints as last guard 9. Is TOCTOU possible across service boundaries? → validate AND modify must be atomic

Final Mental Model — All Concurrency Failures Reduce to 3 Root Causes

1. Shared mutable state → multiple agents can modify the same thing 2. Non-atomic operation → check + act not done together as one unit 3. Wrong isolation level → DB sees intermediate state from another transaction Fix in this order: 1. Eliminate sharing → immutable data, event sourcing, share nothing 2. Make operations atomic → CAS, transactions, idempotency keys 3. Raise isolation level → REPEATABLE READ or SERIALIZABLE where needed The most dangerous concurrency failure: Payment or inventory race under concurrent load because: data looks correct until you count the money

Principal Takeaway

Atomic

Check+act must be one unit.

Idempotent

All mutations safe to retry.

Order locks

Consistent order, every path.

Constrain DB

DB constraints as last guard.
