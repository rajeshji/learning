Latency vs Bandwidth vs Throughput Calculations

Staff Engineer Reference — Networking & Performance

WHY IT MATTERS
Why Should a Staff Engineer Care?

Almost every performance issue in distributed systems comes down to one (or more) of these three factors:

Latency

How quickly data starts moving — time to first byte.

Bandwidth

How much data the network can carry — pipe capacity.

Throughput

How much useful data is actually transferred — effective rate.

"Highway analogy: Latency = time for the first car to arrive. Bandwidth = number of lanes. Throughput = cars reaching the destination per hour."
Common mistake: Assuming more bandwidth automatically means better performance. For small requests, latency is almost always the real bottleneck — doubling bandwidth has almost zero effect.
DEFINITIONS
Core Definitions
1. Latency

Time for a packet/request to travel from source to destination. Measured in ms or µs. Answers: "How long until the first byte arrives?"

Total Latency = Propagation Delay (distance / speed of light) + Serialization Delay (packet size / link bandwidth) + Queuing Delay (time waiting in buffers) + Processing Delay (per-hop: switch, TLS, routing) + Application Delay (DB query, business logic)
EnvironmentRTT

Same Region5–20 ms
Cross Region30–80 ms
India ↔ US150–200 ms
GEO Satellite500–700 ms

Dominated by: REST APIs, RPCs, DB queries, leader election, lock acquisition, auth.

2. Bandwidth

Maximum data a link can transmit per second. Measured in Mbps/Gbps/Tbps. Answers: "How wide is the pipe?"

Bandwidth = Data / Time

Dominated by: Video streaming, backups, ML dataset copies, replication, file transfers.

3. Throughput

Actual useful data successfully delivered. Always ≤ bandwidth. Answers: "How much data is actually flowing?"

Throughput ≤ Bandwidth Gap caused by: TCP overhead, packet loss, retransmissions, congestion, flow control, encryption, serialization/protocol framing Example: 1 Gbps link → 820 Mbps actual throughput

Dominated by: DB replication, Kafka replication, bulk data transfer.

KEY FORMULAS
Key Formulas Every Staff Engineer Must Know

Formula 1 — Transfer Time

Transfer Time = Handshake RTTs + (File Size ÷ Throughput)
Example: 100 MB file, 100 Mbps throughput, 50 ms RTT 100 MB = 800 Mb 800 Mb ÷ 100 Mbps = 8 s + 50 ms RTT overhead ≈ 8.05 s total

Formula 2 — TCP Throughput (approximate)

TCP Throughput ≈ TCP Window Size ÷ RTT

Larger windows and lower RTT increase throughput. Small windows on high-RTT links severely limit performance.

Formula 3 — Bandwidth-Delay Product (BDP) ⭐

BDP = Bandwidth × RTT

BDP represents the amount of data that must be "in flight" to fully utilize a network link.

Example: 1 Gbps link, RTT = 100 ms BDP = 1 Gbps × 0.1 s = 100 Mb = 12.5 MB To fully utilize the link, TCP must have at least 12.5 MB of unacknowledged data in flight. If TCP Window = 1 MB (default) and BDP = 12.5 MB: → Sender runs out of data before ACKs return → Link idles between window completions → 1 Gbps bandwidth → ~80 Mbps effective throughput
BDP is the most important formula for long-distance or high-speed links. TCP Window ≥ BDP is the condition for full link utilization. Enable TCP Window Scaling (tcp_window_scaling) and tune net.core.rmem_max and net.core.wmem_max.

WORKED EXAMPLES
Practical Calculation Examples

Example 1 — API Call

Payload: 2 KB Bandwidth: 1 Gbps RTT: 80 ms Transfer: ≈ 0.02 ms Total: ≈ 80 ms Latency dominates. Upgrading bandwidth has no effect.

Example 2 — Video Upload

Payload: 5 GB RTT: 20 ms Bandwidth: 50 Mbps 5 GB = 40 Gb 40 Gb ÷ 50 Mbps = 800 s (≈13 min) Bandwidth dominates. Latency irrelevant.

Example 3 — Cross-Region Replication

RTT: 150 ms Bandwidth: 10 Gbps Window: 64 KB (default) Throughput ≈ 64 KB ÷ 0.15 s = ~3.4 Mbps BDP = 10Gbps × 0.15 = 1.5 GB in-flight needed Window << BDP → underutilized. Fix: TCP Window Scaling.
OPTIMIZATION
Optimization Strategies

Reduce Latency

  • CDN / Edge computing
  • Local caches
  • Connection reuse (Keep-Alive)
  • HTTP/2, HTTP/3, gRPC
  • Fewer round trips
  • Async processing
  • Regional replicas

Increase Bandwidth

  • Upgrade network links
  • Compression (gzip/zstd)
  • Reduce payload size
  • Better routing
  • Dedicated links

Increase Throughput

  • TCP Window Scaling
  • Match window to BDP
  • Connection pooling
  • HTTP/2 multiplexing
  • QUIC / BBR congestion control
  • Reduce retransmissions
  • Batch operations

STAFF ENGINEER THINKING
Junior → Senior → Staff Progression
LevelThinking Pattern
Junior "Our API is slow. We need more bandwidth."
Senior "I'll profile the request. If the payload is small, it's latency — I'll add caching and keep-alive. If the payload is large, it's bandwidth — I'll add compression."
Staff "I first classify the bottleneck: for API calls (≤ 100 KB), it's almost always latency — I reduce round trips via HTTP/2, connection reuse, and edge caching. For bulk transfers (≥ 10 MB), I check bandwidth utilization and throughput. If utilization is high but throughput is low, I check packet loss and retransmissions. For cross-region replication, I compute BDP = bandwidth × RTT and verify TCP window ≥ BDP, tuning net.core.rmem_max and wmem_max accordingly. I always quantify with iperf3 and ss -ti before recommending changes, and validate improvements with P50/P95/P99 latency and throughput metrics."
Key Takeaways:
  • Latency = responsiveness (time to first byte); Bandwidth = capacity; Throughput = effective performance.
  • Bandwidth ≠ Throughput — packet loss, retransmissions, congestion, and protocol overhead prevent full link utilization.
  • BDP = Bandwidth × RTT — TCP window must be ≥ BDP to fully utilize a link. Critical for long-distance high-speed connections.
  • Identify whether workloads are latency-bound, bandwidth-bound, or throughput-bound before optimizing — and quantify with tools before and after.
  • In system design interviews, justify optimizations with measurable trade-offs, not generic "add a cache" advice.
