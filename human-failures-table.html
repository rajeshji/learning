Why Human Failures Are the Most Underestimated Failure Class

Studies show 70-80% of production outages have a human action as a contributing cause. Systems fail not because the software was wrong — but because a human made a decision. Human failures are uniquely dangerous because: 1. They bypass automated safeguards (humans with enough access can override anything) 2. They are hard to detect (no automated system raises "human did something wrong") 3. They are hardest to prevent (you cannot unit-test a person)

1 — Configuration Push Errors
Wrong Config Pushed to ProductionMust Know Engineer pushes wrong timeout, endpoint URL, or feature flag to production config Anomalous traffic behaviour immediately after config push; correlate with change log Rollback config to previous known-good version immediately Config-as-code with PR review, canary config rollout, schema validation in CI System-wide instability if config controls retry/timeout/routing for all services Config validation adds friction to emergency config changes under pressure
Wrong Environment TargetedMust Know Engineer runs command against production thinking they are in staging (kubectl, aws CLI) Unexpected production change in audit log; production behaving differently Revert change, restore from backup if data deleted Explicit environment confirmation prompt, colour-coded terminal (red=prod), separate credentials per env Production data deletion or misconfiguration with no warning Confirmation prompts slow legitimate emergency actions under incident pressure
Feature Flag Pushed Without Review Engineer enables feature flag directly without going through approval — unintended behaviour activated Unexpected feature visible to users, business metrics change unexpectedly Disable flag immediately Flag change review process, kill switch for every flag, two-person approval for prod flags User-facing behaviour change at scale — may trigger unexpected downstream business logic Mandatory review process slows time-to-ship for experimental features
Secrets Committed to Version Control Developer accidentally commits API key, DB password, or private key to public/private repo Secret scanner alert in CI, external party reports credential use Rotate all exposed credentials immediately, remove from git history Secret scanning in CI (Trufflehog/Gitleaks), pre-commit hook to block credential patterns Compromised credentials used for data exfiltration before rotation completes Secret scanners may produce false positives and block legitimate commits
2 — Data Deletion and Corruption Errors
Accidental Production Data DeletionMust Know Engineer runs DELETE without WHERE clause or drops wrong table in production Sudden data missing in application, user complaints, row count alerts Restore from most recent backup, apply point-in-time recovery Require WHERE clause enforcement, soft-delete over hard-delete, read-only prod access by default Data permanently lost if backup is stale or PITR window missed Soft-delete requires regular purge jobs and complicates queries
Wrong WHERE Clause Mass UpdateMust Know UPDATE statement with incorrect predicate updates millions of rows with wrong value Business metric anomaly, application errors from corrupted field values Roll back transaction if caught in time, restore from backup DRY-RUN mode for bulk updates (SELECT first, then UPDATE), row count confirmation before execute Corrupted data propagates through caches and downstream systems before detected Mandatory SELECT-before-UPDATE adds operational steps under time pressure
Backup Never Tested — Restore Fails During Incident Backup exists but restore procedure untested — during disaster, restore fails or takes 10x longer Discovered only during incident when restore is needed Switch to replica while investigating backup failure Regular restore drills, automated restore validation after every backup, backup SLO Extended outage — team discovers during the worst moment that backup is unusable Regular restore drills consume engineer time and test environment resources
Data Wipe During Cleanup Script Cleanup script written for staging accidentally run against production dataset Data missing in production, script execution in audit log Restore from backup, apply PITR to minimize data loss window Scripts require explicit environment flag (--env=prod), separate IAM roles per environment Irreversible data loss if cleanup deleted records with no recovery path Mandatory environment flags add friction but save from catastrophic mistakes
3 — Deployment and Release Human Errors
Deploy to Production Without Staging ValidationMust Know Engineer skips staging gate (time pressure, process bypassed) — untested code reaches production Production error rate spikes immediately after deploy Rollback deployment immediately Mandatory staging gate in CI/CD pipeline, staging bypass requires manager approval Production outage from untested code — no early warning from staging Hard staging gate slows emergency hotfix deployments under active incident
No Rollback Plan Before DeployMust Know Deploy proceeds without defining rollback steps — when deploy fails, team improvises under pressure Incident response slows, team spending time figuring out how to rollback mid-outage Document and execute rollback steps while trying different approaches simultaneously Rollback plan mandatory in deploy checklist, rollback tested in staging before prod deploy Extended outage — additional errors made during unplanned improvised rollback Mandatory rollback planning adds pre-deploy time for every change
Wrong Artifact Deployed CI system deploys a different build than was tested — different code in production than expected Version mismatch between expected and running binary Redeploy correct artifact, rollback to last known-good Artifact hash verification at deploy time, immutable artifact IDs in pipeline Untested code in production — security vulnerabilities or bugs not caught in review Hash verification adds a pipeline step and slows deployment
Runbook Step Skipped Under Pressure Engineer rushes through runbook during incident, skips a step — recovery incomplete or worsens situation System not recovering as expected after runbook execution Restart runbook from beginning, track which steps were executed Checklist-style runbooks (each step must be checked off), runbook automation where possible Incomplete recovery creates a second failure — situation worsens from intervention Mandatory step-by-step checklists slow response for experienced engineers who know the steps
4 — Capacity and Scaling Errors
No Load Test Before Major EventMust Know Product launch, sale, or viral event hits system that was never tested at expected load System degrades under event traffic, latency and errors spike Emergency scale-out, enable caching, activate CDN, shed non-critical load Load testing as mandatory pre-launch step, capacity planning for 2x expected peak Public-facing outage during high-visibility event — business and reputation impact Realistic load testing requires production-like environment and data volume
Wrong Autoscaling PolicyMust Know Autoscaling configured on wrong metric, wrong threshold, or wrong cooldown — scales too slow or not at all Service not scaling despite load; or scaling triggered by wrong metric during idle Manually scale, override autoscaling policy Test autoscaling policy in load test, monitor effective scale events, review policy quarterly Saturation — service fails to scale under legitimate load, causing outage Complex autoscaling policies are hard to test without production-like traffic
Database Not Scaled Before Application Scaled Application tier scaled out but DB connection pool limit not increased — DB refuses new connections DB connection exhaustion errors despite application looking healthy Scale DB connection pool, add connection pooler (PgBouncer), reduce app replicas temporarily Scale DB tier first, plan connection budget before scaling application replicas Application instances up but all failing — every request hits DB connection limit Connection poolers add a layer of operational complexity
Over-Provisioning That Creates False Confidence System always massively over-provisioned — engineers lose intuition for real capacity limits Discovered during cost review or when budget cuts force right-sizing that exposes limits Right-size gradually with load testing at each step Regular capacity review with load testing to understand actual limits Sudden exposure of real limits when cost-optimisation forced — system fails at much lower load than assumed Running close to capacity limit reduces safety margin for traffic spikes
5 — Incident Response Failures
No Incident Commander — Multiple People Taking ActionMust Know Multiple engineers make simultaneous changes during incident — changes conflict, situation worsens Conflicting actions visible in change log, system behaviour unpredictable Designate single incident commander, stop all other changes immediately Incident response training, clear IC role in on-call process, IR runbook includes "declare IC first" Simultaneous conflicting changes turn fixable incident into extended outage Single IC may be wrong — team members with better ideas cannot act quickly
Wrong Root Cause DiagnosisMust Know Team misidentifies root cause under pressure — fix applied to wrong component, real cause continues System not improving after "fix" applied, second symptom not explained by hypothesis Step back, gather more data, revisit hypothesis Hypothesis-driven debugging (list 3 possible causes before fixing), post-incident review Wasted time on wrong fix — real root cause continues spreading while team celebrates false progress Hypothesis discipline slows immediate action in obvious cases
Escalation Delay — Waiting Too Long to Call for Help On-call engineer struggles alone for too long before escalating — incident extends unnecessarily Incident duration much longer than expected for severity level Escalate immediately when stuck for more than 15 minutes without progress Clear escalation criteria in runbook, culture of early escalation without stigma Outage extends because expertise was available but not called in time Hair-trigger escalation creates alert fatigue for senior engineers
Communication Breakdown During Incident Status updates not shared, different teams take conflicting actions, customer not informed Teams working at cross-purposes, duplicate effort, customer complaints Open incident channel immediately, status updates every 15 minutes Incident communication template, dedicated incident Slack channel, status page Conflicting actions worsen incident; customer trust eroded by silence Mandatory status updates take engineer time away from fixing the problem
6 — Access Control and Permission Errors
Overprivileged Service AccountMust Know Service runs with admin-level permissions — if compromised, attacker has full access Security audit finding, or discovered after breach when blast radius assessed Immediately restrict permissions to minimum needed, rotate credentials Principle of least privilege, IAM review quarterly, infrastructure-as-code for all IAM Full system compromise if the overprivileged account is exploited Minimal permissions require more IAM management effort per service
Shared Credentials Between Environments Production and staging share same API key or DB password — staging breach affects production Discovered during security audit or after credential compromise Rotate all shared credentials immediately, assign unique per environment Unique credentials per environment enforced by IaC, credential rotation automation Staging compromise immediately exposes production Per-environment credential management increases secret management overhead
Expired Certificate Causing Outage TLS certificate expires without renewal — all HTTPS traffic fails SSL handshake failures, users see certificate error in browser Renew certificate immediately (Let's Encrypt auto-renew if configured) Certificate expiry monitoring with 30/14/7 day alerts, automated renewal (cert-manager) Complete service unavailability — no HTTPS traffic can succeed Auto-renewal adds complexity; failure of auto-renewal still causes outage
Rogue Admin Action Without Change Review Engineer with admin access makes undocumented production change — no peer review, no audit trail Unexplained production behaviour; change traced via audit log after the fact Revert undocumented change, review impact All production changes via reviewed PRs, break-glass access with mandatory post-hoc review Unknown production state — no one knows what the system should look like Mandatory review slows legitimate emergency changes during active incidents
7 — Monitoring and Alert Management Errors
Alert Silenced and Never UnsilencedMust Know Alert silenced during maintenance, team forgets to re-enable — real failure goes undetected Outage discovered by user report, not by alerting system Re-enable alert immediately, establish incident timeline from logs Alert silences must have mandatory TTL and owner, silences reviewed weekly Silent failure propagates for hours or days before manual discovery TTL on silences may re-trigger noisy alerts during still-ongoing maintenance
Alert Threshold Never Updated After Traffic Growth System traffic grows 10x — absolute-value alert thresholds become meaningless (too high or too low) Alerts fire constantly (too sensitive) or never fire for real issues (too lenient) Review and retune alert thresholds immediately SLO-based alerting (percentage-based burn rate, not absolute values), quarterly alert review Real incidents missed because threshold is now set too high for current scale SLO-based alerting requires careful SLO definition per service
Dashboard Shows Wrong Data — Team Makes Wrong Decision Metrics misconfigured — dashboard shows healthy when system is degraded User complaints despite dashboard showing green Validate metrics against raw data source, cross-check with logs Metrics correctness testing, synthetic canary to validate dashboard shows expected values Team does not respond to real outage because monitoring says everything is fine Metrics validation adds CI complexity; synthetic canaries add cost
No Alert for New Service / Feature New service shipped without adding alerts — failure goes undetected until users complain User report or manual dashboard check Add alerts immediately for the new service Observability checklist as deploy gate, alerting-as-code reviewed in same PR as service code Silent failure for new service — no automatic detection exists Alerting checklist as deploy gate slows shipping new services
8 — Change Management Failures
Change Made During Peak Traffic HoursMust Know Engineer deploys or modifies production during business peak — any failure hits maximum user count Failure immediately after peak-hour change, maximum user impact Rollback immediately, schedule future changes for off-peak Change freeze during peak hours, deploy windows enforced in CD pipeline Outage at maximum blast radius — every user affected, not a fraction Strict change windows delay urgent security patches and bug fixes
Cascading Change with No Blast Radius Assessment Change touches shared library, schema, or service depended on by many — blast radius unknown Multiple services fail simultaneously after single change Rollback change, assess all affected services Impact assessment required for all shared-dependency changes, dependency graph visibility Unexpected wide blast radius — change assumed low-risk affects 20 services Full blast radius assessment is time-consuming for large dependency graphs
Undocumented Manual Production Change Engineer makes production change outside of code review — drift between code and reality Behaviour inconsistent with code; discovered on next deploy when change is overwritten Document change immediately, codify in IaC Immutable infrastructure (no manual changes ever), all changes via reviewed pipeline Undetected configuration drift — system gradually diverges from documented state Immutable infrastructure requires more upfront IaC investment per change
Dependency Upgrade Without Testing Downstream Impact Library or platform version bumped — breaking change in dependency breaks consuming services Multiple service failures after dependency upgrade Rollback dependency version Consumer-driven contract testing, upgrade in staging first, canary rollout for dependency changes All consumers of the dependency fail simultaneously Canary rollout for dependency upgrades is complex to orchestrate across many consumers
9 — Knowledge and Documentation Failures
No Runbook — Incident Handled From MemoryMust Know Critical service has no runbook — on-call engineer handles incident from personal memory Slow incident response, inconsistent steps taken, institutional knowledge required Document steps as you execute them during the incident Runbook required before any service goes to production, runbook tested in game days Extended outage when primary expert is unavailable — knowledge locked in one person Runbook maintenance takes ongoing engineering time as systems change
Stale Runbook Leading to Wrong ActionMust Know Runbook not updated after system changes — engineer follows outdated steps, makes situation worse Actions described in runbook fail or produce unexpected results Stop following runbook, improvise from first principles while updating runbook Runbook review as part of change review for any infrastructure modification, runbook ownership Wrong action from stale runbook converts fixable incident into extended outage Mandatory runbook updates add engineering overhead to every infrastructure change
Bus Factor — Single Engineer Knows Critical System Only one person understands a critical system — when they are unavailable, incidents cannot be resolved Incident cannot be resolved without the specific engineer; on-call escalation chain exhausted Emergency contact the expert; accept longer MTTR Knowledge sharing sessions, pair on-call rotation, architecture documentation, bus factor reviews Critical system becomes unrecoverable during incident without the key expert Mandatory knowledge sharing takes time from feature development
Post-Incident Action Items Never Closed Post-mortem identifies root cause and fixes — action items tracked but never completed Same failure recurs; post-mortem from previous incident has identical root cause Escalate overdue action items, prioritise preventive work Action items tracked in engineering backlog with owner and deadline, reviewed in sprint Repeated preventable outages — same issue recurs because fix was never shipped Prioritising post-incident work competes with feature development for team capacity

Staff-Level Thinking — 9 Questions to Ask About Your Operational Posture

1. Can one person delete production data? → read-only default + two-person confirm 2. Is every runbook current and tested? → change review includes runbook update 3. Who handles incidents when expert gone? → bus factor check + documented procedures 4. Is prod access separated from staging? → separate creds + colour-coded terminals 5. Can we rollback any change in 5 min? → tested rollback plan before every deploy 6. Are alerts real and actionable? → SLO-based burn rate + quarterly review 7. Are post-incident actions being closed? → tracked in sprint + owner + deadline 8. Was the system load-tested for peak? → load test as mandatory pre-launch gate 9. Is change blast radius understood? → dependency graph + impact assessment

Final Mental Model — Human Failures Reduce to 3 Root Causes

1. Wrong knowledge → did not know the correct action (stale runbook / no docs / bus factor) 2. Wrong context → knew the action but applied to wrong target (wrong env / wrong WHERE) 3. Wrong process → correct knowledge + context but process failed to catch it (no review / no gate) Prevention maps directly: Wrong knowledge → documentation + runbooks + knowledge sharing Wrong context → confirmation prompts + separate environments + colour coding Wrong process → peer review + automated gates + change management The most dangerous human failure: one person with production access, no documentation, no peer review, no audit trail -> no detection + no recovery + no prevention
