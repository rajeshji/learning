1 — Replication Availability Failures
Primary Replica FailureMust Know Leader crash, hardware failure, OOM on primary node Heartbeat failure, write requests all failing Promote follower replica to new primary Multiple replicas in ISR, automated failover (Patroni/Sentinel) Temporary write unavailability — all writes stall until failover completes Automated failover adds coordination complexity and risk of split brain
Follower Replica Failure Replica node crash or network partition from primary Missing replica in replication topology, replica lag stops updating Remove from read pool, rebuild replica from primary Replica redundancy (RF >= 3), replica health monitoring Reduced read capacity — primary absorbs all reads if only replica fails More replicas cost more; rebuilding large replicas adds primary IO load
All Replicas UnavailableMust Know AZ/DC-wide outage — all replica nodes lose power or network Quorum lost, entire cluster write-unavailable Disaster recovery failover to secondary region Multi-region replication, replicas in at least 3 AZs Complete data unavailability — service fully down, no reads or writes Multi-region replication adds cross-region latency and significant cost
Replica Startup Failure Corrupted WAL/snapshot prevents replica from starting Replica restart loop, failed recovery error in logs Restore from clean snapshot, rebuild from primary Checksum validation on WAL, snapshot integrity checks Reduced replica redundancy — increased message loss risk during recovery Longer rebuild time from primary adds IO load on the healthy primary
Replication Service Crash Replication daemon/process crashes — replication silently stops Replica lag stops advancing, replication stopped alert fires Restart replication process, validate replica is caught up after restart HA replication service, watchdog monitoring for replication thread Replica drifts silently — divergence grows until detected and fixed More operational overhead to monitor replication liveness
2 — Replication Lag and Slow Replication Failures
Replication LagMust Know Slow network, slow disk on replica, or heavy write burst from primary Seconds-behind-primary metric, replica offset lag alert Route critical reads to primary, set bounded staleness window Tune replication pipeline, sync replication on critical paths Stale reads system-wide — wrong business decisions made on old data Synchronous replication significantly increases write latency
Cross-Region Replication LagMust Know WAN latency between regions — async replication takes seconds or more Region replication lag metrics, cross-region offset delta Route reads to local region, accept bounded staleness Geo-partitioning — own region data locally, sync only what crosses regions Global stale data — users in remote region see old state Geo-partitioning requires careful data placement and routing logic
Slow Replica Catch-Up Replica restarts or rebuilds — large WAL to replay before it's useful Recovery lag metrics, replica still behind after long time Incremental sync from recent snapshot, not full WAL replay Frequent snapshots to reduce WAL replay length Long window of reduced redundancy — primary exposed if it fails during rebuild More frequent snapshots add storage cost and IO overhead
Async Replication Delay Heavy write traffic overwhelms async replication pipeline Replication queue depth growing, lag increasing under write burst Throttle write rate, increase replication throughput Better batching, increase replication parallelism, tune buffer sizes Replica inconsistency grows — reads from replica return increasingly stale data Sync replication avoids lag but directly hurts write throughput
3 — Replica Divergence and Inconsistency Failures
Replica DivergenceMust Know Missed or reordered replication events — replica has different state from primary Checksum mismatch between primary and replica data Re-sync replica from primary using full or incremental repair Quorum replication, synchronous ack before commit on critical data Different users on different replicas see different truth simultaneously More replication coordination increases write latency and network load
Stale Replica ReadsMust Know Read routed to lagging replica — returns outdated value Version mismatch, user sees old data after their own write Read-your-writes routing — route to primary after write Session consistency, quorum reads on critical paths Incorrect business decisions applied — user acts on wrong balance/inventory Always reading from primary removes read scalability benefit of replicas
Partial Replication Replication stream interrupted — replica has only part of the data range Missing data ranges detected in reconciliation job Replay missing WAL segments from primary or log Reliable WAL shipping, checksums on replication stream segments Incomplete state propagation — downstream services process incomplete data Checksums add validation overhead per replicated segment
Write Conflict Across Replicas Multi-primary concurrent writes to same key — both accepted, both different Conflict detection in write log, version vector mismatch Conflict resolution/merge (LWW, CRDT, manual reconciliation) Single-writer ownership per key, avoid multi-primary for same data Corrupted shared state — one of the conflicting writes silently wins or merges badly Single-writer reduces write availability; CRDT adds data structure complexity
4 — Quorum and Consensus Failures
Quorum LossMust Know Too many replicas unavailable — majority of nodes unreachable Quorum alerts, all writes failing with quorum error Switch to read-only mode, restore nodes to regain quorum Multi-AZ replica placement, RF >= 3 with majority quorum (n/2+1) Write unavailability — entire cluster becomes read-only until quorum restored Larger quorum requirement reduces availability during partial failures
Leader Election FailureMust Know Network partition or coordinator instability — no leader can be elected No leader detected, all writes to cluster fail Trigger re-election, restore network connectivity Stable quorum design, randomised election timeouts (Raft) Replication halts — no leader means no writes accepted anywhere Faster election timeout risks false elections on transient network issues
Stale LeaderMust Know Old leader isolated by partition still accepts writes — unaware it's dethroned Term/epoch mismatch between old leader writes and new leader writes Fence stale leader using fencing tokens — new leader rejects old leader's writes Consensus protocol (Raft term validation), monotonic fencing tokens Conflicting writes accepted by both old and new leader — data corruption Fencing coordination adds overhead per write on the critical path
Consensus Failure Network partition or high latency prevents consensus round from completing Election timeout, write stalls with no progress Retry election round, reduce network latency between quorum nodes Co-locate quorum nodes in low-latency network, optimise log payload size Write stalls — all writes queue up waiting for consensus that never completes Lower quorum node count reduces latency but weakens durability guarantees
5 — Split Brain and Multi-Primary Failures
Split Brain ReplicationMust Know Network partition splits cluster — both halves elect their own leader Multiple active primaries, conflicting writes in WAL on both sides Fence minority partition — refuse writes on the smaller side Strong quorum: majority must agree before any leader election succeeds Massive data conflicts on partition heal — both sides have incompatible history Fencing minority reduces availability — minority side loses writes during partition
Dual Write Conflict Multi-primary setup — two primaries accept writes to same key concurrently Write conflict logs, version vector divergence Conflict reconciliation using LWW (Last Write Wins) or CRDT merge CRDT data structures, single-writer ownership per partition key Corrupted business state — wrong value wins silently, other write lost LWW can silently discard valid writes; CRDT restricts data structure choices
Partition Healing Conflict Cluster reconnects after split brain — both sides have diverging histories Diverging version vectors detected during reconciliation Reconcile state using conflict resolution rules, audit and fix manually Strong consistency to avoid split in first place, clear ownership rules Long-term inconsistency during reconciliation — data in flux for hours Strong consistency prevents split but reduces availability during partition
Stale Leader Writes During Failover Old primary not fenced immediately — accepts writes while new primary is elected Simultaneous writes from two nodes detected in log Fencing tokens — new leader has higher epoch, old leader's writes rejected Reliable failover orchestration with mandatory fencing before promotion Silent data corruption — old primary writes overwrite or conflict with new leader Mandatory fencing adds delay to failover path — increases MTTR
6 — Replication Ordering and Delivery Failures
Out-of-Order ReplicationMust Know Parallel replication threads or network reordering delivers events out of sequence Sequence number mismatch on replica, invalid state after apply Replay replication log in strict order, buffer and reorder before apply Ordered WAL shipping, per-key sequencing in replication pipeline Invalid replica state — subsequent reads return logically impossible data Strict ordering reduces replication parallelism and throughput
Missing Replication Events Packet loss or crash drops events from replication stream Sequence gaps detected in replica log, checksum mismatch Replay WAL/binlog from the last confirmed position Durable replication log, checksums per segment, ack before discard Data inconsistency — replica missing writes, returns wrong data for affected keys Durable logs with per-segment acks add storage and latency overhead
Duplicate Replication Events Retry after uncertain ack — same event written to replica twice Duplicate operations in replica log, duplicate-key errors Idempotent replay — apply only if not already applied (check sequence ID) Deduplication logic using sequence IDs, exactly-once replication Double writes on replica — corrupted counters, double-charged payments Deduplication adds per-event overhead and a dedup state store
Corrupted Replication Stream Disk or network corruption introduces bad data into replication stream Checksum mismatch on replica log segment Re-fetch clean stream from primary, rebuild replica if severe Stream checksums per segment, network integrity checks (TLS in transit) Replica rebuild required — temporary reduction in replication redundancy Checksum validation per segment adds minor read/write overhead
7 — Replication Overload and Scaling Failures
Replication StormMust Know Large-scale re-sync after outage — all replicas rebuilding simultaneously Network/disk IO spike across cluster during recovery Throttle replication bandwidth, stagger replica recovery Controlled repair scheduling, repair priority queues, rate limiting on rebuild Cluster overload — live traffic degrades because replication consumes all IO Throttling extends recovery window — longer reduced-redundancy exposure
Replica Rebuild Overload Full re-sync after failure saturates primary's IO and network Primary IO/network spike during replica rebuild Incremental rebuild from snapshot, throttle rebuild bandwidth Better snapshot strategy — frequent snapshots reduce rebuild data volume Healthy primary slows down for live writes — all clients see latency increase Throttling rebuild slows recovery; snapshots cost storage
Hot Replica Uneven read distribution — all reads routed to one replica One replica at 100% CPU/IO while others are idle Rebalance read routing across replicas Round-robin or load-aware read routing, connection pool balancing Hot replica overloads and crashes — falls behind or fails entirely Load-aware routing adds coordination overhead per read request
Cross-Region Sync Overload Massive geo-replication — WAN link saturated by replication traffic WAN saturation, cross-region lag growing despite best effort Compress replication stream, batch updates before sending cross-region Geo-aware replication design, dedicate WAN bandwidth for replication Regional lag explodes — remote region data grows increasingly stale Compression adds CPU overhead; batching increases replication latency
8 — Persistence and Recovery Failures
WAL CorruptionMust Know Disk crash or software bug corrupts the write-ahead log Recovery failure on startup, WAL checksum error Restore from last clean backup, rebuild from a healthy replica WAL checksums, ECC storage, replica as WAL backup Replica unrecoverable — must rebuild from scratch, long window of reduced redundancy WAL checksum validation adds minor overhead per write operation
Snapshot Corruption Snapshot interrupted or storage error — backup file is invalid Snapshot checksum failure on restore attempt Restore from previous valid snapshot, rebuild from primary Snapshot validation on write, multiple snapshot generations retained Slow rebuild from primary — extended window where replica count is reduced Multiple snapshot generations cost significantly more storage
Replica Restore Failure Backup is inconsistent or incompatible version — restore fails or produces wrong data Restore mismatch, data integrity check fails after restore Full rebuild from primary, use alternate backup Backup testing — regular restore rehearsals with integrity validation Reduced replica redundancy — primary exposed if it fails during recovery Restore rehearsals add cost and operational complexity
Slow Replica Recovery Huge WAL to replay after crash — replica takes too long to catch up Long startup/recovery time, replica still behind after expected window Restore from recent snapshot to reduce WAL replay volume Incremental checkpoints, frequent snapshots, SSD storage for faster replay Extended degraded mode — insufficient replicas for quorum during slow recovery More checkpoints add IO overhead during normal operation
9 — Geo-Replication and Multi-Region Failures
Cross-Region PartitionMust Know WAN failure between regions — cross-region replication stream broken Region sync failure alert, cross-region lag climbing indefinitely Local region isolation — each region serves its own data independently Multi-path WAN networking, replicate across at least 3 regions Global inconsistency — regions diverge independently during partition Multi-region replication adds cost, latency, and conflict resolution complexity
Geo-Replication Delay High WAN latency — async replication to remote region takes seconds to minutes Cross-region replication lag metrics, stale read reports from remote users Route reads to local region, inform users of bounded staleness Geo-partitioning — regions own their data locally, minimal cross-region sync Stale global reads — decisions in remote region made on old primary-region data Geo-partitioning requires careful schema and routing design
Region Failover Conflict Multiple active regions — failover makes two regions both act as primary Conflict detection during cross-region reconciliation Region fencing — designate one region as authoritative Single-writer region per data domain, clear failover ownership rules Diverging global state — two regions independently update shared data Single-writer region reduces write locality for users in other regions
Global Metadata Inconsistency Region config/schema drifts — different regions have different routing or schema Config mismatch between regions, routing errors for cross-region requests Metadata reconciliation from authoritative source region Global consensus-backed metadata, GitOps config propagation Incorrect routing — requests land in wrong region or fail with schema error Global consensus for metadata adds coordination latency per config change

Staff-Level Replication Thinking — 9 Questions to Ask Always

1. Replicas diverge? → quorum writes + read repair + checksums 2. Lag affect correctness? → sync on critical paths + bounded staleness 3. Split brain possible? → majority quorum + fencing + consensus protocol 4. Failover corrupt data? → fencing tokens + epoch validation + drain 5. Rebuild overload cluster? → throttle + stagger + incremental from snapshot 6. Ordering break? → ordered WAL + per-key sequencing 7. Geo lag increase risk? → geo-partition + local reads + multi-path WAN 8. Quorum strong enough? → n/2+1 majority + multi-AZ placement 9. Sync or async? → async=fast+stale | sync=slow+consistent

Sync vs Async Replication — The Core Trade-off

Async replication: low latency + high throughput | stale reads + data loss on crash Sync replication: strong consistency + no data loss | high write latency + availability risk Where to use sync: financial transactions | inventory updates | auth state | primary elections Where to use async: analytics pipelines | search indexes | read replicas | geo-mirrors | audit logs Hybrid (best of both): sync to quorum (min 2 replicas) → ack write async to remaining replicas → improve durability without full sync penalty

Final Mental Model — All Replication Failures Reduce to 5 States

1. Replicas unavailable → crash / AZ outage / quorum loss 2. Replicas lagging → slow network / heavy write burst / async delay 3. Replicas diverging → missed events / out-of-order / partial replication 4. Multiple leaders → split brain / dual write / stale leader 5. Recovery failed → WAL corruption / bad snapshot / slow rebuild Most dangerous combo: split brain + replica divergence multiple truths created → silent corruption → extremely difficult reconciliation
