1 — API Availability and Request Handling Failures
API Server CrashMust Know Runtime bug, OOM kill, or unhandled exception crashes the API process Health check failures, all 5xx, zero successful requests Restart/failover to healthy replica HA replicas, graceful degradation, watchdog supervision Complete request outage — all clients see connection refused or 503 HA replicas add infra cost; watchdog supervision adds operational complexity
Thread Pool ExhaustionMust Know Blocking IO or slow dependency holds all threads — no thread available for new requests Request queue growing, thread pool saturation metric, timeouts increasing Async/non-blocking IO, reject new requests with 503 Non-blocking IO (Netty/reactive), aggressive downstream timeouts, bulkheads Timeout cascade — every API request times out when thread pool is full Async programming is significantly more complex to develop and debug
Connection Pool Exhaustion Too many concurrent downstream calls — connection pool to DB/service runs out Connection pool saturation metric, downstream timeouts growing Increase pool size carefully, circuit-break overloaded downstream Connection reuse, bounded pool with explicit overflow handling Dependency overload — every API call queues waiting for a connection slot Larger pool consumes more memory; too large causes downstream overload
Request Timeout ExplosionMust Know Slow upstream dependencies cascade — every API request exceeds timeout P95/P99 latency spike, timeout error rate rising Fail fast with circuit breaker, return cached/degraded response Per-dependency timeout configuration, shorter timeouts than client expects Retry storm — timed-out clients retry → amplifies load on already-slow backend Tight timeouts may fail valid slow-but-correct operations
Process Deadlock Lock or thread contention — threads mutually wait and make no forward progress All requests hang, CPU low but no throughput, thread dump shows blocked threads Restart service to clear deadlock Lock-free design, global lock ordering, timeout on every lock acquisition Complete API stall — service alive but processing zero requests Lock-free design requires more complex data structures
2 — Input Validation and Parsing Failures
Invalid Request ParsingMust Know Malformed JSON, invalid protobuf, or truncated body received Parse error spike, 400 Bad Request rate increasing Reject with descriptive 400, do not crash on parse error Schema validation at ingress, strict parser with max depth limits Increased error traffic — malformed requests trigger retries, amplifying load Strict parsing rejects valid edge cases; lenient parsing risks security issues
Large Payload AttackMust Know Attacker or misconfigured client sends oversized request body Memory or network spike, OOM kills, latency spike on ingest Reject immediately with 413 at ingress, enforce payload size limits Hard payload size limits (e.g. 10MB max), reject at gateway before parsing OOM kills API servers if body is buffered before size check Payload limits break legitimate large upload use cases
Schema Validation Failure Required field missing, type wrong, or constraint violated in request body Validation error metric spike, 400 errors from schema checks Return descriptive validation error with field-level detail API schema enforcement (JSON Schema/OpenAPI), client SDK validation Client failures at scale if schema changed without consumer notification Strict schema enforcement rejects requests that might be handleable with defaults
Encoding / Unicode Failure Invalid UTF-8 or mixed encoding in request payload or headers Decode exceptions, garbled data in DB, character validation errors Normalize encoding at ingress, reject invalid sequences UTF-8 validation before processing, sanitise input encoding Corrupted data persisted to DB if invalid bytes pass through unchecked Strict encoding validation adds processing overhead per request
3 — Serialization and Deserialization Failures
Serialization FailureMust Know Response object contains unsupported type (circular reference, non-serializable field) Response serialization error spike, 500 errors on specific endpoints Return safe fallback error response, add error boundary around serialization DTO separation — never expose internal domain objects directly in response API endpoint completely broken — every request to that endpoint fails DTO pattern adds boilerplate and mapping code for every response type
Deserialization FailureMust Know Producer schema changed — consumer cannot deserialize new format Decode exceptions in consumer, 500 errors on received messages Apply version fallback, use schema registry to detect mismatch early Backward-compatible schema changes, Avro/Protobuf with schema registry Consumer incompatibility — entire message pipeline stops if deserialization fails Schema registry adds operational infrastructure and process overhead
Payload Size Explosion Deeply nested or large collection in response — network and memory overwhelmed Response latency spike, memory growth on API server, client timeouts Apply pagination, response field filtering (sparse fieldsets) Enforce response size limits, pagination on all list endpoints, gzip compression Gateway/network overload — large responses queue and slow all concurrent requests Pagination requires client to implement multi-page traversal logic
Binary Protocol Corruption gRPC/Protobuf message corrupted in transit — receiver gets garbled bytes Decode mismatch error, protobuf parse exception in consumer Retry request (corruption usually transient on network) End-to-end checksums, TLS to prevent in-transit corruption Service communication failure for that RPC — affects all callers of the endpoint Checksums add per-message compute overhead
4 — Timeout, Retry, and Idempotency Failures
Retry StormMust Know Clients retry aggressively on failure — amplifying load on already-struggling backend Retry traffic spike in backend metrics, backend receiving N×normal load Exponential backoff + jitter immediately, circuit breaker to stop retrying Retry budgets, retry-after header, exponential backoff with jitter in client Backend collapse — retry amplification turns partial outage into full outage Exponential backoff increases latency for legitimate retry-able failures
Duplicate Request ExecutionMust Know Client retries after uncertain success — request processed twice (payment, order) Duplicate operations detected in audit log, double charges, duplicate records Detect and deduplicate by idempotency key, return cached first result Idempotency keys on all mutating endpoints, request deduplication store Double business operations — payments charged twice, inventory decremented twice Idempotency key store adds storage overhead and TTL management complexity
Timeout MisconfigurationMust Know Timeout too short causes false failures; too long causes resource starvation Premature 504 errors (too short) or threads held forever (too long) Tune timeout to dependency's P99 latency + headroom Dependency-aware timeout configuration, separate timeout per dependency Resource exhaustion (too long) or unnecessary failures (too short) Per-dependency timeouts add configuration complexity
Partial Request Completion Multi-step workflow interrupted mid-flight — some steps done, others not Inconsistent state detected, workflow stuck in partial state Saga compensation — run compensating actions to undo completed steps Saga/outbox pattern, idempotent compensating actions Corrupted workflows — partial state causes downstream failures or incorrect data Saga pattern complexity grows with number of steps in the workflow
5 — API Contract and Versioning Failures
Breaking API ChangeMust Know Request/response schema changed without backward compatibility — clients break Client error spike after deployment, deserialization/missing field errors Rollback, serve old schema from new version as compatibility shim Backward-compatible schema changes only, consumer-driven contract testing All consumers of the API break simultaneously Backward compatibility slows API evolution and accumulates tech debt
Version DriftMust Know Different services in the same system use different API contract versions Serialization mismatch between services, intermittent cross-service errors Deploy to central schema registry, force version alignment Contract governance, schema registry (Confluent/AWS Glue) Cross-service communication failures wherever incompatible versions interact Schema registry adds infra and process overhead per team
Field Removal Failure Existing field removed from response — old clients depend on that field Null pointer exceptions or missing field errors in old client code Reintroduce removed field, serve null/default value temporarily Deprecation lifecycle — mark deprecated, wait for all consumers to update, then remove Mobile/web app failures at scale — old app versions crash or behave incorrectly Long deprecation lifecycle means maintaining old fields for months or years
gRPC Proto Incompatibility Proto file changed without following evolution rules — receiver cannot decode message RPC decode errors, "unknown field" warnings escalating to parse failures Multi-version proto support, rollback to compatible proto version Follow proto evolution rules (never reuse field numbers, only add/deprecate) Service-to-service communication failure for all callers using incompatible proto Proto evolution rules constrain schema design flexibility
6 — Dependency Orchestration Failures
Slow Dependency AmplificationMust Know One slow downstream service causes API thread to block — affects all requests API P99 latency spike, correlated with slow downstream in dependency metrics Fail fast with circuit breaker, return cached/partial response Per-dependency timeout isolation, bulkhead pattern (separate thread pool per dep) Entire endpoint slowdown — thread pool fills waiting for slow dependency Bulkhead pattern requires separate thread/connection pool per dependency
N+1 Dependency CallsMust Know API makes one downstream call per item in list — fanout multiplies with list size Downstream QPS much higher than API request rate, latency grows with list size Batch downstream calls, parallelize with bounded concurrency DataLoader pattern, batched RPC calls, precomputed aggregates Backend overload — N×downstream calls for each API request Batching adds complexity; DataLoader requires framework integration
Partial Aggregation FailureMust Know One dependency fails mid-aggregation — API has partial data from multiple backends Partial API failures, some fields null/missing in response Return degraded response with successful parts, mark failed section absent Resilient aggregation — each dependency has independent fallback/timeout Entire endpoint fails if aggregation not resilient to partial backend failure Partial responses may confuse clients expecting complete responses
Cyclic Service Dependency Service A calls B which calls A — request enters infinite loop or mutual deadlock Request timeout after full cycle, recursive call depth exceeded Break dependency cycle, add circuit breaker to detect loops Clear architectural boundaries, dependency graphs must be acyclic Resource exhaustion — recursive calls consume threads/connections until crash Strict architectural boundaries limit flexibility in service communication patterns
7 — Concurrency and State Management Failures
Race ConditionMust Know Concurrent API requests update same resource — interleaved reads/writes cause corruption Inconsistent state detected, data appears randomly wrong under load Optimistic locking — retry on version conflict Idempotent APIs, optimistic concurrency control (version field), compare-and-swap Data corruption — concurrent updates partially applied, creating invalid state Optimistic locking requires retry logic; pessimistic locking reduces concurrency
Shared Mutable State Corruption In-process shared state accessed concurrently — data races cause non-deterministic bugs Random inconsistent behaviour under load, different results for same input Stateless API design, move shared state to external store Immutable request/response objects, share nothing architecture Hard-to-debug failures — non-deterministic, only appears under concurrent load External shared state adds network round-trip and latency per request
Session State LossMust Know API restart or cache eviction — in-process session state lost for active users Users logged out unexpectedly, session-dependent workflows reset Replicate session to external store, re-authenticate user Distributed session store (Redis), JWT (stateless auth) UX degradation at scale — all active users lose session simultaneously on restart Distributed session adds latency; JWT requires careful token revocation design
Sticky Session Imbalance Heavy session users pinned to same node — that node overloads, others idle Uneven load across API replicas, hot node at 100% with others at 10% Migrate sessions to external store, remove stickiness Stateless APIs with external session store (removes need for stickiness) Hot node collapse — overloaded node fails, its session users lose state External session store adds infrastructure cost and round-trip latency
8 — Security and Abuse Failures
Authentication BypassMust Know Validation bug, JWT alg:none exploit, or misconfigured route skips auth check Unauthorized access patterns, requests succeeding without valid token Emergency patch, add auth check to bypassed route Centralised auth middleware applied to ALL routes, deny-by-default Data breach — attacker accesses arbitrary resources without authentication Centralised auth adds latency overhead to every request
Rate Limit Failure (Open)Must Know Rate limiter unavailable or bypassed — unlimited traffic reaches backends Traffic anomalies, rate limiter health check failing Emergency throttling at API layer, local fallback rate limit HA rate limiter (Redis Sentinel), local fallback limiter as defence-in-depth Backend overload — unlimited requests hammer database and downstream services Local fallback limiter cannot enforce global fairness across replicas
API Abuse / Bot AttackMust Know Automated bots make high-volume requests — scraping, credential stuffing, data mining Traffic spike from small number of IPs, high request rate per client Rate limit, block offending IPs/clients, apply CAPTCHA Bot detection (device fingerprinting, CAPTCHA), API quotas per client Resource exhaustion — legitimate users starved while bots consume all capacity Bot detection adds friction and may block legitimate automated clients
Sensitive Data Exposure in ResponseMust Know Internal fields (PII, tokens, hashes) accidentally included in API response DLP alert, security scan finding PII in response body Redact response immediately, rotate exposed credentials Response field filtering layer, allow-list response fields (not block-list) Compliance breach — GDPR/CCPA violation, customer data exposed to all callers Allow-list response filtering requires explicit field definition for every response
Injection via API Input Unsanitised input passed to DB/shell/template — attacker executes arbitrary code Suspicious query patterns, WAF alert, unexpected system behaviour Block request at WAF, patch vulnerable endpoint Parameterised queries, input sanitisation, never concatenate input to queries DB/system compromise — SQL injection can expose or destroy entire database Strict input sanitisation may reject valid inputs containing special characters
9 — Observability and Debugging Failures
Missing Request TracingMust Know Trace context not propagated — distributed request cannot be reconstructed Broken trace chains, orphan spans, impossible to follow request path Generate fallback trace ID at entry point, patch propagation OpenTelemetry standardised propagation, trace ID in all log statements Hard debugging — post-incident analysis cannot determine root cause service Trace propagation requires changes in every service and adds per-request overhead
Silent Partial Failure (HTTP 200 with Error)Must Know API returns HTTP 200 but includes error payload or partial data — client sees "success" Business metric anomaly, client-side parsing reveals hidden error in body Add semantic monitoring that checks response body, not just status code Correct HTTP status codes for all error conditions, error schema standardisation Hidden outages — alerting shows 0% errors while actual error rate is high Strict HTTP status usage requires client error handling for all 4xx/5xx codes
High Cardinality Metrics Explosion Per-user or per-request ID labels on metrics — TSDB explodes in memory Prometheus memory growing, query latency spike, monitoring OOM Drop high-cardinality labels, apply recording rules for aggregation Cardinality governance — no user IDs, request IDs as metric labels Monitoring crash — Prometheus OOM kills observability during an active incident Low cardinality metrics reduce per-request debugging granularity
10 — Multi-Region and Distributed API Failures
Cross-Region API Version DriftMust Know Different API versions deployed across regions — same request behaves differently Inconsistent response behaviour for same user hitting different regions Sync API versions, route user to consistent region during rollout Global deployment orchestration, session affinity during multi-region rollout Regional incompatibility — cross-region service calls fail between versions Synchronised global deployment is slower than region-by-region rollout
Cross-Region Consistency Failure Write committed in primary region but not yet replicated — secondary serves stale data Read-after-write inconsistency, users see old value after successful write Route reads to primary for consistency-sensitive operations Session consistency, read-your-writes guarantee, monotonic reads User confusion — write appears successful but subsequent read shows old value Reading from primary for all operations removes read scalability benefit of replicas
Failover Replay Duplication Request replayed after failover — originally processed but assumed failed Duplicate operations in audit log, double payments or duplicate records Detect duplicates using idempotency key at receiving service Exactly-once or at-least-once with idempotency, request deduplication store Duplicate business actions — payments, orders, inventory changes applied twice Deduplication store adds storage and lookup overhead per request
Geo-Routing Sending to Wrong API Version Geo-routing directs users to a region with an older or broken API version Latency spike or error rate spike for users in specific geographic region Override geo-routing, redirect affected region to healthy API version API version health checks in geo-routing decision, traffic weighted by version health Regional API outage — all users routed to that region experience failures Version-aware geo-routing adds significant routing complexity

Staff-Level API Thinking — 9 Questions to Ask Always

Contracts evolve safely? → backward-compat + contract testing + deprecation lifecycle 4. Thread pools exhaust? → non-blocking IO + aggressive timeout + reject-on-full 5. APIs idempotent? → idempotency key on every mutating endpoint 6. Partial workflows corrupt? → saga + compensating actions + outbox pattern 7. Abuse overloads backends? → rate limit at multiple layers + bot detection + quotas

Final Mental Model — All API Failures Reduce to 5 States

1. Not processed → crash / thread exhaustion / timeout / queue overflow 2. Wrong result → validation fail / serialization bug / contract mismatch 3. Too many times → duplicate execution / retry storm / replay duplication 4. Too slow → dependency amplification / N+1 / blocking IO 5. Insecure → auth bypass / injection / data exposure / rate limit bypass Most dangerous: retry amplification + duplicate execution retries → overload → more retries → collapse + double business ops
