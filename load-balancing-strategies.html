Load Balancing Strategies

Round Robin · Least Connections · Consistent Hashing — choosing the right algorithm

The Big Picture

Load balancing is not simply about spreading requests — it is about maximizing throughput, minimizing P99 latency, preventing hotspots, improving availability, and supporting autoscaling. Choosing the wrong algorithm can overload healthy servers, increase tail latency, or reduce cache efficiency.

Client Requests ↓ Load Balancer ↓ Which server? ├── Round Robin → Next server in rotation ├── Least Connections → Server with fewest active connections └── Consistent Hashing → Server determined by hash of request key
Round Robin Weighted RR Least Connections Consistent Hashing Virtual Nodes Hash Ring Hot Keys Session Affinity

1 — Round Robin (RR)

Requests assigned sequentially. Every backend receives approximately the same number of requests.

Basic Round Robin

Request 1 → Server A Request 2 → Server B Request 3 → Server C Request 4 → Server A Request 5 → Server B ...

Weighted Round Robin

Server A weight=3 Server B weight=2 Server C weight=1 Traffic: A A A B B C A A A B B C → Larger servers get more traffic

✅ Advantages

Extremely simple · O(1) scheduling · Very low CPU · Stateless · Easy to scale

❌ Disadvantages

Ignores backend load · No session affinity · Poor when request cost varies

Best for: stateless REST APIs, static websites, CDN edge servers, homogeneous backend pools where requests are roughly equal in cost.

2 — Least Connections (LC)

Send to the server with the fewest active connections. Adapts to variable request durations.

Current Active Connections: Server A = 50 Server B = 18 ← WINNER Server C = 27 → Next request → Server B WHY: A long-running request on Server A counts as still active even if it's nearly done. LC adapts to this reality.
Weighted Least Connections: Effective Load = Active Connections / Server Capacity → Larger machines receive proportionally more traffic

✅ Advantages

Adapts to workload · Better tail latency · Reduces overloaded servers · Good for variable durations

❌ Disadvantages

Requires real-time metrics · More scheduling overhead · Idle long connections distort count

Best for: API gateways, gRPC services, HTTP/2 workloads, microservices, reverse proxies, anywhere request duration varies significantly.

3 — Consistent Hashing

Map requests to servers using a hash of the request key. Same key always goes to same server.

Hash Ring

Ring: 0 ──────────────── 2^32 Server A at position 100 Server B at position 200 Server C at position 350 Request key hash = 150 → Route to Server B (next clockwise)

When Server Added/Removed

Normal hashing: Add 1 server → almost every key moves! Consistent hashing: Add 1 server → only ~1/N keys move Remove 1 server → only affected keys remapped → Minimal cache invalidation
Virtual Nodes (for even distribution): Instead of: A, B, C (3 points on ring) Use: A1, A2, A3, B1, B2, B3, C1, C2, C3 → Much better distribution even with few servers

✅ Advantages

Stable key-to-server mapping · Minimal key movement · Natural session affinity · Cache locality

❌ Disadvantages

Ignores current load · Hot keys overload one server · More complex implementation

Best for: Redis Cluster, Memcached, Cassandra, Kafka partitioning, CDN cache routing, sticky sessions, distributed caches.

Node Failure Behavior

Round Robin

Remove from rotation. Continue cycling remaining servers.

Least Connections

Connections redistributed across remaining servers. Adaptive balancing continues.

Consistent Hashing

Only affected keys remapped to next server on ring. Minimal disruption to other keys.

Staff Engineer Thinking

Junior

Round Robin distributes evenly

Senior

Use Least Connections for variable requests

Staff asks

  • Is the workload stateless or stateful?
  • Do request durations vary significantly?
  • Is cache locality important?
  • What happens to in-flight requests on server failure?
  • Are there hot keys in consistent hashing?
  • How does the strategy behave during autoscale events?
  • Is the load balancer itself a bottleneck?
  • Should we combine strategies (weighted + health-aware)?

Key Takeaways

Round Robin: Sequential rotation · O(1) · Stateless ✔ Simple, fast, low overhead ✗ Ignores load — bad when request cost varies Use: stateless REST APIs, homogeneous pools Least Connections: Route to server with fewest active connections ✔ Adapts to real workload (variable durations) ✗ Requires real-time metrics; idle conns distort count Use: API gateways, gRPC, HTTP/2, microservices Consistent Hashing: Hash key → position on ring → next server clockwise Virtual nodes needed for even distribution ✔ Stable mapping; minimal key movement on scale ✗ No load awareness; hot keys overload single server Use: caches (Redis, Memcached), Cassandra, Kafka Production: rarely a single algorithm Combine: Weighted RR + health checks Least Conn + capacity weights Consistent Hashing + health failover Metrics to watch: Requests/backend (fairness) Active connections (load) P99 latency per backend Error rate per backend Hot key distribution (consistent hashing)
