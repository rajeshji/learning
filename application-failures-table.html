Application-Level Failure Scenarios

Staff-level · 7 categories · 33 scenarios · detect / mitigate / prevent / cascading / trade-off

Why Application Failures Are the Most Common

Application layer contains: business logic + runtime + threads + memory + dependencies Unlike infra failures, application failures are often: logic-related → bugs, incorrect state, wrong assumptions runtime-related → OOM, GC, crash, hang concurrency-related → deadlock, race, lost update dependency-triggered → slow DB, unavailable cache, contract mismatch

1 — Runtime and Process Failures
Service Crash / Process DownMust Know Unhandled exception, segfault, fatal error, OOM kill Health check failure, process exit alerts, restart count Restart service, failover traffic to healthy replicas Defensive exception handling, multiple replicas Traffic rerouted → healthy nodes overload → cascade More replicas increase infra cost
Application Hang / Freeze Deadlock, blocking IO, infinite wait on external resource Process alive but no response to health checks / traffic Kill and restart stuck instance, failover Timeouts on all calls, watchdog monitoring Thread pool exhaustion → all requests queue/fail Aggressive timeouts may terminate valid slow operations
Runtime Panic / Fatal Error JVM panic, nil pointer, runtime corruption, stack overflow Crash dumps, fatal error logs, process exit code Restart instance, isolate to single replica initially Runtime isolation, input validation, bounds checking Repeated crash loop overloads scheduler and neighbours Strict validation adds runtime overhead
Container CrashLoop (K8s) Startup failure, bad config, runtime error, OOM CrashLoopBackOff alerts, pod restart count metric Rollback deployment, fix config, check logs Canary deployments, readiness/liveness probes Repeated restarts overload cluster scheduler and DNS More validation gates slow deployment velocity
2 — Memory and Resource Exhaustion
Out Of Memory (OOM)Must Know Memory leak, huge payload, unbounded cache growth OOM kill logs, memory usage trending upward Restart process, autoscale, reduce memory pressure Heap limits, memory profiling, bounded caches Restart storm → service unavailable during recovery Strict limits may reject valid large workloads
Memory LeakMust Know Objects not GC'd, listeners not removed, connection not closed Gradual memory growth over hours/days Restart service on schedule as short-term fix Heap profiling, leak detection tools, code review Slow degradation → OOM → crash → restart storm Frequent restarts reduce service stability
CPU SaturationMust Know Expensive computation, high traffic, inefficient algorithms CPU >90%, latency spike, request queue buildup Horizontal scaling, caching, load shedding Async processing, profiling, algorithm optimisation Latency spike → caller timeouts → retry storm → overload Over-provisioning raises costs significantly
File Descriptor Exhaustion Too many open sockets, files, or pipes — connections not closed "Too many open files" errors, failed socket accepts Increase OS FD limits, restart service to clear leaks Connection pooling, explicit resource cleanup, monitoring All new connections/requests fail → cascades to callers Higher FD limits increase kernel memory overhead
Connection Pool ExhaustionMust Know More concurrent requests than DB/cache connections in pool Pool wait time increase, request timeout spikes Queue/rate-limit requests, scale instances Right-size pool, async IO, connection reuse Requests timeout → retries → DB further overloaded Larger pools overload downstream DB with connections
Thread Pool ExhaustionMust Know Blocking operations hold threads, too many concurrent requests Queue buildup, task rejection, high thread wait time Backpressure, async processing, rate limiting Non-blocking IO, right-sized pools, async patterns Requests timeout → retry storm → amplified load Async architectures increase code complexity
3 — Concurrency and Synchronization Failures
DeadlockMust Know Threads wait on each other in circular dependency Thread dump shows BLOCKED threads, no progress Restart affected service, kill deadlocked threads Lock ordering rules, timeout on lock acquisition Entire service freezes → all requests fail Less locking reduces safety guarantees
Race Condition Concurrent updates to shared state without proper synchronization Inconsistent or incorrect data in production logs Add synchronisation/locking around shared state Immutable state, atomic operations, actor model Corrupted state propagates to downstream systems Locks reduce throughput under contention
Lost Update Two concurrent writes — last one silently overwrites first Version mismatch detection, data anomaly alerts Optimistic locking (CAS / version field) Serializable transactions, proper isolation level Data inconsistency spreads to all readers Strong isolation reduces concurrent throughput
Duplicate Processing Retry or at-least-once delivery re-executes same operation Duplicate records, double charges, repeated side effects Idempotency keys, deduplication layer Idempotent API design, exactly-once semantics Double payment, double order → business and data corruption Deduplication adds storage and lookup cost
Thread Starvation High-priority tasks dominate thread pool, low-priority never run Some request types always have high queue wait time Prioritise/rebalance tasks, separate thread pools per priority Fair scheduling, bulkhead thread pool isolation Low-priority requests cascade into timeouts and retries Separate pools increase memory footprint
4 — Dependency-Induced Failures
Dependency TimeoutMust Know Slow DB, API, cache — response exceeds timeout threshold Timeout metric spikes, P99 latency increase Timeout + retry with backoff + circuit breaker Caching, async processing, query optimisation Threads held open → pool exhaustion → full service fails Short timeouts may abort valid slow-but-correct requests
Dependency UnavailableMust Know DB, cache, or third-party API is completely down Error spike, health check failure on dependency Circuit breaker + fallback to cached/default response Redundancy, failover, decouple critical path Service becomes entirely unavailable if dep is hard dependency Fallback may return stale or incorrect data
Slow Dependency DB latency spike, network issue, dep under load P95/P99 latency increase on dep calls Cache responses, reduce sync calls, async pattern Query optimisation, indexing, connection pooling Retry amplification → dep further overloaded → collapse More caching introduces staleness risk
Dependency Overload Service sends too many requests to DB/API — overwhelms it Throttle errors (429), dep error rate spike Rate limiting on outgoing calls, request queueing Backpressure, caching, request batching Dep collapse affects all services sharing it Throttling drops requests — user-visible errors
Version / Contract Mismatch API or schema change breaks backward compatibility Serialization errors, unexpected null fields, API errors Rollback to compatible version, version routing Backward-compatible API design, contract testing Cross-service failures as all callers get bad responses Multi-version support adds significant complexity
5 — Performance and Latency Failures
High Latency / Slow ResponseMust Know Slow code path, DB query, or dependency under load P95/P99 latency metrics, user-visible slowness Cache hot paths, optimise queries, scale horizontally Load testing, profiling, latency budgets Caller timeouts → retries → retry storm → overload More caching risks stale reads
GC Pause (JVM / Runtime)Must Know Full GC on large heap — STW pause stops all threads GC pause metrics, P99 latency spikes at regular intervals Tune GC settings, reduce heap pressure, use G1/ZGC Efficient object allocation, smaller working sets Timeout spike during pause → caller retries → amplified load Smaller heaps increase GC frequency
Hotspot Service / Instance Uneven traffic routing — one instance gets all load One instance at 100% CPU, others idle Rebalance traffic, dynamic routing Better partitioning, consistent hashing Overloaded instance → slow → callers timeout → retry storm Rebalancing adds routing overhead
Queue Backlog Consumers slower than producers — queue grows unbounded Queue lag metrics, consumer throughput drop Scale consumers, prioritise critical jobs, DLQ Backpressure on producers, consumer autoscaling Growing lag → delayed processing → timeout chain → retries Larger queues consume memory and storage
Cache Stampede Cache expiry under high load — all requests hit backend DB QPS spike coinciding with cache miss spike Cache locking (single-flight), mutex on rebuild Staggered TTL, probabilistic refresh, pre-warming DB overload → slowdown → request timeout cascade Cache coordination adds implementation complexity
6 — Deployment and Configuration Failures
Bad DeploymentMust Know Faulty release pushed — code bug, breaking change Error rate spike immediately after deployment Rollback to previous version immediately Canary / blue-green deployments, feature flags Large-scale outage if deployed to all instances at once Slower deployment velocity with canary gates
Configuration ErrorMust Know Wrong env values, bad DB URL, incorrect timeout values Unexpected runtime behaviour, errors after config change Rollback config, hot-reload if possible Config validation in CI, typed config schemas Service-wide failure if bad config affects core component Validation overhead slows config rollout
Feature Flag Failure Wrong flag enabled, flag service unavailable, stale evaluation Traffic anomaly, error rate change after flag toggle Disable/rollback feature flag immediately Safe defaults (flag off = safe), gradual rollout Hidden production issue enabled globally by mistake More flag management adds operational overhead
Schema Mismatch App expects different DB schema — column removed/renamed Serialisation errors, unexpected null fields, query failures Compatibility fallback, rollback migration Expand-contract migrations, backward-compatible schema changes Multiple services fail simultaneously if schema is shared Longer expand-contract migrations slow feature delivery
7 — Business Logic and State Failures
Partial Workflow ExecutionMust Know Multi-step process partially completes — crash or failure mid-flow Inconsistent business state, orphaned records Saga pattern with compensating transactions Atomic workflow design, idempotent steps Cross-service inconsistency — payment done, order not created Saga complexity adds significant design overhead
State Corruption Logic or concurrency bug puts entity into invalid state Invalid state assertions, anomalous data in DB Restore from checkpoint or event log State machine validation, invariant checks Corruption propagates to all downstream consumers Validation and assertions add runtime overhead
Duplicate Side Effects Retry without idempotency — same request causes double action Duplicate records, double charges detected in reconciliation Deduplicate using idempotency key lookup Idempotent API design from the start Financial or business data corruption — very hard to undo Idempotency store adds storage and lookup latency
Ordering Violation Events processed out of sequence — no ordering guarantee Sequence mismatch, logically invalid state transitions Reorder and replay events from durable log Per-key ordered queues (Kafka partitions), sequence numbers Incorrect downstream state — cancel before create processed Ordering constraints reduce parallelism and throughput

Staff-Level Application Thinking — 5 Questions to Ask Always

1. Is the service DOWN or just SLOW? → down: restart / failover / replicas → slow: timeouts / caching / scaling / async 2. Is resource exhaustion causing backpressure? → CPU / memory / threads / connections → scale or shed load 3. Will retries amplify the failure? → circuit breaker? jitter? retry cap? idempotency? 4. Is the failure isolated or spreading? → one instance → add replicas → spreading → circuit breaker, load shedding, bulkhead 5. Can degraded mode preserve core functionality? → fallback response? cached data? disable non-critical features?

Hard Crash vs Slow Degradation — Know the Difference

Hard Crash (Obvious)

  • Process exits immediately
  • Health check fails right away
  • LB removes node quickly
  • Alerts fire promptly
  • Impact: fast and contained

Slow Degradation (More Dangerous)

  • Service alive but slow (GC, leak, dep)
  • Health check still passes
  • Callers accumulate and wait
  • Thread pool quietly fills up
  • Retries amplify the problem silently
  • Detected only when fully broken

Final Mental Model — All Application Failures Reduce to 6 States

1. Crash → unhandled exception / OOM / panic 2. Slowdown → GC / dep latency / hotspot 3. Exhaustion → CPU / memory / threads / connections 4. Concurrency → deadlock / race / lost update / duplicate 5. Dependency → timeout / unavailable / slow / mismatch 6. Bad rollout → config error / bad deploy / schema mismatch Slow failures are most dangerous because they trigger: retries → queue buildup → thread exhaustion → cascading overload

Principal Takeaway

Down or Slow?

Different recovery path for each

Resource Exhausted?

Scale, shed load, or backpressure

Retry Risk?

Circuit breaker + jitter + cap

Degraded Mode?

Fallback, cache, or disable feature
