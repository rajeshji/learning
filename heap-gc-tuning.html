Heap & GC Tuning

JVM, Go, .NET — Staff Engineer level

The Big Picture

Every managed runtime (Java → JVM Heap, Go → Go Heap, .NET → CLR Heap) continuously allocates and reclaims memory. Poor tuning causes:

High GC Pauses CPU Spikes Memory Pressure Latency Spikes OutOfMemory Errors

The goal is to balance latency, throughput, CPU usage, and memory footprint. Every optimization is a trade-off.

Heap Sizing — The First Decision

Heap Too Small

Small Heap ↓ Frequent GC ↓ Higher CPU ↓ Latency spikes

Heap Too Large

Large Heap ↓ Less frequent GC ↓ Longer GC cycles ↓ Higher memory cost

Sizing formula: Heap Size = Live Set + Headroom (30–50% above measured live set)

Go Heap Tuning

Go uses a concurrent garbage collector. Primary tuning knob: GOGC (default = 100).

Lower GOGC (e.g. 50)

More frequent GC → Smaller heap → Higher CPU

Higher GOGC (e.g. 200)

Less frequent GC → Larger heap → Lower CPU

Go 1.19+ also supports GOMEMLIMIT — hard cap on total memory. Best practice: set GOMEMLIMIT just below container limit.

Off-Heap Memory

Not all memory belongs to the managed heap. Ignoring off-heap usage causes unexpected OOM errors.

Process Memory = Managed Heap + Native Memory + Direct Buffers (ByteBuffers) + Thread Stacks + Metaspace / Class Data

Containers & Kubernetes

Heap should never consume the entire container memory limit. Always reserve space for off-heap components.

Container Memory Limit = Heap + Native allocations + Direct buffers + Metaspace + Thread stacks

Common rule: set JVM heap to 50–75% of container memory limit. Use -XX:MaxRAMPercentage=75 for container-aware sizing.

Production Failure Scenarios

Frequent Minor GC

Cause: High object allocation rate  ·  Fix: Reduce temporary object creation or increase Young Generation

Frequent Full GC

Cause: Old Generation exhausted  ·  Fix: Increase heap or reduce long-lived objects

High P99 Latency

Cause: Stop-the-World pauses  ·  Fix: Switch to G1, ZGC, or Shenandoah

OutOfMemory Error

Cause: Memory leak or insufficient heap  ·  Fix: Analyze heap dump to identify retained objects

High GC CPU

Cause: Heap too small or allocation rate too high  ·  Fix: Increase heap or reduce allocation churn

Production Tuning Workflow

Measure Heap ↓ Collect GC Metrics ↓ Identify Bottleneck ↓ Choose Collector ↓ Tune Heap Size ↓ Tune GC Parameters ↓ Load Test ↓ Measure Again ↓ Iterate

Never tune GC blindly. Measure → Tune → Verify.

Production Debugging Checklist

  • ✅ Measure allocation rate
  • ✅ Check live heap size after GC
  • ✅ Monitor Minor vs Major GC frequency
  • ✅ Analyze promotion rate
  • ✅ Review GC pause histograms (P95/P99)
  • ✅ Inspect heap dumps for memory leaks
  • ✅ Correlate GC events with latency spikes
  • ✅ Verify container memory limits (-XX:MaxRAMPercentage)
  • ✅ Measure off-heap memory usage
  • ✅ Load test after every tuning change

Key Takeaways

Heap Sizing • Heap = Live Set + 30–50% headroom. • Too small → frequent GC. Too large → long cycles. • Container: heap ≤ 75% of container memory limit. JVM GC Selection • G1: general production. ZGC: large heaps. • Shenandoah: low-latency services. • Parallel GC: batch throughput. Go Tuning • GOGC (default 100) controls heap growth trigger. • GOMEMLIMIT: hard cap, prevents OOM in containers. .NET Tuning • Server GC for multi-core production servers. • Background GC reduces STW pauses. Staff focus • Allocation rate, live set, promotion rate, GC pause time, Full GC frequency, GC CPU %. • Measure → Tune → Verify. Never guess.
