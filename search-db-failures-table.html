Search Database Failure Scenarios

Staff-level (Elasticsearch / OpenSearch / Solr / Vespa) · 10 categories · 40 scenarios · detect / mitigate / prevent / cascading / trade-off

Failure Scenario When It Occurs How To Detect How To Mitigate How To Prevent Cascading Failure Risk Trade-off
1 — Indexing Failures
Indexing BacklogMust Know Write rate exceeds indexing throughput — index queue grows, documents not yet searchable Index queue depth growing, search freshness lag increasing Throttle ingestion, increase indexing shards Right-size indexing throughput for peak write load, bulk indexing over single-doc Search freshness lag — users search and miss recently written documents Faster indexing needs more shards; more shards add heap and metadata pressure
Document Index FailureMust Know Document violates mapping — wrong field type, too-long string, nested depth exceeded Index error spike in ingestion pipeline, documents missing from search Route to DLQ, fix mapping conflict, retry with corrected document Strict schema validation at ingestion, mapping enforcement with reject policy Missing search results — failed documents never appear in any query result Strict mapping rejects valid edge-case documents that could be coerced
Partial Indexing Crash or pipeline failure mid-batch — some documents in batch indexed, others not Missing docs in search, batch offset not advancing Replay from last committed offset in event stream Idempotent indexing with document-level versioning Search inconsistency — some documents visible, semantically related ones missing Idempotent replay adds metadata overhead and reprocessing cost
Out-of-Order Index UpdatesMust Know Async indexing delays — older version of document indexed after newer version Stale document versions visible in search despite newer write succeeding Apply versioned indexing — reject writes with lower version than stored External versioning or sequence-based conflict detection Stale search results — search returns old data long after update was applied Version checking adds per-document metadata read on every index operation
2 — Query Execution and Search Failures
Query Fanout ExplosionMust Know Query must scatter to every shard — more shards = more fanout per query Query latency spike proportional to shard count, coordinator CPU spike Reduce active shard count, use routing keys to target fewer shards Routing keys, fewer larger shards, pre-filter by index alias Cluster-wide latency — query fanout consumes all coordinator and data node threads Fewer larger shards reduce fanout but increase shard recovery time
Expensive Aggregation QueryMust Know Large cardinality aggregation (terms on high-cardinality field) — heap consumed CPU/memory spike on data nodes, node heap usage approaching limit Limit bucket count, apply circuit breaker Pre-aggregation at ingest time, use doc_values for aggregated fields Node saturation — expensive aggregation starves concurrent read/write threads Pre-aggregation trades query flexibility for ingest-time compute cost
Deep Pagination FailureMust Know Query uses very large offset (from:10000) — coordinator must fetch and discard N documents Heap spike on coordinator, latency growing with page depth Switch to search_after / PIT cursor immediately Enforce pagination depth limit, document search_after as required API pattern Coordinator OOM if unbounded deep pagination allowed at scale Cursor-based pagination requires stateful PIT context management
Wildcard / Regex Query Explosion Leading wildcard or complex regex scans entire inverted index — CPU saturated CPU spike for that query type, query node unresponsive to other queries Reject or timeout wildcard queries, apply query complexity limits Query validation at API layer, prohibit leading wildcards, suggest n-gram alternatives Cluster overload — one query monopolises CPU, starving all other search traffic N-gram indexing for typeahead trades index size for fast prefix search
3 — Shard and Partition Failures
Hot ShardMust Know Uneven query or write distribution — one shard receives most traffic One node at 100% CPU/IO, others idle; hot shard clearly visible in slow log Rebalance or split the hot shard, add routing randomisation Better routing key design, virtual shards with consistent hashing Localised node collapse — hot shard host fails, all queries for that range timeout Better routing distributes load but may hurt locality of related documents
OvershardingMust Know Too many small shards — heap and metadata pressure grow beyond cluster capacity Heap usage high despite small data volume, metadata update latency growing Shrink/merge indices, reduce primary shard count Shard sizing guidelines (10-50 GB per shard), ILM with rollover, max shard count alert Cluster instability — metadata explosion causes master to stall on every update Fewer shards reduce parallelism and may slow large index scans
Shard Relocation Storm Node restart or failure triggers mass shard relocation across cluster Network IO spike, query latency spike during rebalance Throttle relocation rate (cluster.routing.allocation.node_concurrent_recoveries) Controlled cluster rebalancing settings, decommission nodes gradually Cluster saturation — relocation IO competes with live read/write traffic Throttling extends time cluster operates in degraded state
Primary Shard Failure Primary shard's host node crashes — shard must failover to replica Shard unavailable briefly, yellow cluster state until replica promoted Promote replica to primary, trigger new replica allocation Replica redundancy (replica count ≥ 1), cross-zone replica placement Partial index outage — all write operations to that shard rejected until promotion Replicas double storage cost and add replication write overhead
4 — Segment Merge and Compaction Failures
Merge StormMust Know Frequent refresh creates many small segments — merge scheduler triggers many concurrent merges Disk IO 100%, merge thread pool saturated, query latency spike Throttle merge rate (indices.store.throttle), pause non-critical indexing Increase refresh interval (30s for batch pipelines), bulk indexing over real-time Query latency explosion — merge IO starves query read IO completely Longer refresh interval reduces search freshness for newly indexed documents
Too Many SegmentsMust Know Merge cannot keep up with refresh rate — segment count grows unbounded Segment count metric growing, read latency increasing per query Force merge on affected index (forcemerge API) Better refresh/flush tuning, avoid sub-second refresh interval Read amplification — each query must scan more segments, latency grows Force merge is expensive and blocks new segment creation during merge
Disk Exhaustion During Merge Merge needs temporary scratch space — disk fills during merge, index goes read-only Disk full alert, index switches to read-only mode automatically Free disk space immediately (delete old indices), reduce merge size Keep 30% disk headroom, disk usage watermark alerts Cluster read-only — all writes rejected until disk freed, indexing fully stops Reserved headroom reduces usable storage capacity
Segment Corruption Disk failure or crash during merge — segment data partially written and corrupt Checksum mismatch on segment read, corrupt results for affected index range Restore shard from replica, run index recovery Per-segment checksums, replica on separate disk/node Missing or corrupt results for all queries touching that segment Segment checksums add IO overhead on every segment read
5 — Cluster Coordination and Distributed Failures
Split Brain ClusterMust Know Network partition — two sets of nodes each elect their own master Multiple cluster states, index inconsistency, conflicting shard allocations Fence the minority partition, restore network, let majority win Quorum-based election (minimum_master_nodes = n/2+1), dedicated master nodes Index inconsistency — both partitions may accept writes, creating diverged indices Strict quorum reduces availability during partition (minority cannot serve)
Master Node FailureMust Know Dedicated master node crashes — cluster cannot allocate shards or update metadata Cluster instability, shard allocation stalled, metadata operations failing Elect new master from dedicated master pool 3 dedicated master nodes (odd quorum), never use data nodes as masters Allocation instability — no shard can be assigned until master elected Dedicated master nodes consume resources without serving data
Cluster State Explosion Too many indices and shards — cluster state object grows beyond fast-update threshold Master CPU spike on every state update, state propagation latency growing Reduce index/shard count via ILM rollover and delete old indices ILM automation, max shard count guardrails, close/delete unused indices Cluster instability — slow state updates block all allocation and routing decisions Strict ILM deletes historical data that may be needed for long-term analytics
Election Storm Frequent master re-elections due to GC pauses, network jitter, or misconfigured timeout Master election events in log, leadership flapping Stabilise quorum, tune election timeout, fix GC causing pause Dedicated master nodes with lower heap (avoid GC), tune heartbeat timeout Search interruptions — cluster briefly unavailable on every re-election Shorter election timeout detects failures faster but triggers more false elections
6 — Memory and Heap Pressure Failures
Heap ExhaustionMust Know Large aggregation queries or fielddata loading fills JVM heap — OOM or stop-the-world GC Heap usage >85%, long GC pauses, node eventually killed by OOM Restart node, reject large queries via circuit breaker Heap at 50% of RAM (leave OS cache), circuit breakers enabled, heap monitoring Node crash → shard relocation storm → cascading cluster pressure Smaller heap leaves more OS file cache, but limits in-memory sort/agg size
Fielddata ExplosionMust Know Aggregation or sort on text field forces entire field into heap as fielddata Fielddata heap usage spike, GC pressure increasing Disable fielddata on text fields, evict fielddata cache Use keyword type or doc_values for any field used in aggregation/sort GC pause storm — fielddata heap growth triggers repeated long GC pauses keyword type disallows full-text search on that field without separate mapping
GC Pause StormMust Know Large heap cleanup triggers stop-the-world GC — all node operations pause for seconds GC pause metric spike, cluster thinks node is dead and starts re-election Tune GC (G1GC), reduce heap fragmentation G1GC with tuned region size, heap at ≤31 GB (compressed oops), off-heap for segments Timeout cascades — clients time out during pause, trigger retries amplifying load Off-heap segment storage (Lucene) adds OS-level memory management complexity
Circuit Breaker Trigger Query would exceed configured memory threshold — breaker rejects before OOM 429 circuit breaker rejections in query response, users see errors Reduce query complexity, return partial results Proper circuit breaker limits, query governance, user-facing pagination limits User-visible failures — rejected queries fail without clear error messaging Circuit breakers protect cluster but may reject valid large analytics queries
7 — Mapping and Schema Failures
Mapping ExplosionMust Know Dynamic mapping enabled with user-generated keys — field count explodes into thousands Field count spike, heap usage growing, cluster state update slowing Disable dynamic mapping immediately, reduce field count Explicit mapping with dynamic:strict, flatten user-provided keys into a KV array Heap exhaustion — thousands of fields consume heap in mapping cache Strict mapping blocks indexing of genuinely new valid fields
Incorrect Analyzer Configuration Wrong tokeniser, stemmer, or language analyser applied at index creation Poor search relevance, expected search terms not matching documents Reindex data with corrected analyser configuration Search quality testing with sample queries before production, A/B test analyser changes Business impact — wrong analyser silently degrades search quality for all users Changing analyser requires full reindex (cannot update mapping in-place)
Field Type Conflict Same field name mapped as different types in different documents or indices Indexing rejection, type conflict errors in ingestion pipeline Create new index with correct unified mapping, reindex affected data Schema validation at ingestion, single source of truth for field types Partial ingestion failure — documents with conflicting field type rejected Strict unified mapping requires coordination across all data producers
Reindex Migration Failure Large reindex interrupted — partial data in new index, partial in old Document count mismatch between old and new index Resume reindex from last checkpoint, use versioning to avoid duplicates Incremental reindex with version tracking, blue-green index alias swap on completion Search inconsistency — some documents only in old index, others in new Blue-green reindex requires double the storage during migration window
8 — Ranking and Relevance Failures
Ranking RegressionMust Know Scoring change, new field weights, or analyser update silently degrades result quality CTR drop, search quality metrics decline, user session length drops Rollback ranking configuration to last known-good A/B testing all ranking changes, offline evaluation with relevance test suite Business impact — bad ranking reduces conversion, retention, and user trust A/B ranking tests take time; real revenue impact occurs during test window
Stale Search ResultsMust Know Indexing backlog or too-long refresh interval — search returns old documents Version mismatch between source system and search results Force refresh on affected index, reduce refresh interval temporarily Bounded indexing lag SLO, freshness monitoring with source-of-truth comparison Incorrect business decisions — stale inventory, pricing, or product data served Shorter refresh interval increases merge and CPU pressure
Duplicate Search Results Document indexed multiple times (retry without versioning) — same hit returned N times Repeated document IDs in search results, relevance scores unexpectedly high Deduplicate at query layer by ID, fix ingestion idempotency Idempotent ingestion using deterministic document IDs, external versioning Reduced relevance — duplicate documents push true top results down Deterministic document IDs require stable ID generation across retry paths
Missing High-Relevance Documents Index corruption, failed indexing, or analyser mismatch causes key documents to not appear Known product/document absent from expected query results Reindex affected documents, validate analyser configuration Spot-check test queries in CI, document existence monitoring User trust loss — high-value content invisible to users searching for it Spot-check monitoring requires maintaining a golden query set over time
9 — Replication and Recovery Failures
Replica LagMust Know Heavy indexing or slow network — replica cannot keep up with primary write rate Replica freshness lag metric growing, read-your-writes inconsistency Route reads to primary for consistency-sensitive queries Replica sizing matching primary, parallel replication apply, lag monitoring Stale search results for users hitting lagging replica Routing all reads to primary reduces read scale-out benefit of replicas
Replica Recovery StormMust Know Multiple shards rebuild simultaneously after node failure — network/disk saturated Network IO spike, cluster recovery metrics, query latency spike during rebuild Throttle recovery rate, limit concurrent shard recoveries Incremental recovery (sync only delta), bounded concurrent recovery settings Cluster saturation — recovery IO starves live query traffic Throttling extends cluster degraded window
Snapshot Failure Backup interrupted or storage backend unavailable — snapshot incomplete or corrupt Snapshot status shows failed, partial snapshot in repository Retry snapshot, clean up partial snapshot, restore from older clean snapshot Automated snapshot validation, test restore regularly Disaster recovery risk — no valid backup if cluster fully corrupted Regular snapshot validation adds storage and compute cost
Corrupted Index Recovery Failure Index corruption spreads to replica before detected — both copies corrupt Recovery checksum mismatch on both primary and replica Restore from last valid snapshot Checksums, rapid corruption detection before replica sync, immutable snapshots Permanent data loss — if snapshot is also old, recent documents unrecoverable More frequent snapshots reduce data loss window but add storage overhead
10 — Multi-Tenant and Operational Failures
Noisy Tenant QueryMust Know One tenant runs expensive aggregation or wildcard query — cluster-wide slowdown Cluster-wide latency spike correlated with specific tenant ID in slow query log Kill offending query, apply query isolation for tenant Per-tenant query quotas, query complexity limits, tenant-aware circuit breakers Shared cluster instability — all tenants experience degraded search during attack Per-tenant isolation adds routing and quota management complexity
Index Lifecycle Failure ILM policy misconfigured or paused — old indices never archived or deleted Storage growth, cluster approaching high watermark Manual index delete/archive, resume ILM ILM automation with alerting on policy failures Disk exhaustion → cluster read-only → all indexing stops Aggressive ILM deletes historical data that analytics or compliance may need
Search Cluster Upgrade Failure Rolling upgrade hits version incompatibility — nodes on new version cannot join old cluster Node join failures, cluster in mixed incompatible version state Rolling rollback to previous version Rolling upgrade with compatibility matrix validation, test in staging first Cluster instability — mixed versions may disagree on shard allocation protocol Phased upgrades are slower but reduce incompatibility window
Observability Blindness Search slow log, query profiling, or metrics pipeline disabled — hidden slow queries No visibility into which queries are slow or which indices are hot Enable slow log immediately, add Prometheus metrics exporter Search observability as standard: slow log + metrics + query profiling in every env Long MTTR — cannot identify root cause without query-level visibility Slow query logging adds disk IO for every query exceeding threshold

Staff-Level Search DB Thinking — 9 Questions to Ask Always

1. Indexing lag affect correctness? → freshness SLO + backpressure + idempotent writes 2. Queries fan out too many shards? → routing keys + fewer larger shards + alias filter 3. Merges overwhelm disk? → refresh interval tuning + merge throttle + headroom 4. Heap/metadata overwhelm cluster? → heap cap + doc_values + dynamic:strict + ILM 5. Hot shards collapse cluster? → routing key design + virtual shards + split 6. Ranking regress silently? → A/B test all changes + relevance test suite in CI 7. Replica lag create stale search? → lag monitoring + route critical reads to primary 8. Mapping explosion destabilize? → dynamic:strict + field count alert + flatten keys 9. Recovery overload healthy nodes? → throttle recovery + concurrent recovery limits

Root Search FailureCascading Effect

OvershardingHeap/metadata explosion → master stalls → allocation instability
Hot shardNode CPU/IO 100% → node crash → shard relocation storm on cluster
Query fanoutToo many shards → coordinator overwhelmed → cluster-wide slowdown
Heap exhaustionGC pause → cluster thinks node dead → election storm

Final Mental Model — All Search DB Failures Reduce to 4 States

1. Index not fresh → indexing backlog / stale refresh / partial indexing 2. Query too slow → fanout / aggregation / deep pagination / too many segments 3. Cluster unstable → heap exhausted / oversharded / split brain / merge storm 4. Data wrong → ranking regression / mapping explosion / analyser mismatch Most dangerous: oversharding + query fanout Both grow silently → heap → GC → election → disk → read amplification → collapse
