Dependency Failure Scenarios

Staff-level · 7 categories · 34 scenarios · detect / mitigate / prevent / cascading / trade-off

Why Dependency Failures Are the Most Dangerous

Your system can fail even when your own service is perfectly healthy. Modern services depend on: databases | caches | queues | third-party APIs microservices | service discovery | auth systems 7 root causes: unavailable | slow | overloaded | inconsistent incompatible | communication failure | cascading failure

1 — Dependency Unavailable and Down Failures
Database DownMust Know DB process crash, failover not completing, storage failure Connection failures, DB health check alerts Failover to replica, circuit breaker to stop calls HA DB clusters, automatic failover, read replicas Entire service unavailable — every request that needs DB fails Replication increases cost and adds write latency
Cache UnavailableMust Know Redis/Memcached crash, network partition to cache Cache connection errors, miss rate spike Fallback to DB for all reads, rate limit to protect DB Cache replication, multi-AZ cache cluster All cache misses hit DB simultaneously → DB overload Cache replication adds cost and synchronization overhead
Queue / Broker Down Kafka/RabbitMQ broker crash or network partition Consumer lag stops updating, broker health alerts Retry/reconnect producers and consumers, failover broker Multi-broker cluster, partition replication Event pipeline stops — no events processed, backlog builds Multi-broker replication adds latency per write
Microservice DownMust Know Service crash, bad deployment, OOM, CrashLoop 5xx rate spike, health check failure on that service Circuit breaker + fallback response or degraded mode Multiple replicas, canary deployments, health checks Downstream service chain fails — all callers of that service fail Fallback may return stale or reduced-quality response
Third-Party API DownMust Know External provider outage — payment, SMS, email, maps External API timeout/error rate spike Fallback provider, degraded mode (queue for later) Multi-provider strategy, cache recent responses Payment / notification failures → user-visible product failures Multiple providers cost more and add switching complexity
Service Discovery Down Consul/etcd/Zookeeper unavailable or returning stale data Service lookup failures, connection errors to healthy services Use cached service endpoints as fallback Replicated registry (etcd HA), client-side endpoint caching Services cannot locate each other → system-wide communication failure Registry replication adds consistency complexity
Auth Service Down OAuth server, JWT validator, or IAM service unavailable Login/auth failures, 401/403 surge across all services Cached token validation, short-lived degraded mode HA auth infrastructure, local token validation Entire platform inaccessible — no request can be authorized Cached token validation is a security risk if tokens revoked
2 — Slow Dependency and Latency Failures
Slow Database QueriesMust Know Missing index, full table scan, expensive join under load Query latency metrics, slow query log Cache results, optimise query, read from replica Proper indexing, query explain analysis, query timeout Thread pool exhaustion — all callers wait → full service slowdown Indexes increase storage cost and write overhead
Slow Cache Response Cache cluster overloaded, network congestion to cache node Cache latency spike, P99 increase on cache calls Timeout and fallback to DB, local in-memory mini-cache Better cache key distribution, cache cluster partitioning Request queue builds → DB also hit → double slowdown DB fallback under cache slowness can overload DB
Slow External APIMust Know Third-party provider network issue or high load on their end External API latency monitoring, P95/P99 increase Timeout + async retry, degrade gracefully without response Caching recent responses, async processing for non-critical Retry storm — clients retry slow calls → amplify external traffic Short timeouts may abort calls that would have succeeded
Slow Internal Microservice High CPU or load in a dependency service, GC pause P95/P99 increase on calls to that service Circuit breaker, load shedding on that service Autoscaling, SLO-based alerting, async where possible Cascading latency — every caller slows → retry storm → overload More replicas increase cost
Slow Queue Consumption Consumers overloaded, slow message processing logic Consumer lag metrics increasing, throughput drop Scale consumers, increase parallelism, reduce processing time Backpressure on producers, consumer autoscaling Event processing delay → downstream state lags → stale reads Larger consumer pools increase cost and coordination overhead
3 — Dependency Timeout and Retry Failures
Dependency TimeoutMust Know Dependency too slow to respond within configured timeout Timeout metric spike, P99 latency increase Timeout + fail fast + circuit breaker Proper timeout tuning, async non-blocking calls Threads held open → thread pool exhaustion → all requests fail Short timeouts may abort valid slow-but-correct requests
Retry StormMust Know Clients retry failed/slow dependency calls without backoff Dependency receives 2-10× normal traffic from retries Exponential backoff + jitter, circuit breaker Retry budgets, backoff policies, retry caps Dependency collapses from amplified retry traffic Fewer retries reduce resilience for transient failures
Infinite Retry Loop No retry limit — client retries forever on permanent failure Endless retry logs, dependency never gets to recover Circuit breaker opens after threshold, retry cap Safe retry policies — always cap retries, add DLQ Queue explosion, dependency never recovers under constant retries Retry cap may permanently lose requests that would have succeeded
Blocking Synchronous Dependency Service makes sync call — blocks thread waiting on slow dependency Long request duration, thread pool queue depth increasing Add async processing, use timeout + fail fast Event-driven architecture, async non-blocking IO Full request chain slows — all callers hold threads waiting Async systems are harder to reason about and trace
4 — Dependency Overload Failures
Database OverloadMust Know Too many concurrent queries, connection storm, batch job running DB CPU/QPS spike, slow query count increasing Read replicas, query throttling, cache hot paths Read/write separation, sharding, caching, query limits Entire application slows → latency cascade → retries → worse Read replicas can have consistency lag
Cache Overload Too many keys, hot partition, too many requests to cache cluster Cache CPU/memory saturation, eviction rate spike Scale cache cluster, rebalance hot keys Better key distribution, cache partitioning, local L1 cache Cache eviction storm → miss rate spike → DB overloaded Larger cache cluster costs significantly more
Queue Saturation Producers send faster than consumers can process indefinitely Queue lag growing unboundedly, broker memory pressure Scale consumers, drop low-priority messages, DLQ Backpressure on producers, consumer autoscaling Processing delay cascade → broker memory exhaustion → crash More consumers increase cost and coordination overhead
API Rate Limit Exceeded Service makes too many calls to external API in short window 429 responses from external API, feature degradation Local rate limiting, request batching, cache responses Request batching, caching, respect rate limits External API lockout → feature completely unavailable Throttling reduces throughput — some requests are dropped
Service Mesh Overload Sidecar proxy (Envoy/Linkerd) CPU-saturated under high inter-service traffic Sidecar CPU spike, inter-service latency explosion Bypass mesh for heavy internal traffic, scale sidecars Capacity planning for mesh overhead, tune sidecar limits Inter-service latency explodes → entire microservice layer slows Bypassing mesh reduces observability and security controls
5 — Dependency Inconsistency and Data Failures
Stale Cache DataMust Know Cache not invalidated after DB update — old value served Cache value differs from DB value, user complaints Invalidate cache on write, force cache refresh Write-through cache, short TTL, CDC-based invalidation Wrong data served at scale — wrong prices, balances, inventory Aggressive invalidation increases cache miss rate and DB load
Replica Lag Follower replica falls behind leader — replication slow or paused Replica lag metrics in seconds, stale read user complaints Route critical reads to primary/leader Tune replication pipeline, bounded staleness reads Stale reads propagate → wrong business decisions at scale Reading from primary reduces read scalability benefits
Incorrect API Response Provider bug, data corruption, silent serialization error Response validation failures, anomalous data in output Reject and fallback to default/cached value Response schema validation, checksums on critical data Corrupted data propagates to all downstream consumers Validation adds per-request latency overhead
Out-of-Sync Services Eventual consistency lag — services have different view of state Reconciliation job finds mismatched state across services Re-sync via event replay or reconciliation Outbox pattern, CDC, stronger consistency guarantees Cross-service inconsistency → wrong business logic applied Stronger consistency reduces availability during failures
Duplicate Events From Dependency Broker retry or redelivery sends same event more than once Duplicate IDs, repeated side effects in consumer logs Consumer-side deduplication by event ID Idempotent consumers, exactly-once semantics Double processing — double charges, double orders Deduplication store adds storage and lookup overhead
6 — Dependency Compatibility and Contract Failures
API Contract MismatchMust Know Dependency deploys breaking API change — field removed/renamed Serialization/parsing errors, unexpected null fields Rollback dependency, version routing fallback Backward-compatible API design, contract testing in CI Multi-service failure — all callers of that API break simultaneously Supporting multiple API versions adds maintenance complexity
Schema Evolution Failure Producer publishes new schema — consumer cannot deserialize Consumer decode failures, pipeline errors Schema version routing, rollback producer schema Schema registry (Confluent), backward-compatible evolution Entire event pipeline breaks — all consumers error out Slower expand-contract migrations delay feature delivery
Auth Token Mismatch Expired token, wrong signing key, token not yet propagated Auth failures (401/403), service-to-service call rejections Token refresh, re-authenticate, retry with new token Automated token rotation, proactive token refresh before expiry Cross-service auth failure — entire mesh of service calls fails Token automation adds operational complexity
Protocol Version Mismatch gRPC/HTTP/TLS protocol version incompatibility after upgrade Connection failures, protocol handshake errors in logs Version negotiation, rollback to compatible version Compatibility testing before upgrades, canary rollout All inter-service communication fails simultaneously Multi-protocol support adds client/server complexity
7 — Dependency Communication Failures
Service Discovery FailureMust Know Registry unavailable or returning stale/incorrect endpoints Lookup failures, connection errors to healthy services Cached endpoints fallback, hardcoded emergency endpoints HA registry (etcd/Consul), client-side endpoint caching Services cannot locate each other → system-wide comms failure Cached endpoints risk routing to stale/dead instances
DNS Failure to Dependency DNS outage — service cannot resolve dependency hostname DNS resolution errors, connection failures on dep calls Retry alternate DNS resolver, use IP fallback Multi-DNS providers, client-side DNS caching Dependency entirely inaccessible even though it is healthy Cached DNS can route to stale IPs after failover
Cross-Region Dependency Failure WAN link failure, cloud provider inter-region outage Regional traffic errors, high cross-region latency Failover to same-region dependency replica Multi-region active-active, local replicas per region Global service degradation — entire region cannot call dependency Cross-region replication adds cost and consistency complexity
Network Partition to Dependency Partial network failure — service cannot reach dependency Timeout spike on dependency calls, no DNS/connection error Retry with alternate endpoint, circuit breaker Redundant network paths, multi-AZ deployment Dependency isolation → callers fail → cascade up the call chain Network redundancy adds significant infrastructure cost

10 Must-Know Dependency Failures for Interviews

Microservice down → circuit breaker + fallback + redundant replicas 4. 3rd-party API down → fallback provider + cache responses + degrade gracefully 5. Slow DB query → index + cache + query timeout 6. Slow external API → timeout + async + cache recent responses 7. Dependency timeout → fail fast + circuit breaker + thread pool guard 8. Retry storm → backoff + jitter + circuit breaker + retry cap 9. API contract mismatch → backward-compatible APIs + contract tests + canary 10. Stale cache data → write-through + short TTL + CDC invalidation

Staff-Level Dependency Thinking — 7 Questions to Ask Always

1. Is dependency DOWN or just SLOW? → down: circuit breaker + fallback → slow: timeout + async + fail fast 2. Is dependency CRITICAL or OPTIONAL? → critical: HA + redundancy + fallback → optional: degrade gracefully, return default 3. Can FALLBACK / DEGRADED MODE work? → cached data? default value? queue for later? 4. Will RETRIES AMPLIFY the failure? → circuit breaker? jitter? retry cap? 5. Can failures be ISOLATED? → bulkhead: separate thread pools per dependency 6. Is dependency STATE CONSISTENT? → stale cache? replica lag? duplicate events? 7. Can dependency OVERLOAD spread system-wide? → DB overload → application slow → retries → worse

Down vs Slow — Why Slow Dependencies Are Most Dangerous

Dependency Down (Obvious)

  • Connection refused immediately
  • Circuit breaker opens fast
  • Fallback triggers promptly
  • Impact: fast and bounded

Dependency Slow (Most Dangerous)

  • Dependency responds — just slowly
  • Health checks still pass
  • Caller threads queue up silently
  • Thread pool fills gradually
  • Retries multiply the load
  • Full outage by the time anyone notices

Final Mental Model — All Dependency Failures Reduce to 6 States

1. Unavailable → dep is down: circuit breaker + fallback 2. Slow → dep is late: timeout + fail fast + async 3. Overloaded → dep is overwhelmed: rate limit + cache + backpressure 4. Inconsistent → dep returns stale/wrong data: validate + invalidate 5. Incompatible → dep changed contract: versioning + contract tests 6. Unreachable → dep is healthy but can't be found: DNS + discovery + retry Slow dependencies are most dangerous because they silently cause: thread exhaustion → retry amplification → queue buildup → cascade
