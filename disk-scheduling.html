Disk Scheduling Algorithms

CFQ, NOOP, Deadline — I/O ordering for HDDs, SSDs, NVMe — Staff Engineer level

The Big Picture

Linux decides the order of disk I/O requests before sending them to hardware. The scheduler merges, reorders, and prioritizes requests to maximize throughput, minimize seek time, and provide fairness — but different devices need different strategies.

CFQ NOOP Deadline BFQ mq-deadline blk-mq Merging Seek
App → read()/write() → Page Cache → Block Layer → I/O Scheduler (merge + reorder) → SSD/HDD/NVMe Without scheduling: random seeks, unpredictable latency, starvation. With scheduling: merged requests, optimized order, fair access.

The Three Classic Schedulers

CFQ — Fairness

Process A → Queue A Process B → Queue B Process C → Queue C ↓ Round-robin (each gets time slice)

Per-process queues. Fair for desktops. High CPU.

NOOP — Simplicity

Req1 → Req2 → Req3 ↓ Merge adjacent ↓ FIFO dispatch (device handles rest)

Minimal overhead. Ideal for SSD/NVMe. Device does the work.

Deadline — Latency

Sorted Queue (sector) + Deadline Queue (time) Read: 500 ms deadline Write: 5000 ms deadline

Balanced seek + latency. Best for databases on HDD/SSD.

CFQ — Completely Fair Queuing

Each process gets its own I/O queue and a time slice. Requests within each queue are reordered to reduce seek distance.

Primary GoalFairness across processes
Queue TypePer-process

Read LatencyModerate

Modern ReplacementBFQ (Budget Fair Queueing)

Modern Linux has largely replaced CFQ with BFQ (Budget Fair Queueing) for better desktop interactivity.

NOOP — Minimal Scheduler

Only merges adjacent requests and dispatches in FIFO order. No seek optimization. Works because SSDs/NVMe controllers internally optimize I/O.

FeatureNOOP
Primary GoalMinimal CPU overhead
Queue TypeSingle FIFO
Request ReorderingNo
CPU OverheadVery Low
LatencyVery Low
Best DeviceSSD, NVMe, hardware RAID
Best WorkloadVMs, sequential I/O, NVMe workloads

SSD/NVMe controllers have their own parallel queues and wear-leveling — adding a software reorder scheduler is wasted overhead.

Deadline — Latency-Bounded Scheduling

Maintains two queues: one sorted by disk sector (for seek efficiency) and one by deadline (to prevent starvation). Reads get 500 ms deadlines; writes get 5000 ms.

Normal operation: serve requests in sector order (minimize seek) If deadline expires: immediately serve that request (no starvation) Read deadline: 500 ms (reads serve DB queries — latency critical) Write deadline: 5000 ms (writes can batch more aggressively)

HDD vs SSD — Different Needs

HDD — Mechanical

Seek distance matters. Reordering requests reduces head movement.

Without scheduler: Sector 100 → 500 → 101 (lots of seeking) With Deadline: Sector 100 → 101 → 500 (minimal seek)

Use: mq-deadline or CFQ/BFQ

SSD / NVMe — Flash

No moving parts. Controller manages parallel queues internally. Reordering adds overhead without benefit.

Any order: ~same latency Controller: NVMe NCQ, parallel channels, FTL optimization

Use: none or NOOP

Request Merging — Free Throughput

All schedulers merge adjacent block requests before dispatch.

Without merging: Read Block 100 (1 I/O op) Read Block 101 (1 I/O op) Read Block 102 (1 I/O op) → 3 separate device operations With merging: Read Blocks 100–102 (1 I/O op) → 1 device operation, 3× efficiency

Merging is performed by all schedulers. It's the cheapest form of I/O optimization and works for both HDDs and SSDs.

Modern Linux — blk-mq Schedulers

Linux now uses the Multi-Queue Block Layer (blk-mq) for multi-core and high-throughput NVMe storage.

SchedulerBest Use Case
BFQDesktop fairness, interactive responsiveness (replaces CFQ)
mq-deadlineDatabases, HDD, mixed workloads (replaces deadline)
noneNVMe SSDs — device handles all scheduling
KyberLow-latency SSD workloads with QoS
Check active scheduler: cat /sys/block/sda/queue/scheduler Change scheduler: echo mq-deadline > /sys/block/sda/queue/scheduler

Production Failure Scenarios

Slow Database on HDD

Cause: CFQ on busy HDD → reads stuck behind writes  ·  Fix: Switch to mq-deadline

High CPU on NVMe Server

Cause: Complex scheduler adding overhead on NVMe  ·  Fix: Use none

VM Storage Bottleneck

Cause: Guest OS + hypervisor both scheduling (double scheduling)  ·  Fix: Use NOOP in guest, let hypervisor schedule

Desktop Audio/Video Stutter

Cause: NOOP on shared HDD — no fairness, one process starves another  ·  Fix: Use BFQ for interactive responsiveness

Production Debugging Checklist

  • ✅ Identify device type: lsblk -d -o name,rota (rota=1 = HDD, 0 = SSD)
  • ✅ Check active scheduler: cat /sys/block/sda/queue/scheduler
  • ✅ Measure IOPS and latency: iostat -x 1
  • ✅ Measure queue depth: iostat -x (avgqu-sz)
  • ✅ Benchmark with fio before and after changing scheduler
  • ✅ Avoid double scheduling in VMs (use NOOP in guest)
  • ✅ Verify blk-mq is active: cat /sys/block/sda/queue/nr_requests

Key Takeaways

I/O Scheduler: orders disk requests before sending to hardware. All schedulers: merge adjacent requests (free throughput win).
