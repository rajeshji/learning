Snapshotting & Backups (RTO/RPO Definitions)

How production systems protect data, recover from failures, and meet business recovery objectives

The Big Picture

Production systems will eventually fail — disk failures, bugs, human mistakes, ransomware, datacenter outages. Every critical system needs four protection layers: Replication → Snapshots → Backups → Archive. Each solves a different recovery problem.

Live Data ↓ Replication (High Availability) ↓ Snapshots (Fast Rollback) ↓ Backups (Disaster Recovery) ↓ Archive (Long-term Retention)
RPO RTO Snapshot Backup Replication WAL 3-2-1 Rule Disaster Recovery

RPO & RTO — The Business Contract

RPO — Recovery Point Objective

"How much data loss is acceptable?"

The maximum age of files that must be recovered from backup storage for normal operations to resume. Lower RPO → more frequent backups or WAL shipping.

Example: RPO = 15 min → max 15 min of data lost

RTO — Recovery Time Objective

"How quickly must the service recover?"

The maximum tolerable length of time that a system can be offline after a failure. Lower RTO → standby infrastructure, automation, fast restore paths.

Example: RTO = 30 min → service back in 30 min

Reducing RPO requires more frequent snapshots, WAL shipping, or continuous replication. Reducing RTO requires automated failover, standby systems, and fast restore paths. Both together drive infrastructure cost.

Snapshot Internals

Modern snapshots are space-efficient using incremental techniques:

Copy-on-Write (CoW)

Original Block ↓ Copy old block first ↓ Write new data in place

Used by: ZFS, Btrfs, LVM

Redirect-on-Write (RoW)

Original Block ↓ Allocate new block ↓ Update metadata pointer

Used by: AWS EBS, NetApp WAFL

Both techniques store only changed blocks, making snapshots incremental and storage-efficient. The snapshot metadata points to unchanged blocks in the original volume.

Backup Types

TypeWhat is Backed UpStorageRestore Speed
FullEverythingLargestFastest
IncrementalChanges since last backupSmallestSlower (chain)
DifferentialChanges since last fullMediumBalanced
ContinuousEvery change via WAL/logsMediumFast + flexible

Continuous backup via WAL shipping provides the lowest RPO (near-zero) since every committed transaction is streamed to the backup location. Used by PostgreSQL, MySQL, and most production databases.

Replication vs Backup — Critical Distinction

FeatureReplicationBackup
TypeLive copyIndependent copy
PurposeHigh AvailabilityDisaster Recovery
Data corruptionPropagates immediatelyPreserves historical state
FailoverFast (seconds)Slow (hours)
RetentionCurrent state onlyHistorical versions

Replication does NOT replace backups. If corrupted data is replicated, every replica becomes corrupted too. A backup is the final line of defense for data recovery.

The 3-2-1 Backup Rule

3 Copies of Data ↓ 2 Different Storage Media ↓ 1 Copy Offsite (or air-gapped)

Example:

  • Production database (primary)
  • Local NVMe snapshot
  • Encrypted backup in S3 Glacier (offsite)

Disaster Recovery Flow

Failure Detected ↓ Can Replica Take Over? → YES: Automatic Failover (RTO: seconds) → NO ↓ Restore Latest Snapshot → Clean? → Application Online (RTO: minutes) → Corrupted ↓ Restore Backup + Replay WAL → Application Online (RTO: hours) ↓ Post-Incident: Root cause + DR drill review

Real-World Examples

PostgreSQL — Point-in-Time Recovery

Base backup (pg_basebackup) + WAL streaming → continuous backup → Restore: base + replay WAL to any point in time → RPO: near-zero RTO: minutes to hours

AWS EBS — Incremental Snapshots

Volume → Incremental snapshot stored in S3 → Only changed blocks since last snapshot → Fast restore: new EBS volume from snapshot → Cross-region copy for DR

Elasticsearch — Snapshot Repository

Index segments → Incremental snapshot → S3/GCS → Restore: specific indices or entire cluster → ILM manages retention automatically

Kubernetes — Velero

CSI volume snapshots + Kubernetes object backup → Stored in object storage (S3/GCS/Azure Blob) → Restore full cluster or namespaces selectively

  • What RTO is contractually guaranteed?
  • Is replication truly sufficient (or do we need backups)?
  • How are backups validated after creation?
  • Are backups immutable (ransomware-proof)?
  • Are backups encrypted at rest and in transit?
  • Can we restore in another region?
  • When did we last run a DR drill?

Production Failure Scenarios

Snapshot Lost

Cause: Storage array failure  ·  Fix: Maintain independent offsite backups; never rely on snapshots alone

Data Corruption Propagated

Cause: Application bug replicated to all replicas immediately  ·  Fix: Restore from immutable backup or replay WAL to pre-corruption point

Slow Disaster Recovery

Cause: No snapshots; relying solely on large full backup restore  ·  Fix: Use snapshots with incremental WAL backups to reduce RTO

Backup Restore Failure

Cause: Backups never tested; silent corruption or format changes  ·  Fix: Run regular automated restore drills; verify checksums

Ransomware Attack

Cause: All production and backup data encrypted by attacker  ·  Fix: Immutable, air-gapped, offsite backups (S3 Object Lock, WORM)

Production Readiness Checklist

  1. Define business RPO and RTO per service
  2. Automate snapshot schedules (no manual steps)
  3. Maintain encrypted, offsite backups
  4. Use immutable backup storage (S3 Object Lock)
  5. Replicate critical workloads for HA
  6. Monitor backup job success/failure with alerts
  7. Perform regular automated restore drills
  8. Review and enforce retention policies
  9. Validate backup integrity via checksums
  10. Document and rehearse disaster recovery procedures

Key Takeaways

RPO = max acceptable data loss RTO = max acceptable downtime → These two metrics drive every DR design decision. Snapshot = fast rollback (same storage, minutes) Backup = DR (offsite, hours) Replication = HA (live copy, seconds) Archive = compliance (cold, days) Replication ≠ Backup: Corruption propagates to all replicas. Backup is the final defense. Backup types: Full → simplest restore, largest storage Incremental → smallest, slower restore chain Differential→ balanced Continuous → WAL-based, lowest RPO 3-2-1 Rule: 3 copies · 2 media · 1 offsite Production must-haves: Immutable backups (ransomware proof) Encrypted at rest + in transit Regular restore drills (not just backups) Automated monitoring of backup jobs
