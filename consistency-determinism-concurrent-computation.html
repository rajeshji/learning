Consistency & Determinism in Concurrent Computation

Staff Engineer Reference — Memory Models, Correctness, Repeatability & Production Design

THE BIG PICTURE
🌍 Two Pillars of Correct Concurrent Systems

Concurrency introduces uncertainty because multiple threads execute independently and their operations may interleave differently on every run. A correct concurrent system must ensure:

CONSISTENCY
1️⃣ Consistency — Valid Shared State at All Times

Consistency means every thread observes a valid and coherent view of shared data, even while multiple threads access or modify it. It preserves invariants — no thread sees partial writes or invalid intermediate state.

// Example: Bank account — two concurrent operations balance = 100 Thread A: withdraw(50) → balance = balance - 50 Thread B: deposit(20) → balance = balance + 20 WITHOUT synchronization — possible races: Both read balance=100 → A writes 50, B writes 120 → LOST UPDATE Final: 120 ❌ (B's deposit overwrote A's withdrawal) WITH synchronization: A reads 100, writes 50; B reads 50, writes 70 Final: 70 ✅ (100 - 50 + 20 = 70)

DETERMINISM
2️⃣ Determinism — Same Input, Same Output, Always

Determinism means: same input → same logical output regardless of thread scheduling or execution timing. The execution order may differ, but the observable result must remain identical.

// NON-DETERMINISTIC — result depends on scheduling: int counter = 0; Thread A: counter++; // may execute first or second Thread B: counter++; // interleaving determines final value Possible results: counter=1 (lost update) or counter=2 (correct) → Non-deterministic — different result each run ❌ // DETERMINISTIC — result is always correct regardless of order: AtomicInteger counter = new AtomicInteger(0); Thread A: counter.incrementAndGet(); // CAS — always atomic Thread B: counter.incrementAndGet(); // CAS — always atomic Result: always 2 ✅ — regardless of which thread runs first

Staff principle: Choose the weakest consistency and determinism guarantees that still satisfy your business requirements. Paying for sequential consistency on a metrics counter is waste; paying for eventual consistency on a payment system is a bug.
PRODUCTION FAILURES
Common Failure Modes
Lost Update — Consistency Violation

Cause: Two threads read same value, both compute new value, last write wins — first write is lost. Fix: Atomic CAS (compareAndSet) or database-level optimistic locking with version check.

Duplicate Payment — Determinism Violation

Cause: Retry without idempotency — network timeout causes client to retry, payment charged twice. Fix: Idempotency key (UUID per request stored server-side); second call with same key returns first result.

Out-of-Order Messages — Determinism Violation

Cause: Parallel processing consumers on same topic without partition key — messages arrive out of order. Fix: Partition by entity key (user ID, order ID) → single consumer per partition → ordered delivery guaranteed.

Stale Cache — Consistency Violation

Cause: Cache not invalidated after DB write — readers see old data. Fix: Write-through cache (update cache + DB atomically), versioned cache keys, or cache-aside with TTL.

STAFF ENGINEER THINKING
Questions Staff Engineers Ask

About Consistency

  • Is shared state mutable?
  • Who owns the data — which service/thread?
  • Are concurrent writes possible?
  • What consistency level is required?
  • Can eventual consistency be accepted here?

About Determinism

  • Can retries occur (network failures)?
  • Can events arrive out of order?
  • Are operations idempotent?
  • Will same request always produce same result?
  • Can execution timing change the outcome?
Production Readiness Checklist
  • ✅ Identify all shared mutable state
  • ✅ Choose the required consistency model (strong vs eventual)
  • ✅ Eliminate data races using synchronization or immutability
  • ✅ Use atomic operations where a single variable needs protection
  • ✅ Ensure all retryable operations are idempotent
  • ✅ Maintain deterministic ordering for critical workflows (payments, messaging)
  • ✅ Test under high concurrency and across different scheduling scenarios
  • ✅ Validate behavior on both x86 and ARM (different memory models)
  • ✅ Monitor contention, retry rates, and stale read frequency
"Consistency guarantees that all threads or services observe a coherent and valid state of shared data, while determinism guarantees that identical inputs always produce the same logical outcome regardless of scheduling, retries, or execution timing. I use synchronization primitives and memory ordering for consistency, and combine idempotency, ordered event processing, and immutable data for determinism. The right design balances consistency, determinism, throughput, and scalability according to business needs."
KEY TAKEAWAYS
What to Remember
  • Consistency ensures that shared state remains correct and coherent, even when multiple threads or services access it concurrently — no partial writes, no invalid intermediates.
  • Determinism ensures that the same input always produces the same logical result, regardless of thread scheduling, retries, or execution timing.
  • Use locks, atomic operations, memory fences, and well-defined memory models to maintain consistency in concurrent programs.
  • Use idempotent operations, ordered event processing, immutable data, and message passing to preserve deterministic behavior in distributed and concurrent systems.
  • Staff Engineers deliberately balance correctness, performance, scalability, and operational complexity, selecting the weakest guarantees that still satisfy business requirements.

Consistency & Determinism — Code & Systems Reference

Sequential Consistency vs Acquire-Release — Code

// Sequential Consistency (Java volatile / C++ seq_cst): // All operations appear in a single global total order // Every thread agrees on the same interleaving // Java volatile — sequentially consistent: volatile boolean flag = false; volatile int data = 0; // Thread 1: data = 42; // visible before flag flag = true; // volatile write = full fence // Thread 2: if (flag) { // volatile read assert data == 42; // ALWAYS guaranteed ✅ } // C++ seq_cst (default atomic): std::atomic<bool> flag{false}; std::atomic<int> data{0}; data.store(42, std::memory_order_seq_cst); flag.store(true, std::memory_order_seq_cst); // CHEAPER — Acquire/Release (correct but not seq_cst): data.store(42, std::memory_order_relaxed); // no fence flag.store(true, std::memory_order_release); // release fence // Thread 2: while (!flag.load(std::memory_order_acquire));// acquire fence int v = data.load(std::memory_order_relaxed); // guaranteed: 42 ✅ // Acquire-release is correct AND cheaper than seq_cst on ARM

Idempotency — Determinism in Distributed Systems

// Idempotency key pattern — payments, APIs, Kafka consumers // Client generates UUID per logical operation: String idempotencyKey = UUID.randomUUID().toString(); // First call: POST /payments X-Idempotency-Key: abc-123-def { amount: 100, currency: USD } → Server: check idempotency_keys table for abc-123-def Not found → process payment → store (abc-123-def, result) Response: { status: SUCCESS, payment_id: p_001 } // Retry (network timeout): POST /payments X-Idempotency-Key: abc-123-def ← same key { amount: 100, currency: USD } → Server: check idempotency_keys table for abc-123-def FOUND → return stored result immediately Response: { status: SUCCESS, payment_id: p_001 } ← same result ✅ // Payment charged ONCE regardless of retry count → DETERMINISTIC // Implementation: CREATE TABLE idempotency_keys ( key VARCHAR(36) PRIMARY KEY, result JSONB, created_at TIMESTAMP DEFAULT NOW(), expires_at TIMESTAMP -- clean up after 24h );

Kafka — Ordered Deterministic Event Processing

// Kafka guarantees ORDER within a partition // Key insight: same key → same partition → ordered processing // Ordering by user_id ensures deterministic state machine: producer.send(new ProducerRecord<>( "orders", user_id, // partition key — same user always same partition orderEvent // value )); // Consumer processes events for one user in order: // CREATED → PAYMENT_CONFIRMED → SHIPPED → DELIVERED // Never in wrong order within a partition ✅ // Exactly-once semantics (Kafka 0.11+): producer.initTransactions(); try { producer.beginTransaction(); producer.send(record); consumer.commitSync(offsets); // commit offset atomically with produce producer.commitTransaction(); } catch (Exception e) { producer.abortTransaction(); // rollback both produce + offset } // Exactly-once = consistent offsets + deterministic processing

MVCC — Snapshot Isolation for Consistent Reads

// MVCC (Multi-Version Concurrency Control) in PostgreSQL: // Readers never block writers; writers never block readers // Each transaction sees a snapshot of the DB at its start time -- Transaction 1 starts at T=100 BEGIN; SELECT balance FROM accounts WHERE id=1; -- sees balance at T=100 -- Meanwhile, Transaction 2 commits at T=101: UPDATE accounts SET balance = balance - 50 WHERE id=1; COMMIT; -- Transaction 1 still sees the OLD balance (T=100 snapshot): SELECT balance FROM accounts WHERE id=1; -- still old value! -- No locks, no blocking — snapshot isolation ✅ -- Read Committed (PostgreSQL default): each statement sees latest committed -- Repeatable Read: transaction sees snapshot from its own start -- Serializable: full isolation, as if transactions ran serially -- MVCC implementation: -- Each row has xmin (created by txn) and xmax (deleted by txn) -- Readers skip rows where xmax is committed before their snapshot
"Consistency and determinism are orthogonal properties. A system can be consistent but non-deterministic (shared state is always valid, but results vary across runs), or deterministic but inconsistent (results are repeatable but shared state can be corrupted). Staff Engineers ensure both: consistency through synchronization and memory ordering, determinism through idempotency, ordered processing, and isolation."
