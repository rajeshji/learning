Final Interview Cheat Model — 5 Buckets

Network failures = 1. Can't connect → partition / DNS 2. Too slow → latency / timeout 3. Unreliable → packet loss 4. Wrong routing → LB issues 5. Retry storm → cascading amplification

In any design, say: "Let me consider network failures: partition, latency/timeouts, retry storms, routing issues." That is enough to show strong system design thinking.

Staff Pattern — Use Every Time

Detect → Mitigate → Prevent

1. Network Partition

Detect via heartbeat failures / timeouts
→ isolate partitioned nodes (read-only or stop writes)
→ rely on quorum / leader election for consistency
→ reconcile data after partition heals

2. High Latency / Slow Network

Detect via latency metrics (P95 / P99)
→ apply timeouts + retries with backoff
→ reduce synchronous calls, use async processing
→ cache responses to avoid repeated calls

3. Packet Loss / Unreliable Network

Detect via error rate / retry rate increase
→ retry with exponential backoff
→ use idempotent APIs to avoid duplicate side effects
→ reduce payload size or switch protocol if needed

4. Connection Timeout

Detect via timeout metrics
→ set proper client-side timeouts
→ retry with backoff and cap max retries
→ fail fast — don't wait indefinitely

5. Retry Storm (Cascading)

Detect via spike in retry traffic / queue buildup
→ apply circuit breaker to halt retries
→ rate limit incoming requests
→ add jitter to retries to break synchronisation

6. DNS Failure

Detect via DNS resolution errors / failed lookups
→ use DNS caching on client side (TTL tuning)
→ fallback to cached or secondary endpoints
→ configure multiple DNS providers for critical paths

7. Load Balancer / Routing Failure

Detect via uneven traffic / node-level error rates
→ remove unhealthy instances via health checks
→ use failover LB or reroute traffic automatically
→ validate routing rules before every deployment

8. TLS / Handshake Failure

Detect via handshake error logs / connection failures
→ retry the connection with backoff
→ monitor certificate expiry proactively (alert at 30d)
→ automate cert rotation (cert-manager / ACM)

9. Downstream Service Unreachable

Detect via dependency health checks / error spikes
→ apply circuit breaker — stop calling unhealthy service
→ fallback to cached or default response
→ retry with backoff when service recovers

5 Core Network Mitigation Patterns — Everything Maps Here

1. Retry → handle transient failures 2. Timeout → avoid waiting forever 3. Circuit Breaker → stop calling failing services 4. Cache/Fallback → serve something when down 5. Load Balance → route around failure

Staff-Level One-Liner

"I would detect it via latency and error metrics, apply timeouts and retries with backoff for transient issues, use circuit breakers to prevent cascading failures, and fallback to cached responses where possible."

Ultra-Compact Playbook — If You Forget Everything

1. Detect via latency / errors / timeouts 2. Retry with backoff (transient failures) 3. Timeout + fail fast (don't block threads) 4. Circuit breaker (persistent failures) 5. Fallback to cache / default response

Final Design Assumption

Design every service assuming: the network is slow, unreliable, and can fail at any time.
If you build with that assumption, every mitigation pattern above follows naturally.
