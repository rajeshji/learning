Deployment Failure Scenarios

Staff-level · 10 categories · 40 scenarios · detect / mitigate / prevent / cascading / trade-off

Why Deployment Failures Are the Most Common Real-World Outage Cause

Deployments modify: code + infra + config + schema + routing + dependencies Even a healthy system can fail instantly after deployment 10 root failure classes: availability | performance regression | partial deployment | schema migration traffic shifting | config/secrets | CI/CD pipeline | distributed deploy | observability | multi-region

1 — Deployment Availability Failures
Deployment Causes Service CrashMust Know Bad binary, runtime error, or missing config causes new pods/instances to crash-loop CrashLoopBackOff, restart spike, error rate goes to 100% Rollback deployment immediately to last stable version Canary deployments, smoke tests on first instance before fleet rollout Full service outage if all instances updated before crash detected Canary rollout slows deployment velocity significantly
Pods Fail To StartMust Know Missing env var, unavailable dependency, or wrong image tag on startup Startup failure logs, ImagePullBackOff, pod stuck in Pending/Init Rollback, inject missing config, fix image reference Pre-deployment validation (config linting, image existence check) Capacity reduction — no new instances launch, old ones drain away Pre-deploy validation adds CI pipeline steps and time
Health Check Failure After Deploy New version starts but fails readiness/liveness probe — not ready to serve Readiness probe failures, instance never joins load balancer Remove unhealthy instances from LB, rollback Progressive rollout with readiness gate before proceeding Traffic routed to remaining old instances — overload if too few remain Stricter readiness checks slow time-to-serve for each new instance
Rolling Deployment Capacity Drop Too many instances replaced simultaneously — available capacity drops below load Traffic saturation on remaining instances, error rate rising during rollout Pause rollout, scale up old version to handle load Controlled rollout concurrency (maxUnavailable ≤ 25%), pre-scale before rollout System overload → cascading timeouts on all remaining healthy instances Conservative concurrency (slow rollout) extends deployment windows
2 — Performance and Resource Regression Failures
CPU RegressionMust Know New code is computationally expensive — CPU spikes across the fleet after deploy CPU metric spike correlated with deployment timestamp Rollback, or horizontal scale-out as temporary relief Performance benchmarking in CI, CPU regression detection on canary Autoscaling storm → compute bill explosion + scaling lag causing timeouts Performance benchmarking adds significant CI time per build
Memory Leak After DeploymentMust Know New code introduces memory leak — heap grows steadily until OOM kill Heap growth trend post-deploy, OOM kills, pod restarts increasing over time Restart pods to reset heap, rollback while investigating Memory profiling in staging, heap growth canary detection Crash loops across fleet — all instances OOM simultaneously after hours Memory profiling adds staging overhead; leak may only appear under prod load
Latency RegressionMust Know New code introduces slow path — P99 latency spikes after deployment P95/P99 latency spike correlated with deployment, user complaints Rollback, apply circuit breaker to affected endpoints Benchmark testing in CI, latency canary gate before fleet rollout Retry storm — high latency causes clients to retry → amplifies load further Latency gates slow release cadence and require stable staging load
Thread Pool Exhaustion New code introduces blocking calls — threads park on IO, pool fills Request queue growth, thread pool saturation metric spike Scale out, restart instances, rollback Load testing with concurrency, async IO review in code review Timeout cascade — all APIs slow as threads are unavailable for new requests Async IO review adds code review time; load testing requires realistic traffic shape
3 — Partial Deployment and Version Incompatibility Failures
Mixed-Version IncompatibilityMust Know Old and new version services with incompatible APIs running simultaneously Serialization errors, 400/500 spikes from service-to-service calls Rollback newer version to restore single version Backward-compatible changes only during rollout, consumer-driven contract testing Cross-service failures — every call between old→new or new→old fails Backward compatibility slows API evolution and adds maintenance overhead
Partial Deployment StateMust Know Rollout interrupted — fleet split between old and new version indefinitely Some nodes behaving differently, inconsistent responses for same request Complete rollout or rollback to single version Atomic deployment orchestration with all-or-nothing guarantee Inconsistent user experience — same user hits different behaviour on each request All-or-nothing deploys lose the safety of gradual rollout
API Contract MismatchMust Know Request/response schema changed without coordination — consumers break Deserialization failures, unexpected null fields, 400 error spikes Apply API version fallback, serve old schema from new version Consumer-driven contract testing (Pact), API versioning, schema registry All downstream services fail — every consumer of the changed API breaks Contract testing requires both producer and consumer teams to participate
Client-Server Compatibility Failure Old mobile/web clients hit new server API — existing clients see errors Old client user agent error spike, increased 4xx for specific client versions API version fallback, restore old endpoint alongside new Backward-compatible APIs, deprecation warnings well ahead of removal Mobile/web app breakage at scale — all users with old app version affected Multi-version API support increases server-side complexity and maintenance cost
4 — Database and Schema Migration Failures
Breaking Schema MigrationMust Know New schema incompatible with old code — old code cannot read/write new schema Query failures, column not found errors, DB error spike after migration Rollback schema, apply emergency compatibility patch Expand-contract pattern — add column/table first, migrate data, then remove old Global service outage — all instances using DB fail immediately Expand-contract migrations are multi-step and span multiple deployment cycles
Long-Running Migration LockMust Know Large ALTER TABLE blocks all concurrent reads/writes for duration of migration DB lock wait spike, all queries timing out, connection pool exhaustion Kill migration, use online schema change tool (pt-online-schema-change, gh-ost) Online schema change tools, never ALTER TABLE on large tables in production DB-wide slowdown — all services sharing the DB timeout simultaneously Online schema change tools add operational complexity and take longer
Partial Data Migration Migration interrupted mid-run — some rows migrated, some not Missing or inconsistent data, business logic behaves differently per row Resume or rollback migration, reconcile affected data Idempotent migrations with row-level progress tracking Corrupted business state — some records in old format, some in new Idempotent migration design is significantly more complex to implement
Rollback Impossible After Schema Change Destructive schema change (column drop) — rollback code would fail without that column Rollback attempt fails with schema error Emergency compatibility patch in code, restore from backup in worst case Never drop columns/tables before all code references removed (expand-contract) Prolonged outage — cannot roll back, must fix forward under pressure Two-phase schema changes take multiple deployment cycles
5 — Traffic Shifting and Routing Failures
Canary Deployment FailureMust Know Canary version unhealthy but analysis gates not catching it fast enough Error rate spike on canary instances, user complaints from canary cohort Abort canary, route all traffic back to stable version Strict canary error/latency gates before promotion, small canary percentage (1-5%) Partial user outage — canary traffic segment experiences degraded service Small canary % means longer validation time before fleet-wide rollout
Blue-Green Switch FailureMust Know Traffic cutover from blue to green fails or green is unhealthy at switch time Sudden error spike immediately after traffic cut, green health checks failing Revert traffic to blue immediately Health check green thoroughly before cutover, staged switching by user segment Global downtime — all traffic briefly to unhealthy green before revert Blue-green requires double infrastructure during deployment window
Traffic Blackholing After DeployMust Know Wrong routing rule deployed — requests silently dropped or misrouted Timeout spike on client side with no errors on server side (silent drop) Restore correct routing rules, rollback route change Route validation in CI, synthetic probes from client perspective after deploy Retry storm — clients retry silently dropped requests → amplification More routing validation adds deploy time; client-perspective probes need infra
Uneven Traffic Distribution LB misconfiguration after deploy — traffic concentrated on subset of instances Hot instances at 100% CPU, others idle, uneven request metrics Rebalance traffic, fix LB weights LB config testing in staging, gradual traffic shift with distribution monitoring Partial overload — hot instances fail → traffic concentrates further Complex LB config testing requires realistic traffic simulation
6 — Configuration and Secret Deployment Failures
Bad Configuration DeploymentMust Know Wrong timeout, retry count, endpoint URL, or feature flag pushed to production Traffic anomalies, error rate change, unexpected behaviour immediately after config push Rollback config immediately, restore known-good config Config validation in CI, canary config rollout, config schema enforcement System-wide instability — wrong timeouts cause retry storms or silent failures Config validation adds complexity; too strict blocks legitimate emergency config changes
Secret / Key Rotation FailureMust Know New key deployed without overlap period — old key still used by some services Auth failures, decryption errors, services using old key rejected Dual-key support — accept both old and new key during transition Graceful key rotation with overlap window, automated rotation testing Global auth failures — all services still using old key cannot authenticate Dual-key overlap period means old (possibly compromised) key still valid temporarily
Missing Environment Variables Config not injected into new deployment — service starts with missing required vars Startup failures, service crashes on first config access, panic on nil pointer Inject missing vars, restart pods Config templates, startup validation that asserts all required vars present Deployment blocked — no new instances start, old capacity drains Startup config validation delays first request but catches misconfiguration early
Feature Flag Misconfiguration Wrong feature flag state deployed — unintended feature enabled or disabled in prod Unexpected user-visible behaviour, A/B experiment data looks wrong Disable flag immediately, restore previous flag state Flag change review process, canary flag rollout, kill switch for every flag Partial service degradation — affected feature path broken for all users More flag review process slows experimentation velocity
7 — CI/CD Pipeline and Automation Failures
CI Pipeline Failure Blocking DeployMust Know Build, test, or lint failure prevents artifact from being promoted to production Pipeline status red, deployment queue blocked Retry pipeline, investigate test failure, emergency bypass if critical hotfix Reliable CI infra, flake detection for tests, separate slow tests from blocking gates Deployment freeze — no new code can ship, including critical security patches Strict CI gates block critical hotfixes; loose gates let bad code through
Broken Artifact Promotion Wrong artifact version promoted to production — different build than tested Version mismatch between expected and running binary in production Rollback artifact, redeploy correct version Immutable artifact verification (hash check at promotion), artifact provenance Untested code in production — undefined behaviour, security issues possible Artifact hash verification adds pipeline steps and slows promotion
Deployment Script Bug Incorrect automation logic — script deletes wrong resources, misapplies config Unexpected infra changes, services deleted or misconfigured at scale Stop automation, apply manual corrective actions Deployment script testing in staging, dry-run mode, human approval gate Large-scale outage — automation bug can affect entire fleet simultaneously Dry-run mode and approval gates slow automated deployment pipeline
Rollback Automation FailureMust Know Rollback script broken, incompatible state, or wrong version targeted Rollback stuck, partial rollback, or rollback deploys wrong version Manual rollback via kubectl/CLI, escalate to SRE Regular rollback drills, rollback tested in staging, immutable previous artifact Extended outage — cannot automated-rollback, manual process under incident pressure Rollback drills consume engineering time; staging rollback may not match prod
8 — Distributed System Deployment Failures
Distributed Cache Flush on DeployMust Know New deployment invalidates cache (key format change, cold start) — all requests miss Cache hit rate drops to 0%, DB read spike, latency explosion Gradual cache warm-up, limit request rate during warm-up Versioned cache keys, cache warm-up before traffic shift DB overload — every request hits DB simultaneously → DB saturation Versioned cache keys increase cache storage (old and new keys coexist)
Connection Reconnect StormMust Know Large-scale service restart — all connections drop and reconnect simultaneously Connection spike on gateway/LB/DB immediately after deploy Jittered reconnect with exponential backoff Gradual rolling restart, connection keep-alive to avoid reconnect on restart Gateway/LB/DB connection exhaustion — all reconnects compete for slots Gradual rollout extends deployment window; keep-alive adds complexity
Leader Election During Deploy Coordinator/Kafka broker/etcd nodes restarted simultaneously — frequent elections Rapid leadership changes in cluster event log, write instability Wait for cluster stability before proceeding with rollout Staggered deployment of coordination nodes, one-at-a-time restart Cluster instability — writes unavailable during repeated leadership changes One-at-a-time coordinator restart makes deployment take much longer
Partition Rebalance Storm Kafka broker or cluster node restart triggers massive partition reassignment Massive reassignment activity, consumer lag spike, IO saturation Pause rebalance, allow cluster to stabilise Controlled broker rollout (one at a time), sticky partition assignment Cluster processing pause — consumer lag grows, downstream services starve Sticky assignment reduces rebalancing but complicates partition ownership
9 — Observability and Detection Deployment Failures
Missing Monitoring for New VersionMust Know New service/feature deployed without updating dashboards, alerts, or metrics Post-incident: no data available for the new code path Add telemetry and dashboards immediately for new feature Deployment observability checklist, instrumentation as a deploy gate Slow detection — regression in new code path invisible until user reports Observability checklist as a deploy gate slows deployment process
Alert Threshold Drift Post-Deploy New version has different baseline — old alert thresholds fire or miss incorrectly Alert storm immediately post-deploy, or silence when degradation actually occurs Suppress/tune thresholds immediately, apply burn rate alerting Adaptive alerts, SLO-based alerting that adjusts to new baseline automatically Pager fatigue from false alarms, or real incidents missed due to stale threshold Adaptive alerting is more complex; SLO-based alerting requires SLO definition
Rollback Decision Delay Incident unclear — operators unsure if regression is from deployment or other cause Long outage duration, time-to-rollback slow due to uncertainty Manual rollback immediately on any error rate regression post-deploy Clear rollback criteria defined pre-deploy, automated rollback on SLO breach Cascading failure spreads — every minute of delay worsens downstream impact Automated rollback may trigger on transient spikes unrelated to deployment
Log Schema Change Breaks Parsing Log format changed in new version — log parser/dashboard queries fail Dashboard shows no data, log search returns nothing for new version Temporary parser fallback for old format while new queries are updated Versioned log schema, log format changes announced and tested ahead of deploy Reduced observability exactly when needed most — right after the deployment Versioned log schema adds complexity; dual-format parsing adds parser overhead
10 — Multi-Region Deployment Failures
Cross-Region Version DriftMust Know Regions deploy at different times — API incompatibility between regional versions Inconsistent behaviour for same user hitting different regions Sync deployments, route user to consistent region during rollout Global rollout orchestration, session affinity during multi-region rollout Different regional behaviour at scale — some users get new, some get old APIs Synchronised global deploys are slower and more complex to coordinate
Regional Rollout Overload Failover region receives deployment simultaneously — capacity reduced and deployed Saturation spike in secondary region during/after deployment Pause rollout in failover region, restore full capacity first Deployment-aware capacity planning, never deploy to failover during peak Multi-region outage — primary fails and failover is mid-deploy with reduced capacity Avoiding failover deployment windows reduces deployment flexibility
Geo Failover During Active Deployment Region fails mid-rollout — failover region receives mixed-version state Mixed deployment state, inconsistent behaviour after failover Freeze failover, complete or rollback deployment before enabling failover Deployment-aware DR policy — no failover during active deployment window Recovery complexity — failover region has partial new version, partial old Blocking failover during deployment creates a risk window of DR unavailability
Global Config Drift After Deploy Config deployed to primary region, not propagated to all secondary regions Behaviour mismatch between regions, different responses for same request Centralised config sync, force propagation to all regions Immutable config rollout pipeline with mandatory cross-region propagation check Global inconsistency — users routed to different regions see different behaviour Centralised config propagation adds cross-region latency to every config change

10 Must-Know Deployment Failures for Interviews

1. Mixed-version incompatibility → backward-compat APIs + contract testing + canary 2. Breaking schema migration → expand-contract pattern + online schema change tools 3. Cache flush on deploy → versioned cache keys + warm-up before traffic shift 4. Memory/CPU regression → perf benchmarking in CI + canary latency/CPU gate 5. Canary failure → small % (1-5%) + strict error/latency gate + auto-abort 6. Connection reconnect storm → gradual rollout + jittered reconnect + keep-alive 7. Bad config deployment → config validation in CI + canary config + rollback 8. Traffic blackholing → route validation + synthetic probes + client-side monitoring 9. Rollback automation failure → rollback drills + immutable artifacts + tested scripts 10. Rollback impossible (schema) → never drop columns before code removed + expand-contract

Staff-Level Deployment Thinking — 9 Questions to Ask Always

1. Safe rollback possible? → canary + rollback tested + no destructive schema 2. Old/new coexist safely? → backward-compat APIs + contract testing + versioned cache 3. Deploy overloads infra? → reconnect storm + cache flush + rebalance storm prevention 4. Schema change breaks rollback? → expand-contract + never drop before code removed 5. Traffic shifting fails? → canary gate + blue-green revert + route validation 6. Reconnect/cache storm? → gradual rollout + jittered reconnect + warm-up 7. Config drift possible? → config validation + centralised propagation + canary config

Common Deployment Cascading Failure Patterns

Root Deployment FailureCascading Effect
Bad deployment (crash)CrashLoop → capacity drops → remaining instances overload
Breaking schema migrationAll services using DB fail → global outage
Cache flush on deployCache misses → DB read storm → DB saturation → timeouts
Traffic blackholingSilent drops → client retries → amplification storm
Rollback failureCannot revert → must fix forward under incident pressure → extended outage

Final Mental Model — All Deployment Failures Reduce to 4 States

1. New code broken → crash / regression / performance / incompatibility 2. Config broken → wrong config / missing vars / bad secrets / flag misconfig 3. Migration broken → schema lock / partial data / rollback impossible 4. Rollback impossible → schema destructive / automation broken / partial state Most dangerous: successful deployment of broken software rollout appears healthy initially → failure propagates gradually → rollback may become impossible (schema) → cascading failures spread
