Lock-Free & Wait-Free Algorithms

Staff Engineer Reference — Non-Blocking Concurrency, CAS, ABA, Hazard Pointers & Memory Reclamation

THE BIG PICTURE
🌍 The Complete Story

Instead of learning mutexes, CAS, atomic operations, memory ordering, ABA problem, hazard pointers, epoch-based reclamation, lock-free queues, and wait-free algorithms separately, this page explains how modern concurrent systems achieve scalability without blocking, how CPUs enable atomic synchronization, and when Staff Engineers should choose lock-free or wait-free designs.

Traditional synchronization uses locks:

Thread A → Acquire Lock → Critical Section → Release Lock While one thread owns the lock, every other thread WAITS. As CPU cores increase, locks become the scalability bottleneck.

Modern systems use atomic CPU instructions instead:

Multiple Threads → Atomic Operations (CAS / FAA / LL-SC) → No Blocking → High Parallelism

This is the foundation of Lock-Free and Wait-Free algorithms.

LOCK-FREE
Lock-Free Algorithm — How It Works
"At least one thread always completes its operation. Even if another thread pauses or crashes, the system keeps making progress."

Threads compete using CAS. If Thread A's CAS succeeds, Thread B retries. Eventually someone always succeeds — the system never stops.

// Lock-free CAS retry pattern while (true) { int current = atomic.load(acquire); // read current value int desired = compute(current); // calculate new value if (atomic.CAS(current, desired)) { // try atomically break; // SUCCESS — done } // CAS failed — someone else changed it — retry } // Key insight: // Thread A wins CAS → completes // Thread B loses CAS → retries from fresh read // At least ONE thread always makes progress per round
WAIT-FREE
Wait-Free Algorithm — Guaranteed Progress
"Every thread completes within a bounded number of steps — no retries forever, no starvation, every thread eventually succeeds."

Wait-free is harder to implement. Instead of retry loops, algorithms use helping mechanisms where threads help each other complete.

// Wait-Free Counter — simplest example // Each thread writes to its OWN cell — no contention, no retry struct WaitFreeCounter { long cells[MAX_THREADS]; // one cell per thread void increment(int thread_id) { cells[thread_id]++; // always succeeds in O(1) — wait-free! } long sum() { long total = 0; for (int i = 0; i < MAX_THREADS; i++) total += cells[i]; return total; } } // Java equivalent: LongAdder // Every increment finishes immediately — truly wait-free

CAS — Most Important Primitive

// CAS flow: // 1. Read current value from memory // 2. Compare with expected // 3. If equal → write new value atomically → return SUCCESS // 4. If not equal → do nothing → return FAILURE → caller retries bool CAS(int* addr, int expected, int new_val) { atomic { if (*addr == expected) { *addr = new_val; return true; } return false; } } // CAS Retry Loop: int current = read(); do { int desired = current + 1; } while (!CAS(&value, current, desired)); // retry until success
DATA STRUCTURES
Lock-Free Data Structures

Lock-Free Queue (Michael-Scott Queue)

// Producer: CAS on tail // Consumer: CAS on head // Both operate simultaneously — no mutex needed Producer Consumer ↓ ↓ CAS Tail CAS Head ↓ ↓ Queue ←─────────────→ Queue ↓ ↓ Enqueue Dequeue // Java: ConcurrentLinkedQueue uses this algorithm // Multiple producers AND consumers can operate concurrently

Lock-Free Stack (Treiber Stack)

void push(Node* n) { do { n->next = head.load(relaxed); } while (!head.CAS(n->next, n, release, relaxed)); } Node* pop() { Node* old_head; do { old_head = head.load(acquire); if (!old_head) return nullptr; } while (!head.CAS(old_head, old_head->next, release, relaxed)); return old_head; } // Warning: ABA problem — safe memory reclamation required

Sequence Lock (Seqlock) — Linux timekeeping

// Writers increment sequence counter (odd = writing, even = done) // Readers retry if they see an odd sequence // Readers NEVER block — writers use atomic counter, not mutex void write(int val) { seq.fetch_add(1, release); // mark start (odd) data = val; seq.fetch_add(1, release); // mark end (even) } int read() { int s1, val, s2; do { s1 = seq.load(acquire); // read seq if (s1 & 1) continue; // writer active — retry val = data; s2 = seq.load(acquire); } while (s1 != s2); // retry if changed mid-read return val; }
CRITICAL FAILURE MODE
The ABA Problem
⚠️ Most Dangerous Lock-Free Bug

CAS sees same value after A→B→A transition. Although the pointer appears unchanged, the object changed underneath — CAS succeeds incorrectly, corrupting state.

// Lock-Free Stack — ABA Scenario: Initial: head → A → B → C Thread 1 reads head = A (plans to CAS head: A → B) Thread 1 is preempted... Thread 2: pop A → head = B → C Thread 2: pop B → head = C Thread 2: push A → head = A → C ← A is back! Thread 1 resumes: CAS(head, A, B) → SUCCEEDS (head still looks like A) But B was freed! head now points to freed memory → CRASH 💥

MEMORY RECLAMATION
Safe Memory Reclamation

Removing a node is easy. Freeing it safely is hard — another thread may still be reading it.

Hazard Pointers

// Each thread publishes which node it's currently reading // Deleter checks all hazard pointers before freeing Thread A: hp[A] = node; // announce "I'm reading node" use(node); hp[A] = nullptr; // done with node Thread B: retired.add(node); // wants to free node for each hp in all_hazard_pointers: if hp == node: skip // Thread A still using it // safe to free only when no hazard pointer references it

Epoch-Based Reclamation (EBR)

// Track time using global epochs (0, 1, 2, ...) // When all threads advance past epoch N, nodes retired in epoch N are safe to free Thread: enter_epoch(current_epoch); use(node); exit_epoch(); Garbage Collector: if all_threads.epoch > retired_epoch: free(node); // safe — no thread can see epoch N nodes anymore // Much lower overhead than hazard pointers // Used in: crossbeam-epoch (Rust), Folly, many lock-free libraries

Read-Copy-Update (RCU) — Linux Kernel

// Writers create new version, atomically swap pointer, then wait for readers // Readers: always see consistent version, NEVER block Reader: Writer: rcu_read_lock(); new_val = copy(old_val); ptr = rcu_dereference(p); modify(new_val); use(ptr); rcu_assign_pointer(p, new_val); rcu_read_unlock(); synchronize_rcu(); // wait for readers free(old_val); // Linux uses RCU for: routing tables, network stacks, task lists // Readers have ZERO overhead — no lock, no atomic, just a read barrier

PRODUCTION FAILURES
Common Failure Modes
High CPU Usage — CAS Retry Storms

Cause: Many threads hammering the same atomic under heavy contention — CAS loops spin 100% CPU without progress. Fix: Shard the data, use per-thread counters, exponential backoff, or switch to LongAdder.

Memory Corruption — ABA Problem

Cause: Pointer reuse without version tracking. CAS succeeds on a recycled pointer that now points to different data. Fix: Tagged pointers or hazard pointers.

Memory Leak — Epoch Never Advances

Cause: A stalled thread holds an epoch reference, preventing garbage collection of retired nodes. Fix: Detect stalled threads, timeout and force quiescent states.

Cache-Line Bouncing

Cause: Many threads CAS the same 64-byte cache line repeatedly — triggers MESI RFO broadcast storms. Fix: Partition ownership, reduce shared writes, use per-core data with periodic aggregation.

Production Readiness Checklist
  • Measure actual lock contention before going lock-free
  • Verify atomic operations are supported on all target architectures
  • Choose the correct memory ordering (don't default to seq_cst everywhere)
  • Handle the ABA problem — use stamped references or hazard pointers
  • Select a safe memory reclamation strategy (EBR, hazard pointers, or RCU)
  • Benchmark under realistic high-contention load
  • Monitor CAS retry counts in production (metric: retry rate)
  • Minimize shared cache-line updates — pad structs to 64 bytes
  • Stress test with 2×, 4×, 8× expected CPU core count
  • Prefer simpler locking unless scalability truly requires lock-free

Wait-free algorithms provide the strongest guarantee: every thread completes in bounded steps. Correct lock-free code requires proper memory ordering, safe memory reclamation, and protection against the ABA problem."
KEY TAKEAWAYS
What to Remember
  • Lock-free algorithms eliminate blocking by replacing mutexes with atomic CPU instructions such as CAS — at least one thread always makes progress, improving throughput and reducing context-switch overhead.
  • Wait-free algorithms provide the strongest progress guarantee — every thread completes within a bounded number of steps, ideal for real-time and latency-critical systems where starvation is unacceptable.
  • Correct lock-free implementations require more than atomic instructions — they depend on proper memory ordering, safe memory reclamation, and protection against the ABA problem.
  • Modern systems use Hazard Pointers, Epoch-Based Reclamation (EBR), and Read-Copy-Update (RCU) to safely reclaim memory without blocking concurrent readers or writers.
  • Staff Engineers choose between locks, lock-free, and wait-free designs by balancing complexity, scalability, fairness, latency requirements, contention levels, cache behavior, and maintainability — always measuring contention before introducing advanced non-blocking algorithms.
ORIGINAL NOTES — DEFINITIONS & GUARANTEES
Progress Guarantee Taxonomy
// 4 Progress Guarantee Levels (weakest → strongest): 1. BLOCKING (Lock-based) - Thread may wait indefinitely (OS sleep/wake) - Deadlock possible if lock ordering violated - Priority inversion possible - Use when: simple logic, low contention, code clarity matters 2. OBSTRUCTION-FREE - Thread progresses when it runs alone (no contention) - May livelock under concurrent access - Rarely used in practice 3. LOCK-FREE - System-wide: at least one thread always completes - CAS retry loops: fast-path succeeds, others retry - No deadlock, no blocking, but starvation theoretically possible - Use when: high throughput, concurrent queues/stacks 4. WAIT-FREE - Per-thread: every thread completes in bounded steps - No retries, no starvation, deterministic latency - Much harder to implement - Use when: real-time systems, strict latency SLAs
Atomic Operations Reference
// CAS — Compare-And-Swap (most important) // x86: LOCK CMPXCHG | ARM: LDREX/STREX loop bool CAS(T* addr, T expected, T desired) { if (*addr == expected) { *addr = desired; return true; } return false; } // FAA — Fetch-And-Add (atomic increment) // x86: LOCK XADD | ARM: LDADD (ARMv8.1) T FAA(T* addr, T delta) { T old = *addr; *addr += delta; return old; } // LL/SC — Load-Linked / Store-Conditional (ARM native) // LDREX = load + tag address // STREX = store only if no other write since LDREX // Naturally avoids ABA: any write (even A→B→A) causes STREX failure // x86 vs ARM: // x86 CAS is single instruction → simpler but ABA vulnerable // ARM LL/SC is loop → naturally ABA-safe
Lock-Free Queue — Michael-Scott Algorithm
// Both head and tail are atomic pointers // Enqueue: CAS on tail // Dequeue: CAS on head // Multiple producers AND consumers can operate simultaneously struct Node { T data; atomic<Node*> next{nullptr}; }; atomic<Node*> head{new Node{}}; // sentinel atomic<Node*> tail{head.load()}; void enqueue(T val) { Node* n = new Node{val}; Node* last; do { last = tail.load(acquire); Node* next = last->next.load(acquire); if (next != nullptr) { // tail is behind — advance it tail.CAS(last, next, release, relaxed); continue; } } while (!last->next.CAS(nullptr, n, release, relaxed)); tail.CAS(last, n, release, relaxed); // advance tail } T dequeue() { Node *head_node, *next; do { head_node = head.load(acquire); next = head_node->next.load(acquire); if (!next) return EMPTY; } while (!head.CAS(head_node, next, release, relaxed)); T val = next->data; // reclaim head_node safely (hazard pointer or EBR) return val; }
Memory Reclamation — Full Reference
// HAZARD POINTERS // Per-thread pointer array. Thread announces which nodes it reads. // Deleter scans all hazard pointers before freeing. // Cost: O(N*P) scan per retirement (N=nodes, P=threads) // EPOCH-BASED RECLAMATION (EBR) // Global epoch counter (0, 1, 2...) // Thread enters epoch → reads freely → exits epoch // When all threads exit epoch N, all nodes retired in N are freed // Cost: very low — just atomic epoch read/write // Limitation: stalled threads block reclamation // READ-COPY-UPDATE (RCU) // Read path: rcu_read_lock() → rcu_dereference() → rcu_read_unlock() // Write path: copy, modify, rcu_assign_pointer(), synchronize_rcu() // synchronize_rcu() waits until all current RCU readers complete // Readers: ZERO overhead (just read barrier on some archs) // Used in Linux kernel for: routing tables, task lists, network stack // GARBAGE COLLECTION (managed languages) // Java/Go: GC handles reclamation — lock-free structures safe by default // Tradeoff: GC pauses, higher memory usage // ConcurrentLinkedQueue in Java uses GC for reclamation
ABA Problem — Detailed
// THE PROBLEM: // Stack: A → B → C // Thread 1: reads head=A, about to CAS A→B // Thread 2: pops A, pops B, pushes A back → Stack: A → C // Thread 1: CAS(head, A, B) → SUCCEEDS (head==A) // head = B (freed!) → use-after-free → CRASH // SOLUTION 1: Stamped Reference (Java: AtomicStampedReference) struct StampedPtr { Node* ptr; int stamp; }; atomic<StampedPtr> head; void push(Node* n) { StampedPtr old_head; do { old_head = head.load(acquire); n->next = old_head.ptr; } while (!head.CAS(old_head, {n, old_head.stamp + 1})); } // Thread 2 pushes A with stamp=2 // Thread 1's CAS on (A, stamp=1) FAILS correctly ✅ // SOLUTION 2: 128-bit CAS (x86_64 CMPXCHG16B) // Pack (pointer 64-bit + counter 64-bit) → CAS atomically // Eliminates ABA: counter always increases // SOLUTION 3: LL/SC (ARM) // Any write to address between LDREX and STREX fails STREX // A→B→A triggers failure even though value looks same
