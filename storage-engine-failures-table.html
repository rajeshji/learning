Storage Engine Failure Scenarios

Staff-level · 9 categories · 36 scenarios · detect / mitigate / prevent / cascading / trade-off

Failure Scenario When It Occurs How To Detect How To Mitigate How To Prevent Cascading Failure Risk Trade-off
1 — Write Path Failures
WAL FailureMust Know WAL disk corruption or crash before memtable flush — write-ahead log unreadable WAL replay errors on startup, missing committed records after recovery Restore from replica or backup, replay from last clean checkpoint Replicated WAL, WAL checksums, RAID on WAL disk Data loss risk — all writes since last checkpoint may be irrecoverable Replicated WAL doubles write IO; checksums add per-write CPU overhead
Write StallMust Know Memtable full and flush/compaction cannot keep up — engine stops accepting writes Write latency spike, "write stall" event in engine logs Apply backpressure to producers, throttle write rate Better compaction tuning, faster flush, write rate limiting upstream Queue buildup upstream → buffer overflow → producer data loss Tighter write rate limits reduce throughput headroom
Partial / Torn WriteMust Know Power loss or crash during multi-sector write — only part of page written Checksum mismatch on page read, data corruption error on recovery Replay WAL to reconstruct page, restore from replica Atomic page writes (double-write buffer in InnoDB), WAL for all mutations Corrupted page silently served — downstream queries return wrong data Double-write buffer adds 2× write IO for every dirty page flush
fsync Latency Explosion Slow SSD or overloaded IO scheduler — fsync blocks commit for hundreds of ms Commit latency P99 spike, transaction throughput drop Batch commits (group commit), reduce fsync frequency for non-critical paths NVMe SSD, separate WAL disk, group commit design Transaction backlog → client timeouts → upstream retry storm Group commit increases commit latency for individual transactions
2 — Read Path Failures
Read Amplification ExplosionMust Know LSM-tree has too many SSTables — each read must check many levels before finding data Read latency spike, high IO despite small result set, many SSTable reads per query Trigger major compaction to merge SSTables Better compaction strategy (leveled vs tiered), bloom filters per SSTable Cache miss storms — read amplification overwhelms disk IO budget Leveled compaction reduces read amplification but increases write amplification
Cache Miss StormMust Know Working set larger than buffer pool — every read goes to disk Cache hit ratio drops, disk IO 100%, read latency explosion Warm cache from replica, limit concurrent read rate Sufficient buffer pool sizing (working set fits in RAM), tiered storage Disk IO saturation — all queries slow simultaneously, service unavailable Larger buffer pool reduces available RAM for other processes
Corrupted Read Path Bit rot or write corruption — block returns wrong data silently or with error Checksum failure on block read, unexpected data in query results Read from replica, rebuild from backup, run storage scrub End-to-end checksums on every block, regular scrubbing Incorrect query results served silently — corrupt data propagates to application Per-block checksum adds CPU overhead and slightly increases IO size
Range Scan Slowdown Fragmented SSTables — range scan must read many non-contiguous files Range query latency spike while point lookups remain fast Trigger compaction to defragment SSTables for affected key range Better data organisation, consider B-tree engine for range-heavy workloads API latency increase for all range-based queries — secondary index scans too Frequent compaction for locality reduces write throughput
3 — WAL and Recovery Failures
WAL CorruptionMust Know Disk bit flip or incomplete write corrupts WAL records Recovery replay failure on startup, CRC mismatch in WAL segment Restore from replica WAL, rebuild from last valid checkpoint WAL checksums per record, replicated WAL to separate storage Startup failure — engine cannot start until WAL repaired Per-record checksums add latency to every WAL write operation
Recovery Replay StormMust Know Huge WAL backlog at crash — replaying thousands of records takes hours Long recovery time, node offline for extended period after restart Incremental checkpoints to reduce WAL replay scope Frequent checkpoint snapshots, bounded WAL size Extended downtime — node unavailable for hours, capacity reduced Frequent checkpoints add IO overhead and temporarily increase write latency
Checkpoint CorruptionMust Know Power loss or crash during checkpoint write — checkpoint partially written Recovery detects invalid checkpoint, falls back to older checkpoint Roll back to previous valid checkpoint, replay WAL from that point Atomic checkpoint write (write to temp, then rename), dual checkpoints Data inconsistency — must replay larger WAL window, increasing recovery time Dual checkpoint adds storage overhead and checkpoint write complexity
Double Recovery Replay Crash recovery replays same WAL records twice — idempotency not guaranteed Duplicate records detected, inconsistent state after recovery Deduplicate by sequence number, apply idempotent replay logic Sequence tracking per WAL record, at-most-once apply guarantees Duplicate state — phantom records, double-applied mutations corrupt data Sequence tracking adds metadata overhead per WAL entry
4 — Compaction and GC Failures
Compaction StormMust Know Multiple large compactions triggered simultaneously — disk IO fully consumed Disk IO at 100%, write latency spike, CPU spike on compaction threads Throttle compaction rate, pause lower-priority compactions Compaction scheduling with priority levels, IO rate limiting IO starvation — live read/write requests cannot complete alongside compaction Throttling extends compaction duration — read amplification stays higher longer
Compaction StarvationMust Know Write rate exceeds compaction throughput — SSTables accumulate faster than merged SSTable count growing, read latency increasing over time Increase compaction threads, throttle write rate Write rate limiting, compaction capacity planning for peak write load Read amplification explosion — each read must check ever-more SSTables More compaction threads consume CPU that could serve read/write requests
Space Amplification ExplosionMust Know Old versions accumulate faster than GC/compaction cleans them — disk fills Disk growth faster than data ingestion rate, old SSTable files not deleted Force full compaction, enable more aggressive GC TTL/GC tuning, space amplification monitoring with threshold alerts Disk full — engine stops accepting new writes entirely Aggressive GC increases compaction IO and CPU pressure
Tombstone Explosion Excessive deletes generate many tombstone markers — reads must scan all before finding data Read latency increasing despite small live data set, tombstone warning in logs Trigger compaction to purge tombstones, reduce delete rate Better delete strategy (TTL over explicit deletes), compaction tuning for tombstone GC Query latency explosion — all reads must traverse tombstone sea before finding live data Aggressive tombstone compaction generates extra IO and temporary space usage
5 — Concurrency and Locking Failures
Lock ContentionMust Know Heavy concurrent writes on same row/page — threads queue waiting for locks Lock wait metrics spike, throughput drop while CPU is low Backoff and retry, partition hot rows Better key partitioning, avoid sequential hot keys, use lock-free structures Throughput collapse — all writers serialize on single hot lock More partitioning reduces locality and increases coordination complexity
DeadlockMust Know Transaction A holds lock X waiting for Y; Transaction B holds Y waiting for X Deadlock detection log entry, transaction aborted with deadlock error Abort one transaction, apply consistent global lock ordering Consistent lock ordering across all transactions, deadlock detection with timeout Request hangs if deadlock detection too slow — throughput collapses Deadlock detection adds overhead; global ordering limits concurrency patterns
MVCC Version ExplosionMust Know Long-running transactions prevent old MVCC versions from being garbage-collected Old version accumulation in pg_stat_activity / bloat metrics, storage growing Kill/complete long-running transactions, run VACUUM (Postgres) or equivalent Transaction TTL, regular VACUUM/autovacuum tuning, monitor transaction age Storage bloat → disk full → engine stops accepting writes Aggressive vacuum/GC adds background IO pressure
Latch Contention Engine-internal metadata operations (B-tree splits, buffer pool) serialize on latches CPU spin/wait spike, throughput drops while CPU is high Fine-grained latch partitioning, reduce latch scope Lock-free data structures, partitioned latch design CPU exhaustion from spinning — server hot despite low actual work being done Lock-free structures are significantly more complex to implement correctly
6 — Index and Metadata Failures
Index CorruptionMust Know Crash during index update or bit flip corrupts index B-tree/LSM structure Query mismatch — index returns rows not matching predicate, or missing valid rows Rebuild index from primary data (costly but correct) Index page checksums, validate index against primary data periodically Incorrect query results silently — wrong data returned to all users of that index Index validation adds IO overhead; rebuild is expensive for large tables
Index Rebuild Storm Multiple large index rebuilds triggered — CPU and disk IO saturated CPU and disk IO at 100% during rebuild, query latency spike Incremental index rebuild, throttle rebuild IO rate Online indexing (non-blocking), schedule rebuilds during low-traffic windows Cluster-wide slowdown — index rebuild competes with live query IO Online indexing is more complex and takes longer than offline rebuild
Metadata CorruptionMust Know System catalog or engine metadata tables corrupted — engine cannot map data locations Engine startup failure, "table not found" for existing tables Restore metadata from backup, apply replica metadata Metadata replication to separate storage, atomic metadata writes Entire DB inaccessible — cannot find any data without correct metadata Metadata replication adds coordination overhead and storage cost
Secondary Index Lag Async secondary index update — primary data updated but index not yet reflecting it Missing rows in index-based queries, eventual consistency lag detected Read from primary scan as fallback, rebuild index Synchronous index update (higher write latency) or bounded-staleness index Query inconsistency — queries via secondary index return stale results Synchronous index update adds write latency for every indexed write
7 — Buffer Pool and Memory Failures
Buffer Pool ExhaustionMust Know Working set exceeds buffer pool — all reads miss cache and go to disk Cache hit ratio drops to <50%, disk IO 100%, read latency explodes Increase buffer pool size, limit working set with partitioning Right-size buffer pool to working set, tiered hot/warm storage Disk IO explosion — every read hits disk simultaneously, service collapses Large buffer pool reduces memory available for other processes
Dirty Page Flush Storm Too many modified pages in buffer pool — checkpoint forces massive flush to disk Write latency spike during checkpoint, disk IO spike in bursts Controlled page flushing (InnoDB adaptive flushing), reduce checkpoint interval Better checkpoint tuning, adaptive flushing to spread IO evenly Disk saturation during checkpoint — reads and writes both blocked More frequent controlled flushing adds baseline IO but removes IO spikes
OOM Crash Unbounded memory growth (cache + connections + query memory) — OS kills process OOM kill in kernel log, process crash with no application error Restart engine, reduce per-query memory limits Memory quotas, per-query memory limits, monitor heap growth Recovery storm — all in-flight transactions lost, replica must catch up Strict per-query memory limits may reject complex analytical queries
Eviction Thrashing Working set slightly larger than cache — every page evicted is needed again immediately Cache churn metrics high, IO amplification despite normal query rate Tune eviction policy (LRU vs LFU vs ARC), add cache capacity Better data locality design, partition hot/cold data IO amplification — effective throughput drops as cache does no useful work More cache capacity costs RAM; advanced policies add implementation complexity
8 — Replication and Distributed Engine Failures
Replication Apply LagMust Know Replica engine slower than leader — cannot apply changes at write rate Replica lag metric growing, replication offset falling behind leader Scale replica vertically, batch apply changes for efficiency Parallel replication apply, replica sizing matching leader write throughput Stale reads — queries on replica return old values, inconsistent results Parallel apply adds complexity and may reorder transactions
Out-of-Order Replication Apply Async replay with parallel threads — dependent operations applied in wrong order Sequence mismatch, foreign key violation during apply, inconsistent replica state Replay in dependency order, serialise conflicting operations Ordered replication log, write-set ordering in parallel apply Inconsistent replica state — reads return logically impossible data combinations Strict ordering reduces parallelism benefit of parallel replication
Storage Engine Split BrainMust Know Network partition — both leader and replica think they are the writer Conflicting writes on both sides, version vectors diverge Fence stale leader using fencing tokens, reject writes from old leader Consensus protocol for leadership (Raft/Paxos), unclean leader election off Silent data corruption — two leaders write conflicting data to same keys Strict consensus reduces availability during partition (CA trade-off)
Replica Recovery Overload Replica falls so far behind it must sync full SSTable snapshot — massive transfer Network IO spike, replica unavailable during full sync, disk write surge Throttle snapshot transfer rate, incremental sync where possible Bounded replication lag monitoring, replica restart before lag exceeds snapshot threshold Cluster slowdown — snapshot transfer competes with live replication IO Throttling extends recovery window — replica lags longer before becoming consistent
9 — Storage Engine Scaling Failures
LSM Tree Level ExplosionMust Know Write rate exceeds compaction throughput — SSTables accumulate across many levels SSTable count growing monotonically, read latency increasing over time Add compaction capacity, throttle write rate Write pacing, compaction capacity pre-planned for peak write load Read amplification cascade — each read touches more levels, latency explodes Pre-planned compaction capacity over-provisions CPU/disk at normal load
Shard Hotspot Sequential or monotonic keys cause all new writes to land on one shard/node One engine instance at 100% IO/CPU while others idle Rebalance hot shard, add a local cache in front of hot engine Better shard key (hashed, not sequential), consistent hashing with virtual nodes Localised engine collapse — the hot shard fails, that key range fully unavailable Hashed keys lose range locality — range scans require cross-shard scatter-gather
Metadata Scaling Bottleneck Too many tables, partitions, or files — engine metadata operations become slow Metadata operation latency increasing, engine catalog queries slow Hierarchical metadata, reduce file count via compaction File count monitoring, fewer larger SSTables, compaction keeping file count bounded Cluster instability — metadata slowdown affects all operations across the engine Fewer larger files means coarser compaction granularity
File Descriptor Exhaustion Too many open SSTable files exceed OS file descriptor limit EMFILE errors in engine logs, new connections refused Increase OS fd limit (ulimit), compact SSTables to reduce file count Monitor open fd count, set ulimit well above expected SSTable count Engine instability — cannot open new files for reads or writes Very high fd limits add OS-level resource tracking overhead

LSM-Tree vs B-Tree — Engine Architecture Trade-offs

LSM-Tree (RocksDB, Cassandra, LevelDB): Strength: sequential writes, high write throughput, compresses well Weakness: read amplification, compaction overhead, tombstone explosion Failures: compaction storm, write stall, SSTable explosion, tombstone lag B-Tree (InnoDB, WiredTiger, PostgreSQL): Strength: random reads, range scans, ACID, consistent read performance Weakness: write amplification (page splits), buffer pool dependency, lock contention Failures: buffer pool exhaustion, page fragmentation, lock/latch contention Interview rule: Write-heavy + append → LSM-Tree Read-heavy + ACID + range → B-Tree Both have different dominant failure modes — know which you are designing for

Final Mental Model — All Storage Engine Failures Reduce to 4 States

1. Write path broken → WAL fail / write stall / torn write / fsync latency 2. Read path broken → read amplification / cache miss storm / index corruption 3. Recovery broken → WAL corruption / checkpoint corruption / replay storm 4. Resource exhausted → compaction storm / buffer pool exhaustion / lock contention Most dangerous: silent corruption during recovery or replication corruption propagates to replicas → backups may contain corrupt data → recovery makes corruption permanent → data loss irrecoverable
