Network-Level Failure Scenarios

Staff-level · 7 categories · 32 scenarios · detect / mitigate / prevent / cascading / trade-off

Why Network Failures Are Hardest

Networks are: slow + unreliable + partially failing + asymmetric Unlike server crashes, network failures are often: intermittent → sometimes works, sometimes doesn't partial → A can reach B but B cannot reach A asymmetric → one direction works, other fails silent → no error thrown, just a timeout

2 — Latency and Slow Network Failures
High Network LatencyMust Know Congestion, long routing paths, cross-region calls P95/P99 latency metrics, latency histogram Timeout + retry with backoff, caching Regional routing optimisation, latency budgets Timeouts → retries → overload → full cascade Aggressive timeouts may abort valid slow requests
Packet LossMust Know Congestion, hardware errors, faulty network equipment TCP retransmission spikes, error rate increase Retry with backoff, reduce payload size Traffic shaping/QoS, hardware health checks Retry amplification → retry storm Retries add traffic and latency
Jitter (Latency Variability) Unstable routing, network congestion bursts High latency variance, P99 vs median gap Buffering, hedged requests Better routing paths, stable QoS Real-time / streaming systems destabilised Buffering adds end-to-end delay
Bandwidth SaturationMust Know Traffic exceeds NIC/link capacity, large file transfers Throughput maxed, packet drops, latency spike Throttle traffic, compress payloads, CDN Capacity planning, CDN for static assets Replication lag → replica inconsistency → queue buildup Higher bandwidth capacity costs money
Tail Latency Spikes (P99) Queue buildup, garbage collection, transient congestion P99/P999 latency monitoring, outlier detection Load shedding, hedged requests (backup requests) Distributed load balancing, avoid hot paths Cascading retries from slow responses Hedged requests double traffic on slow paths
3 — Routing and Load Balancing Failures
Load Balancer MisroutingMust Know Bad routing rules, stale backend list, misconfiguration Uneven traffic distribution, error rate on backends Reroute traffic, remove bad backend, rollback config Health checks, config validation in CI/CD Hotspot overload → retry storm on overloaded node More LB routing logic adds complexity
Traffic Blackholing Router silently drops traffic — no RST, no response Requests time out with no error response Alternate routing path, failover Redundant routing, route monitoring Services appear completely down — cascades to all callers Network redundancy adds cost and complexity
Asymmetric Routing Forward and reverse path use different routes Connection instability, stateful session failures Re-establish routing, force symmetric path Consistent routing rules, ECMP tuning Stateful services (TCP, sessions) break unpredictably Routing constraints reduce flexibility
Hotspot Routing Too much traffic routed to one node or shard Uneven node metrics, one node at 100% CPU Rebalance traffic, dynamic routing Better LB algorithms, consistent hashing One node overloaded → retry storm → neighbours overload Rebalancing adds routing overhead
Anycast Instability Traffic jumps between regions due to BGP changes Regional traffic fluctuations, session resets Sticky routing, session affinity Smarter geo-routing, BGP stability Session inconsistency for stateful services Sticky sessions reduce load balancing efficiency
4 — DNS Failures
DNS Resolution FailureMust Know DNS server unavailable, network unreachable to resolver DNS lookup errors, service connection failures Retry with secondary DNS provider Multi-DNS providers, DNS caching on client Entire service unreachable — healthy servers exist but unfindable Multiple providers increase cost and config complexity
Stale DNS Cache DNS TTL too long — old IP still cached after failover Requests routed to dead IP, connection refused Force DNS refresh, lower TTL before failover Proper TTL tuning for failover scenarios Traffic continues hitting failed node after recovery Lower TTL increases DNS resolver load significantly
Slow DNS Lookup DNS server overloaded or network issue to resolver Increased lookup latency, request latency spikes Local DNS cache, DNS prefetching DNS caching layers, dedicated DNS infrastructure Every new connection slows → latency cascade Cached DNS can serve stale records
Wrong DNS Record Misconfiguration — IP changed, record not updated Sudden routing failures, unexpected connection errors Rollback DNS changes immediately DNS change validation, automated testing pipelines Global routing failure — entire service unreachable Slower DNS validation slows deployments
5 — TLS and Security Communication Failures
TLS Handshake Failure Certificate mismatch, protocol version incompatibility TLS/SSL errors in logs, connection refused before request Retry connection, check cert validity Certificate management automation, cert-manager Services completely cannot communicate TLS overhead adds latency to every new connection
Certificate ExpiryMust Know SSL/TLS certificate not renewed before expiry Cert expiry monitoring, TLS errors in logs Emergency cert renewal, hot-swap cert Automated cert rotation (cert-manager, ACM), expiry alerts at 30d Entire API unavailable — all clients reject cert Automation adds operational complexity
mTLS Authentication Failure Service identity mismatch, cert rotation during active connections Auth handshake errors, 403 / connection refused Re-authenticate, hot-reload certs Centralised cert management, coordinated rotation Service isolation failure — whole mesh breaks mTLS adds significant operational overhead
Firewall Blocking Valid Traffic Wrong ACL, security group misconfiguration, policy change Traffic blocked unexpectedly, connection timeouts Update firewall/security group rules immediately Infrastructure-as-code, pre-deployment validation Services appear unreachable though infra is healthy Strict firewall rules reduce routing flexibility
6 — Protocol and Connection-Level Failures
TCP Connection Reset (RST) Abrupt socket close — LB timeout, proxy, firewall idle timeout Connection reset metrics, RST packet spikes Retry idempotent requests Consistent keepalive settings, timeout alignment Client retry amplification on RST burst More retries add traffic
Half-Open Connection One side thinks connection alive, other has closed it Requests hang with no response, idle timeout mismatch Connection timeout cleanup, reset stale sockets TCP keepalive probes, aligned idle timeouts Connection leaks exhaust file descriptors More keepalive traffic overhead
Connection Pool ExhaustionMust Know Too many active connections, slow consumers hold connections Pool wait time metrics, connection queue depth Queue / rate limit new requests, scale instances Connection pooling, async/non-blocking IO New requests all fail → retry storm → amplified load Larger pools consume memory and FDs
WebSocket Disconnects Mobile network switch, proxy timeout, LB restart Frequent reconnect metrics, connection duration histograms Auto-reconnect logic with backoff Sticky sessions, connection-aware LB Reconnect storms on LB restart Persistent connections consume server resources
gRPC Stream Breaks Long-lived stream interrupted by proxy/LB timeout Stream reset metrics, error rate on streaming RPCs Resume / reconnect stream with backoff Heartbeat pings on streams, max-age tuning Streaming service unavailability cascades to subscribers Stream recovery adds client complexity

Downstream Service UnreachableMust Know Dependency network failure, connection refused Connection timeout / error rate spike on dep calls Circuit breaker + fallback to cached/default response Service mesh, redundant routing to dependency Cascades upstream — callers fail, then their callers fail Fallback may return stale or default data
Service Discovery Failure Registry unavailable, service not registered Lookup failures, connection errors to healthy services Cached service endpoints as fallback Replicated service registry (etcd/Consul HA) Entire service cluster unreachable despite running Registry replication adds consistency complexity
Cross-Region Communication Failure WAN link failure, cloud provider inter-region outage Regional traffic errors, elevated inter-region latency Failover to local region, reduce cross-region sync Multi-region active-active, local read replicas Global service degradation, data divergence across regions Cross-region replication adds significant cost and latency
Message Queue Connectivity Failure Broker network issue, consumer/producer disconnect Consumer lag increasing, producer errors Retry/reconnect consumers and producers Multi-broker clusters, replication across brokers Queue backlog explosion → memory exhaustion → broker crash Multi-broker replication adds overhead

8 Must-Know Network Failures for Interviews

1. Network partition → quorum + leader election + minority isolation 2. High latency → timeouts + retries + caching + regional routing 3. Packet loss → retry + backoff + idempotency 4. DNS failure → multi-DNS + client-side cache + lower TTL 5. LB failure → HA LB + health checks + fallback routing 6. Retry storm → circuit breaker + jitter + rate limit 7. Dep. unreachable → circuit breaker + fallback + async decoupling 8. TLS/cert expiry → automated cert rotation + expiry alerting

Staff-Level Network Thinking — 5 Questions to Ask Always

1. Is the network DOWN or just SLOW? → down: fail fast, failover → slow: timeout tuning, retries, async 2. Is the failure partial or total? → total: straightforward failover → partial: hardest — some succeed, some fail silently 3. Will retries amplify traffic? → is there a circuit breaker? jitter? retry cap? 4. Can a fallback serve a degraded response? → cached data? default value? graceful degradation? 5. Can the failure isolate a region or service? → is data diverging? are writes happening in both partitions?

Slow vs Down — Why Slow Is More Dangerous in Networks

Network Down (Hard Failure)

  • Immediate connection refused / RST
  • Client detects quickly
  • Circuit breaker opens fast
  • Failover triggers promptly

Network Slow (More Dangerous)

  • Requests hang, threads held open
  • Health checks still pass
  • Callers queue up waiting
  • Thread pool exhausts silently
  • Retries amplify the problem

Final Mental Model — All Network Failures Reduce to 4 States

1. Cannot connect → partition / DNS / firewall / TLS 2. Connects slowly → latency / bandwidth / congestion 3. Connects incorrectly → misrouting / wrong DNS / blackhole 4. Connection unstable → intermittent drops / jitter / resets And in distributed systems: slow networks are often MORE dangerous than dead networks because they trigger: retries → queue buildup → thread exhaustion → cascade
