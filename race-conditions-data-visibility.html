CORE CONCEPTS
The Three Core Problems

A correct concurrent program must satisfy all three:

⚛️
Atomicity

Can two threads modify data simultaneously without one seeing a half-written state?

👁️
Visibility

Can another thread see my update, or is it stuck in a local CPU cache?

📐
Memory Ordering

Will operations execute and become visible in the correct order?

You can have one without the others. volatile gives visibility but not atomicity. CAS gives atomicity and visibility but not necessarily global ordering. Know which problem you're solving.
RACE CONDITIONS
What Is a Race Condition?

A race condition occurs when multiple threads access the same data, at least one writes, and the final result depends on execution timing.

// counter++ is NOT atomic — it's 3 CPU operations: // 1. READ: load counter into register // 2. MODIFY: add 1 // 3. WRITE: store back to memory Counter = 0 Thread A: READ(0) → MODIFY(1) → WRITE(1) Thread B: READ(0) → MODIFY(1) → WRITE(1) ← races! Final Counter = 1 ❌ Expected = 2 // The threads "race" to update shared state // Result is non-deterministic — depends on OS scheduler timing // Bug may disappear during debugging (Heisenbug)

DATA VISIBILITY
Data Visibility Problem — Stale Cached Values

Even without data corruption, threads may see stale values. Each CPU core has private caches. Core 2 may keep reading its cached copy of a variable even after Core 1 has updated it.

// Thread A writes: running = false; // stored in Core 1's cache // Thread B reads: while (running) { // reads Core 2's cache → still sees true! doWork(); } // Thread B may NEVER observe the update → infinite loop // Why: // Core 1 Cache: running = false (Modified) // Core 2 Cache: running = true (Stale — not yet invalidated) // MESI protocol will eventually propagate, but without barriers // there's no ordering guarantee about WHEN
This is a visibility bug, not a race condition. No torn write — just stale read. Fix: declare volatile boolean running (Java) or use atomic store with release ordering.
VOLATILE
volatile — Visibility Guarantee

volatile solves the visibility problem. It ensures the latest value is always read from and written to main memory (via cache coherence), and prevents compiler/CPU from reordering around the access.

Double-Checked Locking — volatile prevents broken singleton

// Without volatile: partially constructed object may become visible // volatile prevents constructor writes from being reordered after publish class Singleton { private static volatile Singleton instance; public static Singleton getInstance() { if (instance == null) { // 1st check (no lock) synchronized (Singleton.class) { if (instance == null) { // 2nd check (with lock) instance = new Singleton(); // volatile write = release barrier } // constructor writes guaranteed visible } } return instance; // volatile read = acquire barrier } } // Without volatile: JVM may publish reference before constructor finishes // → another thread reads partially initialized object → NPE / corrupt state

Acquire/Release Handshake — Most Efficient Pattern

// Producer (Thread 1): data[0] = 1; // write data data[1] = 2; flag.store(true, memory_order_release); // RELEASE: all prior writes visible // before this store // Consumer (Thread 2): while (!flag.load(memory_order_acquire)); // ACQUIRE: all reads after this // see everything before release int v0 = data[0]; // guaranteed: 1 ✅ int v1 = data[1]; // guaranteed: 2 ✅ // The release store SYNCHRONIZES-WITH the acquire load // Everything before release → visible after acquire // Cost: much cheaper than full MFENCE on ARM

COMMON MISTAKES
Mistakes & Failure Modes
volatile for Counters — Does NOT Make i++ Atomic

volatile int count; count++ is still 3 operations: read, add, write. Two threads can interleave between read and write → lost updates. Fix: AtomicInteger.incrementAndGet()

Assuming x86 Behavior on ARM

x86 has a strong memory model (TSO). Code that works on x86 may silently fail on ARM (weak model) because ARM allows Load-Load, Store-Store, and Load-Store reordering that x86 doesn't. Fix: Always use language-level abstractions (std::atomic, volatile), not architecture assumptions.

Worker Thread Never Stops

Non-volatile stop flag: JIT compiler may hoist the read outside the loop (if (!stop) while(true)) — thread never terminates. Fix: volatile boolean stop prevents the hoist.

Lock-Free Queue Corruption — Missing Release/Acquire

Producer writes data then atomically updates tail pointer — but without release ordering, consumer may read the new tail before the data writes are visible. Fix: Release store on tail update; acquire load on tail read.

Production Readiness Checklist
  • Identify all shared mutable state — every field accessed by multiple threads
  • Determine whether the issue is atomicity (compound ops) or visibility (stale cache)
  • Use volatile only for visibility — never for compound updates
  • Prefer AtomicXxx classes for counters and references
  • Use Acquire–Release instead of full fences where possible (cheaper on ARM)
  • Benchmark synchronization overhead under realistic contention
  • Test on both x86 and ARM platforms (different memory models)
  • Monitor contention and cache-line false sharing (perf c2c)
  • Avoid unnecessary shared state — immutability eliminates the problem class
  • Document memory-order assumptions in code comments
"Race conditions, visibility bugs, and ordering violations are three distinct problems requiring three distinct solutions. Staff Engineers distinguish between atomicity (CAS/locks), visibility (volatile), and ordering (acquire/release fences) — choosing the lightest primitive that satisfies correctness for the target CPU architecture."
KEY TAKEAWAYS
What to Remember
  • Race conditions occur when multiple threads modify shared state without proper synchronization, leading to non-deterministic behavior because operations like read–modify–write are not atomic.
  • Data visibility is a separate problem from atomicity: even if data is updated correctly, other CPU cores may continue reading stale cached values unless visibility guarantees are provided.
  • volatile guarantees visibility and ordering but does not provide atomicity, making it suitable for shared flags and simple state publication — not for compound operations such as incrementing counters.
  • Memory fences (Acquire, Release, Full) prevent compiler and CPU instruction reordering, ensuring that writes become visible to other threads in the intended order while enabling efficient lock-free algorithms.
  • Staff Engineers distinguish between atomicity, visibility, and memory ordering, choosing the lightest synchronization primitive that satisfies correctness while considering CPU architecture, cache behavior, scalability, and performance.

Race Condition — Classic Counter Example

// Java — lost update race public class RaceCounter { private int count = 0; // NOT volatile, NOT atomic // Thread A and Thread B both call increment() concurrently: public void increment() { count++; // compiled to: GETFIELD, IADD, PUTFIELD (3 bytecodes) } // Timeline of lost update: // T=1: Thread A reads count=0 // T=2: Thread B reads count=0 (A hasn't written yet) // T=3: Thread A writes count=1 // T=4: Thread B writes count=1 (overwrites A's update) // Expected: 2 Actual: 1 DATA RACE } // Fix 1: synchronized public synchronized void increment() { count++; } // Fix 2: AtomicInteger (CAS-based, no lock) private AtomicInteger count = new AtomicInteger(0); public void increment() { count.incrementAndGet(); } // Fix 3: LongAdder (high-contention, per-thread cells) private LongAdder count = new LongAdder(); public void increment() { count.increment(); } public long get() { return count.sum(); }

Memory Reordering — 4 Types

// 4 types of reordering that compiler + CPU can perform: // 1. Load-Load: CPU reads B before A even though A appears first in code r1 = x; // may execute AFTER r2 = y; // this // 2. Store-Store: Store to B visible before Store to A x = 1; // may become visible AFTER y = 2; // this // 3. Load-Store: Load of y happens after store to x r1 = x; // load may move after y = 1; // store // 4. Store-Load (most common — x86 allows this via store buffer): x = 1; // store may not be visible r1 = y; // before this load // x86 (TSO): Only StoreLoad reordering allowed // ARM (Weak): All 4 types allowed — more barriers needed! // Barrier mapping: // LFENCE = LoadLoad + LoadStore barrier (x86) // SFENCE = StoreStore + LoadStore barrier (x86) // MFENCE = All 4 types (x86 full fence) // DMB ISH = All 4 types (ARM full fence)

Java Memory Model — Complete Happens-Before Rules

// JMM: if action A "happens-before" B → all writes by A visible to B 1. PROGRAM ORDER: Each action in a thread HB later actions in same thread 2. MONITOR LOCK: unlock(m) HB subsequent lock(m) 3. VOLATILE: write to volatile x HB subsequent read of volatile x 4. THREAD START: Thread.start() HB any action in the started thread 5. THREAD JOIN: last action in thread T HB Thread.join(T) returns 6. TRANSITIVITY: if A HB B and B HB C → A HB C // Memory barrier summary in Java: // volatile write = StoreStore + StoreLoad barrier (full fence on x86) // volatile read = LoadLoad + LoadStore barrier // synchronized unlock = StoreStore + StoreLoad // synchronized lock = LoadLoad + LoadStore // VarHandle precision (Java 9+): // setRelease() → release store (cheaper than volatile on ARM) // getAcquire() → acquire load // setOpaque() → no fence (compiler barrier only) // setVolatile() → full seq_cst (same as volatile field)
"The Java Memory Model does not guarantee that threads see each other's writes unless a happens-before relationship exists. Building correct concurrent Java code requires understanding which operations establish happens-before: volatile, synchronized, start, join, and the transitivity rule."
