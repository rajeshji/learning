Object Pooling & Caching

Reducing allocation churn — Staff Engineer level

The Big Picture

Every request creates temporary objects. Without optimization, this produces continuous allocation → GC → fragmentation → latency spikes.

Allocate less. Reuse more. Two techniques address this: Object Pooling (reuse objects) and Caching (reuse data and computation results).

Lower CPU Reduced GC Pressure Better Cache Locality Predictable P99 Higher Throughput

Two Optimization Strategies

TechniqueReusesGoal
Object PoolingObjectsReduce allocations & GC
CachingData / ResultsReduce computation & I/O

They are complementary — pooling reduces how often you allocate; caching reduces how much work you do.

Why Allocation Churn Matters

Millions of heap allocations per second cause:

Minor GC frequency ↑ CPU on allocation work Cache locality ↓ Fragmentation ↑ P95/P99 latency ↑
Without pooling: Allocate → Use → GC → Allocate → Use → GC (repeat) With pooling: Borrow → Use → Return → Borrow → Use → Return

Object Pool Lifecycle

App Starts → Pool Creates Objects ↓ Thread Borrows Object ↓ Business Logic Executes ↓ Reset Object State ↓ Return Object to Pool ↓ Another Thread Reuses It

A poorly implemented pool can perform worse than allocating new objects.

Caching — Reuse Expensive Results

Without cache: Request → Database → Business Logic → Response (slow) With cache: Request → Cache Hit → Return Immediately (fast)

Thread-Local Pools

Shared Pool

Shared Pool ↓ (lock required) Thread 1, Thread 2, Thread 3

Thread-Local Pool

Thread 1 → Pool 1 Thread 2 → Pool 2 Thread 3 → Pool 3

Thread-local pools: no locking, better CPU cache locality, higher scalability.

Real-World Examples

Netty — ByteBuf Pooling

Pools ByteBuf objects instead of allocating new ByteBuffer() per request. Result: lower GC, lower latency, better throughput.

HikariCP — Connection Pool

DB connections involve TCP + auth + session setup. HikariCP reuses them. Connection setup happens only once; subsequent requests borrow and return.

Kafka — Buffer Pooling

Pools network and compression buffers. Result: stable throughput, lower allocation rate, lower GC frequency.

Redis — Data Caching

Caches frequently accessed values. Eliminates repeated DB calls, object creation, and network round trips. Memory ↑, latency ↓.

When NOT to Pool

Don't pool

  • Small immutable objects
  • Strings
  • Lightweight DTOs
  • Short-lived objects

Modern allocators & GCs handle these well.

Do pool

  • Large buffers
  • DB / network connections
  • Compression contexts
  • Parsers / serializers
  • Large reusable arrays

Production Failure Scenarios

High Minor GC Frequency

Cause: Millions of temporary allocations  ·  Fix: Reuse buffers or reduce allocation rate

Connection Creation Bottleneck

Cause: Opening DB connections per request  ·  Fix: Use HikariCP or equivalent connection pool

Pool Exhaustion

Cause: Objects not returned  ·  Fix: Monitor active count, investigate leaks

Cache Miss Storm

Cause: Cold cache or wrong TTL  ·  Fix: Tune cache size, preload hot data, optimize eviction

High CPU Despite Pooling

Cause: Lock contention on shared pool  ·  Fix: Partition or use thread-local pools

  • ✅ Measure GC pause time
  • ✅ Check pool utilization (active vs idle)
  • ✅ Measure cache hit ratio
  • ✅ Monitor allocator contention

  • ✅ Benchmark before and after pooling

Key Takeaways

Object Pooling • Reuse expensive mutable objects (buffers, connections, parsers). • Lower allocator overhead, GC frequency, and tail latency. • Thread-local pools eliminate contention. • Always reset state before returning to pool. Caching • Reuse frequently accessed data or computation results. • Reduces CPU, DB calls, and network requests. • Monitor hit rate — low hit rate = wasted memory. When NOT to pool • Small, short-lived, immutable objects → let GC handle. • Only pool: large buffers, connections, parsers, compression. Staff focus • Measure allocation rate, GC time, pool utilization, cache hit ratio, and P99 latency. • Benchmark before optimizing. Never assume.
