Why Storage Failures Are the Durability Failures of Distributed Systems

Storage provides: persistence + durability + retrieval + replication + recovery Storage failure: data unavailable, corrupted, inconsistent, or permanently lost 8 root failure classes: hardware | performance | capacity | replication | consistency distributed coordination | object storage | erasure/RAID | backup/recovery | multi-region

1 — Physical Storage and Hardware Failures
Disk FailureMust Know SSD/HDD hardware crash — controller error, media failure, or wear-out SMART alerts, IO errors, disk offline events Failover to replica disk, begin data rebuild on spare RAID / replication factor ≥ 3, hot-spare disks, SMART monitoring Replication factor drops → single remaining replica is now risk of data loss More replicas multiply storage cost and replication write amplification
SSD Wear-Out Write-intensive workloads exhaust SSD write endurance (TBW exceeded) SSD wear-level metrics, increased read-retry counts Replace SSD proactively on wear threshold alert Monitor TBW, use enterprise SSDs with higher endurance ratings Sudden storage node failure with no advance warning if unmonitored Enterprise SSDs with high TBW are significantly more expensive
Storage Node FailureMust Know Host OS crash, power failure, or kernel panic on storage node Node heartbeat failure, data unavailable on that node's key range Reroute requests to replica node, begin background re-replication Multi-node replication across AZs, node health monitoring Reduced redundancy — remaining replicas are now the last copies Re-replication generates substantial network and disk IO on healthy nodes
Filesystem CorruptionMust Know Improper shutdown, kernel bug, or power loss during write — FS metadata corrupt fsck errors, file not found for existing objects, mount failures Run fsck, restore from snapshot if beyond repair Journaling filesystems (ext4/XFS), UPS for graceful shutdown Node cannot start → capacity lost → higher load on remaining nodes Journaling adds small write overhead on every filesystem operation
Bit Rot / Silent CorruptionMust Know Long-term cosmic ray / media degradation silently flips bits on disk Checksum mismatch on read — detectable only if you check Recover block from healthy replica, scrub all replicas End-to-end checksums (ZFS/Ceph), regular scrubbing, replicated storage Corrupted data served silently — downstream processing produces wrong results Checksum computation and regular scrubbing add CPU and IO overhead
2 — Storage Performance Failures
Disk IO SaturationMust Know Read/write throughput maxes disk IOPS — queue builds up behind saturated IO IO wait spike, %iowait high, storage latency increasing Add more disks, route to less-loaded replicas, add read cache Better data distribution, tiered storage, capacity planning IO queue backlog → request timeouts → upstream services see latency spikes More disks add cost; read cache adds memory pressure
Storage HotspotMust Know Uneven access pattern — all traffic concentrating on one node or disk One disk/node IO 100% while others idle, uneven storage metrics Rebalance hot data, add local cache in front of hot node Better partitioning/sharding key, consistent hashing with virtual nodes Localised collapse — hot node fails under load, requests fail for its key range Rebalancing generates heavy IO; virtual nodes add routing complexity
High Write Latency Sync replication or fsync wait holds write thread — large batches or slow replicas Write latency P99 spike, storage write queue growing Batch writes, reduce fsync frequency for non-critical data Async writes where durability allows, write buffer tuning Write queue buildup → upstream backpressure → service request failures Async writes risk data loss on crash before flush
Metadata IO Bottleneck Massive number of small files or excessive inode operations saturate FS metadata Metadata operation latency spike, directory listing hangs Metadata caching, reduce metadata operation frequency Distributed metadata service, avoid millions of small files per directory Cluster-wide slowdown — all operations waiting on metadata layer Distributed metadata adds coordination complexity
3 — Capacity and Space Exhaustion Failures
Disk FullMust Know Storage exceeds capacity — all new write operations start failing Disk usage alerts (>85% = warning, >95% = critical) Emergency cleanup, archive cold data, expand volume Capacity planning, automated tiering, lifecycle policies Writes fail globally — databases, logs, uploads all fail simultaneously Aggressive cleanup policies risk deleting data still needed for recovery
WAL / Log Growth Explosion Consumer lag or cleanup failure — WAL/log segments accumulate unbounded Log size growing, disk usage spike from log directory Force log compaction, increase consumer throughput Retention policies, log size alerts, consumer lag monitoring Storage exhaustion → writes fail → DB/Kafka crash or reject all traffic Short retention windows reduce recovery options after failure
Snapshot Storage Explosion Snapshot retention not enforced — old snapshots accumulate indefinitely Snapshot storage usage growing, disk usage alerts Clean up expired snapshots, apply retention policy immediately Automated snapshot retention policy (keep N latest, delete older) Storage node saturation → node fails → reduced replication factor Fewer retained snapshots reduce recovery point options
Small File Problem Millions of tiny files overwhelm filesystem metadata layer and FS namespace Directory listing slow, inode exhaustion, metadata performance degradation File compaction — merge small files into larger containers (Parquet, ORC) Better storage format design, compact on write, avoid small writes Metadata bottleneck → cluster-wide IO slowdown → cascading timeouts Compaction adds processing complexity and CPU overhead
4 — Replication and Redundancy Failures
Replication LagMust Know Slow network or overloaded replica — replica falls behind primary Replica lag metrics, replication offset difference growing Read from primary for consistency-sensitive operations Faster replication pipeline, dedicated replication bandwidth Stale reads from lagging replica → incorrect business decisions Sync replication (zero lag) adds write latency and reduces throughput
Replica DivergenceMust Know Missed or out-of-order updates — replicas have different content for same key Checksum mismatch, anti-entropy scan finds replica inconsistency Re-sync replica from authoritative primary Quorum replication with ordering guarantees, anti-entropy background repair Inconsistent reads — different replicas serve different answers for same key Anti-entropy background repair adds ongoing IO overhead to the cluster
Under-Replicated Data Multiple replica failures — fewer copies than required replication factor Under-replication alerts, RF < target for affected partitions Create new replicas on healthy nodes immediately Multi-AZ replica placement, monitor replication factor continuously Increased data loss risk — one more node failure causes permanent loss Cross-AZ replicas add cross-zone network cost and latency
Replication Storm Node failure triggers massive re-replication — all data must copy to new node Network and disk IO spike across cluster during recovery Throttle replication bandwidth, prioritise live traffic over repair Controlled repair scheduling, rate limiting on replication bandwidth Network saturation during rebuild → live request latency degrades cluster-wide Throttling extends repair window — stays under-replicated longer
5 — Data Consistency and Integrity Failures
Lost WriteMust Know Crash before write durably persisted — data acknowledged then lost on restart Audit mismatch, expected data missing after recovery Replay WAL to recover unflushed writes Durable commits (fsync before ACK), write-ahead logging Missing business data — financial transaction, user data, or event silently gone fsync before ACK adds significant write latency
Partial / Torn WriteMust Know Crash mid-write — only part of a block or record is written to disk Checksum or version mismatch on object/block read after recovery Rewrite block from replica or WAL Atomic write protocol, WAL, copy-on-write (ZFS, Btrfs) Corrupted objects/files used by downstream processes → wrong outputs Copy-on-write adds space and IO overhead per write
Stale Read Client reads from lagging replica — gets old value after recent write Version mismatch detected in application logic, stale data observed Read from primary / leader for consistency-sensitive operations Session consistency, monotonic reads, bounded staleness settings Incorrect business logic — overwriting new data with old, or showing stale state Always reading from primary removes read scalability from replica fleet
Corrupted Object / File Bit flip in storage media or network — object bytes silently changed Checksum validation failure on read, object hash mismatch Restore from healthy replica, run storage scrub End-to-end checksums on every object, regular scrubbing jobs Broken downstream processing — corrupted file causes application errors Per-object checksum computation adds CPU overhead on every read
6 — Distributed Storage Coordination Failures
Metadata Service FailureMust Know Coordinator / NameNode / etcd down — storage lookup routing fails All storage lookup operations failing, data locations unknown Use cached metadata, operate in degraded mode HA metadata cluster (3-node ensemble), client-side metadata caching Entire storage cluster inaccessible — all reads and writes fail HA metadata cluster adds operational complexity and consensus overhead
Split Brain Storage ClusterMust Know Network partition — both halves of cluster accept writes as primary Diverging replica versions, conflicting object states detected on heal Fence minority cluster, reject writes from minority partition Consensus protocol for primary election, majority quorum requirement Silent data corruption — conflicting writes produce irreconcilable state Majority quorum means minority partition is unavailable during split
Stale Metadata Mapping Delayed metadata propagation — storage clients route to old or moved data location Wrong storage routing, objects not found at cached location Force metadata refresh, retry with fresh lookup Faster metadata propagation, versioned routing with client refresh Request failures cascade — multiple callers hit stale routing simultaneously Frequent refresh increases metadata service load
Distributed Lock Failure Multiple writers obtain concurrent access to same object — no mutual exclusion Concurrent modification detected, version conflict on write Fencing tokens / version control to reject stale writers Lease-based distributed locks, optimistic concurrency control Data corruption — both writers' data partially applied to object Distributed locks add coordination latency to every write operation
7 — Object Storage and Blob Storage Failures
Multipart Upload Failure Network interruption mid-upload — parts uploaded but final composition not called Incomplete upload state, orphaned part objects in bucket Resume multipart upload from last successful part checkpoint Client-side retry with chunk checksums, lifecycle rule to expire stale parts Orphaned storage accumulates — bucket fills with incomplete upload parts Chunked upload adds complexity to client and storage accounting
Blob / Object CorruptionMust Know Network corruption or storage media error — object bytes change in transit/at rest Checksum mismatch (MD5/SHA256 header vs actual), validation failure Restore from replica or versioned backup Erasure coding, end-to-end checksums, multi-region replication Media delivery failure — corrupted image/video/asset served to all users Erasure coding adds compute overhead for encoding and reconstruction
Object Version Conflict Concurrent writes to same object key — last-writer-wins overwrites a valid write Version mismatch, missing expected version in object history Conflict resolution via versioning, conditional PUT with If-Match header Object versioning enabled, conditional writes, optimistic concurrency Incorrect object state — downstream consumers use wrong version Object versioning multiplies storage usage; many old versions accumulate
Cold Storage Retrieval Delay Object archived to cold/glacier tier — restore takes hours before access Long restore latency, restore-in-progress status blocking read Initiate async restore ahead of need, async restore pattern Tiered access planning — keep hot objects in standard, archive only truly cold Slow disaster recovery — archived backups not accessible for hours during incident Keeping objects in standard tier costs more; cold tier is cheaper but slow
8 — Erasure Coding and RAID Failures
RAID Rebuild FailureMust Know Second disk fails during RAID rebuild — array loses too many members RAID degraded alert, second disk failure during rebuild window Restore from backup immediately Hot-spare disks, short rebuild windows, faster rebuild drives Permanent data loss — two simultaneous failures exhaust RAID tolerance Rebuild IO competes with live traffic; rebuild window is highest-risk period
Erasure Coding Reconstruction Failure Too many shard losses exceed parity tolerance — object unrecoverable Reconstruction failure alert, object marked unrecoverable Restore from separate backup or cross-region replica More parity shards (higher k+m overhead), multi-region erasure coding Permanent object loss — no replica or parity left to reconstruct More parity shards increase storage overhead (e.g. RS 6+3 = 50% overhead)
Slow RAID Rebuild Large modern disks take hours to rebuild — window of vulnerability extended Rebuild progress metric, extended degraded array state Prioritise rebuild IO, temporarily reduce other storage load NVMe SSDs for faster rebuild, smaller RAID sets, choose RAID architecture wisely Increased failure risk — another disk failure during slow rebuild = data loss Faster rebuild prioritisation competes with live traffic IO budget
9 — Backup and Recovery Failures
Backup Job FailureMust Know Network issue, storage error, or backup agent crash — backup not created Missing backup alert, backup job exit code ≠ 0 Retry backup immediately, validate last successful backup age Backup monitoring with alerting, automated retry, backup SLA enforcement No disaster recovery — next incident has no recent backup to restore from Backup infrastructure adds cost; backup IO competes with live workload
Snapshot CorruptionMust Know Interrupted snapshot — snapshot metadata inconsistent or data partially captured Snapshot validation failure, checksum mismatch on snapshot files Fall back to older clean snapshot, or rebuild from WAL Snapshot checksums, atomic snapshot creation, validate after each snapshot Recovery impossible from this snapshot — must use older, potentially stale backup Snapshot validation adds time and storage overhead per backup cycle
Restore FailureMust Know Backup corrupted, incomplete, or incompatible version — cannot restore successfully Restore validation mismatch, restore process exits with error Try alternate backup generation, rebuild from WAL if available Periodic restore testing in staging, restore drills, backup validation Extended outage — every failed restore attempt costs hours during an incident Regular restore testing consumes staging resources and engineering time
Slow Recovery Large dataset replay — restoring TB-scale data takes hours or days Long restore duration metric, RTO SLA at risk Parallel restore from multiple sources, staged partial restore Incremental checkpoints, more frequent snapshots, partial restore capability Long downtime — services unavailable until restore completes More frequent checkpoints increase snapshot storage cost and overhead
10 — Multi-Region Storage Failures
Cross-Region Replication DelayMust Know WAN latency — writes in primary region not yet visible in secondary region Geo replication lag metric, stale reads observed in secondary region Route reads to primary region for consistency-sensitive operations Geo-aware replication with bounded staleness SLA monitoring Stale global reads — users in remote region see outdated data Reading from primary region adds cross-region latency for remote users
Region Storage Isolation WAN or DC outage — entire region's storage cut off from other regions Region unreachable, replication heartbeat failure for that region Failover to secondary region storage, activate DR plan Multi-region replication with ≥ 2 copies outside primary region Regional outage — all users in that region lose access to storage Multi-region storage multiplies cost; cross-region replication adds bandwidth cost
Cross-Region Recovery Conflict Both regions fail simultaneously — each recovers independently and diverges Diverging object versions, conflicting state after both regions recover Manual reconciliation, apply conflict resolution rules Controlled DR process with designated authoritative region Silent corruption — both regions write conflicting data, one overwrites the other Designating one authoritative region means the other region's writes may be lost
Global Metadata Drift Regional storage metadata nodes diverge — different regions route to different locations Metadata mismatch, object routing errors in secondary region Metadata reconciliation from authoritative global source Consensus-backed global metadata, GitOps propagation with validation Wrong object routing globally — users cannot find or access their data Global metadata consensus adds cross-region latency to every metadata operation

10 Must-Know Storage Failures for Interviews

1. Disk failure → RAID + RF≥3 + hot-spare + SMART monitoring 2. Bit rot → end-to-end checksums + regular scrubbing + replicated storage 3. Disk full → capacity planning + lifecycle policies + 85%+ alert 4. Replication lag → lag monitoring + read from primary when consistent 5. Lost write → WAL + fsync before ACK + durable commits 6. Partial/torn write → atomic write + WAL + copy-on-write FS 7. Metadata service → HA coordinator + client-side cache + degraded mode 8. Split brain storage → majority quorum + fencing + consensus primary 9. Snapshot/backup fail → validate + restore test + backup monitoring 10. Replication storm → throttle rebuild + prioritise live traffic

Staff-Level Storage Thinking — 9 Questions to Ask Always

1. Data permanently lost? → RF≥3 + checksums + backup + WAL 2. Storage bottleneck? → IO saturation + hotspot + metadata IO 3. Replicas diverge? → quorum + anti-entropy + checksums 4. Metadata fail independently? → HA coordinator + client cache + degraded mode 5. Rebuild overloads healthy? → throttle + hot-spare + controlled scheduling 6. Corruption silent? → end-to-end checksums + scrubbing + no silent drop 7. Recovery itself fail? → restore testing + backup validation + incremental CP

Common Storage Cascading Failure Patterns

Root Storage FailureCascading Effect

Disk fullAll writes fail → DB/logs/uploads fail simultaneously
Metadata service downAll storage locations unknown → entire cluster inaccessible
Replication stormNetwork saturated during rebuild → live traffic latency degrades
Snapshot corruptionRecovery impossible from latest backup → extended outage

Final Mental Model — All Storage Failures Reduce to 5 States

1. Unavailable → disk fail / node fail / metadata down / full 2. Slow → IO saturation / hotspot / replication lag / high write latency 3. Corrupted → bit rot / torn write / lost write / object corruption 4. Inconsistent → replica diverge / stale read / split brain / version conflict 5. Unrecoverable → backup fail / snapshot corrupt / RAID double fail / cold storage Most dangerous: silent corruption + unrecoverable backup corruption spreads silently to backups → recovery impossible → permanent data loss
