Allocation Strategies

Buddy System, Slab Allocator, jemalloc — Staff Engineer level

The Big Picture

When an application calls malloc(), new Object(), or mmap(), memory is never allocated directly from RAM. The request passes through multiple allocation layers, each optimized for a different purpose.

Application ↓ User Allocator (jemalloc / glibc / tcmalloc) ↓ Virtual Memory Manager ↓ Buddy Allocator ↓ Slab Allocator (Kernel Objects) ↓ Physical RAM
Fast Allocation Low Fragmentation Cache Locality NUMA Awareness Scalability

Why Multiple Allocation Strategies Exist

No single allocator works well for every workload.

WorkloadRequirement

RedisSmall, high-frequency allocations

Layer 1 — User-Space Allocator

Applications use allocators like glibc malloc, jemalloc, tcmalloc, or mimalloc — never communicating directly with the kernel for small allocations.

Responsibilities

  • Reuse freed memory
  • Reduce system calls
  • Minimize fragmentation
  • Support multithreading

Behavior

  • Small allocs → internal pools
  • Large allocs → mmap()

Layer 2 — Virtual Memory Manager (VMM)

The VMM does not allocate physical RAM immediately. It reserves virtual address space and uses demand paging — physical memory is allocated only when the page is first accessed (page fault).

Virtual Address ↓ Page Table Entry Created ↓ Physical Page NOT yet assigned ↓ First Access → Page Fault → Buddy Allocator

Layer 3 — Buddy Allocator

Manages physical pages in powers of two. Splits larger blocks on allocation and merges adjacent free blocks ("buddies") on free.

Order 0 → 4 KB Order 1 → 8 KB Order 2 → 16 KB Order 3 → 32 KB ... Order 9 → 2 MB ← Huge Page

Allocation example (request 16 KB, only 32 KB available)

32 KB → Split → 16 KB + 16 KB Allocate first 16 KB, keep second free. On free: 16 KB + 16 KB → Merge → 32 KB

Strengths

  • Fast allocation & merge
  • Simple implementation
  • Excellent for page management

Weaknesses

  • Internal fragmentation
  • Huge Page failures under frag.
  • DMA allocation issues

Layer 4 — Slab Allocator

Optimized for fixed-size kernel objects. Allocating an entire 4 KB page for a 512-byte inode wastes memory — the Slab Allocator avoids this.

Kernel requests inode (512 B) ↓ Slab Cache (inode pool) ↓ Free Object Found → Return immediately (no page allocation needed) On free: Object returns to same slab, stays initialized.
Extremely fast Object reuse CPU cache locality Minimal fragmentation Predictable latency

Kernel objects using slab caches

task_struct inode dentry socket buffers

Almost all production Linux systems use SLUB.

vmalloc() — Large Kernel Buffers

When Linux needs a large virtual region but contiguous physical memory is unavailable, it uses vmalloc() — virtually contiguous but physically non-contiguous.

vmalloc(): Virtual region → contiguous Physical pages → non-contiguous (stitched via page tables)

Used by: kernel modules, driver buffers, large kernel memory.

Modern Allocators — jemalloc / tcmalloc

Modern allocators use arenas + size classes + thread-local caches instead of simple free lists (first-fit, best-fit, worst-fit), eliminating lock contention and fragmentation.

Arena ↓ Size Classes (8B, 16B, 32B … 4KB, large, huge) ↓ Per-thread Free Lists ↓ O(1) allocation, no global lock
AllocatorStrengthsUsed By
jemallocLow fragmentation, NUMA-awareRedis, PostgreSQL, ClickHouse
tcmallocVery fast, low contentionGoogle production systems
mimallocCompact, secureMicrosoft, .NET

Managed Runtime Allocation (JVM / Go / .NET)

Region-based allocation with GC. Object allocation is often just a pointer increment — extremely fast. GC reclaims and compacts memory later.

Young Generation (bump pointer allocation → very fast) ↓ Surviving objects promoted to Old Generation ↓ GC (Compaction / Concurrent Collection)

End-to-End Allocation Flow

Application ↓ malloc() jemalloc ↓ mmap() (if no pooled memory) Virtual Memory Manager ↓ page fault on first access Buddy Allocator ↓ Physical Page ↓ MMU Mapping Updated ↓ Application uses memory

Kernel path

Kernel ↓ Slab Cache (hit → fast return) or Buddy Allocator (miss → page allocation) ↓ RAM

Production Failure Scenarios

Huge Page Allocation Failure

Cause: Buddy allocator fragmented  ·  Fix: Preallocate Huge Pages or run compaction

High Kernel Memory Usage

Cause: Slab caches growing continuously  ·  Fix: Inspect slabtop to identify leaking caches

High Allocation Latency

Cause: Allocator contention in multithreaded app  ·  Fix: Switch to jemalloc or tcmalloc

NUMA Imbalance

Cause: Allocations hitting remote NUMA nodes  ·  Fix: NUMA-aware allocators + CPU affinity

Production Debugging Checklist

  • ✅ Check /proc/buddyinfo for page availability by order
  • ✅ Monitor slab usage (slabtop)
  • ✅ Measure fragmentation index (/proc/pagetypeinfo)
  • ✅ Inspect allocator stats (malloc_info, jemalloc profiling)
  • ✅ Check NUMA allocation (numastat)
  • ✅ Look for Huge Page failures
  • ✅ Verify page compaction activity (vmstat)

Key Takeaways

Buddy Allocator • Physical pages in power-of-two blocks. • Splits on alloc, merges on free. • Fragmentation breaks Huge Pages. Slab Allocator • Fixed-size kernel objects (inode, task_struct…). • Objects reused pre-initialized → extremely fast. • SLUB is the production default. Modern User-Space (jemalloc / tcmalloc) • Arenas + size classes + thread-local caches. • O(1), low contention, NUMA-aware. • Used by Redis, PostgreSQL, Google. Managed Runtimes (JVM / Go) • Bump-pointer alloc → very fast. • GC handles reclaim & compaction. • Trade: GC pauses for allocation speed. Staff focus • Allocator choice, fragmentation, Huge Pages, NUMA locality, slab usage, allocator contention.
