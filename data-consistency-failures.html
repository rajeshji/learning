Data Consistency Failures

Interview-focused · 13 failure types · idempotency / transactions / saga / ordering · staff patterns

Core Insight — All Data Failures Come From

ordering + duplication + missing data + stale data + conflicts

13 types below — but you only need to recall the 6-bucket model in interviews. The types are the "why" behind it.

1 Lost Update (Write Overwrite)
WhatTwo writes race — one silently overwrites the other
ExampleTwo users update the same record — last write wins incorrectly
Concurrent writes → data overwritten
(no error thrown)
2 Duplicate Write / Double Processing Critical
WhatSame operation applied more than once
ExamplePayment charged twice because of a retry
Retry → same action executed again
3 Missing Write / Data Loss Critical
WhatWrite was acknowledged but never actually persisted
ExampleMessage sent — client sees success — not stored
Request succeeded but data not saved
4 Stale Read
WhatClient reads outdated data from a replica or cache
ExampleUser sees old profile info immediately after updating it
Read from replica/cache → outdated data
5 Out-of-Order Updates
WhatEvents arrive and get applied in the wrong sequence
Example"Cancel order" processed before "Create order"
Event order mismatch → wrong final state
6 Partial Write (Incomplete State) Critical
WhatMulti-step operation only partially completes
ExamplePayment deducted but order never created
Half success → inconsistent system state
7 Replica Inconsistency
WhatDifferent replicas hold different versions of the same data
ExamplePrimary DB has the new value, read replica still has old value
Replication lag or failure
8 Read-Write Inconsistency
WhatA read immediately after a write doesn't see the write
ExampleUser posts content — refreshes — post not visible
Write done → read doesn't see it yet
9 Cross-Service Inconsistency
WhatMultiple services hold contradictory state
ExampleOrder service says "paid" — payment service says "failed"
Distributed services out of sync
10 Conflict (Concurrent Updates)
WhatTwo clients produce competing versions — no clear winner
ExampleTwo users edit the same document simultaneously
No clear winner → conflict state
11 Cache Inconsistency
WhatCache holds a value that differs from the database
ExampleDB updated — cache still serves the old value
Cache not invalidated → stale served
12 Eventual Consistency Delay
WhatData is correct eventually — but not immediately
ExampleSocial feed updates after a few seconds — not instantly
System not yet converged
13 Reconciliation Failure
WhatSystems never reconcile their inconsistencies
ExampleLedger mismatch stays unresolved indefinitely
Mismatch persists over time

6-Bucket Memory Model — Use This in Interviews

Data can be wrong in exactly 6 ways: 1. Missing → write never persisted 2. Duplicate → applied more than once 3. Outdated → stale read from replica/cache 4. Out-of-order → events applied in wrong sequence 5. Conflicting → competing versions, no winner 6. Partial → multi-step update half-done

Staff Pattern — Use Every Time

Detect → Mitigate → Prevent

1. Lost Update (Write Overwrite)

Detect via version mismatch / write conflicts
→ optimistic locking (version field / CAS)
  or row-level locks for critical writes
→ Prevent with proper isolation level
  (repeatable read or serializable)

2. Duplicate Write / Double Processing

Detect via duplicate IDs / repeated requests
→ idempotency keys on every write operation
  or unique constraints in the DB
→ Prevent with exactly-once semantics
  or a deduplication layer

3. Missing Write / Data Loss

Detect via audit logs / missing records check
→ retries with durable queues (WAL / message queue)
  acknowledge only after commit confirmed
→ Prevent with durable storage guarantees
  (fsync, acks=all in Kafka)

4. Stale Read

Detect via replica lag metrics
→ route critical reads to primary
  or enforce read-after-write consistency
→ Prevent with quorum reads
  or event-based cache invalidation

5. Out-of-Order Updates

Detect via sequence mismatch / timestamp gaps
→ sequence numbers or ordering guarantees
  via partitioned log (Kafka per-key ordering)
→ Prevent by processing events in strict order
  within a partition

6. Partial Write (Incomplete State)

Detect via inconsistent cross-service state
→ distributed transactions (2PC) for strong needs
  or Saga pattern with compensating actions
→ Prevent by designing atomic workflows
  or orchestrated multi-step transactions

7. Replica Inconsistency

Detect via replica divergence / checksum comparison
→ read repair or manual re-sync of replicas
→ Prevent with quorum writes and strong
  replication (sync replication where needed)

8. Read-Write Inconsistency

Detect via user-reported inconsistency / tests
→ read-your-writes consistency
  or sticky session routing to same replica
→ Prevent by routing reads to primary
  immediately after write

9. Cross-Service Inconsistency

Detect via reconciliation jobs / audit pipelines
→ Saga pattern with compensating transactions
  to undo partial state
→ Prevent with event-driven architecture
  and idempotent consumers

10. Conflict (Concurrent Updates)

Detect via conflicting versions / merge failures
→ conflict resolution strategy:
  last-write-wins, merge logic, or CRDT
→ Prevent with optimistic locking
  or version checks before commit

11. Cache Inconsistency

Detect via mismatch between cache and DB
→ cache invalidation on write
  or write-through cache pattern
→ Prevent with short TTL
  or event-based cache updates

12. Eventual Consistency Delay

Detect via replication lag metrics
→ inform user of eventual state
  or use stronger consistency for critical paths
→ Prevent by reducing replication lag
  or switching to sync replication

13. Reconciliation Failure

Detect via periodic reconciliation jobs
→ reprocess events or correct state from log
→ Prevent by maintaining audit logs
  and idempotent event processing

5 Core Data Mitigation Patterns — Everything Reduces to These

1. Idempotency → avoid duplicates (keys, unique constraints) 2. Transactions/Saga → avoid partial state (2PC, compensating actions) 3. Ordering → avoid out-of-order (Kafka partitions, sequence #s) 4. Consistency model → avoid stale reads (quorum, primary reads, TTL) 5. Reconciliation → fix mismatches (audit logs, periodic jobs)

Staff-Level One-Liner

"I would ensure idempotent operations, enforce ordering, use transactions or Saga for multi-step workflows, apply the appropriate consistency model, and run reconciliation jobs to guarantee eventual correctness."
