Interview-focused · 14 types · consensus / quorum / idempotency / saga · staff patterns

Core Mental Model — All Distributed Failures Come From

coordination + ordering + replication + time + partitions

Key insight: multiple machines = multiple truths. Your job is to coordinate, order, and reconcile those truths.

6-Bucket Memory Model — Use This in Interviews

Distributed failures = 1. Partition → nodes can't communicate (split brain) 2. Coordination → leader / quorum / consensus fails 3. Replication → lag / inconsistency across replicas 4. Ordering → duplicate / missing / out-of-order events 5. Time → clock skew breaks ordering and TTLs 6. Transactions → partial completion / conflict

Staff Pattern — Use Every Time

Detect → Mitigate → Prevent

1. Network Partition (Split Brain)

Detect via heartbeat failures / cluster split alerts
→ quorum-based writes (majority must acknowledge)
  + leader election via Raft / Paxos
→ Prevent: minority partition stops accepting writes
  reconcile data after partition heals

2. Leader Election Failure

Detect via missing heartbeat / multiple-leader signals
→ re-run leader election via Raft consensus
  + fencing tokens to reject stale leader writes
→ Prevent with stable election timeouts
  and reliable heartbeat intervals

3. Replica Inconsistency

Detect via checksum comparison / divergence monitoring
→ read repair: sync lagging replica from leader
→ Prevent with quorum reads/writes
  or synchronous replication on critical paths

4. Replication Lag

Detect via replica lag metrics (seconds behind leader)
→ route critical reads to leader
→ Prevent by tuning replication settings
  and using bounded staleness where tolerable

5. Quorum Failure

Detect via insufficient nodes for quorum threshold
→ switch to degraded read-only mode
  (serve stale reads, block writes)
→ Prevent by distributing nodes across
  multiple zones / regions

6. Duplicate Event Processing

Detect via duplicate event IDs / repeated actions
→ idempotency keys on every consumer
  + deduplication store (Redis / DB unique key)
→ Prevent with exactly-once semantics
  where critical (Kafka transactions)

7. Missing Event / Data Loss

Detect via audit logs / missing sequence numbers
→ replay events from durable log (Kafka)
→ Prevent with persistent queues,
  acks=all, and consumer offset commits

8. Out-of-Order Event Processing

Detect via sequence number mismatch
→ buffer and reorder using sequence numbers
  or partition by key to guarantee order
→ Prevent: enforce per-key ordering
  in partitioned message queues

9. Clock Skew / Time Drift

Detect via time-sync monitoring / NTP drift alerts
→ use logical clocks (Lamport) or vector clocks
  instead of wall clock for ordering
→ Prevent with NTP synchronisation
  and avoiding time-based ordering

10. Consensus Failure (Raft / Paxos)

Detect via inability to elect leader / commit log
→ retry consensus round / re-elect leader
→ Prevent by maintaining stable quorum
  and ensuring reliable network between nodes

11. Distributed Transaction Failure

Detect via partial state across services
→ Saga pattern with compensating actions
  to undo partial work
→ Prevent by avoiding 2PC; design
  idempotent, retryable workflow steps

12. Conflict (Concurrent Updates)

Detect via version conflicts / merge failures
→ conflict resolution: last-write-wins,
  application-level merge, or CRDT
→ Prevent with optimistic locking
  or serializable transactions

13. Service Discovery Failure

Detect via lookup failures / connection errors
→ use cached service registry entries
  + fallback to hardcoded endpoints
→ Prevent by replicating service registry
  and health-checking all registered endpoints

14. Partition Healing Conflict

Detect via divergent states after partition recovery
→ reconciliation job: merge or pick winner
  using CRDT, LWW, or business logic
→ Prevent with strong consistency on
  critical paths (avoid split-write design)

5 Core Distributed System Patterns — Everything Reduces to These

1. Consensus (Raft/Paxos) → coordination + leader election 2. Quorum → consistent reads and writes 3. Idempotency → handle duplicates safely 4. Ordering → event correctness (partitioned logs) 5. Saga / reconciliation → distributed transaction recovery

Staff-Level One-Liner

"I would use quorum-based consensus for coordination, ensure idempotent processing to handle duplicates, enforce ordering via partitioned logs, use Saga for distributed transactions, and apply reconciliation to guarantee eventual correctness."
