Database Failure Scenarios

Staff-level · 9 categories · 37 scenarios · detect / mitigate / prevent / cascading / trade-off

Why Database Failures Are Highest-Impact

Databases are: source of truth + bottleneck + consistency layer Almost every large-scale outage eventually touches the database layer. 9 root failure classes: availability | performance | replication | consistency | concurrency storage | scaling | schema | recovery
Failure Scenario When It Occurs How To Detect How To Mitigate How To Prevent Cascading Failure Risk Trade-off
1 — Database Availability Failures
Primary DB CrashMust Know Hardware/software failure, OOM kill, VM termination DB health checks fail, connection refused Failover to replica, circuit breaker on app side HA replication, automatic failover (RDS Multi-AZ, Patroni) Entire application unavailable — every write fails HA replication adds cost and failover complexity
Replica Failure Replica node crash, network partition to replica Replication lag stops updating, replica health alert Remove from read pool, rebuild replica Multi-replica setup, automated replica rebuild Reduced read capacity → read traffic overloads primary More replicas cost more and require monitoring
Complete DB OutageMust Know Cluster failure, DC outage, network failure to DB tier Connection failures across all services simultaneously Disaster recovery failover to secondary region Multi-region DB deployment, automated DR runbooks Global service outage — every dependent service fails Cross-region replication adds latency and significant cost
Connection Refused / ExhaustedMust Know DB max_connections reached — app sends more than DB accepts Connection pool wait time maxed, "too many connections" errors Increase max_connections carefully, queue requests via pooler PgBouncer/ProxySQL, proper pool sizing, connection reuse App thread pool exhaustion → all requests fail → retry storm Larger connection pools can overload DB with concurrent queries
2 — Database Performance Failures
Slow QueriesMust Know Missing index, full table scan, expensive join, N+1 problem Query latency metrics, slow query log, p99 spike Cache results, optimise query, add index, read from replica EXPLAIN ANALYZE on all queries, index review, query limits Thread pool exhaustion → all callers slow → retry amplification More indexes hurt write performance and increase storage
CPU Saturation Heavy query load, complex aggregations, insufficient hardware DB CPU >90%, latency spike, query queue depth Read replicas for heavy reads, query sharding Capacity planning, async processing, query caching Latency spike → caller retries → DB further overloaded Over-provisioning hardware is expensive
Lock ContentionMust Know Many concurrent writes competing for same rows/tables Lock wait time metrics, pg_locks / SHOW PROCESSLIST Retry with backoff, reduce lock scope, batching Better partitioning, row-level locking, optimistic locking Transaction backlog → connection pile-up → service unavailable Reduced lock granularity reduces consistency guarantees
Disk IO Bottleneck Heavy concurrent reads/writes exceeding disk throughput High IO wait %, disk latency metrics, slow query correlation SSD upgrade, read caching, buffer pool tuning Faster storage (NVMe), I/O partitioning, caching layer Query timeouts cascade → retry storm → worse IO pressure NVMe/SSD storage is significantly more expensive
Query Storm Traffic spike, buggy query pattern, missing connection limit QPS spike, CPU and connection count surge simultaneously Rate limiting on queries, cache hot queries immediately Query throttling, connection pooling, query analysis CI DB collapses → entire application layer unavailable Query throttling drops requests — user-visible errors
3 — Replication and Replica Failures
Replication LagMust Know Follower falls behind primary — slow network, large write burst Seconds-behind-primary metric, replica lag alert Route critical reads to primary, set bounded staleness Tune replication, synchronous replication on critical paths Stale reads at scale → wrong business decisions applied Synchronous replication significantly increases write latency
Replica Divergence Missed replication events, storage issue on replica Checksum mismatch between primary and replica Re-sync replica from primary, read repair Quorum writes, sync replication on critical paths Inconsistent reads — different users see different data More replication traffic increases network bandwidth cost
Split Brain DBMust Know Network partition causes both sides to promote a primary Two primaries detected, conflicting writes in WAL Fencing tokens, force one primary down Consensus-based failover (Patroni+etcd, AWS RDS Multi-AZ) Silent data corruption — both primaries accept incompatible writes Consensus failover reduces availability during partition
Failed Failover Replica not promotable — stale, lagged, or unreachable Failover timeout, no new primary elected Manual failover, promote replica manually Continuous failover testing (chaos engineering), replica monitoring Extended outage — primary down, replica cannot take over Failover testing in production adds operational risk
4 — Database Consistency Failures
Stale ReadMust Know Read routed to lagging replica — returns outdated data Version mismatch, user-visible data mismatch post-write Route critical reads to primary, read-your-writes routing Session consistency, quorum reads on critical paths Wrong business decisions — user acts on outdated balance/state Reading from primary reduces read scalability of replica set
Lost WriteMust Know Write acknowledged before durably persisted — crash before fsync Audit mismatch, expected record not found after crash Replay from WAL or event log fsync=on, synchronous_commit=on, acks after durable write Missing business state propagates — downstream processes on absent data Synchronous commit significantly increases write latency
Dirty Read Transaction reads uncommitted data from another transaction Inconsistent reads during concurrent transactions Raise isolation level to at least Read Committed Proper isolation level enforcement, MVCC Incorrect calculations — reads in-flight data that later rolls back Higher isolation levels reduce concurrent throughput
Write Conflict Concurrent writes to same row — optimistic lock violation Conflict errors (OCC violation), serialization failures Retry transaction with backoff Optimistic locking (version column), serializable isolation User-visible failures — transaction rejected, must retry More retries add latency; serializable isolation hurts throughput
Phantom Read New rows added during transaction — re-read returns different set Query inconsistency — different count on repeated SELECT Serializable isolation or predicate locking Serializable transactions on critical business logic Invalid business rules applied based on phantom row set Serializable isolation significantly reduces concurrency
5 — Transaction and Concurrency Failures
DeadlockMust Know Two transactions wait on locks held by each other Deadlock detection logs, transaction aborted errors DB aborts one transaction — app must retry Consistent lock ordering, timeout on lock acquisition Transaction backlog builds — all pending work stalls Less aggressive locking reduces safety guarantees
Long-Running TransactionMust Know Large batch update, missing LIMIT, forgotten open transaction pg_stat_activity duration, SHOW PROCESSLIST wait time Kill transaction, break into smaller batches Statement timeout, query analysis, batch size limits Holds locks → blocks all writers → connection pile-up Breaking into batches adds application complexity
Connection Leak App fails to close DB connections — pool fills permanently Connection pool exhausted, idle connections accumulating Restart/recycle connections, force close idle connections Connection pooler (PgBouncer), idle timeout, proper try-finally Pool exhausts → all new requests blocked → service-wide failure Aggressive idle timeout may disconnect valid long-lived connections
Transaction Timeout Slow DB or network — transaction exceeds configured timeout Timeout metrics, user-visible operation failures Retry with backoff, break operation into smaller transactions Faster queries/indexing, appropriate timeout tuning Retry amplification — each timeout triggers another try Short timeouts may abort valid slow-but-correct operations
6 — Storage and Persistence Failures
Disk FullMust Know WAL/log/temp file growth fills disk — no space left for writes Disk usage alerts, write failure errors from DB Emergency cleanup of logs/temp files, expand volume Log rotation, retention policies, disk monitoring with headroom alert DB cannot write WAL → all writes fail → entire service down Aggressive cleanup risks deleting WAL needed for replication
WAL Corruption Unclean shutdown, storage hardware failure, bit flip in WAL DB fails to start, recovery errors in log Restore WAL from replica, restore from backup Checksums on WAL, ECC storage, replica as WAL backup DB cannot start → extended downtime until restored from backup Checksum validation adds minor write overhead per record
Data Corruption Hardware bug, bit flip, software bug, bad upgrade Checksum mismatch, unexpected null/garbled records Restore affected rows from replica or backup ECC memory, storage checksums, page-level verification Corrupted data propagates to analytics, downstream services, reports Continuous page verification adds read overhead
Backup FailureMust Know Backup job fails — network issue, disk full, process killed Missing backup in scheduled window, backup job alerts Retry backup, switch to alternate backup target Automated backup monitoring, backup testing (restore rehearsal) Disaster recovery impossible — no valid backup to restore from Backup infrastructure adds cost; restore rehearsal adds risk
7 — Scaling and Partitioning Failures
Hot Partition / Hot ShardMust Know One shard receives disproportionate traffic (hotkey, hotuser) One shard at 100% CPU while others are idle Rebalance shards, replicate hot shard, local cache Better shard key selection, virtual partitions Single shard overloads → all queries to that shard fail Rebalancing is complex and risks data inconsistency mid-migration
Cross-Shard Query Explosion Query requires data from multiple shards — fan-out to all shards Query latency spike, all shards hit simultaneously Denormalization, caching aggregated results Query-aware sharding design, precomputed aggregates Massive DB load — all shards hit by scatter-gather query Denormalization duplicates data, complicating writes
Shard Rebalancing Failure Migration interrupted mid-flight — partial shard state Uneven shard distribution, routing errors post-migration Resume migration, rollback to pre-migration state Gradual migration with checkpointing, dual-write period Partial unavailability — some records inaccessible during migration Slower migration extends dual-write period and complexity
Metadata Node Bottleneck Central coordinator/metadata service overloaded (HDFS NameNode) Coordinator latency spike, all operations slow Cache metadata, replicate coordinator Distributed metadata (federated NameNode, sharded coordinator) Entire cluster slowdown — every op waits on coordinator Distributed metadata adds consistency complexity
8 — Schema and Migration Failures
Schema Migration FailureMust Know Breaking schema change deployed — NOT NULL added, column removed Query/app errors immediately after migration Rollback migration, apply expand-contract fix Expand-contract migration pattern, online schema change tools Entire application incompatible — all services fail on query Longer expand-contract migrations delay feature delivery
Backward Compatibility Failure Old application version incompatible with new schema Serialization/query errors, unexpected null fields in old app Dual-write support, add backward-compatible fallback Never break existing columns — add new, deprecate old gradually Multi-service outage — all old-version services fail simultaneously Supporting multiple schema versions adds application complexity
Large Index Build Failure Adding index on large table — interrupted or crashes during build Index missing, slow queries resume, index build job alert Retry online index build, run CONCURRENTLY (Postgres) Online index builds, monitor progress, schedule off-peak Slow query storm resumes — queries that relied on index degrade CONCURRENT index build takes longer and may be blocked by long txns
9 — Recovery and Failover Failures
Slow RecoveryMust Know Large WAL to replay after crash — long time before DB accepts connections Recovery in progress, DB not accepting connections, long downtime Restore from recent snapshot to reduce WAL replay length Frequent checkpointing, incremental backups, fast storage Extended service downtime — all dependents wait for DB recovery More frequent checkpoints increase IO and write latency
Failed RestoreMust Know Backup corrupted, incomplete, or incompatible version Restore validation failure, checksum mismatch on restore Use alternate backup, restore from replica WAL Backup testing — regular restore rehearsal, checksum validation Permanent data loss if no valid backup — catastrophic Regular restore rehearsal adds cost and operational overhead
Failover Loop Unstable primary — fails, replica promoted, fails again repeatedly Frequent failover events, repeated leader changes in short window Stabilise election, find root cause of primary instability Better health checks, separate DB liveness from query liveness Write unavailability throughout loop — service writes all fail Slower failover threshold reduces flapping but extends MTTR
Cold Start Recovery Overload DB recovers — all users reconnect and query simultaneously Immediate CPU/QPS spike right after recovery completes Gradual traffic ramp-up, circuit breaker on app side DB warm-up: pre-populate buffer pool, gradual traffic admission DB immediately re-crashes from cold-start traffic surge Slower traffic ramp-up extends total user-facing recovery time

Staff-Level Database Thinking — 8 Questions to Ask Always

1. Unavailable or slow? → failover/circuit-breaker vs index+cache+timeout 2. Replicas diverge? → quorum reads + read repair + sync replication 3. Retries overload DB? → circuit breaker + rate limit + connection pooler 4. Transactions deadlock? → lock ordering + statement timeout + optimistic lock 5. One shard hotspot? → virtual partitions + hot shard cache + rebalance 6. Failover itself fail? → regular failover testing + replica monitor + fencing 7. Recovery overloads? → gradual ramp-up + buffer pool warmup + throttle 8. Stale reads harmful? → read-your-writes routing + session consistency

Unavailable vs Slow DB — Know the Difference in Interviews

DB Unavailable (Obvious)

  • Connection refused immediately
  • Circuit breaker opens fast
  • Alerts fire promptly
  • Recovery: failover or restart

DB Slow (More Dangerous)

  • Queries return — just slowly
  • Health checks still pass
  • App threads queue up silently
  • Retries multiply load on DB
  • Full outage before anyone detects

Final Mental Model — All DB Failures Reduce to 7 States

1. DB unavailable → crash / failover / connection exhaustion 2. DB slow → slow query / lock contention / IO bottleneck 3. Replicas inconsistent → lag / divergence / split brain 4. Transactions blocked → deadlock / long tx / lock contention 5. Storage exhausted → disk full / WAL corruption / backup fail 6. Shards overloaded → hot partition / cross-shard / metadata bottleneck 7. Recovery failed → slow WAL replay / bad backup / failover loop Slow DB failures are most dangerous — silent, gradual, then catastrophic
