Head-of-Line Blocking & Multiplexing (HTTP/2, QUIC)

Why HTTP/3 was created and how QUIC fixes TCP's biggest networking problem

The Big Picture

Modern distributed systems send hundreds of requests over a few connections. Head-of-Line (HOL) Blocking is when one lost packet prevents subsequent data from being delivered, even if later packets have already arrived. This is why HTTP/3 (QUIC) was created.

HTTP/2 (TCP): Packet loss → ALL streams wait HTTP/3 (QUIC): Packet loss → ONLY that stream waits Multiplexing alone is not enough. The transport layer must support independent streams.

What is Head-of-Line Blocking?

A delayed or lost packet prevents all later data from being delivered — even data that has already arrived.

Analogy: Highway Traffic Jam Truck breaks down in lane 1 ↓ All cars behind it STOP ↓ Lanes 2, 3, 4 are unaffected — but not lane 1 TCP equivalent: Packet 1 ✔ Packet 2 ✔ Packet 3 ✗ (Lost) Packet 4 ✔ (arrived but NOT delivered) Packet 5 ✔ (arrived but NOT delivered) Packet 6 ✔ (arrived but NOT delivered) → TCP delivers in order, so 4/5/6 WAIT for 3 to be retransmitted

Transport-Level HOL (TCP)

TCP requires strict ordering. One missing byte blocks the entire connection, regardless of how many other streams are waiting.

This is the HOL problem in system design interviews.

Application-Level HOL (HTTP/1.1)

HTTP/1.1 pipelining sends multiple requests but requires responses in order. One slow response blocks all others behind it.

HTTP/2 multiplexing solved this version.

Evolution of HTTP Multiplexing

HTTP/1.1 — No Multiplexing

Browser opens 6 TCP connections (one per parallel request) TCP1: image1.png TCP2: style.css TCP3: script.js TCP4: image2.png TCP5: font.woff TCP6: api/data Problems: 6 TCP handshakes × 1 RTT each 6 TLS handshakes × 1–2 RTT each High memory and kernel resource usage

HTTP/2 — Multiplexed Streams over One TCP

One TCP connection Stream 1: image1.png Stream 2: style.css Stream 3: script.js (frames interleaved) Stream 4: image2.png Benefits: one handshake, lower overhead PROBLEM: TCP doesn't know about streams! Packet 3 lost → Streams 2, 3, 4 ALL WAIT → Transport-level HOL blocking remains

HTTP/3 — Multiplexed Streams over QUIC (UDP)

One QUIC connection Stream 1: image1.png (independent) Stream 2: style.css (independent) Stream 3: script.js (independent) Stream 4: image2.png (independent) Stream 3 packet lost → Only Stream 3 waits Streams 1, 2, 4 continue normally ✔ WHY: QUIC handles ordering per stream, not per connection

Why HTTP/2 Still Has HOL Blocking

HTTP/2 multiplexes HTTP frames, but TCP only sees bytes — not streams:

HTTP/2 layer: [Stream A frame] [Stream B frame] [Stream C frame] TCP layer: [Byte 100] [Byte 101] [Byte 102] [Byte 103] ... TCP does NOT know: "Byte 102 belongs to Stream B" "Byte 103 belongs to Stream C" TCP only knows: "Byte 102 is missing → cannot deliver 103+" Result: ALL streams blocked until byte 102 retransmitted

This is the fundamental mismatch: HTTP/2's stream abstraction lives above TCP, but TCP's ordering is byte-level and stream-agnostic. QUIC fixes this by implementing streams natively in the transport layer.

How QUIC Solves HOL Blocking

HTTP/2 (TCP) — Packet Loss

Sent: P1 P2 P3 P4 P5 P6 Recvd: P1 P2 __ P4 P5 P6 TCP: "waiting for P3" Stream A: ⏸ blocked Stream B: ⏸ blocked Stream C: ⏸ blocked Stream D: ⏸ blocked → All 4 streams halt until P3 retransmitted

HTTP/3 (QUIC) — Packet Loss

P3 belongs to Stream A only Stream A: ⏸ waiting for P3 retransmit Stream B: ✔ continues normally Stream C: ✔ continues normally Stream D: ✔ continues normally → Only Stream A waits → P99 latency dramatically improved
Additional QUIC advantages: 0-RTT / 1-RTT connection setup (TLS 1.3 built-in) Connection migration (IP change transparent) User-space implementation (no kernel update needed)

Common Production Problems

→

High P99 latency

HOL blocking on packet loss. Fix: upgrade to HTTP/3.

→

Many stalled requests

TCP retransmission blocking all HTTP/2 streams. Monitor with ss -ti.

→

Mobile reconnect delays

TCP connection reset on network switch. QUIC connection migration eliminates this.

→

Slow page loads on lossy networks

HTTP/2 HOL magnifies impact of packet loss vs HTTP/3.

Key Takeaways

HOL Blocking = delayed packet blocks all later delivery Even if packets 4, 5, 6 arrived — they wait for 3. HTTP/1.1: 6 TCP connections (6 handshakes, 6 TLS) No multiplexing → low efficiency HTTP/2: One TCP connection, multiplexed streams ✔ BUT: TCP byte-level ordering blocks all streams on loss ✗ HTTP/3 (QUIC): Built on UDP QUIC implements streams natively at transport level Packet loss → only THAT stream waits ✔ 0-RTT setup (TLS 1.3 built-in) ✔ Connection migration (IP change transparent) ✔ No kernel update needed (user-space) ✔ Why TCP can't fix this: TCP sees bytes, not streams Stream awareness lives in HTTP/2 layer ABOVE TCP → TCP can't know which bytes belong to which stream Tradeoffs of QUIC: ✔ Lower P99 latency ✔ Better mobile experience ✗ Higher CPU (user-space vs kernel TCP) ✗ Harder debugging (encrypted transport) ✗ UDP may be blocked by enterprise firewalls Real-world: YouTube, Gmail, Cloudflare, Fastly → HTTP/3 Internal microservices → often still HTTP/2
