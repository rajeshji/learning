Load Balancer Failure Scenarios

Why LB Failures Are Uniquely Dangerous

LB provides: routing + availability + failover + traffic distribution When LB fails: even healthy backends become unreachable or overloaded 8 root failure classes: availability | overload | routing | health check network | session | config | multi-region
Failure Scenario When It Occurs How To Detect How To Mitigate How To Prevent Cascading Failure Risk Trade-off
1 — Load Balancer Availability Failures
Load Balancer CrashMust Know Software/hardware failure, OOM kill, process crash LB health check failure, all traffic stops immediately Failover to standby LB, update DNS to secondary Active-active HA LB pair, no single point of failure Entire service inaccessible — all backends unreachable via LB HA LB pair doubles infrastructure cost and operational complexity
Single Point of Failure LBMust Know Only one LB deployed — it fails and nothing else can route Total traffic outage — zero connections reaching backends Emergency failover to backup or direct backend routing Multiple redundant LBs (active-active or active-passive) Global outage — entire service down for duration of recovery More LBs add cost; active-active adds state sync complexity
LB Process Hang Deadlock, high CPU, or memory leak — LB alive but not routing LB responds to ping but traffic stops flowing, connection timeouts Watchdog detects and restarts LB process Watchdog monitoring, automated restart on hang detection Connection timeout cascade — all clients retry simultaneously Aggressive auto-restart may drop valid in-flight connections
Control Plane Failure Cloud LB management plane fails — config updates blocked Cannot update LB rules, autoscaling changes not applied Operate with existing config until control plane recovers Separate control/data plane — data plane continues independently Autoscaling and failover blocked — cannot adapt to traffic changes Separate control/data plane adds architectural complexity
LB Startup Failure Config corruption, bad deploy, or cert error prevents LB starting LB restart loop, traffic routing unavailable Rollback to last known-good config Config validation in CI/CD, blue-green LB deployment Traffic routing unavailable during restart loop — full outage Config validation in pipeline slows deployment velocity
2 — Load Balancer Overload and Resource Failures
LB CPU SaturationMust Know Massive traffic spike or heavy TLS termination workload LB CPU >90%, latency increase, connection queue growing Add more LB nodes, offload TLS to dedicated hardware Capacity planning, horizontal LB scaling, TLS session reuse Latency spike → client retries → LB further overloaded → collapse More LB nodes cost more; TLS hardware adds upfront cost
Connection Exhaustion Too many concurrent connections — LB max connection limit reached Connection limit errors, new connections refused Increase connection limit, enable keepalive reuse Connection pooling, HTTP/2 multiplexing, keepalive tuning New requests rejected — service unavailable to new clients More connections consume memory; keepalive delays cleanup
TLS Handshake OverloadMust Know Massive HTTPS reconnects — TLS setup is CPU-intensive at scale TLS handshake latency spike, LB CPU pegged TLS session resumption/reuse, TLS offloading Session ticket reuse, ECDSA certs (cheaper than RSA), TLS 1.3 LB CPU exhaustion → all HTTPS connections slow or dropped TLS offloading removes end-to-end encryption visibility
Bandwidth Saturation Traffic volume exceeds LB network interface capacity Network throughput maxed, packet drops, latency increase Traffic shaping, CDN offload, increase NIC capacity CDN for static/cacheable traffic, better capacity planning Packet drops → retransmits → more traffic → amplification CDN adds caching complexity; more bandwidth is expensive
3 — Traffic Distribution Failures
Uneven Traffic DistributionMust Know Bad balancing algorithm or sticky sessions concentrating traffic Some backends at 100% load, others idle — uneven QPS metrics Switch algorithm, redistribute sticky sessions Least-connections or weighted round-robin, stateless backends Hotspot backend crashes → that traffic redistributes → chain overload Stateless backends require external session storage (DB/cache)
Traffic BlackholingMust Know LB silently drops traffic — misconfigured ACL, routing bug, wrong VPC Requests timeout from client side but LB shows no errors Route traffic through alternate path, rollback config Redundant routing paths, config validation, traffic monitoring Service appears healthy but clients see timeouts — retry storm More redundant paths add routing complexity and cost
Hotspot Routing Sticky sessions pin heavy users to same backend continuously One backend at capacity, others underutilised Session migration, reduce stickiness duration Stateless services with external session store Pinned backend overloads and crashes — those users fully disrupted External session store adds latency and infrastructure cost
Wrong Backend Selection Misconfigured routing rule sends requests to wrong service/version Unexpected errors or wrong responses from seemingly healthy backends Rollback LB config immediately Routing rule validation in CI, canary validation before full rollout Cascading service errors — wrong backends return bad data Canary validation adds time to every config deployment
Infinite Routing Loop Misconfigured rules route traffic back to LB or in a cycle Request cycles, max hop count exceeded, TTL expiry Break routing chain, identify and remove cyclic rule Route validation, loop detection in config tooling Network congestion — looped traffic consumes bandwidth and CPU Loop detection adds validation overhead to every config change
4 — Health Check Failures
False Negative Health CheckMust Know Healthy backend marked unhealthy — too strict threshold, slow check Sudden capacity drop, errors increase despite backends being up Re-enable node manually, tune threshold Multi-layer health checks, grace period before removal Remaining backends overloaded — capacity reduced incorrectly Grace period delays removal of genuinely failing nodes
False Positive Health CheckMust Know Dead/unhealthy backend passes health check — LB sends it traffic Backend errors despite showing healthy status in LB Remove backend manually, improve check logic Deep health checks that verify actual functionality (not just TCP ping) Traffic routed to dead node — errors for subset of users Deep checks add overhead and may trigger slow dependencies
Health Check Storm Many LBs probing many backends simultaneously — thundering herd of checks Backend QPS spike from health checks alone Stagger health check timing across LB nodes Dedicated lightweight health endpoint, jitter on check schedule Health checks overload the service they are trying to verify Staggered checks slow detection of genuinely failing nodes
Dependency-Based Health Failure Health endpoint calls DB/cache internally — those fail, node removed Entire cluster removed from LB despite app layer being fine Serve degraded health response (not hard fail) when deps slow Separate shallow (app alive) from deep (deps alive) health checks Entire fleet removed — all traffic fails despite app code being healthy Shallow checks miss deep dependency failures that affect users
Slow Health Checks Heavy health endpoint is slow — LB times out and marks node unhealthy Nodes cycling in/out of LB pool frequently Use dedicated lightweight health endpoint Health endpoint must be fast: only check in-process, not dependencies Node flapping — traffic shifts constantly, increasing error rate Lighter checks provide less signal about real system health
5 — Network and Connectivity Failures
DNS Failure to LBMust Know DNS outage, misconfiguration, or TTL mismatch — clients cannot find LB DNS lookup failures, connection refused before reaching LB Secondary DNS resolver, reduce DNS TTL for faster propagation Multi-provider DNS, low TTL for critical records, DNS monitoring Entire application unreachable — all clients fail at DNS stage Multi-provider DNS adds cost; low TTL increases DNS query volume
LB Network Partition LB isolated from backend servers — network cut between LB and backend tier Backend unreachable alerts, all requests fail with connection error Route to alternate LB with connectivity, fail open if safe Multi-network redundancy between LB and backend, redundant paths Partial service outage — all traffic through that LB path fails Redundant network paths add significant infrastructure cost
Cross-Zone LB Failure AZ network issue — LB cannot reach backends in specific AZ Zone-specific errors, AZ-scoped latency increase Shift traffic to healthy AZs, enable cross-zone LB Multi-AZ deployment, cross-zone load balancing enabled Regional overload — healthy AZs absorb failed AZ's traffic suddenly Cross-zone traffic adds inter-AZ latency and data transfer cost
DDoS / SYN Flood Attack Malicious traffic overwhelms LB connection table with fake SYNs Massive connection spike, LB CPU at 100%, legitimate traffic fails Rate limiting, WAF, scrubbing service, block at upstream DDoS protection (AWS Shield, Cloudflare), anycast routing LB unavailable — all legitimate traffic blocked by attack traffic DDoS protection adds cost; aggressive filtering causes false positives
6 — Session and Stateful Routing Failures
Sticky Session FailureMust Know Backend that owns the session crashes — LB routes session to wrong backend User session loss, forced re-authentication, 500 errors Re-establish session, failover to distributed session store Distributed session store (Redis), stateless backend design User-visible session errors — affected users cannot complete workflows Distributed session store adds latency and infrastructure cost
Session Imbalance Heavy users pinned to one backend — that node carries disproportionate load Uneven node load distribution, one node near capacity Session migration, reduce sticky TTL Stateless backend — session in external store not in-process Overloaded pinned backend crashes — all its pinned users disrupted Stateless design requires external session storage for every request
WebSocket Connection Failure LB terminates long-lived WebSocket connection on restart or timeout Frequent client reconnects, WebSocket error events in logs Auto-reconnect on client, graceful LB drain before restart LB timeout set above WebSocket idle duration, connection draining Reconnect storm — all dropped WebSocket clients reconnect simultaneously Long LB timeout delays detection of genuinely dead connections
Session Table Overflow Too many active sessions exceed LB session table memory limit Session storage saturation, LB memory alerts Expire idle sessions aggressively, increase session table size Session TTL optimization, stateless design removes session table entirely LB memory exhaustion → LB crash → cold cache storm for sessions Short TTL breaks long-lived legitimate user sessions
7 — Configuration and Deployment Failures
Bad LB ConfigurationMust Know Wrong routing rules pushed — wrong backend pool, wrong port, wrong algo Sudden traffic anomalies, error rate spike after config change Rollback config immediately Config testing in staging, blue-green LB deployment Global outage — all traffic misrouted to wrong backends Blue-green deployment doubles LB infrastructure during switchover
Certificate Misconfiguration TLS cert expired, wrong domain, or mismatched key — HTTPS breaks TLS handshake errors, browser certificate warnings Rollback to previous cert, emergency cert rotation Automated cert rotation (Let's Encrypt/ACM), cert expiry monitoring All HTTPS traffic fails — clients see cert errors, cannot connect Automation adds complexity; cert rotation can briefly break traffic
Canary Routing Failure Wrong traffic split — canary receives too much or too little traffic Traffic imbalance, unexpected error rate on canary Disable canary, restore 100% traffic to stable version Safer rollout strategy with validation gates before traffic increase Partial outage if bad canary handles too much traffic before detected Slower canary ramp reduces experimentation velocity
Ingress Controller Failure Kubernetes ingress controller crashes — cluster-level LB gone Routing unavailable for all services behind ingress Restart ingress controller, failover to backup ingress HA ingress setup (multiple replicas), ingress health monitoring Cluster-wide routing failure — all HTTP services unreachable HA ingress setup adds pod resource cost and complexity
8 — Multi-Region and Geo-Routing Failures
Region Failover FailureMust Know Primary region fails — secondary region not ready or also unavailable Failover timeout, global traffic still directed to failed region Manual failover, redirect via DNS or global LB Active-active multi-region, regular failover drills Global outage — both regions unavailable or failover incomplete Active-active adds significant cost and data consistency complexity
Geo-Routing Failure Wrong region selected — user routed to far-away region or misconfigured geo Increased latency, users complaining of slow response Override geo-routing rules, manual region assignment Smarter geo-DNS with latency-based routing, regular geo-routing tests Regional overload — one region serves all global traffic incorrectly Latency-based routing is more complex and harder to reason about
Traffic Spillover Overload Failed region's traffic spills to secondary — secondary cannot absorb it all Secondary region at capacity, latency spike, errors appear Rate limit spillover traffic, shed less-critical requests Active-active with sufficient headroom in each region Multi-region cascade — secondary overloads and fails too Headroom means over-provisioning each region during normal operation
Cross-Region Config Sync Failure LB config replication lags — different regions have different routing rules Inconsistent behavior across regions, routing rule mismatch alerts Force config sync from authoritative source Distributed config consensus, GitOps config propagation with validation Different user experiences per region — A/B users unintentionally Strong config consensus adds synchronisation latency per change

Staff-Level LB Thinking — 8 Questions to Ask Always

1. LB itself highly available? → active-active pair + no SPOF 2. LB become bottleneck? → CPU + conn limit + TLS offload + horizontal scaling 3. Routing uneven? → least-conn algo + stateless backends 4. Health checks accurate? → shallow vs deep + grace period + stagger timing 5. Retries overload LB? → circuit breaker + backoff + client-side retry limits 6. One region absorb failover? → active-active + 50% headroom in each region 7. Session affinity hotspot? → distributed session store + stateless design 8. LB config cause global outage? → staging validation + blue-green + rollback plan

Silent Routing Failures — Most Dangerous LB Pattern

Silent routing failure: system appears healthy, traffic disappears Signs: LB shows green health → but requests timeout on client side Backend servers idle → but clients see errors No LB error logs → but users report failures Causes: traffic blackholing | wrong ACL | routing loop | VPC misconfiguration Detection: active synthetic probes + client-side error rate, not just server metrics Rule: always monitor from the CLIENT perspective, not just the LB/backend

Final Mental Model — All LB Failures Reduce to 5 States

1. Traffic not routed → crash / SPOF / DNS fail / network partition 2. Traffic misrouted → bad config / wrong backend / infinite loop / geo-fail 3. Traffic uneven → hotspot / sticky imbalance / poor algorithm 4. LB overloaded → CPU / conn exhaustion / TLS / DDoS 5. Health checks wrong → false positive / false negative / dependency-based fail Silent routing failure is hardest: LB appears healthy, backends are fine, traffic vanishes
