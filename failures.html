Staff-Level Mental Model — Remember This, Not 100+ Types

Failures come from: 1. Infrastructure → hardware, power, disk 2. Network → partition, latency, DNS 3. Application → crash, leak, deadlock 4. Data → corruption, lost writes, stale reads 5. Load → spikes, hot keys, stampede 6. Dependencies → database, cache, third-party 7. Humans → config push, deletion, wrong runbook

Memorise 7 buckets, not 100+ types. Interviewers reward structured thinking.

For ANY System — Ask These 6 Questions

What can fail in: - Infra? → servers, disks, data center - Network? → partition, timeout, DNS - Service? → crash, leak, exhaustion - Data? → corruption, stale, lost - Load? → spike, hot key, stampede - Dependencies? → DB, cache, third-party

This covers almost all real-world failures and is what Staff engineers say in system design interviews.

The Core Interview Truth

Staff engineers don't memorise failures.

They think: "Everything will fail → design for it."

Engineer Progression — What Interviewers Expect

LevelWhat They Say
Junior "The server might crash or the database might go down."
Senior "Infrastructure can fail, networks can partition, services can crash, and dependencies can be unavailable — I'd handle each with retries, circuit breakers, and replication."
Staff "I categorise failures into 7 buckets: infra, network, application, data, load, dependencies, and human. For each, I define the failure mode, detection signal, and recovery mechanism. The trickiest are distributed failures like split brain and clock drift because they're subtle and data-corrupting."
Principal "Failures are a design input, not an edge case. I start system design by asking: what is the blast radius of each component failure? How do we detect it within 30 seconds? How do we recover in under 2 minutes without data loss? I design for failure budgets, not for zero failures."

Hardest Failures to Detect (Interviewers Love These)

Split Brain

Two leaders think they're primary. Both accept writes. Data diverges silently.

⏱ Clock Drift

Timestamps from different nodes disagree. Event ordering breaks. Distributed transactions corrupt.

Lost Update

Two concurrent writes — one silently overwrites the other. No error thrown. Data just disappears.

Partial Network

Some nodes can reach others but not all. System is alive but split. Consistency breaks.

Stale Reads

Read replica lags behind primary. User reads old data after a write. No error — just wrong data.

Retry Storm

One failure triggers thousands of retries. Retries overload the recovering service. Full cascade.

How to Answer "What Can Fail?" in an Interview

Step 1: State your framework "I think about failures in 7 categories: infra, network, application, data, load, dependencies, and human." Step 2: Walk through relevant categories for THIS system "For a payment system, the critical failures are: - Data failures: lost writes, double-charging (concurrency) - Dependency failures: payment gateway down - Distributed failures: split brain on DB leader election - Network failures: timeout between services" Step 3: For each failure — detection + mitigation "Lost writes → use WAL + idempotency keys Gateway down → circuit breaker + retry with backoff Split brain → Raft consensus, fencing tokens Timeout → bulkhead, graceful degradation" Step 4: Close with a principle "The goal isn't zero failures — it's fast detection, blast radius isolation, and automatic recovery."

Golden Rules — Say These in Interviews

  • Failures are a design input, not an afterthought.
  • Every component has a blast radius — design to contain it.
  • Detection speed matters as much as recovery speed.
  • Cascading failures are caused by tight coupling — use bulkheads.
  • Distributed system failures (split brain, clock drift) are the hardest — design consensus carefully.
  • Human failures kill more systems than hardware failures — automate everything.
