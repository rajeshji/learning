Latency and Performance Failure Scenarios

Staff-level · 9 categories · 36 scenarios · detect / mitigate / prevent / cascading / trade-off

Why Latency Failures Are the Hardest to Debug

System is UP and returning correct results — but too slowly to be usable No error rate alert fires. Users just abandon. Business metric drops silently. Latency failures hide behind: P50 looking fine while P99 is 10x higher Root causes live in: tail requests / queuing / GC / cold paths / resource contention
Failure Scenario When It Occurs How To Detect How To Mitigate How To Prevent Cascading Failure Risk Trade-off
1 — Tail Latency / P99 Failures
Long Tail Request AccumulationMust Know Small percentage of requests hit slow code paths (GC, cold cache, lock wait) — P99 diverges from P50 P99 / P999 much higher than P50 in latency histogram; P50 looks healthy Hedged requests — send duplicate to second replica if no response within threshold Reduce tail causes: GC tuning, cache warm-up, lock contention reduction Timeout amplification — slow 1% requests block threads, reducing throughput for everyone Hedged requests double backend load for slow-request percentile
P99 Amplification in Fan-OutMust Know Request calls 10 services in parallel — P99 of result is the MAX P99 of all 10 End-to-end latency much higher than any individual service latency Bounded timeout on fan-out, return partial results if some shards slow Reduce fan-out degree, parallel scatter-gather with strict per-shard deadline Fan-out latency grows with shard count — adding shards makes P99 worse Partial results require clients to handle incomplete responses
Head-of-Line BlockingMust Know One slow request at head of a single-connection queue blocks all requests behind it High latency on requests that follow a slow one on same connection Multiplex requests over many connections, use HTTP/2 or gRPC streaming Connection pooling with many connections, HTTP/2 multiplexing, async request handling All requests on that connection experience slow-request latency, not just one Many parallel connections increase memory and connection-management overhead
Tail Latency from Resource Contention CPU scheduling or lock wait adds variable latency to requests competing for same resource Latency variance high (stddev large), no clear single root cause in traces Reduce contention: partition data, use lock-free structures CPU affinity for latency-sensitive threads, lock-free data structures, work stealing Latency spikes cascade when slow requests pile up and fill thread pools CPU affinity reduces scheduler flexibility and may underutilise cores
2 — Database and Query Latency
Missing Index Full Table ScanMust Know Query on un-indexed column forces sequential scan of entire table as data grows Slow query log, query plan shows Seq Scan, latency grows with row count Add index immediately (use CONCURRENTLY in Postgres to avoid lock) Index all query predicates, EXPLAIN ANALYZE in CI for new queries DB CPU 100% from scans → all queries slow → application-wide latency spike Indexes consume storage and add write overhead to every INSERT/UPDATE
Lock Contention Query WaitMust Know Long-running transaction holds row/table lock — all queries on same rows queue behind it Lock wait metric spike, queries show "lock wait" in pg_stat_activity Kill long-running transaction, apply query timeout Short transactions, statement timeout, avoid user-interactive transactions All concurrent queries on that row set delayed — throughput collapses Aggressive lock timeouts may abort valid long analytical queries
N+1 Query ProblemMust Know ORM or application code issues one query per item in a list — 1 request triggers N+1 DB calls DB QPS much higher than application RPS; trace shows N sequential queries Rewrite with batch query or JOIN; add DataLoader pattern ORM lazy-loading audit, query count assertion in tests, DataLoader for GraphQL DB connection pool exhaustion as N grows — each API request drains N pool slots Eager loading fetches more data than needed; JOIN complexity grows with schema
Query Planner Wrong Plan Statistics stale — query planner chooses sequential scan over index on large table Sudden latency regression without schema change; EXPLAIN shows unexpected plan Run ANALYZE to refresh statistics; add query hint if supported Autovacuum/autoanalyze tuning, statistics target increase for skewed columns All queries using that table degrade simultaneously — looks like data volume regression Query hints tie application to specific DB version behaviour
3 — GC and Runtime Pauses
Stop-the-World GC PauseMust Know JVM full GC triggered — all application threads pause for tens to hundreds of milliseconds Latency spike aligned with GC log events, P99 spike without error rate increase Tune GC (switch to G1GC/ZGC), reduce allocation rate G1GC or ZGC with tuned region size, heap at 50-60% of available RAM Client timeouts during pause trigger retries — post-GC overload spike ZGC uses more memory for concurrent GC bookkeeping; tuning GC requires expertise
GC Pressure from Large HeapMust Know Heap too large — GC takes longer to scan, pause duration grows with heap size GC pause duration growing over time, heap fragmentation increasing Reduce heap size, move large objects to off-heap storage Cap heap at 31 GB (compressed oops threshold), use off-heap for caches (Chronicle Map) Progressively longer pauses lead to client timeouts → retry storms Off-heap storage bypasses GC but requires manual memory management
JIT Compilation Cold Path Latency Newly deployed code not yet JIT-compiled — interpreter runs until hot path detected Latency higher immediately after deploy, normalises after minutes of traffic Warm up with synthetic traffic before routing real users post-deploy JVM warm-up in deploy pipeline, AOT compilation (GraalVM native image) First real users post-deploy experience slow responses — bad deploy impression Synthetic warm-up adds deploy time; GraalVM native image has longer build time
Python GIL Contention CPU-bound threads in Python compete for Global Interpreter Lock — concurrency serialised CPU-bound tasks slow despite multiple cores, profiler shows GIL wait time Move CPU-bound work to separate processes (multiprocessing), use C extensions Async IO for IO-bound work, multiprocessing for CPU-bound, consider compiled alternatives Single-threaded bottleneck — throughput cap hit regardless of core count Multiprocessing adds IPC overhead and higher memory footprint per worker
4 — Network and I/O Latency
TCP Connection Setup OverheadMust Know New TCP connection per request — SYN/ACK round trip adds 1+ RTT to every request Latency correlated with new connection rate, connection setup visible in traces Enable connection keep-alive, use connection pool HTTP keep-alive, connection pooling, HTTP/2 multiplexing over single connection Reconnect storm on restart floods server with SYN packets, exhausting accept queue Persistent connections hold server resources for idle clients
Non-Sequential Disk I/O Seek Latency Random read access pattern on spinning disk — each seek adds ms of latency High disk latency with low throughput, iowait metric elevated Add read cache layer, switch to SSD for random-access workloads SSD for databases, sequential write patterns (LSM-tree), OS page cache tuning Query latency grows with data volume — each additional row adds seek overhead SSD has higher cost per GB and finite write endurance
DNS Resolution on Every Request DNS TTL too short or cache disabled — each API call triggers a DNS lookup adding RTT Latency spike correlated with DNS lookup time, DNS queries much higher than request rate Enable DNS caching at client, increase TTL DNS caching (ndots config, resolv.conf), service discovery via sidecar (Envoy) DNS server overload if all services do uncached resolution at scale Longer DNS TTL means slower failover when IP address of endpoint changes
Cross-AZ Network Latency Service and its dependency in different AZs — every call adds 1-3ms cross-AZ RTT Latency higher than expected for same-region calls, AZ routing visible in traces Co-locate service and dependency in same AZ where possible AZ-aware routing (prefer local AZ replica), Topology Aware Routing in Kubernetes Cross-AZ latency multiplied by number of hops — microservice chains become very slow AZ affinity reduces cross-AZ traffic cost but creates load imbalance during AZ failure
5 — Cold Start and Warm-Up Latency
Container / JVM Cold StartMust Know New instance started — JVM startup, Spring context load, class loading all add seconds before ready First requests to new instance much slower, readiness probe slow to pass Pre-warm with health check traffic before adding to LB pool Smaller container images, GraalVM native for instant startup, pre-warming in deploy Slow scaling — new instances take too long to be useful during traffic spike Native image compilation has longer build time and loses JIT optimisation at runtime
Connection Pool Cold Start New service instance starts with empty connection pool — first requests create connections, adding latency Latency spike for first N requests to new instance (N = pool size) Pre-establish connections on startup before serving traffic Pool pre-warming in startup hook, min pool size = target concurrent requests Slow autoscale — new instances take seconds to be effective at absorbing load Pre-warming holds connections that may not be needed if scale-out was unnecessary
Cache Cold Start After Deploy Deploy flushes or replaces cache — all traffic misses until cache refills Cache hit ratio at 0% post-deploy, backend load spike Pre-warm cache before shifting traffic, use versioned keys to avoid full flush Versioned cache keys (old and new coexist during deploy), pre-warm step in deploy pipeline Backend overload on every deploy — DB or origin gets full traffic until cache warms Versioned keys double cache storage during the deployment transition window
Serverless / Lambda Cold Start Lambda not invoked recently — container spun up fresh, adding 500ms-2s before first response Bimodal latency distribution — fast warm invocations and slow cold start invocations Provisioned concurrency (keep containers warm), async invocation for tolerant paths Provisioned concurrency for latency-sensitive functions, keep-alive pings Burst traffic triggers many cold starts simultaneously — P99 spikes sharply Provisioned concurrency adds cost even when functions are idle
6 — Resource Contention Latency
Noisy Neighbour CPU StealMust Know Shared hypervisor — another VM bursting consumes CPU cycles allocated to this VM %steal CPU metric elevated, latency increases without application-level explanation Move to dedicated/bare-metal instance, isolate CPU with cgroups CPU-pinned instances, dedicated hosts for latency-sensitive workloads Unpredictable latency spikes — P99 becomes non-deterministic, SLO breached randomly Dedicated hosts eliminate sharing efficiency and significantly increase cost
Memory Bandwidth Saturation Working set too large for L3 cache — memory bus saturated, all memory accesses slow Cache miss rate high in CPU perf counters, latency grows with memory access frequency Reduce working set size, improve data locality, compress in-memory data Data structure alignment, cache-friendly access patterns, working set fits in L3 All threads slow simultaneously — memory bus is shared, so saturation affects all Compression reduces working set but adds CPU overhead per access
Disk I/O Contention Between Processes Compaction, backup, or logging competing with query I/O on same disk iowait spike, query latency growing during backup/compaction window Throttle background I/O (ionice), schedule heavy I/O in low-traffic windows Separate disks for WAL vs data vs compaction, I/O rate limiting for background tasks Query latency spike during backups — production SLO breached on schedule Separate disks increase hardware cost and operational complexity
Mutex / Lock Wait Latency High concurrency on shared data structure — threads queue waiting for lock Thread profiler shows lock wait dominating CPU, throughput plateaus under concurrency Reduce lock scope, shard the data structure, switch to lock-free Partitioned data structures, lock-free algorithms (CAS), read-write lock separation Throughput ceiling — adding more threads makes it worse as lock contention grows Lock-free algorithms are harder to implement and reason about correctness
7 — Serialization and Computation Latency
Expensive JSON SerializationMust Know Large or deeply nested JSON response — CPU time for serialization dominates request handling CPU spike without complex business logic in profiles, serialization visible in flame graph Apply response field filtering (sparse fieldsets), switch to binary protocol Protobuf/MessagePack for high-throughput APIs, response size limits, field projection CPU saturation — serialization hogs cores, reducing throughput for all requests Binary protocols lose human readability and require schema management
O(n^2) or Worse Algorithm Nested loop or quadratic sort on growing data — latency grows faster than data size Latency grows super-linearly with input size in load tests Impose input size limit immediately, replace algorithm Algorithmic complexity analysis in code review, load tests with realistic data sizes Latency explosion — O(n^2) on user-controlled n allows latency DoS attack Optimal algorithms are often more complex to implement and maintain
Synchronous Block in Async Context Blocking I/O or Thread.sleep called inside async event loop — event loop thread stalls Event loop thread blocked, all other async tasks on that loop frozen Move blocking call to separate thread pool, use async equivalent Async code linting (asyncio.sleep not time.sleep), blocking detector in testing All requests on that event loop frozen while block runs — latency spike for all Offloading to thread pools adds context switch overhead
Excessive Object Allocation / GC Pressure Hot path allocates many short-lived objects — GC runs frequently to reclaim High GC frequency in metrics, allocation rate high in profiler Object pooling, reduce allocations in hot path Allocation profiling in staging, object reuse patterns, value types where available GC frequency grows with traffic — latency degrades proportionally to load Object pooling adds complexity and risk of pool exhaustion under burst
8 — Queueing and Backpressure Latency
Queue Depth Latency (Little's Law)Must Know Arrival rate slightly exceeds processing rate — queue grows, latency = queue_depth / throughput Latency growing steadily as queue depth increases even though throughput looks healthy Scale processors, reduce arrival rate, apply backpressure to sender Process faster than arrival rate with buffer, model with Little's Law before capacity planning Latency grows unboundedly — small over-capacity leads to seconds of latency Excess processing capacity wastes resources when queue is empty
Head-of-Queue Blocking One slow job at head of work queue blocks all subsequent jobs even if they are fast Most jobs complete fast but P99 matches the slowest job in the queue Priority queue — fast jobs can bypass slow ones Multiple priority queues, job size estimation with admission control Fast urgent tasks experience same latency as slow batch jobs Priority queues can starve low-priority jobs under sustained high-priority load
Slow Consumer Backpressure Latency Slow downstream consumer propagates backpressure upstream — producers stall waiting to write Producer latency growing, downstream consumer visible as bottleneck in traces Decouple via async queue, increase consumer throughput Reactive backpressure (Project Reactor), async queue between producer and consumer Backpressure propagates all the way upstream — entire pipeline latency grows Async queue decoupling introduces at-least-once delivery complexity
Thundering Herd Post-Queue Drain Large backlog drains simultaneously — downstream suddenly receives huge burst Latency spike on downstream immediately after backlog clears Rate-limit drain speed, introduce controlled release of queued work Token bucket release from queue, gradual drain rather than burst drain Downstream overloaded by drain burst — may trigger cascading failure in downstream Rate-limited drain means backlog takes longer to clear during recovery
9 — Cross-Service and Dependency Latency
Synchronous Fan-Out LatencyMust Know Service calls N dependencies in sequence — total latency is sum of all, not max End-to-end latency much higher than any single dependency Parallelise independent calls, apply scatter-gather pattern Parallel fan-out with bounded timeout, identify and eliminate sequential dependency chains Sequential latency adds — each added dependency makes the chain worse Parallel fan-out increases peak load on dependencies simultaneously
Chatty API Round-Trip LatencyMust Know Client makes many small requests instead of one batch — each RTT adds network latency Many small requests visible in traces, latency = N × RTT even for simple operations Batch requests, aggregate on server side, use bulk endpoints Chunky API design (not chatty), batch endpoints, GraphQL for flexible field selection Latency grows with N round trips — mobile clients on high-latency links most affected Batch endpoints are less flexible and harder to cache at individual-item granularity
Slow Dependency Without Timeout Downstream dependency slow but reachable — calling service waits indefinitely Latency growing on calling service, dependency trace shows slow response time Apply per-dependency timeout immediately, fail fast Timeout on every downstream call, circuit breaker for persistent slow dependency Thread pool of caller fills with waiting threads — all endpoints of caller become slow Tight timeout may fail valid slow-but-correct operations on the dependency
Service Mesh / Sidecar Overhead Envoy/Linkerd sidecar adds per-request overhead — latency increases for every service call Latency regression after service mesh introduction, sidecar CPU visible in profiles Tune sidecar worker threads, enable gRPC multiplexing to reduce connections Benchmark service mesh overhead before adopting, tune worker thread count and connection reuse Overhead multiplied by number of hops — deep microservice chains accumulate ms per hop Service mesh adds critical observability and security — cannot simply remove it

10 Must-Know Latency Failures for Interviews

1. P99 fan-out amplification → parallel scatter-gather + bounded per-shard timeout 2. Head-of-line blocking → HTTP/2 multiplexing + connection pooling 3. Missing DB index → EXPLAIN ANALYZE + index all query predicates 4. N+1 query problem → batch query / JOIN + DataLoader pattern 5. Stop-the-world GC → G1GC/ZGC + heap cap at 31 GB + reduce allocation 6. Cold start latency → pre-warm + provisioned concurrency + native image 7. Noisy neighbour steal → dedicated hosts / CPU pinning for latency-sensitive 8. Queue depth latency → Little's Law + scale processors + backpressure 9. Sequential fan-out → parallelise independent calls + scatter-gather 10. Slow dep without timeout → timeout on every call + circuit breaker

Staff-Level Latency Thinking — 9 Questions to Ask Always

1. P99 vs P50 diverging? → tail causes: GC / lock / cold path / fan-out 2. Latency grows with load? → queuing / Little's Law / connection pool saturation 3. Latency grows with data? → missing index / O(n^2) / scan instead of seek 4. Latency spikes periodically? → GC pause / disk flush / scheduled backup I/O 5. Latency after deploy? → cold start / cache cold / JIT warm-up 6. Cross-service slower? → sequential vs parallel / RTT per hop / sidecar overhead 7. Unpredictable latency? → noisy neighbour / resource contention / GC non-determinism 8. Fan-out latency high? → max(P99_all_shards) / reduce shard count / hedged requests 9. Client timeout mismatch? → server timeout must be shorter than client timeout

Final Mental Model — All Latency Failures Reduce to 4 States

1. Compute slow → GC / CPU steal / O(n^2) / serde overhead 2. I/O slow → missing index / disk seek / non-sequential / no cache 3. Waiting → lock / queue / HOL blocking / slow dep without timeout 4. Cold → JIT / connection pool / cache / serverless cold start The most insidious: system looks healthy (no errors, P50 fine) while P99 is 10x higher and users are silently abandoning

Principal Takeaway

Measure P99

Not P50. Tail is where users hurt.

Parallel fan-out

Max not sum. Bounded per-shard timeout.

Timeout every call

Server timeout < client timeout always.

Pre-warm

JIT + pool + cache before traffic arrives.
