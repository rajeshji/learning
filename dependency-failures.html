Dependency Failures

Interview-focused · 12 types · circuit breaker / fallback / retry / decouple · staff patterns

Core Mental Model — Generate Any Dependency Failure From This

Dependency failure = unavailable / slow / partial / incorrect / overloaded / incompatible

Key insight: your service is fine — but it fails because of what it depends on. This is why isolation (circuit breaker, fallback) matters more than correctness alone.

1 Dependency Unavailable (Down) Most Common
WhatDB, cache, or third-party API is completely down
ExampleDatabase outage / Redis unavailable / payment gateway down
Service cannot proceed without dependency
2 Slow Dependency (Latency Spike) Dangerous
WhatDependency responds but very slowly — ties up caller threads
ExampleDB query takes 10s instead of 10ms — upstream API times out
Your service becomes slow
because dependency is slow
3 Partial Availability
WhatDependency works for some requests but fails for others
ExampleOne DB shard down / partial region outage
Inconsistent success / failure
→ hardest to detect
4 Dependency Timeout
WhatCall to dependency does not return within the allowed time
Waiting too long → request fails
→ thread held open
5 Dependency Overload
WhatDependency cannot handle the incoming request volume
ExampleDB overwhelmed by queries / API rate limit exceeded
Dependency becomes the bottleneck
6 Incorrect Response / Data Corruption
WhatDependency returns wrong or corrupted data — call succeeds
ExampleWrong pricing data / corrupted cache value
System misbehaves even though
call technically succeeds
7 Version / Contract Mismatch
WhatAPI change breaks compatibility — field removed, schema changed
ExampleDependency deploys v2 — your service still expects v1 response shape
Services don't agree on contract
→ silent data errors
8 Third-Party API Failure
WhatExternal service outside your control fails
ExamplePayment provider / SMS gateway / email service down
No control over dependency behavior
→ must design for absence
9 Auth / Authorization Failure
WhatAccess to dependency is denied — expired token, wrong credentials
Dependency exists and is healthy
but access fails
10 Network Issue to Dependency
WhatCannot reach dependency due to network failure — partition, DNS, timeout
Dependency is healthy
but unreachable
11 Dependency State Inconsistency
WhatDependency holds outdated or inconsistent state
ExampleRead replica lags behind / cache not yet invalidated
Dependency returns stale data
12 Cascading Dependency Failure Most Dangerous
WhatOne dependency fails — downstream impact propagates to many services
Failure propagates across system
→ entire fleet affected

6-Bucket Memory Model — Use This in Interviews

Dependency failures = 1. Down → unavailable entirely 2. Slow → latency spike / timeout 3. Partial → works for some, fails for others 4. Incorrect → returns wrong / corrupt data 5. Overloaded → rate limited or overwhelmed 6. Incompatible → version / contract mismatch

Staff-level insight: your system is only as reliable as its weakest dependency. Design for the absence of every dependency.

Staff Pattern — Use Every Time

Detect → Mitigate → Prevent

1. Dependency Unavailable (Down)

Detect via health checks / error rate spike
→ circuit breaker: stop calling failing dep
→ fallback to cached or default response
→ Prevent by decoupling and reducing
  hard synchronous dependencies

2. Slow Dependency (Latency Spike)

Detect via latency metrics (P95 / P99)
→ strict timeouts + async / non-blocking calls
→ reduce synchronous dependency calls
→ Prevent with caching and request batching

3. Partial Availability

Detect via inconsistent success/error rate
→ retry with backoff to healthy instances
→ route traffic via load balancing away from
  failing shards / regions
→ Prevent with multi-region redundancy

4. Dependency Timeout

Detect via timeout metrics
→ set strict client-side timeouts everywhere
→ fail fast — don't block threads waiting
→ Prevent by tuning timeout values
  and reducing latency in the dep path

5. Dependency Overload

Detect via high error rate / throttling signals
→ rate limit outgoing calls to the dep
→ queue requests / degrade non-critical paths
→ Prevent by caching and reducing
  request volume hitting the dep

6. Incorrect Response / Data Corruption

Detect via response validation / anomaly checks
→ validate responses before using them
→ reject bad data, fallback to last known good
→ Prevent with schema validation
  and checksums on critical paths

7. Version / Contract Mismatch

Detect via API errors after deployment
→ ensure backward-compatible APIs
  (never remove fields, use versioned endpoints)
→ Prevent with contract testing in CI
  and gradual canary rollouts

8. Third-Party API Failure

Detect via external API monitoring / error rate
→ fallback to secondary provider or degraded mode
→ retry with backoff if idempotent and safe
→ Prevent by caching responses and
  reducing real-time reliance on 3rd parties

9. Auth / Authorization Failure

Detect via auth error responses (401 / 403)
→ auto-refresh tokens / re-authenticate
→ fallback to limited access if possible
→ Prevent with proactive token rotation
  and expiry monitoring + alerting

10. Network Issue to Dependency

Detect via connection errors / timeout spikes
→ retry with backoff + alternate endpoints
→ circuit breaker to stop failing calls
→ Prevent with multi-region routing
  and redundant network paths

11. Dependency State Inconsistency

Detect via data mismatch checks / lag metrics
→ reconcile: re-fetch from authoritative source
→ fallback to primary over replica for critical reads
→ Prevent with cache invalidation strategies
  and quorum reads where needed

12. Cascading Dependency Failure

Detect via multi-service latency / error spikes
→ circuit breakers + bulkheads to contain blast
→ degrade non-critical features to protect core
→ Prevent by isolating services:
  strict timeouts, async decoupling, no fan-out

5 Core Dependency Mitigation Patterns — Everything Maps Here

1. Retry → handle transient / intermittent failures 2. Timeout → avoid blocking threads indefinitely 3. Circuit Breaker → stop calling a known-failing dependency 4. Fallback → serve cached or degraded response 5. Decouple → async messaging, local cache, queue

Staff-Level One-Liner

"I would detect dependency issues via latency and error metrics, apply timeouts and retries for transient failures, use circuit breakers to prevent cascading failures, and fallback to cached or degraded responses where possible."

Ultra-Compact Playbook — Say This When You Freeze

1. Detect via errors / latency metrics 2. Stop calling failing dep → circuit breaker 3. Retry if transient → exponential backoff 4. Fallback to cache or degraded response 5. Decouple long-term → async / caching / queue

Final Design Principle

Your system is only as reliable as its weakest dependency. Design for the absence of every dependency you call.
Ask for every dep: "What happens to my service if this is down for 5 minutes?"
