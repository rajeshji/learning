Storage Tiering — Hot / Warm / Cold

Right data on the right storage at the right cost — Staff Engineer level

The Big Picture

5–10% of data is hot, 20–30% warm, 60–80% cold. Keeping everything on SSDs wastes money. Keeping everything on HDDs kills performance. Storage tiering puts the right data on the right medium automatically.

Data Lifecycle & Migration Policies

Data naturally cools over time. Systems migrate it based on:

Age-based: < 7 days → Hot (NVMe SSD) 7–90 days → Warm (HDD / Object) > 90 days → Cold (Glacier/Tape) Access-based: > 100 reads/day → Hot 1–100 reads/day → Warm < 1 read/month → Cold Business rules: Customer invoices → Warm after 30 days Audit logs → Cold after 90 days Backups → Archive after 1 year

Most production systems combine age + access frequency policies. Add a minimum residency time (hysteresis) to avoid frequent oscillation between tiers.

Automatic Tiering — Heat Score

Systems assign every object a "temperature" score and migrate transparently:

Heat Score = Read Count + Write Count + Recency + Business Priority High score → promote to Hot (NVMe SSD) Low score → demote to Warm or Cold Monitor Usage → Calculate Heat Score → Choose Tier → Move Data → Update Metadata → Application never notices

Real-World Examples

Elasticsearch — Index Lifecycle Management (ILM)

Hot Node → recent logs (NVMe, fast indexing) ↓ Warm Node → 7–30 days (lower cost) ↓ Cold Node → 30–90 days (read-only) ↓ Frozen Node → archive (object storage)

Kafka — Tiered Storage

Recent partitions → Local SSD (fast consumer reads) Old segments → Object storage (S3) — infinite retention

Prometheus + Thanos

Last 7 days → Local SSD (fast queries) Older → Object storage (S3/GCS)

Banking Database

Current month → NVMe SSD (active transactions) Last year → HDD (occasional queries) Older 7+ years → Archive storage (compliance)

Caching vs Tiering — Key Distinction

AspectCachingTiering
Data ActionCopies dataMoves data
DurationTemporaryPermanent (policy-driven)
GoalImprove latencyOptimize cost
EvictionAnytime (LRU/LFU)Only via lifecycle policy
Source still availableYesNo (data has moved)

Caching accelerates access. Tiering optimizes storage economics. They are complementary, not alternatives.

Production Failure Scenarios

SSD Storage Full

Cause: Old data never migrated off hot tier  ·  Fix: Implement automatic lifecycle policies

Slow Analytics Queries

Cause: Frequently queried data demoted to cold storage  ·  Fix: Adjust heat thresholds or cache popular datasets

High Storage Costs

Cause: All data stored on premium SSD by default  ·  Fix: Introduce hot/warm/cold tiering with lifecycle policies

Unexpected Retrieval Delays

Cause: Cold archive retrieval takes minutes/hours  ·  Fix: Communicate SLA clearly or pre-warm required datasets

Tier Oscillation

Cause: Objects repeatedly moving between hot and warm  ·  Fix: Add hysteresis (minimum residency time before migration)

Key Takeaways

5–10% hot · 20–30% warm · 60–80% cold → Tiering matches storage cost to access frequency. Hot → NVMe/SSD: <1ms, highest cost, active data Warm → HDD/Object: 5–20ms, medium cost, periodic access Cold → Glacier/Tape: seconds–hours, lowest cost, archive Migration policies: Age-based: time since creation Access-based: read/write frequency Heat score: composite (reads + recency + priority) Business: regulatory retention rules Hysteresis: minimum residency prevents oscillation Caching ≠ Tiering: Cache = copy, temporary, latency goal Tier = move, permanent, cost goal Cloud: S3→Glacier, Elasticsearch ILM, Kafka tiered storage, Prometheus+Thanos, database partitioning all use tiering. Staff monitors: SSD utilization, cold retrieval latency, cost per GB per tier, heat score distribution.
