Why MQ Failures Are Uniquely Dangerous

MQ provides: async communication + buffering + decoupling + event streaming MQ failures involve: producers + brokers + partitions + consumers + offsets + ordering 8 root failure classes: broker | producer | consumer | ordering | delivery replication | backpressure | coordination
Failure Scenario When It Occurs How To Detect How To Mitigate How To Prevent Cascading Failure Risk Trade-off
1 — Broker Availability Failures
Broker CrashMust Know Hardware failure, OOM kill, process crash on broker node Broker health check fails, partition leader alerts Failover to replica broker, trigger leader re-election Multi-broker cluster, replica factor >= 3 Producers blocked, consumers stalled — event pipeline stops More brokers add replication overhead and cost
Complete Cluster OutageMust Know DC outage, network failure, all broker nodes unavailable Cluster-wide unavailable alerts, producer/consumer failures DR failover to secondary region cluster Multi-region clusters, MirrorMaker/Replicator for cross-region Entire event-driven pipeline stops — all downstream services stall Cross-region replication adds significant latency and cost
Leader Broker FailureMust Know Partition leader broker crashes — that partition loses its leader Partition leader unavailable, producer write failures Leader re-election from ISR (In-Sync Replicas) Multiple replicas in ISR, unclean leader election = off Temporary write unavailability — producers queue up or fail Larger ISR increases replication overhead and write latency
ZooKeeper / KRaft Failure Coordination node fails — cluster loses metadata/leader management Metadata errors, leader election failures, cluster instability Failover coordinator, restore quorum Replicated ZooKeeper ensemble (3/5 nodes), or KRaft mode (Kafka 3+) Cluster-wide instability — no leader elections, metadata stale Consensus quorum adds coordination overhead per metadata op
Broker Disk Full Log retention not configured — disk fills with uncompacted segments Disk usage alerts, broker refuses to accept new messages Emergency log cleanup, expand volume Retention limits (size + time), disk monitoring with headroom alert Broker stops accepting writes — producers fail, cluster unbalanced Aggressive retention can delete messages before consumers read them
2 — Broker Performance and Resource Failures
Broker CPU Saturation High-throughput compression (gzip/lz4) or heavy fanout traffic Broker CPU >90%, produce/consume latency spike Add brokers, reduce compression level, shed load Better partition distribution, compression tuning (snappy) Produce latency spike → producer timeouts → retry storm Less compression reduces CPU but increases network/disk usage
Disk IO Bottleneck Heavy sequential writes + replication IO competing on same disk IO wait spike, produce/replicate latency increase NVMe/SSD upgrade, separate log and replication IO Dedicated log disks, proper batch size tuning Producer timeout cascade → retry storm → broker further overloaded NVMe SSDs are significantly more expensive
Network Saturation Heavy replication traffic + consumer fanout saturates broker NIC Network throughput maxed, replication lag increases Throttle replication (kafka-configs), reduce consumer fanout Better partition balancing, dedicated replication network Replication lag grows → ISR shrinks → message loss risk increases More bandwidth is expensive; throttling replication slows ISR sync
Broker Memory Pressure Large retention or page cache exceeded by concurrent readers Heap / OS memory alerts, GC pause spike Tune JVM heap, reduce retention, add brokers Proper retention policy, off-heap page cache awareness OOM broker crash → leader re-election → temporary unavailability Less page cache reduces read performance for catching-up consumers
3 — Producer Failures
Producer Retry StormMust Know Broker slowness/timeout triggers all producers retrying simultaneously Retry traffic spike, broker request queue depth growing Exponential backoff + jitter, circuit breaker on producer Retry budgets, per-producer rate limits Broker overload — retry amplification buries the already-slow broker Backoff increases end-to-end message latency
Duplicate Message ProductionMust Know Producer retries after uncertain ack — message written twice Duplicate message IDs in consumer logs Idempotent producer (enable.idempotence=true) Exactly-once producer semantics (Kafka EOS), producer ID + sequence Duplicate downstream processing — double payment, double order Idempotent producers add coordination overhead per produce request
Message Loss Before Ack Producer crashes after send but before receiving broker ack Missing sequence numbers, consumer gap detection Replay from durable producer buffer on restart Durable producer buffer, acks=all, sync produce with confirmation Missing downstream events — workflow steps silently skipped acks=all significantly increases produce latency
Producer Buffer Exhaustion Broker slow/unavailable — local send buffer fills completely BufferExhaustedException, producer blocking metrics Apply backpressure — block or drop with alerting Better flow control, producer buffer sizing, circuit breaker Producer crashes or drops messages — event pipeline data loss Blocking producers adds latency; dropping loses messages
4 — Consumer Failures
Consumer LagMust Know Consumers process messages slower than producers produce them Consumer lag metrics, increasing offset delta Scale out consumer group, increase batch size Better consumer design, capacity planning, autoscaling Queue backlog explodes → disk exhaustion → broker disk full More consumers increase coordination and rebalance frequency
Poison MessageMust Know Malformed/unprocessable message enters topic — consumer fails every time Consumer retry loop on same offset, DLQ growth Dead-letter queue — route poison message aside, continue Schema registry enforcement, producer-side validation Entire partition blocked — all subsequent messages on that partition stall DLQ requires operational process to investigate and reprocess
Consumer Crash / RebalanceMust Know Consumer crashes or rejoins group — triggers partition reassignment Consumer heartbeat loss, rebalance events in group coordinator Sticky partition assignment, graceful rebalance Consumer groups, proper session timeout tuning Processing pause during rebalance → lag builds → delay cascade Longer session timeout slows detection of dead consumers
Offset Commit Failure Commit times out or consumer crashes before committing offset Duplicate message consumption, reprocessing on restart Retry commit, handle duplicates with idempotent consumer Reliable offset storage, synchronous commit on critical paths Duplicate processing — side effects replayed on restart Synchronous offset commits add latency per batch
Slow Consumer Heavy processing logic — consumer takes too long per message Processing latency spike, session timeout fires during processing Parallelise processing, offload heavy work async Efficient consumer design, separate IO from processing Session timeout triggers rebalance → further disruption mid-processing More parallelism can break per-key message ordering
5 — Ordering and Delivery Failures
Out-of-Order DeliveryMust Know Parallel consumers, retries from different partitions, multi-thread processing Sequence mismatch in consumer output, invalid state transitions Reorder buffer using sequence numbers before processing Per-key partition ordering (Kafka: same key = same partition) Wrong state transitions — cancel processed before create Per-key ordering reduces consumer parallelism
Duplicate DeliveryMust Know At-least-once delivery — retry delivers same message more than once Duplicate IDs detected in consumer processing logs Idempotency key deduplication on consumer side Exactly-once semantics (Kafka EOS), dedup store Double payment, double order, duplicate notification Exactly-once semantics add significant complexity and latency
Message LossMust Know Broker crash before replication, acks=0 or acks=1 config Sequence gaps in consumer, audit mismatch Replay from replica, replay from upstream source acks=all, replication factor >= 3, min.insync.replicas=2 Missing business workflow steps — order never fulfilled acks=all with min.insync.replicas increases produce latency significantly
Delayed Delivery Queue backlog or network congestion — messages arrive late High consumer lag, event timestamp age metrics Prioritise critical messages, scale consumers immediately Capacity planning, separate queues per priority tier Stale business events processed — decisions made on old data Priority queues add routing complexity and risk starvation
6 — Partition and Replication Failures
Under-Replicated PartitionMust Know Slow or unavailable replica — ISR shrinks below min.insync.replicas UnderReplicatedPartitions metric, ISR shrink alerts Re-sync replica, add brokers if capacity is the issue Monitor ISR size, spread replicas across AZs Increased message loss risk — fewer durability guarantees Larger ISR requirement reduces availability during partial failure
Hot PartitionMust Know Skewed message key — one partition receives most traffic Uneven partition lag, one broker CPU at 100% Repartition with better key, or add sub-partition prefix Better partition key selection, random suffix for hot keys Single broker overload → that broker crashes → downstream stall Random suffix breaks per-key ordering guarantee
Partition Rebalance Storm Rapid consumer scaling or crash-restart loop triggers repeated rebalance Frequent rebalance events, consumer processing pauses Sticky partition assignment (cooperative rebalancing) Controlled scaling, incremental cooperative rebalance protocol Consumer processing pauses repeatedly → lag builds continuously Sticky assignment slows detection of truly dead partitions
Replication Lag Slow follower broker — replica falls behind leader's log offset Replica lag metric, ISR shrink alert Throttle replication bandwidth tuning, investigate slow broker Dedicated network for replication, SSD storage, broker sizing ISR shrinks → durability guarantee weakened → message loss on crash Forcing ISR sync reduces throughput during catch-up
7 — Coordination and Consensus Failures
Leader Election Failure Network partition — no broker can achieve quorum for leader election No partition leader detected, all writes to that partition fail Restore quorum, retry election Multi-AZ broker placement, stable ZooKeeper/KRaft ensemble Write unavailability for affected partitions — producers queue up Faster election timeout risks false elections on transient issues
Split Brain MQ Cluster Network partition — both cluster halves think they have the leader Conflicting leaders, diverging log offsets Fence minority partition (unclean leader election = false) Consensus protocol, unclean.leader.election.enable=false Diverging message logs — different consumers read different data Disabling unclean election reduces availability during partition
Metadata Inconsistency Coordinator lag — different brokers have different partition views Producers routing to wrong broker, metadata mismatch errors Re-fetch metadata from authoritative coordinator Consensus-backed metadata, fast metadata sync Producers route incorrectly — messages to wrong broker or dropped Consensus metadata adds coordination latency per metadata refresh
Quorum Loss Too many broker/ZooKeeper nodes fail — majority unavailable ISR below min.insync.replicas, write failures cluster-wide Read-only / degraded mode, restore nodes Multi-AZ quorum, 3+ replicas across failure domains All writes blocked until quorum restored — full pipeline stall Multi-AZ quorum adds cross-AZ latency to every write
8 — Backpressure and Load Failures
Queue Backlog ExplosionMust Know Producers faster than consumers — lag grows unbounded Consumer lag growing, disk usage increasing Scale consumers immediately, apply producer rate limits Backpressure signals to producers, autoscaling consumers Disk exhaustion → broker stops accepting writes → full pipeline stall Producer rate limiting reduces throughput and slows upstream systems
Reconnect Storm Broker restart or network recovery — all producers/consumers reconnect at once Massive connection attempt spike, broker CPU/network saturated Throttle reconnections, stagger client reconnects Exponential backoff on client reconnect, reconnect jitter Broker overloaded by reconnect flood → slow to accept traffic → retry loop Slower reconnect means clients take longer to resume processing
Load Amplification Retries + rebalance + consumer lag combine — traffic multiplies Traffic spike beyond expected load, cascading metric alerts Rate limiting, shed less-critical topics Better retry policy, separate critical and non-critical traffic Cluster collapse — amplified load overwhelms all brokers simultaneously Shedding traffic drops messages — downstream gaps
Infinite Retention Growth Consumers stall or fall far behind — unread segments grow unbounded Disk usage spike, retention growing beyond configured limits Cleanup aged segments, enforce retention limits immediately Retention limits (size and time), disk alerts with response runbook Broker disk full → writes fail → full event pipeline stops Aggressive cleanup may delete messages before stalled consumers read them
9 — Persistence and Recovery Failures
Log Segment Corruption Disk crash, storage hardware failure, bit flip in log segment Segment checksum failure on load, broker startup error Restore from replica, skip/truncate corrupted segment Log checksums, replication for redundancy, ECC storage Partition unavailable — all consumers of that partition stall Checksum validation adds minor overhead to every log read/write
Offset Store Corruption Crash during __consumer_offsets write — committed offset is wrong Consumer restart delivers wrong messages, duplicate or gap detected Reset offset to last known good position, replay from safe point Replicated __consumer_offsets topic (3+ replicas), durable commits Duplicate or missing processing on all partitions of that consumer group More replicas on offset topic increase write latency for every commit
Slow Broker Recovery Large log to replay after broker crash — long startup before joining cluster Broker startup time exceeds normal, ISR missing for partitions Restore from recent checkpoint, use faster storage Frequent checkpointing, SSD storage, controlled log retention Extended partition under-replication — message loss risk during recovery More frequent checkpoints add IO overhead during normal operation
Log Compaction Failure Compaction interrupted — disk full or bug — log grows unbounded Log size growing despite compaction enabled, disk alert Retry compaction, free disk space, adjust compaction config Compaction monitoring, sufficient disk headroom for compaction temp space Disk exhaustion from uncompacted log → broker stops writing Aggressive compaction uses significant CPU and extra disk during run

Staff-Level MQ Thinking — 9 Questions to Ask Always

1. Messages lost? → acks=all + RF>=3 + min.insync.replicas 2. Messages duplicated? → idempotent consumer + exactly-once EOS 3. Ordering broken? → per-key partition + sequence numbers 4. Consumers behind? → scale out + backpressure + autoscaling 5. Retries overload broker? → backoff + jitter + circuit breaker 6. One partition hot? → better key + random suffix + repartition 7. Rebalance destabilize? → sticky assignment + cooperative protocol 8. Backlog exhaust storage? → retention limits + producer rate limits 9. Broker failover safe? → ISR >= 2 + multi-AZ + unclean election off

Delivery Semantics — Know the Trade-off for Every Interview

At-Most-Once → no retries, may lose messages → use: metrics / logs / telemetry At-Least-Once → retries, may duplicate → use: most production systems (idempotent consumer required) Exactly-Once → no loss, no duplicate → use: payments / financial events (Kafka EOS, high complexity)

Final Mental Model — All MQ Failures Reduce to 5 States

1. Broker unavailable → crash / disk full / coordination failure 2. Consumer slow → lag + backlog + disk exhaustion 3. Message corrupted → duplicate / lost / out-of-order 4. Partition problem → hot key / under-replicated / rebalance storm 5. Coordination failed → split brain / quorum loss / metadata inconsistency Most dangerous combo: consumer lag + retry storm lag → backlog → disk full → broker stop → producers retry → amplification loop
