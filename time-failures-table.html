Why Time Failures Are the Most Subtle Failure Class

Time is the hidden dependency of every distributed system. Every node has its own clock. Every clock drifts. Every timezone has edge cases. Time failures are dangerous because: 1. They are often invisible — no error is thrown, just wrong behaviour 2. They are intermittent — DST transitions and leap seconds only hit once 3. They are hard to reproduce in testing — you cannot easily advance system clocks

1 — Clock Synchronisation Failures
NTP Failure / Clock DriftMust Know NTP server unreachable or misconfigured — node clock drifts from wall clock over time Clock skew monitoring alert, distributed trace timestamps out of sequence Force NTP sync (ntpdate), restart NTP service Redundant NTP sources, clock skew monitoring alert, chrony preferred over ntpd Distributed ordering broken — events appear to arrive before they were sent More frequent NTP sync adds network traffic; chrony uses slewing which is slow to correct large drift
Clock Skew Causing Event ReorderingMust Know Two nodes have different clock values — events timestamped on each appear out of order to consumers Events in stream arriving with timestamps earlier than previous events from other nodes Use logical clocks (Lamport / HLC) for ordering instead of wall clock Lamport timestamps or Hybrid Logical Clocks for event ordering, never rely on wall clock for causality Incorrect event ordering leads to wrong stream processing results, corrupted state Logical clocks add metadata overhead per event and require understanding of causal ordering
VM / Container Clock Drift After Migration VM live-migrated or container suspended/resumed — clock pauses but real time advances Clock jumps forward at resume, timestamps suddenly far ahead of expected Force NTP sync immediately on resume, use monotonic clocks for intervals Hypervisor clock sync on resume, monotonic clock for all interval measurements All time-based logic (TTL, lease, session) jumps forward — immediate expiry storm Hypervisor sync requires guest OS cooperation and introduces a sync latency window
Leap Second Bug UTC leap second inserted — some systems add extra second, others do not — 1 second skew Errors on systems that hit leap second handling bug (often at midnight UTC June/December 30) Leap smearing via NTP as workaround, restart affected services Use leap smearing NTP servers (Google/AWS), test leap second handling in staging Consensus failures — nodes disagree by 1 second on event ordering at epoch boundary Leap smearing means time does not precisely match UTC during the smear window
2 — Timezone and DST Bugs
Local Timezone Stored Instead of UTCMust Know Application stores timestamps in server local timezone — after timezone change, all historical times wrong Data anomalies after server timezone change, times off by UTC offset Migrate stored timestamps to UTC, standardise all code to output UTC Always store UTC, always convert to local timezone at display layer only All time-based queries, reports, and SLAs compute incorrectly after timezone change UTC-everywhere requires discipline across all teams and is harder to debug locally
DST Transition Duplicate / Missing HourMust Know Clocks go back 1 hour — 1am to 2am occurs twice; cron jobs run twice or appointment times ambiguous Duplicate job executions at DST fall-back, double-billing or duplicate records Deduplicate by idempotency key, treat duplicate execution as expected Store and schedule in UTC, convert to local timezone for display only, idempotent job design Duplicate financial transactions, duplicate notifications, duplicate state changes UTC scheduling correctly handles DST but breaks user expectations for "run at 2am local"
Timezone-Aware vs Naive Datetime Comparison Code compares timezone-aware datetime with naive datetime — runtime error or silent wrong comparison TypeError in Python, unexpected comparison results, wrong date calculations Add explicit timezone to all naive datetimes, fix comparison Type enforcement (pytz / Joda-Time / java.time), linting to disallow naive datetime construction Silent wrong results — expiry checks, scheduling, and billing calculations return wrong values Strict timezone-aware types require more verbose code in all datetime operations
Multi-Region Log Timestamp Mismatch Services in different regions log with local timezone — correlating logs across regions is impossible Log correlation fails, events appear out of sequence across regions Standardise all log timestamps to UTC immediately Logging framework configured to always output UTC, enforced in log schema Incident debugging becomes extremely slow — cannot establish causal sequence from logs UTC logs are less intuitive for developers working in a single local timezone
3 — Cron and Scheduled Job Failures
Cron Job Silently Never RunsMust Know Cron misconfigured, cron daemon down, or job exits non-zero silently — scheduled work not done Business data not updated (stale reports, unpurged records) — discovered late Run job manually, fix cron configuration Cron monitoring (heartbeat to dead-man switch), alerting on missed job execution Accumulating backlog or stale data — effect grows silently until business impact detected Dead-man switch monitoring requires external monitoring infrastructure per job
Cron Timezone MisconfigurationMust Know Cron expression interpreted in server timezone instead of intended timezone — job runs at wrong time Job runs at unexpected time (e.g. 5am instead of midnight), business reports at wrong schedule Convert cron expression to UTC immediately Always write cron in UTC, document intended local time alongside UTC expression Financial reports, billing cycles, and batch jobs run at wrong times — downstream process depends on output being ready UTC cron expressions are non-intuitive when communicating schedule to business stakeholders
Overlapping Job ExecutionsMust Know Job takes longer than schedule interval — next execution starts before previous finishes Multiple instances of same job running simultaneously, resource contention, data duplication Add distributed lock to prevent concurrent execution Idempotent job design, distributed lock with TTL, single-instance job scheduler Data corruption or double processing if job is not idempotent Distributed lock means if previous job is stuck, next execution cannot start
Duplicate Cron Across Multiple Instances Application scaled to multiple replicas — cron runs on all replicas simultaneously Job effects appear N times (N = replica count), duplicate records, N× notifications sent Add leader election or distributed lock for cron coordination Single-instance cron coordinator (Kubernetes CronJob), leader-elected cron execution N× emails sent, N× charges billed, N× records created — proportional to replica count Single-coordinator cron creates single point of failure for job execution
4 — TTL and Expiry Failures
TTL Unit Confusion (ms vs seconds)Must Know Developer passes milliseconds where seconds expected — TTL set to 1000x longer or shorter than intended Cache entries never expire (very long TTL) or expire immediately (too short TTL) Fix TTL value, flush incorrectly-TTL'd entries Named constants for TTL values, unit tests for TTL behaviour, strongly-typed Duration types Too-short TTL causes cache miss storm on DB; too-long TTL serves stale data indefinitely Strongly typed Duration requires API changes across call sites
Distributed Lock TTL Expires Before Work CompletesMust Know Lock TTL set too short — another worker acquires lock while first is still working Two workers operating on same resource simultaneously, duplicate or conflicting operations Stop second worker, verify first completed correctly Lock TTL must be 2x maximum expected job duration, lock refresh during long operations Two concurrent writers corrupt shared resource Lock refresh requires heartbeat implementation; if refresh fails, lock may be held too long
Token / Session Expiry During Long Operation User auth token expires mid-operation (file upload, form submission) — operation rejected mid-flight Mid-operation 401 errors, user experience broken at arbitrary point in workflow Refresh token before expiry, retry with fresh token Sliding session expiry, long-lived refresh tokens, token refresh before starting long operations User loses work in progress — frustration, data loss, support tickets Sliding expiry keeps tokens alive longer — increased risk window if token is compromised
Cache TTL Set to Zero / Negative Configuration error sets TTL to 0 or -1 — all cache writes immediately expire Cache hit rate drops to 0%, backend load spikes Fix TTL configuration, flush and rebuild cache TTL validation at startup (reject 0 or negative), alarm on sustained 0% hit rate Database overload from every request being a cache miss TTL validation blocks using 0 as an intentional "no cache" signal
5 — Distributed Event Time Failures
Event Time vs Processing Time MismatchMust Know Stream processor uses processing time instead of event time — results change based on when events arrive, not when they occurred Results differ between reprocessing and live processing of same events Switch aggregations to event-time windowing with watermarks Always use event-time semantics in stream processing, embed event timestamp in every record Non-deterministic results — same data produces different output depending on processing time Event-time processing requires buffering late events, adding latency to results
Late-Arriving Events After Window ClosedMust Know Event arrives after the processing window it belongs to has closed and been emitted — event silently dropped Aggregate counts lower than expected, events in DLQ or late-event metric counter Configure allowed lateness window, reprocess late events into corrections Generous allowed lateness (minutes, not seconds), side output for late events Incorrect aggregates emitted — downstream consumers act on incomplete counts Longer allowed lateness delays finalisation of results and increases state memory
Watermark Too Aggressive — Events Always Late Watermark advances too quickly relative to actual event time distribution — most events classified as late Late-event counter very high, most events going to side output instead of main results Increase watermark slack to match actual event time distribution Profile event time distribution, set watermark = median delay + 2 standard deviations All aggregation results incomplete — virtually no events processed in-window Generous watermark slack increases result latency for all windows
Out-of-Order Event Processing Without Ordering Events processed in arrival order rather than event order — state machine or aggregate is wrong State machine reaches impossible state, aggregate results non-deterministic Apply event-time reordering buffer, sort before processing Partition by entity ID (all events for same entity go to same partition), event-time sorting Corrupted state — incorrect sequence of operations applied to entity Sorting adds latency; partitioning by entity limits parallelism for hot entities
6 — Deadline and Timeout Misconfiguration
Deadline Not Propagated Through Call ChainMust Know Incoming request has 100ms deadline — service makes downstream calls without passing deadline — downstream works for 500ms Caller times out but downstream continues work and commits — phantom writes without a successful response Cancel downstream work when deadline expires Propagate deadlines via context (Go context.Context, gRPC deadline propagation), never start work after deadline Wasted backend compute + inconsistent state (work done but caller timed out) Deadline propagation requires explicit handling at every call site
Lease Expiry During GC PauseMust Know Leader holds lease but GC pause suspends all threads — lease expires, new leader elected while old leader still thinks it is leader Dual leader scenario, conflicting writes detected after GC resumes Fence old leader via epoch/fencing token before accepting any new writes Lease TTL must be 2x maximum expected GC pause, low-pause GC (ZGC) for lease-holders Split brain — two leaders write to same resource simultaneously Longer lease TTL means slower detection of truly dead leaders
Absolute Deadline vs Relative Timeout Confusion Code passes relative timeout (duration) where absolute deadline (timestamp) expected — deadline set in past or far future Requests immediately timing out or never timing out Fix API call to pass correct deadline type Strong types for deadline vs duration (do not use plain integers for both) All calls on that path fail immediately or never fail — either outage or resource leak Strongly typed time types require more verbosity at every call site
Clock Skew Causing Lease Conflict Two nodes have different wall-clock times — a node whose clock is ahead thinks lease is expired when it is not Spurious leader elections, lock contention despite no actual expiry Use monotonic clocks for lease timing, not wall clock Monotonic clock for all lease/timeout measurements, NTP skew monitoring alert Election storm — repeated spurious elections disrupt cluster coordination Monotonic clocks cannot be compared across machines — cannot use for cross-node expiry
7 — Time-Based Data and Retention Failures
Retention Policy Deletes Too AggressivelyMust Know Retention misconfigured in wrong unit or wrong value — data deleted before intended expiry Data missing that should still be present, queries return empty where values expected Restore from backup, fix retention policy Retention policy testing with synthetic data, dry-run mode for retention jobs Compliance violation if deleted data was within legal retention window Dry-run retention adds operational steps; harder to detect bugs without actually deleting
Time-Range Query Returns Wrong Results in DST Window Query for "between 1am and 2am" during DST fall-back returns two hours of data instead of one (or zero) Unexpected row counts in DST period, reports show data anomalies twice a year Rewrite query in UTC, re-run affected reports All stored timestamps in UTC, all queries in UTC, timezone conversion at display only Financial and audit reports wrong twice a year on all systems not using UTC UTC-only storage makes it harder for business to reason about "business hours" data
Time-Series Gap from Clock Reset Server clock reset backwards (NTP correction) — metrics timestamped in past, gap or overlap in time series Metric spikes or gaps in monitoring at moment of clock correction Use monotonic counters with reset detection, tolerate gaps in dashboards Use monotonic timestamps for metric collection, detect and handle clock resets in ingestion pipeline Alert fires for "missing data" during clock correction — false incident triggered Monotonic metric timestamps cannot be compared across machines without additional metadata
Partition Pruning Fails Due to Clock Skew Partitioned table uses timestamp column — clock skew means rows land in wrong partition — pruning skips data Queries returning incomplete results, partition scan showing missing rows Rebuild affected partitions, fix clock sync NTP sync, partition boundary with buffer (write to N-1 and N partitions), clock skew monitoring Silent data loss in partition-pruned queries — looks correct but returns incomplete data Writing to multiple partitions increases write amplification and storage use
8 — Job Queue and Scheduling Failures
Delayed Job Pile-Up After System RestartMust Know System down for maintenance — hundreds of delayed jobs all become due simultaneously on restart Massive job queue depth immediately after restart, workers saturated Rate-limit job processing on restart, process in priority order Staggered job scheduling (jitter on initial delay), rate-limited job dequeue on startup Worker overload — job pile-up overwhelms processing capacity on restart Jitter on job delays makes scheduling less predictable for SLA commitments
Job Starvation from Priority InversionMust Know Low-priority jobs hold resources needed by high-priority jobs — high-priority jobs wait indefinitely High-priority jobs backed up while low-priority complete normally Apply priority inheritance or preempt low-priority jobs Priority-aware scheduler, priority inheritance protocol, aging for low-priority jobs SLA violation for high-priority work — urgent tasks delayed behind bulk processing Aggressive priority enforcement may starve low-priority jobs entirely
Distributed Cron Without Coordination — Duplicate Run Multiple scheduler instances (no leader election) each trigger the same job Job effects appear N times — duplicate emails, duplicate charges, duplicate records Add idempotency check at job start, deduplicate by job ID Single coordinator with leader election (Kubernetes CronJob), idempotent job logic N× business effects for every scheduled run — severity scales with replica count Single coordinator is a SPOF for job scheduling — coordinator failure means no jobs run
Job Deadline Missed — Silent No-Op Job execution starts after its deadline has passed — job runs but result is no longer useful Job completes successfully but downstream consumer ignores it (too late), SLA breached Check deadline at job start, skip if past deadline and log it Deadline check at job pickup, alerting on deadline-exceeded jobs SLA violations accumulate silently — jobs run but produce no useful output Skipping past-deadline jobs may cause data gaps if work was genuinely needed
9 — Clock-Dependent Security Failures
JWT Rejected Due to Clock SkewMust Know Issuer and validator clocks differ — JWT issued at t=0 but validator's clock is behind, rejects as "not yet valid" Auth failures for valid tokens, correlated with recent NTP drift event Add clock skew tolerance (nbf/exp leeway of 5 minutes) at validator NTP sync on all nodes, small allowed clock skew leeway (30-300 seconds) in JWT validation All users logged out simultaneously if validator clock drifts far enough Skew leeway allows replayed tokens within the leeway window
TOTP Auth Failure from Client Clock DriftMust Know User device clock drifts from server — TOTP code generated for wrong time window, rejected Users unable to log in despite correct TOTP app, support tickets spike Accept adjacent time windows (T-1, T, T+1) at validator TOTP validation accepting one adjacent window each side, user instructions to sync device clock User lockout — cannot authenticate until device clock corrected Accepting adjacent windows reduces security window per code
Certificate Validity Window Violated by Clock Skew Server clock behind — presents a certificate whose notBefore is in the "future" relative to server clock TLS handshake failures, certificate invalid errors in client Sync server clock, request replacement certificate if needed Clock monitoring with tight drift alert, certificate issuance with grace period before notBefore Complete TLS failure — all HTTPS connections rejected until clock corrected Grace period before notBefore means certificate is valid slightly before intended
Token Replay via Time Confusion System accepts tokens with past timestamps due to loose expiry validation — attacker replays captured token Security audit finding, or detected via anomalous re-use of same token ID Tighten expiry validation, add jti (JWT ID) nonce to prevent replay Strict expiry enforcement, jti tracking to detect replay, short token lifetime (15 minutes max) Unauthorized access using expired but accepted tokens — data breach risk jti tracking requires server-side storage that scales with token issuance rate

10 Must-Know Time Failures for Interviews

1. Clock skew ordering → Lamport / HLC instead of wall clock for causality 2. DST duplicate cron → store+schedule in UTC, idempotent job design 3. Cron silently not run → dead-man switch heartbeat monitoring per job 4. Duplicate cron replicas → leader election or Kubernetes CronJob (single instance) 5. Lock TTL too short → TTL = 2x max job duration + heartbeat refresh 6. JWT clock skew reject → NTP sync + leeway (30-300s) at validator 7. Event time vs proc time → always use event-time windowing with watermarks 8. Late events dropped → allowed lateness + side output for late events 9. Deadline not propagated → pass context deadline to every downstream call 10. Local TZ stored not UTC → store UTC always, convert at display layer only

Staff-Level Time Thinking — 9 Questions to Ask Always

1. Are all timestamps stored in UTC? → if not, DST bugs are guaranteed twice a year 2. Are deadlines propagated through chain? → if not, phantom work continues after caller times out 3. Is event ordering by wall clock? → wall clock is wrong — use Lamport / HLC / partition 4. Are cron jobs idempotent? → if not, duplicate run = data corruption 5. Are lock TTLs 2x max job duration? → if not, two workers will run simultaneously 6. Do JWT validators allow clock skew? → if not, NTP drift = user lockout 7. Are late events handled gracefully? → if not, aggregates will be silently incomplete 8. Is there a dead-man switch per job? → if not, silent cron failure goes undetected 9. Are monotonic clocks used for intervals? → wall clock can jump backwards; monotonic cannot

Final Mental Model — The 4 Time Rules

1. Store UTC → store timestamps in UTC always; convert to local only at display 2. Use logical → use Lamport / HLC for ordering; never trust wall clock for causality 3. Make idempotent → crons and jobs must be safe to run twice (DST, duplicate, retry) 4. Monitor silence → dead-man switch for every scheduled job; silence = failure The single most impactful practice: Store all timestamps in UTC. This one rule eliminates 80% of DST bugs, timezone confusion, and cross-region mismatches.
