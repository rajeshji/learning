Performance Laws for Distributed Systems

Little's Law • Amdahl's Law • Universal Scalability Law

Why These Laws Matter

These laws help engineers predict system capacity, identify bottlenecks, and make scaling decisions instead of guessing.

Staff/Principal Engineers are expected to know: when to apply each law • what problem it solves • how to identify violations in production • design implications • trade-offs

1

Little's Law — Capacity Planning

Relates concurrency, throughput and latency

L = λ × W

SymbolMeaning
LConcurrency (Requests in system)
λThroughput (Requests/sec)
WLatency (Seconds)

Example

1000 RPS × 0.2 s = 200 concurrent requests Netflix example: 5000 RPS × 0.05 s = 250 concurrent

When to Use

Thread Pool Sizing Connection Pool Queue Sizing API Capacity Load Testing

Failure Symptoms

  • Queue keeps growing
  • Increasing thread count
  • Rising latency
  • Request timeouts

How to Fix

  • Reduce latency
  • Increase throughput
  • Increase concurrency
  • Remove bottlenecks

Staff Thinking

Why is latency high?

Is latency causing a concurrency explosion?

Golden Rule

Increasing latency automatically increases concurrency.

Interview Q: How many threads if API handles 2000 RPS at 100 ms latency? A: 2000 × 0.1 = 200 threads

2

Amdahl's Law — Parallel Speedup

Maximum speedup achievable through parallelisation

Speedup = 1 / (S + P/N)

SymbolMeaning
SSequential portion (cannot be parallelised)
PParallel portion
NNumber of CPUs

Example

20% sequential + 80% parallel 100 CPUs → Max speedup = 4.8x (NOT 100x) The sequential 20% is your ceiling.

When to Use

CPU Optimization MapReduce / Spark Fork-Join Parallel Streams GPU Workloads

Failure Symptoms

  • Adding CPUs doesn't improve performance
  • High CPU but no throughput gain
  • Single-threaded sections visible in profiler

How to Fix

  • Reduce sequential work
  • Use parallel / async algorithms
  • Remove global locks
  • Lock-free data structures

Staff Thinking

How many CPUs should we add?

What percentage is actually parallelisable?

Golden Rule

The sequential portion is your scalability ceiling.

Interview Q: Why doesn't doubling CPUs double throughput? A: The sequential portion is never reduced by adding CPUs — Amdahl's Law.

3

Universal Scalability Law — Real-World Scaling

Why systems stop scaling due to contention & coordination overhead

Throughput(N) = N / (1 + α(N-1) + βN(N-1))

SymbolMeaning
αContention (competition for shared resources)
βCoherency (communication / coordination cost)
NNumber of users or resources

Scaling Phases

Good Scaling: Users↑ → Throughput↑ Diminishing: Contention↑ slows growth Negative: Throughput↓ despite more servers Real Example: 100 Kafka consumers 20 partitions → 80 consumers sit idle

When to Use

Distributed Systems Kubernetes Microservices Kafka / Queues Databases

Failure Symptoms

  • Throughput plateaus with more servers
  • Higher latency with more instances
  • High lock wait / CPU contention
  • Increased network RTT & queue wait

How to Fix

  • Sharding / partition data
  • Reduce shared state
  • Event-driven async messaging
  • Local caching & lock-free structures

Staff Thinking

Add more servers

What shared resource is limiting scaling?

Golden Rule

More servers don't always increase throughput.

How Staff Engineers Think — The Decision Chain

Traffic Increases ↓ Little's Law → How many requests exist in the system? ↓ Amdahl's Law → Can we parallelise to handle more? ↓ USL → Will adding servers actually help?

Interview Cheat Sheet

Little's Law • Concurrency = Throughput x Latency • Capacity Planning, Thread Pools, Queue Sizing • Q: 2000 RPS × 100ms = 200 threads needed Amdahl's Law • Parallelisation Limit • Sequential code limits speedup regardless of CPUs • Q: 20% sequential = max 5x speedup, ever Universal Scalability Law • Real distributed scaling • Contention (α) + Communication (β) = Scaling Limit • Q: Why did adding pods stop helping?
