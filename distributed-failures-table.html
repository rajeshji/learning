Distributed System Failure Scenarios

Staff-level · 9 categories · 38 scenarios · detect / mitigate / prevent / cascading / trade-off

Why Distributed Failures Are the Hardest

Once multiple machines coordinate, failures become: partial + asynchronous + inconsistent + non-deterministic Root causes: coordination | replication | ordering | consensus partition | time sync | distributed transactions | state divergence
Failure Scenario When It Occurs How To Detect How To Mitigate How To Prevent Cascading Failure Risk Trade-off
1 — Network Partition and Split Brain Failures
Network PartitionMust Know Network link cut — some nodes cannot communicate with others Heartbeat timeout, missing peer responses, split cluster view Quorum-based writes, isolate minority partition (no writes) Multi-path networking, quorum-based systems (Raft/Paxos) Cluster splits → two sides each think they are authoritative Availability reduced during partition (CP over AP)
Split BrainMust Know Partition causes both sides to elect a leader — two leaders exist Multiple leaders detected, conflicting writes in audit logs Fence minority partition with fencing tokens, refuse writes Raft/Paxos consensus — only majority can elect leader Both leaders accept writes → data diverges → reconciliation nightmare Lower write availability during partition
Partial Partition Some nodes can reach others but not all — uneven reachability Inconsistent peer visibility in cluster health checks Dynamic routing/re-election to restore clean majority Better network topology, redundant paths between all nodes Replica inconsistency — different nodes see different cluster state More complex recovery logic required
Asymmetric Partition A can reach B but B cannot reach A — one-way communication Bidirectional heartbeat mismatch alerts Force reconnection, rebuild from clean state Symmetric health checks, bidirectional probes Inconsistent cluster state — one side thinks link is healthy Monitoring and recovery add significant complexity
2 — Coordination and Leader Election Failures
Leader Election FailureMust Know Consensus timeout, network issue, insufficient quorum for election No leader detected, write requests all fail Trigger re-election, add nodes to restore quorum Stable election timeout tuning, reliable heartbeat intervals Write unavailability until new leader elected — service stalls Slower elections reduce the frequency of false leader changes
Multiple Leaders (Dual Primary) Partition or race condition — two nodes both believe they are leader Conflicting writes detected, version/term collision Force fencing — one leader's writes rejected via fencing token Strong consensus (Raft epoch/term validation), monotonic token Silent data corruption — both leaders accepting incompatible writes Lower write availability during fencing resolution
Leader Flapping Frequent re-elections due to unstable heartbeat or overloaded leader Rapid leader changes in cluster event log Stabilise election timeout, reduce leader load Proper health check tuning, separate leader from data IO Continuous write interruptions — service effectively unavailable Slower failover but more stable once leader elected
Coordinator Node Failure Metadata server / transaction coordinator crashes Coordinator health alerts, all coordinated ops fail Failover to standby coordinator Replicated coordinators, standby ready to take over immediately Entire cluster coordination failure — all distributed ops stall Coordination replication adds latency to every coordinated write
3 — Replication and Replica Failures
Replica LagMust Know Follower falls behind leader — slow network, large write burst Replication lag metrics (seconds behind leader) Route critical reads to leader, set bounded staleness Tune replication pipeline, synchronous replication on critical paths Stale reads at scale — all users on that replica see old data Synchronous replication increases write latency significantly
Replica DivergenceMust Know Missed replication events, network error mid-stream Checksum mismatch between replicas Read repair, anti-entropy sync from leader Quorum replication, synchronous ack before commit Different users on different replicas see different data More replication network traffic and bandwidth
Failed Replica Sync Sync process interrupted — node partially rebuilt Persistent divergence after repair attempt Full replica rebuild from primary Incremental sync with checkpointing, resume on failure Long-term inconsistency if diverged replica serves reads Full rebuild increases IO and network load significantly
Replica Overload During Rebuild Re-replication storm after node failure — primary bombarded High IO/network throughput on primary during recovery Throttle rebuild bandwidth, stagger replica recovery Smarter replica placement, controlled rebuild rate limits Primary overloaded → writes slow → latency cascade for live traffic Throttling slows recovery — longer inconsistency window
Replication Storm Massive resync needed after outage — all replicas rebuilding at once Replication traffic spike, network saturation during recovery Rate-limit replication, stagger recovery of replicas Controlled repair scheduling, repair priority queues Network saturation → live traffic degrades during recovery Slower controlled recovery extends window of inconsistency
4 — Event Ordering and Messaging Failures
Duplicate Event ProcessingMust Know At-least-once delivery retries same message after uncertain ack Duplicate IDs, repeated side effects in consumer logs Consumer-side idempotency key deduplication Exactly-once semantics (Kafka idempotent producer + transactions) Double payment, double order, duplicate notifications Exactly-once semantics add significant implementation complexity
Missing Event / Data LossMust Know Broker crash, consumer acks before processing, network failure Sequence gap detection, consumer lag anomaly Replay events from durable log (Kafka, WAL) Persistent queues, acks=all, replication factor ≥ 3 Missing workflow steps — order never fulfilled, state incomplete Persistent brokers with high RF cost significantly more
Out-of-Order EventsMust Know Parallel consumers, network reordering, different partition speeds Sequence mismatch, invalid state transition in downstream Buffer and reorder using sequence numbers before processing Per-key ordered partitioning (Kafka partition by entity key) Invalid workflow state — cancel processed before create Per-key ordering reduces consumer parallelism
Poison Message Corrupt, malformed, or unprocessable message enters queue Consumer fails repeatedly on same offset/message Dead-letter queue — move poison message aside, continue Message validation at producer, schema registry enforcement Queue processing blocked entirely — all subsequent messages stall DLQ management adds operational overhead and monitoring
Consumer Group Rebalance Failure Consumer crashes or re-joins — triggers partition reassignment Rebalance instability, processing pauses, lag spike Graceful rebalance, cooperative incremental rebalancing Sticky partition assignment, longer session timeouts Processing pauses during rebalance → lag builds → delay cascade Slower rebalancing reduces elasticity of consumer group
5 — Consensus and Quorum Failures
Quorum LossMust Know Too many nodes unavailable — insufficient nodes for majority Cluster alerts: insufficient quorum, write failures Switch to read-only mode, restore nodes to regain quorum Distribute quorum nodes across multiple AZs/regions Write unavailability — entire system stalls waiting for quorum Multi-AZ quorum adds cross-AZ latency to every write
Consensus Timeout Slow network or high load prevents consensus round from completing Consensus latency metrics, write delay spikes Retry consensus round, reduce network latency Optimise network, co-locate quorum nodes, reduce log payload Write delays cascade — queued writes build up behind stalled consensus Faster timeout increases risk of false leader changes
Stale Leader Old leader, isolated by partition, still accepts writes Version/term mismatch between writes from old and new leader Fencing tokens: new leader increments token, old leader rejected Strong term/epoch validation, monotonic fencing Conflicting writes from two leaders → data corruption on heal Extra coordination on every write for term validation
Consensus Deadlock No progress in leader voting — perpetual split vote Repeated failed elections, no progress in Raft log Force leader reset, randomise election timeout Randomised election timeouts (built into Raft), stable quorum Entire cluster freezes — no writes accepted until deadlock resolved More operational complexity to monitor and recover from
6 — Time Synchronization and Clock Failures
Clock SkewMust Know Different nodes have different wall-clock times — NTP diverged Timestamp drift monitoring alerts, ordering anomalies Use logical clocks (Lamport) or vector clocks for ordering Reliable NTP/PTP sync, never use wall clock for ordering Incorrect event ordering → wrong TTL expiry → wrong scheduling Logical clocks add complexity; vector clocks scale poorly
Time Drift Node clock slowly diverges from reference over time Drift monitoring, gradual timestamp anomalies Resync NTP, apply monotonic clock correction Better time servers (GPS-backed NTP), frequent sync intervals Expired sessions/leases fired incorrectly → spurious evictions Frequent sync adds extra network traffic overhead
Event Ordering Error by Clock Two events with close timestamps have reversed order due to skew Timestamp anomalies in event log, events appear out of causal order Sequence-number-based ordering instead of timestamp Event-time semantics with watermarks, logical clocks Wrong workflow execution — later event treated as earlier More metadata storage for sequence numbers per event
Lease Expiry Misfire Clock mismatch causes lease to expire prematurely or not at all Lease conflict detection, dual ownership signals Fencing tokens on lease acquisition, reject stale holders Monotonic clocks for lease duration, conservative lease timing Dual ownership of lease → two nodes act as primary simultaneously Conservative lease timing reduces throughput due to idle periods
7 — Distributed Transaction and Workflow Failures
Partial Distributed TransactionMust Know Multi-service workflow — one step succeeds, another fails mid-flow Cross-service reconciliation finds mismatched state Saga pattern — run compensating transactions to undo completed steps Idempotent workflow design, avoid 2PC, use outbox pattern Payment deducted, order not created — user charged with no delivery Saga complexity grows with number of services involved
2PC Coordinator Failure Coordinator crashes after prepare phase, before commit decision Participants stuck in prepared state — locks held indefinitely Transaction recovery protocol, timeout and rollback Avoid 2PC where possible — use Saga or event-driven patterns All participating services hold locks → writes blocked system-wide 2PC hurts availability — any participant failure blocks commit
Saga Compensation Failure Compensating transaction also fails — cannot undo partial work Workflow stuck in compensating state with no resolution Retry compensation with exponential backoff, manual fallback Idempotent compensating actions, persistent retry tracking Permanent inconsistent state requiring expensive manual reconciliation Extra operational complexity for monitoring compensation failures
Distributed Deadlock Services wait on each other in circular dependency for resources Timeout/deadlock detection, workflow makes no progress Abort one transaction, apply global resource ordering Global lock ordering, timeout on all resource acquisitions Workflow freeze — no progress until manually resolved Global ordering reduces concurrency and parallelism
8 — Service Discovery and Membership Failures
Service Discovery FailureMust Know Registry (etcd/Consul/Zookeeper) unavailable or returning wrong data Service lookup failures, connection errors to healthy services Cached service endpoints as fallback HA registry cluster, client-side endpoint caching All services unable to find each other → cluster-wide outage Cached endpoints risk routing to stale/dead instances
Stale Membership Information Delayed heartbeat updates — dead node still listed as healthy Traffic routed to dead node, connection failures on those routes Force membership refresh, remove stale entries Faster heartbeat intervals, aggressive stale-entry eviction Traffic routed to dead nodes → requests fail → caller retries More frequent heartbeats increase membership gossip overhead
Zombie Node Dead node appears alive to registry — still responding to pings Inconsistent heartbeat, node responds to pings but fails on requests Force fencing and removal from cluster membership Better liveness checks — health check must test actual functionality Traffic routed to zombie → requests fail → cascades to callers Aggressive fencing risks false positives — removes live nodes
Node Join / Leave Storm Rapid autoscaling, crash-restart loops, or mass eviction Membership churn spike, cluster rebalancing continuously Stabilise scaling, dampen membership changes Controlled scaling policies, cool-down periods Rebalance instability → consumer lag spike → processing delay Slower elasticity — nodes take longer to join/leave cleanly
9 — Distributed State Divergence Failures
State DivergenceMust Know Concurrent conflicting updates on different nodes — no coordination Version mismatch between nodes, reconciliation job finds conflicts Reconciliation job — merge or pick winner using business rules Strong consistency on critical writes, single-writer ownership Different users on different nodes see different truth simultaneously Strong consistency reduces availability during failures
Conflict Resolution Failure Merge logic cannot automatically reconcile divergent versions Persistent conflict state, stuck records in reconciliation queue Manual reconciliation, expose conflict to application layer CRDT data structures, operational transforms for collaborative state Corrupted shared state if bad merge applied — propagates to readers CRDT and OT algorithms add significant implementation complexity
Cache-Replica Divergence Cache not invalidated when replica updates — lag between layers Cache value differs from replica value in spot checks Cache refresh, force cache invalidation on write Event-driven invalidation (CDC), write-through cache Stale data served at scale across entire fleet of cache nodes More frequent invalidation increases cache miss rate and DB load
Metadata Inconsistency Coordinator replication lag — different nodes have different schema/config view Metadata mismatch between nodes, conflicting routing decisions Rebuild metadata from authoritative source Consensus-backed metadata store (etcd/Raft), strong read guarantee Entire cluster confused about topology → routing chaos system-wide Consensus-backed metadata adds latency to every metadata operation

Monolith vs Distributed — Why Distributed Is Fundamentally Harder

Monolith (Simpler)

  • One process — clear failure boundary
  • Either up or down — no partial state
  • No replication lag or divergence
  • Recovery: restart one process

Distributed (Fundamentally Harder)

  • Partial failures — some up, some down
  • Replicas diverge silently
  • Split brain creates multiple truths
  • Clock skew breaks ordering
  • Recovery may create new inconsistencies

Final Mental Model — All Distributed Failures Reduce to 6 States

1. Cannot communicate → partition: quorum + isolation 2. Cannot agree → consensus: Raft/Paxos + fencing 3. Replicas diverge → sync + read repair + quorum reads 4. Ordering breaks → per-key partition + sequence numbers 5. Transactions partial → Saga + compensation + outbox 6. Time inconsistent → logical clocks + NTP + lease fencing Hardest = split brain: alive system, multiple leaders, silent conflict
