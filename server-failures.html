Server / Application Failures

Interview-focused · 11 failure types · instant mitigation lines · staff patterns

Think of a service as

Code + Runtime + Resources + Dependencies

Failures come from exactly these four layers. A small set with clear reasoning beats a 30-item list every time.

1 Service Crash / Process Down
WhatService stops running — exception, segfault, or OOM kill
WhyImmediate downtime for that service / instance
Instance is dead → requests fail
2 Out Of Memory (OOM) Very Common
WhatService consumes too much memory and gets killed by the OS
WhyOne of the most common production failures
Memory leak → sudden crash
3 CPU Saturation
WhatCPU usage hits 100% — no capacity to process requests
WhyRequests slow down → timeouts → cascading failure
Service alive but extremely slow
4 Thread Pool / Connection Exhaustion
WhatNo threads or connections left to serve new requests
WhyRequests queue up, time out, or get rejected entirely
System cannot handle new requests
5 Deadlock / Blocking
WhatThreads waiting on each other forever — no progress
WhyService appears running but completely stuck
No progress → requests hang indefinitely
6 Slow Service / Performance Degradation
WhatService responds but very slowly
WhyUpstream callers time out → retry → further overload
Latency increases → retries → overload
7 Dependency Failure Propagation Cascading
WhatDownstream service is slow or unavailable
WhyYour service fails even when it is perfectly healthy
Service A fails because B is slow/down
8 Memory Leak / Resource Leak
WhatGradual resource consumption — memory, file handles, sockets
WhyDelayed failure — hard to detect until it crashes
System fine initially → crashes hours later
9 Misconfiguration Very Common
WhatWrong config — bad timeout values, DB URL, connection limits
WhyResponsible for a huge % of real-world production outages
System breaks after deployment
10 Version / Compatibility Issues
WhatNew version is incompatible with existing services or APIs
WhyBreaks inter-service communication silently
Service mismatch → errors between services
11 Rate Limit / Throttling Failure
WhatService rejects too many requests to protect itself
WhyUsers see errors even when system infrastructure is healthy
System protects itself but drops traffic

Final Interview Cheat Model — 6 Buckets

Application failures = 1. Crash → service is down 2. Slow → service has high latency 3. Exhaustion → CPU / memory / threads at limit 4. Blocked → deadlock or stuck threads 5. Dependency → downstream is failing 6. Bad deploy → config / version mismatch

Ultra-Simple Recall Trick — Ask This

Is the service: - down? → crash / OOM - slow? → CPU / latency / degradation - overloaded? → thread pool / rate limit - blocked? → deadlock - broken by dependency? → propagation failure - broken by deploy? → config / version

That covers almost every application failure in a real interview.

Staff Pattern — Use Every Time

Detect → Mitigate → Prevent

1. Service Crash / Process Down

Detect via health checks / heartbeats
→ remove instance from load balancer
→ auto-restart via orchestrator (Kubernetes)
→ rely on multiple replicas to stay available

2. Out Of Memory (OOM)

Detect via memory metrics / OOM kill events
→ restart affected instances immediately
→ set memory limits + trigger autoscaling
→ fix root cause: memory leak or large payload

3. CPU Saturation

Detect via CPU metrics / latency increase
→ scale horizontally to spread load
→ offload heavy work to async workers
→ add caching to reduce repeated computation

4. Thread Pool / Connection Exhaustion

Detect via queue length / thread metrics
→ apply backpressure or rate limiting
→ increase pool size cautiously with testing
→ move blocking I/O to async / non-blocking

5. Deadlock / Blocking

Detect via stuck threads / timeout spikes
→ fail fast using timeouts on all calls
→ restart affected instances
→ redesign with non-blocking patterns

6. Slow Service / Performance Degradation

Detect via latency metrics (P95 / P99)
→ cache hot data / optimise slow queries
→ reduce synchronous dependency calls
→ degrade non-critical features if needed

7. Dependency Failure Propagation

Detect via dependency health checks / error spikes
→ circuit breaker — stop calling failing service
→ fallback to cached or default response
→ retry with exponential backoff when recovered

8. Memory Leak / Resource Leak

Detect via gradual memory growth metrics
→ restart instances on schedule (short-term fix)
→ add memory + leak profiling in pre-prod
→ fix leak in code — enforce resource cleanup

9. Misconfiguration

Detect via sudden error spike post-deployment
→ rollback config immediately
→ use config versioning / feature flags
→ validate configs in CI before rollout

10. Version / Compatibility Issues

Detect via API errors between services
→ ensure backward-compatible APIs (never break)
→ use versioned endpoints (/v1, /v2)
→ roll out changes gradually via canary

11. Rate Limit / Throttling Failure

Detect via rejection rate / 429 error spike
→ apply smarter rate limiting per client tier
→ prioritise critical traffic over best-effort
→ scale system capacity to absorb more load

5 Universal Patterns — Everything Reduces to These

1. Restart → recover a crashed / stuck service 2. Scale → handle load (CPU / memory / threads) 3. Retry → handle transient failures 4. Cache → reduce dependency on slow services 5. Isolate → circuit breaker / rate limit / bulkhead

Staff-Level One-Liner

"I would detect it via metrics, isolate the failing component, recover using restart or horizontal scaling, and prevent recurrence through better resource management or decoupling."

Final Truth — All Failures Reduce to Three States

Service is either: DOWN → crash / OOM / unresponsive SLOW → CPU / latency / blocked MISBEHAVING → bad config / version / rate limit

If you can state which of these three applies and then give one mitigation pattern, you've answered the question.
