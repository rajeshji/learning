Write-Ahead Logging & Journaling Strategies

WAL, redo/undo logs, checkpoints, group commit — Staff Engineer level

The Big Picture

Never modify data before the log becomes durable. WAL records intent first, then applies the change — enabling crash recovery, ACID durability, and high-throughput sequential I/O.

WAL Redo Log Undo Log Checkpoint Group Commit Journaling COW LSN
Core WAL principle: Log Intent → Persist Log → Modify Data → Commit Without WAL: Update Balance → Power Failure → No record → Corruption With WAL: Write WAL → Flush WAL → Update DB → Crash? → Replay WAL → Consistent

WAL Architecture & Write Path

Application → SQL INSERT/UPDATE ↓ Buffer Pool (RAM) ← dirty page lives here ↓ Generate WAL Record ← TXN ID, page ID, before/after values, LSN ↓ WAL Buffer ← batched in memory ↓ fsync() → WAL File ← DURABLE — commit can proceed ↓ Commit Transaction ↓ Background Data Flush ← data page written later at checkpoint

The actual database page may be written much later. The WAL guarantees recovery if a crash happens before the data page is flushed.

WAL Record Contents & Lifecycle

Each WAL record contains

  • Transaction ID
  • Page ID
  • Operation type (INSERT/UPDATE/DELETE)
  • Before value (for undo)
  • After value (for redo)
  • Log Sequence Number (LSN)
  • Commit marker

Why WAL is fast

Sequential append vs random page writes:

Random pages: seek → write seek → write seek → write WAL: append → append → append (sequential = fast)

Crash Recovery via WAL

On restart after crash: Read Last Checkpoint ↓ Replay WAL from checkpoint LSN ↓ REDO committed transactions (reapply changes) ↓ UNDO incomplete transactions (roll back) ↓ Database consistent ✓
Log TypePurpose
Redo LogReapply committed changes after crash
Undo LogRoll back incomplete/aborted transactions
WALStores redo (and often undo) in a single sequential log

Checkpoints

Dirty pages live in memory; a checkpoint flushes them to disk. Recovery replays WAL only from the last checkpoint.

Frequent checkpoints

  • Faster crash recovery ✅
  • Smaller WAL to replay ✅
  • More disk I/O ⚠

Infrequent checkpoints

  • Less disk I/O ✅
  • Larger WAL file ⚠
  • Slower recovery ⚠

Tune checkpoint_completion_target and max_wal_size in PostgreSQL based on RTO requirements.

Group Commit — Key Throughput Optimization

Without group commit

TXN 1 → fsync() TXN 2 → fsync() TXN 3 → fsync() (3 device flushes = slow)

With group commit

TXN 1 ─┐ TXN 2 ─┤→ one fsync() TXN 3 ─┘ (1 flush, all commit ✓)

PostgreSQL, MySQL InnoDB, Kafka, and RocksDB all use group commit to achieve high TPS with durability.

Filesystem Journaling Strategies

1. Metadata Journaling (ext4 default, XFS)

Only inode, directory, and permission changes are journaled. File data is not. Fast, but data may be lost on crash.

2. Ordered Journaling (ext4 ordered mode)

Data written to disk before metadata is committed. Metadata never references unwritten data. Best default balance.

Write Data → Flush → Journal Metadata → Commit

3. Full Data Journaling (ext4 journal mode)

Both data and metadata are journaled. Safest, but doubles write traffic.

4. Copy-on-Write (ZFS, Btrfs)

No journal replay needed. New blocks written, pointer atomically switched. Crash-consistent by design.

Write New Block → Checksum → Atomic Pointer Update → Commit

Production Failure Scenarios

Lost Transactions After Crash

Cause: Async WAL flush  ·  Fix: Enable synchronous commit for critical data

Huge WAL Files Consuming Disk

Cause: Checkpoint too infrequent  ·  Fix: Tune checkpoint interval and max_wal_size

High Commit Latency

Cause: One fsync() per transaction  ·  Fix: Enable group commit

Double Write Overhead

Cause: DB WAL + full filesystem journaling on same data  ·  Fix: Use ordered metadata journaling or O_DIRECT for WAL path

Slow Crash Recovery

Cause: Large WAL replay from distant checkpoint  ·  Fix: Increase checkpoint frequency

Production Debugging Checklist

  • ✅ Measure WAL generation rate (pg_stat_bgwriter)
  • ✅ Monitor fsync() latency: fio --fsync=1
  • ✅ Check checkpoint frequency and WAL file size
  • ✅ Review filesystem journal mode
  • ✅ Verify WAL lives on dedicated fast storage (NVMe)
  • ✅ Measure group commit efficiency (txns per fsync)
  • ✅ Time crash recovery in staging (WAL replay duration)
  • ✅ Check for double journaling (DB WAL + FS journal)
  • ✅ Validate recovery procedures before going to production

Key Takeaways

WAL Core Rule: Log intent → persist log → modify data → commit Never modify data before the log is durable. Why WAL is fast: Sequential append (not random page writes) → fast on both HDD and SSD Crash Recovery: Checkpoint → REDO committed → UNDO incomplete → consistent state Key optimizations: Group Commit → many TXNs, one fsync (= high TPS) fdatasync() → skip metadata flush for WAL Checkpoint → tune for RTO vs disk I/O balance Dedicated NVMe → isolate WAL from data I/O Journaling strategies: Metadata only → fast, data may be lost (ext4 default) Ordered → data before metadata (safe default) Full journal → safest, 2× write traffic COW (ZFS) → atomic, no replay, native snapshots Staff picks based on: Durability SLA, RTO, TPS target, hardware, snapshot needs, operational simplicity
