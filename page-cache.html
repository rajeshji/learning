Page Cache vs Buffer Cache

File I/O caching, dirty pages, writeback, O_DIRECT — Staff Engineer level

The Big Picture

Applications constantly read and write files. Without OS caching, every operation would hit disk — thousands of times slower than RAM. Linux caches data in two complementary layers:

Page Cache

Caches file contents in RAM. Serves read(), write(), mmap().

Buffer Cache

Caches disk blocks & filesystem metadata. Inodes, journals, superblocks.

Application (read/write, mmap, etc.) ↓ Virtual File System (VFS) ↓ ↓ Page Cache Buffer Cache (File Contents) (Disk Blocks & Metadata) ↓ ↓ Block Layer (I/O Scheduler) ↓ Disk Driver → Physical Disk (HDD / SSD)

Modern Linux uses a Unified Page Cache — the same physical pages can represent both file contents and block metadata. No double caching.

Why Caching Exists — The Latency Cliff

Without caching: every file read touches disk, metadata lookups are expensive, and applications become I/O bound. Caching eliminates repeated disk access.

Page Cache — What It Caches

Stores file contents in RAM. When an app reads a file, the OS checks the Page Cache first.

Application ↓ read() Page Cache ──► Cache HIT? YES → return from RAM NO → Filesystem → Buffer Cache → Disk → fill Page Cache → return data

Second read of the same file = zero disk I/O. This is why applications start faster after the first execution.

Buffer Cache — What It Caches

Stores raw disk blocks and filesystem metadata — operates below the filesystem layer.

InodesDirectory entriesSuperblocks Journal blocksRaw block device dataext4 metadata
Filesystem internals ↓ Buffer Cache (Block Device Layer) ↓ Physical Disk Blocks

Write Path — Dirty Pages & Writeback

Writes are asynchronous — Linux delays disk writes, batching them into larger sequential operations for much higher throughput.

Application ↓ write() Page Cache ↓ Mark Dirty Background Writeback (pdflush / flusher thread) ↓ Buffer Cache (Block Layer) ↓ Disk Write

Dirty Page Risk

  • Dirty = memory has newer data than disk
  • If system crashes before flush → data loss
  • Too many dirty pages = writeback spike → high P99
  • Tune with vm.dirty_ratio and vm.dirty_background_ratio

Unified Cache in Modern Linux (2.4+)

Old UNIX (Before 2.4)

Separate Page Cache + Buffer Cache. Same data could exist twice. Wasted RAM, duplicate copies, synchronization bugs.

Modern Linux

Single Unified Page Cache. Same physical pages hold file data and block metadata. No double caching, better memory efficiency.

Benefits: no duplicate copies · consistent view · better memory utilization · simpler kernel design.

mmap() and Page Cache

Memory-mapped files use the same Page Cache — no copy needed. Shared between mmap() and read() callers.

Application ↓ mmap() Virtual Memory ←→ Page Cache ←→ Disk (lazy load via page faults)
No explicit read() after mappingLazy loading via page faultsShared cache with read()Used by Elasticsearch

Databases & O_DIRECT — Bypassing Page Cache

Most databases bypass the Page Cache entirely. Reason: they already implement sophisticated internal caching.

Page Cache (Default)

  • Data cached in RAM
  • Great for repeated reads
  • Supports mmap()
  • Kernel handles eviction
  • Best for: web servers, logs

O_DIRECT — Bypass Cache

  • Bypasses Page Cache
  • No double caching
  • Application manages caching
  • Used by: PostgreSQL, MySQL, Oracle
  • Predictable, lower memory footprint
WorkloadRecommendation
Web servers / static files Page Cache
Large databases O_DIRECT
Search engines (Elasticsearch) mmap() + Page Cache
Sequential streaming readsO_DIRECT or tuned readahead
Kafka log segments Page Cache (sequential)

Real-World Examples

Nginx

Serves static files through Page Cache. Repeated requests return from RAM at memory speed. No disk I/O after first serve.

PostgreSQL

Uses O_DIRECT. Its own Shared Buffer Cache handles caching. Linux Page Cache is minimized to avoid wasted RAM.

Elasticsearch

Uses mmap() extensively. Index segments stay in Page Cache. Low-latency searches because data is already in RAM.

Kafka

Sequential log appends + reads. Page Cache retains log segments. Consumers can read at near-memory speed via OS cache.

Production Failure Scenarios

Slow File Reads

Cause: Cold Page Cache (restart or eviction). Solution: warm the cache or preload files with cat file > /dev/null.

DB Uses Too Much Memory

Cause: DB buffer pool + Linux Page Cache double-caching the same data. Solution: Use O_DIRECT.

High Disk Write Latency

Cause: Too many dirty pages flushed simultaneously. Solution: tune vm.dirty_ratio and vm.dirty_background_ratio.

Memory Pressure / OOM

Cause: Page Cache consumes too much RAM. Solution: adjust vm.vfs_cache_pressure, monitor cache reclaim.

Production Debugging Checklist — File I/O Degradation

  1. Check cache usage: free -h and /proc/meminfo — look at Cached, Dirty, Writeback.
  2. Measure disk activity: iostat -x 1, iotop — identify which process is causing I/O.
  3. Check major page faults: vmstat 1 — pgmajfault/s spiking = memory pressure.
  4. Verify O_DIRECT usage: are databases bypassing the cache as expected?
  5. Tune dirty page thresholds if writeback is spiking: vm.dirty_ratio, vm.dirty_background_ratio.
  6. Check swap usage: si/so in vmstat — swapping = insufficient RAM, 10,000× latency hit.
  7. Investigate cache eviction: vm.vfs_cache_pressure controls how aggressively the kernel reclaims page cache.

Key Takeaways

  • Page Cache stores file contents in RAM, dramatically accelerating repeated reads and writes.
  • Buffer Cache stores filesystem metadata and raw disk blocks, enabling efficient low-level storage operations.
  • Modern Linux uses a Unified Page Cache — page and buffer cache share the same physical memory, eliminating duplicate copies.
  • mmap(), read(), and filesystem operations all share the same page cache pages — no redundant caching.
  • Databases bypass the page cache using O_DIRECT because they already implement sophisticated internal caching.
  • Staff Engineers optimize cache utilization, dirty page writeback, memory pressure, and direct I/O decisions to balance latency, throughput, durability, and RAM usage.
  • Monitor: Cached, Dirty, Writeback in /proc/meminfo + pgmajfault/s in vmstat.

Principal Takeaway

Cache Is Your Best Friend

RAM is 100,000× faster than disk. Let the OS cache work for you — don't fight it.

Know Your I/O Path

VFS → Page Cache → Buffer Cache → Block Layer → Disk. Every optimization happens at a layer.

Avoid Swapping

Swap extends memory but at 10,000× the latency. If you're swapping, fix root cause.

Measure, Then Tune

Profile before tuning dirty ratios or cache pressure. Always validate with before/after metrics.
