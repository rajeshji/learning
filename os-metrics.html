OS Metrics: Load Average, Run Queue & Context Switches

Scheduler Pressure • CPU Saturation Detection • Latency Correlation • Production Diagnosis

Core Idea — Three Metrics, One Story

CPU utilization at 75% tells you almost nothing on its own. Load average 12, run queue 10, and context switches at 80K/sec on an 8-core server tell you the system is saturated. These three metrics form a chain — read them together.

Load Average

Overall system demand — runnable + uninterruptible I/O tasks over 1m / 5m / 15m. How much work exists?

uptime

Run Queue Length

Runnable threads waiting for CPU right now. Best real-time CPU pressure signal. How many tasks waiting?

vmstat 1 → r col

Context Switches/sec

Voluntary + involuntary CPU switches per second. Measures scheduler overhead. How much CPU wasted switching?

vmstat 1 → cs col

1. Load Average — Deep Dive

Load average is the exponential moving average of runnable (R) and uninterruptible sleeping (D) tasks over 1, 5, and 15 minute windows.

# uptime output 14:35:22 up 7 days, load average: 3.42, 5.10, 6.78 1m 5m 15m # What each window tells you 1m → current pressure (right now) 5m → recent trend (last 5 min) 15m → baseline (stable background) # Key: compare against CPU core count nproc # or: lscpu | grep "CPU(s)"

Interpretation (8-core server)

Load AvgMeaningAction
≤ 4Plenty of headroomMonitor normally
4 – 8Healthy, fully utilizedWatch for growth
8 – 12At capacity, some waitInvestigate run queue
> 12Saturated — tasks waitingAct now
> 25Severe overloadImmediate action

Trap: High load average with low CPU % usually means processes are blocked on I/O (D state) — not a CPU problem. Always check run queue AND iowait together.

2. Run Queue Length — Deep Dive

Run queue shows tasks ready to run but waiting for a CPU core right now. Unlike load average it is instantaneous — ideal for real-time diagnosis.

# vmstat 1 output procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu----- r b swpd free buff cache si so bi bo in cs us sy id wa st 12 2 0 142344 182916 2.4g 0 0 0 142 832 45023 68 8 23 1 0 r = 12 → 12 tasks in run queue b = 2 → 2 tasks blocked (D state, I/O) cs → context switches/sec On 8 cores: r=12 means 4 tasks waiting → SATURATED

Healthy Values

Run Queue (r)vs Core CountState
< coresUnder-utilizedIdle / headroom
= coresFully utilizedHealthy
> coresOver-utilizedSaturation begins
>> coresMuch higherScheduler bottleneck

Commands

vmstat 1 # r column — run queue top # load average header sar -q 1 # run queue + load over time cat /proc/loadavg

3. Context Switches/sec — Deep Dive

Every context switch: saves registers, loads another task's state, disrupts cache and TLB. Millions of switches per second = significant CPU overhead with no useful work done.

Voluntary vs Involuntary

TypeCauseSignal
VoluntaryThread blocks on I/O, lock, sleepI/O or lock contention
InvoluntaryTime slice expires — OS preemptsThread oversubscription

What High Context Switches Indicate

  • Too many runnable threads (oversubscription)
  • Frequent blocking I/O (network / disk wait)
  • Lock contention — threads blocking on mutexes
  • Excessive syscall frequency
  • Poorly tuned thread pools

Reference Ranges

Context Switches/secTypical Meaning
< 10KLow — idle / lightly loaded
10K – 40KModerate — healthy, fully utilized
40K – 100KHigh — approaching saturation
> 100KVery high — CPU saturated / overloaded

Commands

vmstat 1 # cs column (system-wide) pidstat -w 1 # per-process voluntary + involuntary perf sched record # full scheduler trace perf sched timehist # latency per task cat /proc/PID/status | grep ctxt

On a single server, context switches > 40–100K/sec is usually a red flag. Context switches are the cost of scheduling inefficiency.

How They Work Together — The Chain

More requests / work arrives ↓ More runnable threads created ↓ Run Queue Length increases ↓ Load Average rises (1m first, then 5m/15m) ↓ Context Switches increase (scheduler busier) ↓ CPU Saturation begins ↓ Cache / TLB pollution per switch ↓ Higher P95 / P99 latency (scheduler delay) ↓ Throughput plateaus — then drops

Rules of Thumb

  • Load avg > CPU cores → CPU is likely saturated
  • Run queue > CPU cores → tasks waiting for CPU
  • Context switches > 40K/sec → usually a red flag
  • High load + low CPU% → check I/O wait (D state tasks)
  • Keep CPU utilization at 60–80% for best latency/throughput balance

Real-World Examples & Common Patterns

Web Server (Nginx) — Saturated

Cores: 8 Load avg: 15 (1m) Run queue: 12 Ctx switches: 90K/s

CPU saturated. Requests waiting. P99 rising. Fix: reduce blocking, tune workers, scale out.

DB Server (PostgreSQL) — Healthy

Cores: 16 Load avg: 6 (1m) Run queue: 2 Ctx switches: 8K/s

Healthy. No CPU bottleneck. Latency likely caused by I/O or query plans — investigate differently.

Kubernetes Node — Overloaded

Cores: 8 Load avg: 22 (1m) Run queue: 18 Ctx switches: 120K/s

Too many pods competing. Fix: CPU quotas, reduce oversubscription, scale cluster.

What To Do When Saturated

Scale Out (Add CPUs)

More CPU capacity → shorter run queues

Reduce Concurrency

Fewer threads → less contention, less switching

Optimize Code

Lower CPU time per request → less load per req

Async / Non-blocking

Fewer threads → less scheduling pressure

Improve I/O

Reduce I/O wait → lower load average

CPU Affinity

Better cache locality, fewer migrations

Engineer Progression

Junior: "CPU is high."
Senior: "Load avg is 15 on 8 cores — that's bad."
Staff: Run queue growing? Ctx switches vs load balanced? I/O or CPU bound? Optimize or scale?
Principal: Correlate load/queue/ctx with P99 latency. Set SLOs on scheduler pressure, not just CPU%.

Principal Engineer Takeaway

Load Average — system demand including I/O. Smoothed over time. Compare against core count.

Run Queue — CPU-specific instant pressure. Best real-time saturation signal. Should stay near core count.

Context Switches — scheduler overhead. High = too many threads, lock contention, or I/O blocking.

Read together — never in isolation. Correlate with P99 latency to find the real bottleneck.

Staff Engineers diagnose performance by correlating load average, run queue, context switches, CPU utilization, and P95/P99 latency before deciding whether to optimize code, tune thread pools, or scale infrastructure. The goal: CPUs busy but not saturated, queues short, latency predictable.
