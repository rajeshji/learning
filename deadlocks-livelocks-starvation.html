Deadlocks, Livelocks & Starvation

Staff Engineer Reference — Concurrency Failure Modes

THE BIG PICTURE
Why Concurrent Systems Stop Making Progress

Instead of learning deadlock, livelock, and starvation separately, understand why concurrent systems stop making progress, how operating systems detect these problems, and how Staff Engineers design systems that avoid them.

Concurrency allows multiple threads or processes to execute simultaneously. However, when they compete for shared resources — Locks, Mutexes, CPU, Semaphores, Thread pools, Database connections, Files, Network resources — three major failure modes can occur:

Concurrent System │ ┌──────────────┼──────────────┐ ▼ ▼ ▼ Deadlock Livelock Starvation (Waiting) (Busy Loop) (Unfair Wait)
ProblemWhat HappensCPU UsageProgress
DeadlockThreads wait foreverLowNone
LivelockThreads constantly retryHighNone
StarvationOne thread never gets resourcesMixedPartial
Although they appear similar, their causes and solutions are completely different.
DEADLOCK
Deadlock — Everyone Waits Forever

Deadlock occurs when multiple threads wait for each other in a circular dependency. No thread can continue.

Thread A Thread B ↓ ↓ Lock A Lock B ↓ ↓ Waiting For Lock B Waiting For Lock A Neither thread releases its lock → System freezes

Coffman's Four Conditions

A deadlock can occur only if all four conditions are true. Breaking any one condition prevents deadlock.

ConditionDescription
Mutual ExclusionResource owned by one thread
Hold and WaitThread holds one resource while waiting for another
No PreemptionResource cannot be forcibly taken
Circular WaitThreads form a dependency cycle

Deadlock Flow

Thread A: Acquire Lock A → Needs Lock B Thread B: Acquire Lock B → Needs Lock A → Both threads remain blocked indefinitely (Forever Waiting)

Preventing Deadlocks

The simplest and most effective solution is consistent lock ordering. Common strategies:

StrategyMechanism
Global lock orderingAlways acquire locks in same order (A→B→C)
Try-lock with timeoutUse tryLock(timeout) — fail gracefully on contention
Resource hierarchyAssign levels; threads only acquire higher-level locks
Deadlock detectionWait-for graph cycle detection (PostgreSQL, MySQL)
Transaction rollbackDB aborts one transaction and retries
LIVELOCK
Livelock — Everyone Keeps Working, Nothing Completes

Livelock occurs when threads are not blocked, but continuously react to each other, preventing useful work. Unlike deadlock — threads keep running, CPU usage is high, but no thread completes work. The system appears busy but makes zero forward progress.

Thread A Thread B Acquire Lock → Conflict Acquire Lock → Conflict ↓ ↓ Release Lock → Retry Release Lock → Retry ↓ ↓ Acquire Lock → Conflict Acquire Lock → Conflict ↓ ↓ (Repeat Forever) (Repeat Forever) → Both threads remain active, but nothing finishes

Preventing Livelock

Randomization prevents threads from colliding repeatedly:

StrategySolution
Random delay (jitter)Insert random sleep before retrying
Exponential backoffDouble retry intervals after each failure (TCP, gRPC, AWS SDK)
Fair locksAllow one thread to "win" (e.g., ticket lock)
Retry limitsLimit retries; fallback to blocking mutex
Yield CPU occasionallyAdaptive spinning with backoff (Linux spinlocks)
STARVATION
Starvation — One Thread Never Gets a Turn

Starvation occurs when a thread waits indefinitely because other threads continuously receive resources first. The system works — but one thread never progresses.

CPU Scheduler ↓ High Priority Thread ↓ High Priority Thread ↓ High Priority Thread ↓ Low Priority Thread (Never Runs)

Common causes: Priority scheduling · Unfair locks · Busy thread pools · Resource monopolization · Queue imbalance

Preventing Starvation

Operating systems typically use:

StrategyExplanation
Fair schedulingRound-robin, FIFO ordering
Priority agingGradually increase priority of waiting threads until scheduled
Completely Fair Scheduler (CFS)Linux: tracks virtual runtime, schedules most-starved thread next
Fair locksTicket locks guarantee FIFO order for lock acquisition
Bounded waitGuarantee max waiting time (real-time systems)

STAFF ENGINEER THINKING
Staff Engineer Decision Framework

A Staff Engineer asks the right questions before a system hangs in production:

  • Is there a circular dependency in resource acquisition?
  • Are retries synchronized across nodes?
  • Is scheduling fair across threads or services?
  • Are locks acquired in a consistent order?
  • Is backoff randomized?
  • Can bounded waiting be guaranteed?
  • Is thread pool isolation required for blocking tasks?
  • Can the system recover automatically?
ScenarioRecommended Solution
Multiple LocksGlobal Lock Ordering
Retry LogicExponential Backoff + Jitter
Thread PoolFair Queue + Bounded Queue
Priority SchedulingPriority Aging
Distributed TransactionsTimeouts + Deadlock Detection
High ContentionLock-Free / Optimistic Algorithms

Production Readiness Checklist

  1. Define global lock ordering.
  2. Avoid nested locks where possible.
  3. Use try-lock for long waits.
  4. Add exponential backoff to retries.
  5. Monitor blocked threads.
  6. Track thread pool queue length.
  7. Measure scheduler fairness.
  8. Detect retry storms.
  9. Monitor lock contention.
  10. Load test concurrent workloads.
KEY TAKEAWAYS
Summary — Staff Engineer Soundbite
  • Deadlock occurs when threads form a circular dependency, causing every participant to wait indefinitely. Prevent through lock ordering, timeouts, resource hierarchies, or deadlock detection.
  • Livelock occurs when threads continuously retry or react without making progress, typically consuming high CPU. Fix with randomized backoff, exponential delays, and fair retry policies.
  • Starvation occurs when one thread is continuously denied access to CPU or shared resources due to unfair scheduling or resource monopolization. OS prevents this with fair scheduling and priority aging.
  • These problems exist at both the OS level (threads, locks, schedulers) and the distributed systems level (microservices, databases, message queues, leader elections).
  • Staff Engineers design for forward progress, fairness, bounded waiting, and graceful recovery — using global lock ordering, adaptive backoff, fair schedulers, bounded thread pools, circuit breakers, and load balancing.
"Deadlock = no progress, no CPU. Livelock = no progress, high CPU. Starvation = some progress, one waits forever. Prevent with consistent lock ordering, randomized backoff, and fair scheduling policies."

SECTION 1 — DEADLOCK
Deadlock — The "Waits-For" Cycle

A deadlock occurs when two or more threads are waiting for each other's resources, creating a circular wait — none can proceed.

"Thread A waits for Thread B's lock; Thread B waits for Thread A's lock → both freeze forever."

OS-Level Conditions — Coffman's 4 Necessary Conditions

For a deadlock to occur, all four must be true. Break any one of these, and deadlock is impossible.

#ConditionMeaning
1️⃣Mutual ExclusionA resource can be held by only one thread at a time.
2️⃣Hold and WaitA thread holds one resource while waiting for another.
3️⃣No PreemptionResources can't be forcibly taken; must be released voluntarily.
4️⃣Circular WaitA → B → C → A dependency loop exists.

Example (Classic Deadlock — C)

pthread_mutex_t lockA, lockB; void* task1(void* arg) { pthread_mutex_lock(&lockA); sleep(1); // Simulate delay pthread_mutex_lock(&lockB); // ... pthread_mutex_unlock(&lockB); pthread_mutex_unlock(&lockA); } void* task2(void* arg) { pthread_mutex_lock(&lockB); sleep(1); pthread_mutex_lock(&lockA); // ... pthread_mutex_unlock(&lockA); pthread_mutex_unlock(&lockB); } // Deadlock occurs if: // Thread 1 holds lockA and waits for lockB // Thread 2 holds lockB and waits for lockA // Both wait forever → no progress

Detection & Prevention

StrategyMechanismExample
Avoid Circular WaitImpose lock ordering (always acquire locks A→B→C)Code convention

SECTION 2 — LIVELOCK
Livelock (Reactive Deadlock)

A livelock occurs when threads aren't blocked but are constantly reacting to each other in a way that prevents forward progress.

"Everyone keeps moving — but nobody gets closer to completing work."
void* threadA() { while (true) { if (try_acquire(lockA)) { if (try_acquire(lockB)) { // do work release(lockB); release(lockA); break; } else { release(lockA); // retry later } } } } void* threadB() { // Same pattern, opposite order } // Both threads keep acquiring & releasing locks repeatedly to "avoid" deadlock // — but NEVER actually enter the critical section // They're busy looping (high CPU) → system looks active, but NO PROGRESS = LIVELOCK
StrategySolution
Random backoffInsert random sleep before retrying (like in network protocols)
Fair schedulingAllow one thread to "win" (e.g., lock with ticket number)
State transition limitsLimit retries; fallback to blocking mutex
Exponential backoffIncrease delay with each failure (used in Ethernet CSMA/CD, spinlocks)
Linux spinlocks use adaptive spinning with backoff to prevent livelock under heavy contention.
SECTION 3 — STARVATION
Starvation (Unfair Scheduling)

Starvation happens when some threads never get CPU or resource access, because others continuously take priority.

"The thread is alive but never scheduled to run."

Example 1 — CPU Starvation

pthread_mutex_t lock; void* greedy_thread() { while (true) { pthread_mutex_lock(&lock); // holds lock very long pthread_mutex_unlock(&lock); } } void* polite_thread() { while (true) { pthread_mutex_lock(&lock); // small work pthread_mutex_unlock(&lock); sleep(1); } } // greedy_thread continuously reacquires lock before polite_thread can // → polite_thread starves (makes little or no progress)

Example 2 — Scheduling Starvation

  • Thread with low priority never scheduled if high-priority threads always runnable.
  • Common in priority-based schedulers without aging.
StrategyExplanation
Fair QueuingMaintain FIFO order or round-robin scheduling
Priority AgingGradually increase priority of waiting threads
Randomized AccessRandom selection avoids starvation bias
Bounded WaitGuarantee max waiting time (real-time systems)

SECTION 5 — VISUAL
Thread State Visual (Whiteboard-Friendly)

Normal Thread Life Cycle

┌──────────────────┐ │ READY (runnable)│ ← waiting for CPU └───────┬──────────┘ │ scheduled by OS ▼ ┌──────────────────┐ │ RUNNING (active)│ ← executing code └───────┬──────────┘ │ waiting for I/O / lock ▼ ┌──────────────────┐ │ WAITING (blocked)│ ← sleeping on futex, lock, I/O └───────┬──────────┘ │ event occurs (lock released, I/O done) └────────► back to READY

Deadlock — Circular Waiting Forever

Thread A: holds Lock1, waiting for Lock2 Thread B: holds Lock2, waiting for Lock1 [Thread A - WAITING] ◄──────────► [Thread B - WAITING] ↑ ↑ └─────────────── Locked resources ┘ => Both are blocked (WAITING) => No thread ever transitions back to READY or RUNNING => CPU idle → 0% utilization

Livelock — Everyone Moves, Nothing Progresses

Thread A: tries to acquire Lock → sees contention → releases and retries Thread B: does the same → both keep retrying [Thread A - RUNNING] ◄──────────► [Thread B - RUNNING] │ │ ▼ ▼ keeps yielding or retrying keeps yielding or retrying => Threads never blocked (no WAITING) => CPU 100% busy, but no useful work done

Starvation — Unfair Access

Thread A (high priority) keeps getting CPU time Thread B (low priority) always preempted CPU Timeline: |--A--|--A--|--A--|--A--|--A--|--A--|--A--| | B never scheduled | [Thread A - RUNNING → READY → RUNNING] [Thread B - READY → READY → READY (never scheduled)] => One thread keeps running => One thread starves (never progresses)

Distributed Deadlock Examples

// Microservices Circular Wait Service A ──► Service B ──► Service C ──► Service A ▲ │ └──────────────────────────────────┘ // Scenario: // Service A calls B (holds transaction lock on A's DB row) // B calls C (locks its own DB row) // C calls A (tries to access the locked row in A) // All three block — distributed deadlock
TechniqueDescription
TimeoutsEach request or transaction has a TTL; abort after deadline.
Wait-for graph detectionDB or distributed lock managers detect dependency cycles (e.g., PostgreSQL, Spanner).
Global orderingImpose consistent lock ordering (e.g., always lock users before orders).
Idempotent retriesOn timeout, safely retry (design endpoints to handle duplicates).
Deadlock avoidance algorithmsE.g., timestamp ordering (younger transactions back off).

Distributed Livelock Examples

// API Retry Storm Client → API → DB (slightly slow) Client timeouts too early → retries API overloaded → responds slower Clients retry even more → total meltdown → All components actively working, but none finishing = distributed livelock // Leader Election Livelock (Raft / ZooKeeper) // Multiple nodes detect leader failure simultaneously // Each starts an election — votes split → no majority → all restart → repeat forever // Cluster never converges to a stable leader → high CPU + no progress
TechniqueDescription
Randomized backoff / jitterEach node waits a random delay before retrying or starting election.
Exponential backoffDouble retry intervals after each failure (used in TCP, gRPC, AWS SDK).
Leader stickiness / fencing tokensPrevent multiple concurrent leaders.
Quorum requirementRequire majority votes before progressing (Raft, Paxos).

// Load Balancer Starvation Node 1 → 95% of traffic (overloaded, queue delays) Node 2 → 5% of traffic (idle) // Requests to Node 1 starve for CPU / threads // Priority-based Queue // High-priority jobs keep arriving → low-priority never picked // Queue never empties → low-priority ones STARVE

Fair queuing / weighted round-robinBalance load evenly or by capacity.
Priority agingGradually increase waiting job's priority.

SOUNDBITE
Staff Engineer Interview Soundbite
"Deadlock is a circular wait where threads block forever; livelock is where threads stay active but never make progress; and starvation is where some threads never get scheduled due to unfairness. In distributed systems, deadlocks appear as cyclic waits between services or transactions; livelocks happen when nodes keep retrying simultaneously without progress; and starvation occurs when some nodes or clients never get scheduled or served. The fixes mirror OS-level strategies — use timeouts, randomized backoff, fair scheduling, circuit breakers, and global ordering to ensure forward progress and fairness."
