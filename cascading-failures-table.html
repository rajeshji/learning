Cascading Failure Scenarios — Most Dangerous

Staff-level · 9 categories · 36 scenarios · detect / mitigate / prevent / cascading / trade-off

Why Cascading Failures Are the Most Dangerous

Cascading failure = one failure causes another causes another → total system collapse They are dangerous because each step looks like a new independent failure The 3 root causes of every cascade: 1. No isolation → failure can spread (no bulkhead, no circuit breaker) 2. No backpressure → load keeps arriving into degraded system 3. Positive feedback loop → degradation amplifies the original failure

1 — Retry Storm Cascades
Exponential Retry AmplificationMust Know Client retries aggressively on failure — each failure triggers N more requests Upstream request rate exceeds downstream capacity by N×, error rate climbing Apply exponential backoff + jitter immediately, shed excess retries Retry budgets, client-side retry limits, retry-after header from server Backend collapse — partial outage becomes total outage as retries multiply load Exponential backoff increases latency for legitimate transient failures
Synchronised Retry BurstMust Know All clients use identical retry interval — they all retry at exactly the same moment Spike pattern in retry traffic — sudden bursts exactly N seconds apart Add jitter to all retry intervals immediately across all clients Full jitter on all retry timers (jitter = random × base_delay) Thundering herd — synchronised burst overwhelms server repeatedly Jitter makes retry timing less predictable for SLO tracking
Cross-Service Retry CascadeMust Know Service A retries on Service B, B retries on C — load amplifies at every hop Request rate multiplied by (retry factor)^hops downstream — exponential fan-out Apply circuit breaker at each hop, stop retrying at first persistent failure Per-hop retry budget, total retry budget across call chain, circuit breakers at every service Entire service mesh overloaded — every layer amplifies load onto the next Stopping retries at hop 1 may drop requests that would have succeeded at hop 2
DLQ Overflow from Retry Flood DLQ configured but retry volume overwhelms it — DLQ storage fills, messages lost DLQ depth growing, storage alerts, retry messages being dropped Throttle retry feed to DLQ, archive overflow to cold storage DLQ capacity planning with retry storm scenarios, DLQ depth monitoring alert Silent message loss — DLQ overflow drops the messages that needed recovery Large DLQ storage reserves capacity for rare storms but normally sits idle
2 — Resource Exhaustion Chains
Thread Pool → Connection Pool ChainMust Know Slow dependency holds threads → thread pool fills → connection pool requests queue → timeouts Thread pool saturation, then connection pool saturation in sequence Kill slow requests, apply aggressive timeout to dependency Bulkhead — separate thread pool per dependency so one slow dep doesn't starve all Total API freeze — no thread available to accept new requests of any kind Bulkhead pools require more threads total, increasing baseline memory use
OOM → Crash → Redistribution → OOM ChainMust Know One node OOMs and crashes → its traffic shifts to remaining nodes → they OOM → cascade First OOM kill, then rapid sequential OOM kills on other nodes Immediately shed load (rate limit), stop new traffic entering Memory quotas per node, load shedding before OOM, anti-affinity with capacity buffer Full cluster OOM cascade — all nodes crash in sequence as traffic redistributes Conservative memory limits reduce per-node cache effectiveness
GC Pause → Timeout → Retry Storm Long GC pause on server → clients time out → clients retry → server under double load when GC ends GC pause event followed immediately by retry traffic spike Drop retries arriving during/after GC with backpressure, slow restart Tune GC (G1GC, ZGC for low pause), heap cap, avoid GC pauses exceeding client timeout Post-GC overload — server recovers from GC but immediately gets hammered by retries Smaller heap means more frequent (though shorter) GC cycles
File Descriptor Exhaustion Chain Leaked connections or too many open sockets — FD limit hit, new connections refused EMFILE errors, new connection failures while CPU/memory look fine Kill leaked connections, raise ulimit, restart process Connection leak detection, FD monitoring alert, enforce connection pool limits Downstream services cannot connect → their queues fill → their cascades start Strict connection limits may reject valid burst connections during traffic spikes
3 — Load Redistribution Cascades
Node Failure → Overload → Next Node FailsMust Know N-1 capacity design — one node fails, remaining nodes absorb 100%/N-1 of load and fail too Sequential node failures, each crash preceded by CPU/latency spike Shed load aggressively, stop routing to remaining nodes until load normalises N+2 capacity design, load shedding before cascade, autoscale ahead of capacity cliff Total cluster collapse — each node death makes remaining nodes less able to cope N+2 capacity runs at lower utilisation — higher cost at normal load
Hot Spot Collapse → Traffic Shift Cascade Hot partition node fails — its load shifts to adjacent partitions, making them hot too Sequential partition overload events, hot key metrics shifting across partitions Add local cache in front of hot partitions, rate limit hot keys Consistent hashing with virtual nodes, hot key detection + replication Entire cluster saturated — every partition becomes hot as collapse propagates Hot key replication increases write fan-out and coordination complexity
AZ Failure → Cross-AZ Overload One AZ fails — other AZs receive 50% more traffic than designed for AZ health check failure followed by latency spike in remaining AZs Activate autoscaling in remaining AZs, shed non-critical traffic N+1 AZ capacity (each AZ handles 100% of traffic alone), pre-scale on AZ event Remaining AZs overload and begin failing → region-wide outage N+1 AZ sizing doubles infra cost in each AZ vs N×50%
Reconnect Storm After Mass Restart Fleet-wide restart (deploy, crash recovery) — all clients reconnect simultaneously Connection spike on LB/gateway exactly at restart time Jittered startup, stagger restart across fleet Gradual rolling restart, exponential backoff on reconnect, connection keep-alive LB/gateway connection exhaustion — reconnect storm exceeds connection slot limit Staggered restarts extend deployment windows significantly
4 — Dependency Cascade Failures
Single Dependency Outage SpreadsMust Know One shared dependency (DB, auth, cache) fails — all services depending on it fail together Correlated error spike across multiple services pointing to same dependency Apply circuit breaker to failing dependency, return cached/degraded responses Bulkhead per dependency, graceful degradation mode for every dependency Entire platform outage if dependency is central (auth, config service) Degraded responses without dependency may return stale or incomplete data
Slow Dependency Backpressure CascadeMust Know Slow dependency holds threads → upstream service threads fill → upstream slows → its callers slow Latency spike propagating upstream, each service showing high thread wait Per-dependency timeout + fail fast at first slow sign, shed load upstream Timeout isolation per dependency, non-blocking IO, bulkhead Entire call chain slows → user-facing latency becomes seconds → retries amplify Tight timeouts may fail slow-but-correct operations in dependency
Circular Dependency Failure Loop Service A calls B calls A — when one degrades, the loop amplifies degradation Both services showing mutual high error rate, recursive call depth in traces Break loop with circuit breaker, introduce async/queue decoupling Acyclic dependency graph — enforce via architecture review Both services exhaust resources together — neither recovers without external intervention Strict acyclic dependencies limit some valid architectural patterns
Third-Party Failure Propagation External API/SaaS fails — internal services waiting on it hold threads → cascade inward External dependency latency spike followed by internal latency cascade Circuit break external dependency, serve cached/default response Strict timeout on all external calls, fallback for every external dependency Internal platform degraded by external provider's outage without circuit breaker Serving defaults without external data may mislead users (e.g. stale prices)
5 — Queue and Backlog Cascades
Consumer Lag → Queue Exhaustion → CrashMust Know Slow consumer — queue grows — broker runs out of memory/disk — broker crashes Consumer lag growing, broker disk/memory alert, then broker unavailable Scale consumers immediately, apply backpressure to producers Consumer lag SLO alert, broker disk watermarks, producer backpressure design Broker crash → all consumers lose connection → reconnect storm → lag grows further Aggressive backpressure on producers blocks upstream ingestion pipelines
Backpressure Failure → Producer Crash Backpressure mechanism fails or is absent — producer buffers fill to OOM Producer memory growing, eventually OOM kill Apply system-level backpressure (TCP flow control), restart producer Bounded producer buffers, explicit backpressure signal from queue to producer Producer crash → data loss for in-flight messages → pipeline gap Bounded buffers may reject valid bursts that would have cleared quickly
Queue Consumer Restart Storm Consumer crashes on poison message — restarts, crashes again, restarts — tight loop Consumer restart count spiking, same partition lag not clearing Skip or quarantine poison message, move to DLQ DLQ for unprocessable messages, max retry before DLQ, deserialization error handling Partition processing stalled — lag grows while consumer thrashes on bad message DLQ-after-N-retries may drop messages that fail intermittently but are valid
Queue Overload → Timeout → Retry Feed Queue too full — producers time out — producers retry — more messages flood the queue Queue depth spike, producer timeout metric, accelerating queue growth Rate limit producer writes, circuit break queue when above high watermark Queue high-watermark circuit breaker, producer rate limiter Queue fills faster than consumers can drain — positive feedback loop to broker crash Queue circuit breaker drops messages that could have been processed later
6 — Cache Failure Cascades
Cache Stampede → DB Overload CascadeMust Know Cache expires or fails — all requests miss simultaneously — all hit DB at same moment Cache hit ratio drops to 0%, DB connection pool exhaustion, DB latency explosion Single-flight (only one request fetches, others wait), serve stale while refreshing Probabilistic early expiry, cache locking (mutex on miss), soft TTL + background refresh DB overload → DB slow → more cache misses as refresh takes longer → spiral Single-flight increases cache-miss latency for all requesters while one fetches
Cache Node Failure → Hot Key Cascade Cache cluster node fails — all keys it held now miss — one key is hot → DB gets all its traffic Specific key miss rate spikes, DB QPS spike for single query pattern Replicate hot keys to local/L1 cache, shed hot key excess load Hot key replication to multiple cache nodes, L1 local cache for top-N hot keys DB hotspot for that query → DB latency → all other cache refreshes slow → broader cascade Hot key replication adds write fan-out cost for writes to those keys
Cold Start Cache Miss Flood New deployment or cache restart — cold cache, all traffic misses until warmed Cache hit ratio at 0% immediately after deploy, DB spike Warm cache before routing traffic, canary deploy with pre-warm step Cache pre-warming in deploy pipeline, traffic shifting only after hit ratio recovers DB overload on deploy — every deployment event causes a mini-outage Pre-warming extends deployment windows and requires read access to production data
Cache Eviction Storm → Backend Flood Memory pressure causes mass cache eviction — many hot keys evicted simultaneously Cache eviction metric spike, backend request rate jump Increase cache memory, apply eviction priority (protect hot keys) Cache memory headroom, eviction policy tuning (LFU over LRU for hot key protection) Backend flood → backend slow → slower cache refresh → more misses → amplification LFU eviction protects hot keys but may evict recently accessed data needed once
7 — Memory and GC Cascade Failures
Memory Leak → Fleet Slow Death SpiralMust Know New deployment introduces memory leak — heap grows slowly over hours until OOM Heap trend growing monotonically post-deploy, GC frequency increasing Rollback deployment, restart leaking instances to buy time Heap growth canary gate in deploy pipeline, heap trend monitoring All instances OOM simultaneously after hours — entire fleet crashes at once Canary heap monitoring adds hours to deployment validation time
GC Pause → Node Eviction → Overload Long GC pause causes node to miss heartbeat — cluster evicts it — traffic redistributes → remaining nodes GC too GC pause events correlating with cluster membership changes Tune GC pause limits to stay below heartbeat timeout, use ZGC/Shenandoah GC pause SLO below heartbeat interval, low-pause GC algorithms for all cluster members Sequential node evictions — GC cascades across fleet as load increases on remaining nodes Low-pause GC (ZGC) has higher memory overhead than G1GC
Heap Fragmentation Performance Spiral Long-running process — heap fragmenting — allocation slower — latency growing — timeouts increasing Latency trend growing over days, GC activity high but no single long pause Scheduled restart during low-traffic window to defragment Regular rolling restarts, off-heap storage for large objects Latency spiral → more timeouts → more retries → more load → faster fragmentation Scheduled restarts are operational complexity; off-heap adds implementation effort
JVM Metaspace / Class Loading Leak Dynamic class generation (reflection, codegen) — metaspace fills — OutOfMemoryError: Metaspace Metaspace usage growing, class count increasing, eventually OOM on class load Restart JVM, increase MetaspaceSize limit as emergency measure Metaspace monitoring, bounded class loading with weak references JVM crash → recovery deploys new instance → metaspace refills → recurring crash Larger MetaspaceSize delays but doesn't fix the underlying leak
8 — Data and Consistency Cascades
Corrupt Data Replication CascadeMust Know Corrupted record on primary replicated to all replicas before detected Checksum failure on replicas, downstream services returning corrupt results Stop replication immediately, restore from pre-corruption snapshot Checksums on all data, replication lag monitoring, immutable snapshots All replicas corrupt — no clean copy remains if corruption reached all replicas and backup Frequent snapshots reduce data loss window but add storage and IO cost
Split Brain → Dual Write → Data Corruption Network partition — both partitions accept writes — when partition heals, data conflicts irreconcilably Conflicting versions of same record on both sides after partition heals Fence minority partition writes during partition, apply conflict resolution on heal Consensus protocol (Raft) — minority partition cannot accept writes without quorum Permanent data inconsistency — conflicting writes may be impossible to reconcile Fencing minority reduces availability during partition (CAP theorem: CP over AP)
Schema Migration Cascade Failure Breaking schema change deployed — old services can't read new schema, new can't read old Query failures and deserialization errors across multiple services simultaneously Rollback schema change, restore backward-compatible column Expand-contract migration pattern — never break backward compatibility in a single step All services fail simultaneously — the schema is the shared contract for the whole system Expand-contract requires multi-deployment migration spanning weeks
Stale Leader → Wrong Decision Cascade Old leader (zombie) still accepting writes after new leader elected — conflicting decisions propagate Conflicting state detected after partition heals, term/epoch mismatch in logs Fence zombie leader via epoch/fencing token, reject writes with stale term STONITH, fencing tokens in all write paths, leader lease expiry before accepting writes Both leaders' decisions replicated — system state diverges across all followers Leader lease adds latency to every write (must hold valid lease before accepting)
9 — Multi-Layer and Observability Cascades
Microservice Fan-Out CascadeMust Know Gateway calls 10 services, each calls 3 more — one slow leaf service makes entire request tree hang Gateway latency spike, all 10 upstream services show high thread wait on same downstream Apply per-service timeout + partial response, return what's available Scatter-gather with bounded timeout, partial response design for all fan-out endpoints Gateway thread exhaustion — fan-out cascade fills all gateway threads simultaneously Partial responses require clients to handle incomplete data gracefully
Bulkhead Absence → Total System CollapseMust Know All services share one thread pool — one slow dependency fills all threads, no service can respond All endpoints slow/failing simultaneously despite only one dependency being degraded Emergency: kill slow dependency calls, restart to clear threads Bulkhead isolation — separate thread pool per dependency, reject-on-full per pool Complete API failure from single dependency degradation — amplified from partial to total Per-dependency thread pools multiply total thread count, increasing baseline memory
Alert Storm → Pager Fatigue → Delayed Response Cascade triggers hundreds of alerts — operator overwhelmed — critical alert missed in noise Massive alert volume, on-call not acknowledging in time, incident spreading Suppress/correlate alerts immediately, escalate via secondary channel SLO-based burn rate alerting (few high-signal alerts vs many threshold alerts) Cascading failure spreads while operator manages alert noise instead of root cause Fewer alerts means some real issues won't generate a page
Observability Overload During Cascade Cascade generates massive telemetry — metrics/log pipeline overwhelmed — operators fly blind Log pipeline backlog, Prometheus OOM, dashboards stale during the worst moment Prioritise critical metrics, apply telemetry sampling during incident HA observability infrastructure, separate observability network plane, adaptive sampling Operators cannot see what is happening → slower response → cascade worsens Separate observability infra doubles cost; adaptive sampling reduces data fidelity

The 3 Universal Cascade-Breaking Patterns — Apply in This Order

1. ISOLATE first → bulkhead + circuit breaker (stop the spread before fixing the root cause) 2. SHED LOAD → rate limit + load shedding + reject-on-full (reduce pressure on degraded components) 3. RECOVER slowly → jittered restart + staggered rollout + gradual re-enable (avoid reconnect storm or stampede when recovering)

Why Cascades Are Uniquely Hard to Debug

During cascade, every layer shows failures → operators see 10+ "root causes" Each symptom looks independent → team splits effort across wrong targets By the time root cause identified → cascade has already spread further Key insight: the FIRST failure is the root cause. Everything else is cascade. Debug strategy: 1. Check timeline — what failed FIRST? (look at earliest alert timestamp) 2. Check dependency graph — who depends on the first failure? 3. Stop the cascade first (shed load, circuit break) THEN debug root cause

Principal Takeaway — Cascade Prevention Design

Isolate

Bulkhead + circuit breaker per dependency

Shed

Rate limit + load shed before saturation

Capacity

N+2 headroom for node failure absorption

Backoff

Jitter + retry budget breaks amplification
