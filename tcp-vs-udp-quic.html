TCP vs UDP vs QUIC

Use cases, latency trade-offs, and when to choose each protocol

Why It Matters

Protocol selection is a system design decision that directly impacts latency, reliability, scalability, CPU usage, user experience, and cost. A Staff Engineer must justify why a protocol is chosen, what trade-offs it introduces, and how it affects the overall architecture.

Reliable applications

TCP — Transmission Control Protocol

Characteristics

  • Connection-oriented (3-way handshake)
  • Reliable, ordered delivery
  • Automatic retransmissions
  • Congestion + flow control
  • Kernel implementation
  • Byte stream abstraction

Typical Use Cases

  • REST APIs, gRPC over HTTP/2
  • MySQL / PostgreSQL
  • Elasticsearch replication
  • SSH, FTP, SMTP, IMAP
  • Banking / financial transactions
  • Large file transfers

✅ Advantages

Reliable · Auto-retransmit · Congestion control · Mature ecosystem · Excellent observability

❌ Disadvantages

1-RTT handshake · Head-of-line blocking · Higher latency · Kernel update required for innovation

Choose TCP when: every byte matters, data loss is unacceptable, transactions must be correct, or broad compatibility is required.

UDP — User Datagram Protocol

Characteristics

  • Connectionless (no handshake)
  • No retransmission
  • No ordering guarantee
  • Datagram-based
  • Tiny header (8 bytes vs TCP's 20)
  • Minimal CPU overhead

Typical Use Cases

  • DNS queries
  • Online gaming
  • VoIP / video calls (WebRTC)
  • Live video streaming
  • IoT telemetry (fire-and-forget)
  • Network discovery / multicast

✅ Advantages

Zero setup overhead · Lowest latency · Minimal CPU · Broadcast + multicast support

❌ Disadvantages

No reliability · No ordering · No congestion control · App must implement retries

Choose UDP when: milliseconds matter, small packet loss is acceptable, or real-time experience is more important than perfect delivery.

QUIC — Quick UDP Internet Connections

Characteristics

  • Built on UDP
  • TLS 1.3 integrated (always encrypted)
  • Multiplexed independent streams
  • 0-RTT / 1-RTT connection setup
  • Connection migration (IP change)
  • User-space (no kernel update needed)
  • HTTP/3 transport layer

Typical Use Cases

  • HTTP/3 websites (Chrome, Cloudflare)
  • YouTube / Gmail
  • WhatsApp (mobile network switching)
  • Modern gRPC
  • CDN edge delivery
  • Mobile-first applications

✅ Advantages

0-RTT setup · No HoL blocking · Built-in TLS · Multiplexing · Mobile connection migration

❌ Disadvantages

Higher CPU · Harder to debug (encrypted) · Depends on UDP path · Less mature tooling

Choose QUIC when: building modern Internet services, users switch networks frequently, tail latency matters, or many concurrent streams need independent reliability.

Head-of-Line Blocking — The Key Difference

TCP (HTTP/2)

Packet 1 ✔ Packet 2 ✔ Packet 3 ✗ Lost Packet 4 ⏸ BLOCKED Packet 5 ⏸ BLOCKED Packet 6 ⏸ BLOCKED

One lost packet blocks all streams on that connection.

UDP

Packet 1 ✔ Packet 2 ✔ Packet 3 ✗ Lost Packet 4 ✔ (continues) Packet 5 ✔ (continues) Packet 6 ✔ (continues)

No waiting. Loss is the app's problem.

QUIC (HTTP/3)

Stream A: pkt 3 lost → only Stream A waits Stream B: continues ✔ Stream C: continues ✔ Stream D: continues ✔

Loss affects only the impacted stream.

Staff asks

  • What is the acceptable packet loss rate?
  • Does ordering matter at the transport or app layer?
  • How often do users switch networks?
  • Is head-of-line blocking hurting P99?
  • Is handshake cost significant at our request rate?
  • Is QUIC feasible given our firewall/UDP blocking risk?
  • How do we observe QUIC in production (encrypted)?
  • Does HTTP/3 improve perceived performance for our users?

Key Takeaways

TCP: Correctness above all Connection-oriented · Reliable · Ordered · 1-RTT setup Best for: APIs, databases, SSH, financial transactions UDP: Speed above all Connectionless · No reliability · 0-RTT · Minimal overhead Best for: gaming, VoIP, DNS, IoT, live streaming QUIC: Speed + Reliability + Modern features Built on UDP · TLS 1.3 built-in · 0-1 RTT Multiplexed streams (no HoL blocking across streams) Connection migration (IP change transparent) Best for: HTTP/3, mobile apps, CDN edge, modern gRPC Head-of-Line Blocking: TCP/HTTP2: one lost packet blocks ALL streams on connection QUIC/HTTP3: one lost packet blocks only THAT stream Protocol selection criteria: Correctness required? → TCP Latency critical, loss ok? → UDP Modern web, mobile? → QUIC Financial/transactional? → TCP (non-negotiable) Real-world: YouTube, Gmail, Cloudflare, Chrome → QUIC MySQL, PostgreSQL, Redis → TCP DNS, WebRTC, online games → UDP
