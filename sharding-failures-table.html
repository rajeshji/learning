Why Sharding Failures Are Hard to Diagnose

Sharding enables: horizontal scale + distributed storage + distributed processing But introduces: hotspots | uneven load | routing complexity | rebalancing | metadata consistency 8 root failure classes: availability | hot partition | routing | rebalancing cross-shard coordination | consistency | scaling | data placement

1 — Partition Availability Failures
Shard Node CrashMust Know Hardware/software failure on the node hosting one or more shards Partition unavailable alerts, health check failure for that shard Failover to replica of the shard, reroute traffic Replicated shards (RF >= 3), multi-AZ shard placement Partial data unavailability — all keys on that shard unreachable Replication multiplies storage cost and write amplification
Entire Shard Unavailable AZ/DC outage — all replicas of a shard in same AZ fail together Partition read/write failures for a key range, error spike Route to replica in surviving AZ Spread replicas across at least 3 AZs per shard Partial service outage — affected key range fully unavailable Cross-AZ replication adds inter-zone latency and egress cost
Partition Leader FailureMust Know Shard leader node crashes — that shard loses write authority Leader unavailable for partition, write requests failing Trigger leader re-election from ISR replicas Multi-replica partitions, unclean leader election = off Temporary write outage for that shard's key range — election latency Faster election reduces outage but risks false elections on transient issues
Partition Startup Failure Corrupted shard WAL or snapshot — shard cannot start Restart loop, shard recovery error in logs Restore from last clean snapshot, rebuild from replica WAL checksums, snapshot integrity validation Reduced cluster capacity — fewer shards online means uneven load on rest Rebuild from replica adds IO load on the healthy replicas
Partition Network Isolation Network partition — shard node cannot communicate with cluster Missing shard heartbeats, partition unreachable from coordinator Fence isolated partition, reroute to healthy replicas Multi-network paths, redundant links between shards and coordinator Data inconsistency if isolated shard continues accepting writes Fencing isolated shards reduces write availability during partition
2 — Hot Partition and Uneven Distribution Failures
Hot PartitionMust Know Skewed key distribution — majority of traffic routes to one shard One shard at 100% CPU/IO while others are idle Split hot shard, add local cache in front of hot partition Better shard key design, virtual partitions, random suffix for hot keys Single shard collapse → all traffic for that key range fails Random suffix breaks key ordering and complicates range queries
Hot Key ProblemMust Know Single key (viral content, popular user) gets millions of requests One key dominates read/write metrics, shard CPU pegged Replicate hot key to multiple shards, serve from local process cache Local in-process cache, CDN for read-heavy hot keys CPU/memory saturation on hot shard — shard crash → full miss cascade Hot key replication increases invalidation complexity on write
Skewed Hash Distribution Poor hashing function — keys cluster on subset of shards Uneven shard utilisation metrics, some shards consistently hot Rehash with better function, virtual node rebalancing Consistent hashing with many virtual nodes, test key distribution Uneven scaling — adding shards does not help overloaded subset Rehashing requires data migration — expensive and disruptive
Write Hotspot (Sequential Keys) Time-series or auto-increment keys — all new writes hit same shard Write-heavy shard at capacity, others idle Range splitting on hot write shard Randomised/hashed IDs, avoid sequential keys as shard keys Disk/CPU bottleneck on write shard — new writes begin failing Randomised IDs lose range-query locality — scans become slower
Celebrity / Fan-out Problem Millions access same entity — all reads funnel to one shard Read amplification spike, single shard saturated Fanout-on-read, multi-layer caching (L1 process + L2 distributed) Tiered caching, CDN for top-N entities, precomputed aggregates Hotspot shard overloads and crashes — all celebrity-tier reads fail Fanout-on-read adds read latency; caching adds consistency complexity
3 — Routing and Partition Lookup Failures
Metadata Service FailureMust Know Coordinator / ZooKeeper / etcd / KRaft down — routing lookups fail All routing lookup failures, cluster effectively inaccessible Use cached routing table, operate in degraded-but-functional mode HA metadata service (3-node ensemble), client-side routing cache Entire cluster inaccessible — all shards unreachable without routing table Client-side cached routing may be stale after shard changes
Stale Partition MappingMust Know Routing table not updated after rebalance — requests go to old shard Missing or wrong data returned, requests routed to wrong node Retry with refreshed routing metadata from coordinator Faster metadata propagation, versioned routing table with client refresh Increased request failures — misrouted requests hit wrong shard Frequent metadata refresh adds overhead; cached routing reduces it
Incorrect Shard Routing Routing rule misconfigured — wrong key range mapped to wrong shard Missing/wrong data from requests, data not found where expected Rollback routing config, manual key range correction Routing config validation, canary routing before full rollout Requests fail or return wrong data for affected key ranges Canary routing slows config rollout velocity
Partition Discovery Failure Nodes cannot locate shard assignments — registry unavailable or stale Missing partition errors, shard not found responses Fallback lookup to secondary registry, rebuild discovery state Replicated service registry, client-side shard address caching Partial cluster outage — some shard ranges become unreachable Redundant registry adds infra cost and consistency management
4 — Rebalancing and Resharding Failures
Shard Rebalancing StormMust Know Many nodes join/leave simultaneously — massive data movement triggered Network/disk IO spike across cluster during rebalance Throttle rebalance bandwidth, pause low-priority rebalance Gradual rebalance with rate limiting, virtual nodes to reduce migration scope Live traffic degradation — rebalance consumes IO needed for user requests Throttling extends rebalance window — longer inconsistency period
Failed ReshardingMust Know Migration interrupted mid-flight — some data moved, some not Partial data movement, routing errors for migrated key range Resume migration from checkpoint, or rollback to pre-migration state Online migration tooling with checkpointing, dual-write during migration Data inconsistency — keys split across old and new shards with wrong routing Dual-write during migration doubles write load and adds coordination
Dual Write Conflict During Migration Writes arrive during resharding — both old and new shard accept the write Conflicting values in old vs new shard after migration completes Sync reconciliation after migration, atomic cutover Pause writes during cutover (brief), or use CRDT for conflict resolution Silent data corruption — wrong value silently wins after shard cutover Write pause during cutover causes brief unavailability
Partition Split Failure Hot shard split interrupted — partial key range moved to new shard Missing key ranges, routing errors for keys near split boundary Retry split from checkpoint, rollback if not feasible Automated split testing in staging, idempotent split operations Partial unavailability — keys near split boundary inaccessible Online shard splitting is complex and requires careful coordination
Partition Merge Failure Merging underutilised shards — merge interrupted or produces inconsistent metadata Metadata inconsistency, routing confusion for merged key range Rollback merge, restore original shard boundaries Safe merge orchestration with rollback plan, dry-run validation Routing confusion — some keys in merged range become temporarily lost Conservative merge scheduling slows cluster right-sizing
5 — Cross-Shard Query and Transaction Failures
Cross-Shard Query ExplosionMust Know Query spans many shards — fan-out to all shards simultaneously Latency spike, all shards hit simultaneously for one query Cache aggregated results, limit fan-out with query routing Query-aware sharding design, precomputed aggregates, denormalisation Massive cluster load — scatter-gather query overwhelms all shards Denormalisation duplicates data and complicates write paths
Distributed Transaction FailureMust Know Multi-shard transaction — one shard commits, another fails or times out Inconsistent state across shards, partial commit detected Saga compensation — run compensating actions on committed shards Minimise cross-shard transactions, outbox pattern, idempotent operations Cross-shard inconsistency — one entity partially updated globally Saga complexity grows rapidly with number of shards involved
Scatter-Gather Timeout One slow/unreachable shard delays the entire scatter-gather query Partial query failures, query times out waiting for straggler shard Partial results with fallback, timeout straggler with best-effort Better partitioning to reduce fan-out, straggler mitigation (hedged requests) User-visible latency spike — slow shard blocks entire query result Hedged requests double load on shards to speed up stragglers
Global Secondary Index Failure Cross-shard index has async replication lag — index out of sync with data Missing query results, index returns stale or incorrect shard references Rebuild index from authoritative shard data Async index maintenance with bounded staleness SLA, eventual consistency Incorrect query responses — users cannot find data that exists Synchronous index maintenance adds write latency to every indexed write
6 — Consistency and Replication Failures Across Shards
Cross-Shard Inconsistency Async replication lag between shards — global state temporarily diverged Data mismatch in cross-shard reconciliation job Reconciliation job, read from authoritative shard Stronger consistency guarantees on cross-shard operations Incorrect global state — users see partial or conflicting data Strong consistency across shards reduces write throughput dramatically
Replica Lag Per Shard Slow follower replica within a shard — reads routed to lagging replica Per-shard lag metrics, stale reads from that shard's replica Route reads to shard leader, set bounded staleness Faster replication, sync replication on shard-critical paths Stale reads for that shard's key range — wrong data served Reading from shard leader removes read scalability from replicas
Split Brain on a ShardMust Know Network partition within a shard — both replicas think they are leader Conflicting writes accepted, version mismatch on shard Fence minority shard replica using fencing tokens Consensus protocol (Raft) per shard, unclean leader election = off Silent data corruption within that shard — conflicting writes accepted Disabling unclean leader election reduces availability during partition
Out-of-Order Shard Updates Async processing of events across shards — updates arrive out of causal order Version mismatch, logically impossible state detected on read Replay events in correct order, buffer and reorder before applying Ordered event streams per shard key, vector clocks for causality Invalid state — subsequent operations build on corrupted shard state Strict ordering per shard reduces cross-shard processing parallelism
7 — Scaling and Capacity Failures
Shard Capacity ExhaustionMust Know Shard storage fills up — disk full on shard node Disk usage alerts, shard refuses new writes Emergency shard split, expand volume, archive old data Predictive scaling, disk monitoring with headroom alerts, auto-split Writes fail for that shard's key range — partial service outage Auto-split adds complexity; more shards increase metadata overhead
Partition Count Explosion Too many small shards — metadata overhead becomes bottleneck Metadata lookup latency spike, coordinator CPU high Merge underutilised partitions, right-size shard count Better initial shard sizing, merge policy for small shards Coordinator overload — metadata latency cascades to all shard lookups Larger shards are harder to rebalance; too many shards overwhelm metadata
Metadata Scalability Bottleneck Cluster has too many shards — metadata service becomes the bottleneck Metadata lookup latency increase, coordinator saturation Distributed/hierarchical metadata, cache routing tables on client Hierarchical metadata design from the start, limit total shard count Cluster instability — every request pays metadata latency overhead Distributed metadata adds consistency management complexity
Autoscaling Lag Traffic grows faster than shards can be added and rebalanced Sustained shard saturation, autoscaling event lag metric Manual scale-up, pre-warm new shards before traffic arrives Predictive autoscaling, capacity buffers, fast pre-provisioned shard pool Overloaded shards cascade — existing shards fail under sustained overload Pre-provisioned shard pool wastes resources during low traffic
8 — Data Placement and Locality Failures
Poor Data Locality Related data placed on different shards — every query requires cross-shard join High cross-shard traffic, consistently slow queries for related entities Co-locate related data on same shard, denormalise for locality Domain-aware partitioning — group entities that are accessed together Increased cross-shard latency for every query involving related data Co-location requires careful schema design and limits flexibility later
Tenant Co-location Problem Multiple heavy tenants placed on same shard — noisy neighbour effect Uneven shard load, one tenant's traffic degrades another's performance Migrate heavy tenant to isolated shard Tenant-aware partitioning, isolate top-N tenants by usage Noisy neighbour overloads shard — all co-located tenants impacted Tenant isolation increases shard count and operational overhead
Geo-Shard Misplacement Users routed to geographically distant shard — not their local region High regional latency, users in region X hitting shard in region Y Geo-routing fix, migrate data to correct regional shard Geo-aware sharding — place shard data close to primary user base Poor UX at scale — all affected users experience high latency Geo-aware sharding requires data residency planning and migration tooling
Shard Affinity Loss Requests for same key routed to different shards inconsistently Cache miss spike, inconsistent reads for same key Sticky routing, force consistent hash routing Deterministic consistent hashing, stable routing layer Reduced cache efficiency — every request potentially misses local cache Strict affinity reduces load balancing flexibility

Shard Key Selection — The Most Consequential Design Decision

A bad shard key causes EVERY failure in this table. Good shard key properties: high cardinality → spreads data evenly uniform access → avoids hotspots query locality → related data on same shard immutable → never changes (re-keying is catastrophic) write distribution → avoids sequential write hotspot Common bad shard keys: timestamp/auto-increment → sequential write hotspot user country → uneven (US >> others) boolean field → only 2 shards possible celebrity user ID → hot key problem Best shard keys: hash(user_id) + virtual nodes → uniform, immutable, high cardinality composite key (region + hash) → geo-aware + even distribution

Final Mental Model — All Sharding Failures Reduce to 4 Problems

1. Uneven distribution → hot partition + hot key + skewed hash 2. Routing failure → stale mapping + metadata down + discovery fail 3. Rebalancing problem → storm + failed resharding + dual write during migration 4. Cross-shard problem → query explosion + distributed tx + scatter-gather timeout Most dangerous combo: hot partition + rebalancing storm overloaded shard triggers rebalance → rebalance saturates IO → live traffic degrades → more shards overload → cascade
