Backpressure Handling

Staff Engineer Reference — Flow Control, Queue Strategies, Cascading Failures & Resilience

DEFINITION
🌍 What Is Backpressure?

Backpressure is a feedback mechanism that slows producers when consumers cannot process data fast enough. It is not a failure — it is a stabilization signal that prevents overload from cascading through the system.

Arrival Rate > Processing Rate ↓ Queue / Buffer fills ↓ Backpressure triggered ↓ Producer slows / blocks / sheds load ↓ System remains stable

CAUSES
⚠️ How Backpressure Is Created

Backpressure occurs whenever Arrival Rate > Processing Rate:

CauseExample
Slow consumersDatabase queries, disk I/O latency
Thread pool saturationAll workers busy — new tasks queue or reject
Network congestionSlow downstream service; TCP window fills
Queue fullBounded queue reaches capacity
Producer burstTraffic spike; Kafka producer surge
Fan-in bottleneckMany producers → single consumer (database write)
CASCADING FAILURE
🔄 How Backpressure Propagates — Cascading Risk
Database slows down ↓ Worker queue fills ↓ API service blocks new requests ↓ Clients start retrying (more load!) ↓ More pressure → more timeouts ↓ Cascading failure across all services
⚠️ Without Proper Handling

Uncontrolled backpressure becomes a cascading failure: unbounded queues exhaust heap memory, retry storms amplify load, and timeouts spread upstream service by service until the entire system is unavailable.

LayerImpact When Ignored
MemoryOOM from unbounded queues
Thread PoolsTask starvation and rejections
NetworkTimeouts and retransmissions
KafkaConsumer lag grows unbounded
MicroservicesCascading failures across the mesh
UsersSlow APIs, 429/500 errors
DETECTION
🔍 How to Detect Backpressure

Monitor these signals — backpressure is often silent until it becomes a crisis:

Primary Metrics

  • Queue depth (absolute and trend)
  • Queue utilization % (used / capacity)
  • Consumer lag (Kafka, stream processing)
  • Response latency P95 / P99

Secondary Signals

  • Dropped requests / rejection rate
  • Retry count (rising = upstream pressure)
  • Thread pool saturation %
  • CPU low but latency high → blocked threads
Staff-level insight: "CPU low but latency high" is the classic signature of a thread-blocked backpressure scenario — threads are waiting for I/O or locks, not burning CPU. Don't confuse this with a compute bottleneck.

QUEUE STRATEGIES
📊 Queue Overflow Strategies
✅ Block Producer

Queue full → producer waits until space available

✔ Reliable, no data loss
❌ Higher latency, upstream blocking

Use for: thread pools, ordered processing

⚡ Reject Requests

Queue full → return 429 / throw RejectedExecutionException

✔ Protects system
❌ Data loss, client must handle

Use for: APIs under traffic spikes

🔄 Drop Oldest

Queue full → remove head, insert new item

✔ Keeps latest data
❌ Older data lost

Use for: video frames, telemetry, sensors

📦 Buffer Bursts

Temporary queue expansion to absorb spikes

✔ Absorbs traffic spikes
❌ Higher memory, hides overload

Use for: short bursts only

PREVENTION
🛡 Design Principles — How to Prevent Backpressure Problems
  • ✅ Always use bounded queues — never unbounded in production
  • ✅ Apply rate limiting at ingress (API gateway, Kafka producer config)
  • ✅ Use asynchronous processing — decouple producers from consumers
  • ✅ Autoscale consumers — respond to queue depth or consumer lag metrics
  • ✅ Monitor queue depth continuously — alert on sustained saturation
  • ✅ Avoid fan-in bottlenecks — partition workloads across shards
  • ✅ Use graceful degradation — shed non-critical load before the queue fills
  • ✅ Implement exponential backoff — prevent retry storms on recovery

Production Readiness Checklist
  • Define queue capacity intentionally — never leave it unbounded
  • Monitor queue depth and consumer lag as primary SLIs
  • Apply bounded queues with explicit overflow policy
  • Configure rate limiting at the ingress layer
  • Implement exponential backoff on retry (never linear)
  • Add circuit breakers to isolate slow downstream services
  • Autoscale consumers when queue depth exceeds threshold
  • Alert on sustained queue saturation (>30s at >80% capacity)
  • Load test burst traffic at 2–3× expected peak
  • Document overload behavior in runbook
"Backpressure is a feedback mechanism that prevents fast producers from overwhelming slower consumers. In production systems, I always use bounded queues, rate limiting, and flow control so overload is propagated upstream instead of causing unbounded memory growth or cascading failures. The key trade-off is balancing throughput, latency, and reliability while keeping the system stable under peak load."
KEY TAKEAWAYS
📌 What to Remember
  • Backpressure is feedback, not failure — it helps stabilize overloaded systems by signaling producers to slow down before the system breaks.
  • It occurs when producers generate work faster than consumers can process it — caused by slow consumers, thread pool saturation, network congestion, or traffic bursts.
  • Bounded queues are the foundation of effective backpressure — without capacity limits, queues grow unbounded and exhaust memory.
  • Monitor queue depth, consumer lag, latency, and thread pool saturation to detect backpressure early before it becomes a cascading failure.
  • Staff Engineers treat backpressure as a system-wide resilience mechanism, combining flow control, autoscaling, rate limiting, and graceful degradation to prevent overload from becoming a cascading failure.
ORIGINAL NOTES — IMPLEMENTATION REFERENCE
Backpressure Implementation Patterns

Java ThreadPoolExecutor — Complete Backpressure Config

// ThreadPoolExecutor is the canonical backpressure example in Java ThreadPoolExecutor executor = new ThreadPoolExecutor( corePoolSize, // always-alive threads maxPoolSize, // max threads under load keepAliveTime, // idle thread TTL TimeUnit.SECONDS, new ArrayBlockingQueue<>(queueCapacity), // BOUNDED — key! rejectedHandler // what happens when queue is full ); // 4 built-in rejection policies (RejectedExecutionHandler): // 1. AbortPolicy (default) → throw RejectedExecutionException // 2. CallerRunsPolicy → caller thread runs the task (natural backpressure) // 3. DiscardPolicy → silently drop the task // 4. DiscardOldestPolicy → drop oldest task, retry new one // CallerRunsPolicy is often the best backpressure mechanism: // → Slows down the thread submitting tasks → self-regulating // → No data loss, no exception → graceful degradation // Monitor with JMX: executor.getQueue().size(); // current queue depth executor.getActiveCount(); // active worker threads executor.getCompletedTaskCount(); // throughput executor.getRejectedExecutionCount(); // rejection rate (via custom handler)

Kafka Producer Backpressure

// Kafka producer has internal send buffer — backpressure via blocking Properties props = new Properties(); props.put("buffer.memory", 33554432); // 32MB send buffer props.put("max.block.ms", 60000); // block up to 60s when buffer full props.put("linger.ms", 5); // batch messages for 5ms props.put("batch.size", 16384); // 16KB batches KafkaProducer<String, String> producer = new KafkaProducer<>(props); // When broker is slow or unavailable: // 1. Send buffer fills → producer.send() blocks for max.block.ms // 2. After max.block.ms → throws TimeoutException (backpressure signal) // 3. Application should catch and apply exponential backoff // Consumer lag = primary backpressure metric for Kafka: // kafka.consumer:type=consumer-fetch-manager-metrics, // attribute=records-lag-max → growing lag = consumer too slow

TCP Flow Control — Hardware-Level Backpressure

// TCP uses receive window to implement backpressure: // Receiver advertises available buffer space in every ACK // Sender may not send more bytes than receiver's window allows Sender Receiver │ │ │ SEQ=1, DATA[1-1000] │ │ ──────────────────────────────► │ │ │ Buffer: [1-1000] │ ◄──────────────── ACK=1001, WIN=4096 │ (4096 bytes free) │ │ │ SEQ=1001, DATA[1001-5000] │ (sends up to window) │ ──────────────────────────────► │ │ │ Buffer almost full │ ◄──────────────── ACK=5001, WIN=0 │ WIN=0 → STOP sending! │ │ │ (sender pauses) │ Application reads buffer │ ◄──────────────── ACK=5001, WIN=4096 │ Space freed → resume

Reactive Streams — Demand-Driven Backpressure

// Reactive Streams spec: subscriber controls demand // Publisher sends AT MOST N items per request(N) call // Never more than subscriber can handle // Project Reactor example: Flux.range(1, 1_000_000) .onBackpressureBuffer(1000) // buffer up to 1000 items // or: .onBackpressureDrop() // drop items subscriber can't handle // or: .onBackpressureLatest() // keep only most recent item .subscribe(new BaseSubscriber<Integer>() { @Override protected void hookOnSubscribe(Subscription subscription) { request(10); // request only 10 items initially } @Override protected void hookOnNext(Integer value) { process(value); request(1); // request 1 more after each processed } }); // RxJava 2+ also requires explicit backpressure handling: // Observable → no backpressure (will OOM on fast sources) // Flowable → explicit backpressure strategies required

Circuit Breaker — Backpressure + Failure Isolation

// Resilience4j circuit breaker pattern CircuitBreakerConfig config = CircuitBreakerConfig.custom() .failureRateThreshold(50) // open if 50% of calls fail .waitDurationInOpenState(Duration.ofSeconds(60)) .permittedNumberOfCallsInHalfOpenState(5) .build(); CircuitBreaker cb = CircuitBreaker.of("db", config); // States: // CLOSED → normal operation // OPEN → reject all calls immediately (fast fail, no backpressure) // HALF-OPEN → let limited calls through to test recovery // Exponential backoff with jitter: RetryConfig retryConfig = RetryConfig.custom() .maxAttempts(3) .intervalFunction(IntervalFunction.ofExponentialRandomBackoff( 1000, // initial interval ms 2.0, // multiplier 0.5 // jitter factor )) .build(); // 1st retry: ~1s, 2nd retry: ~2s±jitter, 3rd: ~4s±jitter // Jitter prevents retry storms (thundering herd)
"Every production queue must have three things: a bounded capacity, a defined overflow policy, and continuous depth monitoring. A large queue without backpressure is not a buffer — it is a latency bomb and an OOM risk masquerading as reliability."
