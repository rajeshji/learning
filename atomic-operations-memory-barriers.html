Atomic Operations & Memory Barriers

Staff Engineer Reference — Hardware, OS & Language-Level Concurrency Primitives

THE BIG PICTURE
Why Staff Engineers Must Master This

Every synchronization primitive — mutex, spinlock, semaphore, monitor, lock-free queue — is built on top of atomic operations and memory barriers. Without them, concurrent programs produce incorrect results even on single-core CPUs due to compiler reordering, and catastrophically wrong results on multi-core CPUs due to CPU reordering and cache incoherence.

Concurrency Stack (bottom to top): CPU Hardware → Cache coherence (MESI), atomic instructions (CAS, LOCK prefix) Memory Model → Ordering guarantees (acquire/release/seq-cst/relaxed) OS Kernel → Futex, atomic kernel primitives, memory barriers Language Runtime → Java volatile, AtomicInteger, C++ std::atomic Library → Mutex, RWLock, Semaphore, ConcurrentHashMap Application → Thread-safe code
Staff-level insight: You must know this stack from bottom to top — understanding why volatile isn't enough, why CAS can ABA-fail, why barriers exist, and when relaxed ordering is safe.
ROOT CAUSE
Why Reordering Happens — The Problem

Modern CPUs and compilers reorder instructions for performance. This is invisible on a single thread (sequential consistency illusion) but breaks multi-threaded programs.

1. Compiler Reordering

Compiler may reorder independent reads/writes for optimization. Breaks intended ordering.

2. CPU Out-of-Order Execution

CPU executes instructions out of order (superscalar pipelines). Stores may be visible to other cores out of order.

3. Store Buffer / Write Buffer

Stores go into a write buffer first; other CPUs may not see them immediately. ARM and x86 both have store buffers.

Classic Example — Broken without barriers: Thread 1: Thread 2: data = 42; if (ready == 1) { ready = 1; print(data); // may print 0! } CPU or compiler may reorder ready=1 BEFORE data=42 from Thread 2's perspective. → Thread 2 sees ready=1 but data=0 → DATA RACE → undefined behavior

Compare-And-Swap (CAS) — Most Important

// Pseudocode for CAS bool CAS(int* addr, int expected, int new_val) { atomic { if (*addr == expected) { *addr = new_val; return true; // success } return false; // failure — someone changed it } } // x86 hardware: LOCK CMPXCHG // Java: Unsafe.compareAndSwapInt(), VarHandle.compareAndSet() // C++: std::atomic::compare_exchange_strong()

ABA Problem — Critical CAS Failure Mode

Thread 1 reads A. Thread 2 changes A → B → A (back to same value). Thread 1's CAS succeeds (sees A), but state has changed invisibly. Fix: Stamp/Version counter — CAS on (value, version) pair. Java: AtomicStampedReference, AtomicMarkableReference C++: ABA-safe with LL/SC on ARM, or versioned pointers
MEMORY BARRIERS
Memory Barriers / Fences — Controlling Visibility

A memory barrier (fence) is an instruction that prevents the CPU/compiler from reordering memory operations across the barrier boundary. They enforce visibility ordering between threads.

MEMORY ORDERING
Memory Ordering Models — Acquire/Release/SeqCst

C++ std::atomic and Java's memory model expose memory orderings that give you fine-grained control over barriers — letting you use cheaper orderings where full fences aren't needed.

OrderingGuaranteeCostUse Case
RelaxedAtomicity only — no ordering relative to other opsCheapestCounters, statistics (order doesn't matter)
AcquireNo load/store after this can be reordered BEFORE itLowLock acquire, read side of flag
ReleaseNo load/store before this can be reordered AFTER itLowLock release, write side of flag
Acq_RelBoth Acquire and Release (for RMW ops)MediumCAS for mutual exclusion
Seq_CstGlobal total order across all threads — full fenceMost expensiveDefault Java volatile; safety first
// Acquire/Release pattern — the correct way to pass data between threads // C++ std::atomic example: std::atomic<int> data{0}; std::atomic<bool> ready{false}; // Thread 1 (producer): data.store(42, std::memory_order_relaxed); // no ordering needed ready.store(true, std::memory_order_release); // RELEASE: data visible before this // Thread 2 (consumer): while (!ready.load(std::memory_order_acquire)); // ACQUIRE: see all stores before release int val = data.load(std::memory_order_relaxed); // safe: guaranteed to see 42 assert(val == 42); // ALWAYS passes
Acquire/Release handshake: A release store on Thread 1 "synchronizes-with" an acquire load on Thread 2. Everything before the release is visible after the acquire. This is the foundation of mutexes.

CACHE COHERENCE
MESI Protocol — How Caches Stay Consistent

Modern CPUs use the MESI protocol to keep L1/L2/L3 caches coherent across cores. Understanding MESI explains why atomics and barriers work.

StateMeaningShared?Modified?
ModifiedDirty copy — only this cache has it, written back on evictionNoYes

SharedClean copy — multiple caches have itYesNo

// What happens when Core 1 writes to a cache line: Core 1: RFO (Request For Ownership) → broadcast to all cores Other cores: Invalidate their copies (state → I) Core 1: Gets Exclusive (E), writes → Modified (M) // When Core 2 reads the same line: Core 2: Cache miss → requests line from Core 1 Core 1: Writes back → line goes Shared (S) in both caches // Atomic CAS on a cache line: LOCK prefix → acquires cache line ownership (E/M state) → other cores see Invalid until LOCK released → guarantees atomicity across all cores
JAVA MEMORY MODEL
Java — volatile, AtomicInteger, VarHandle

Java's Memory Model (JMM) defines happens-before relationships that guarantee visibility across threads.

volatile — Sequential Consistency on a single variable

// volatile guarantees: // 1. Visibility: write is immediately visible to all threads // 2. Ordering: no reordering across volatile read/write // 3. NOT atomicity for compound operations (i++ is NOT atomic) volatile boolean ready = false; volatile int data = 0; // Thread 1: data = 42; // write data ready = true; // volatile write = full barrier → data always visible after // Thread 2: while (!ready); // volatile read = acquire barrier System.out.println(data); // always 42 // WARNING: volatile int counter; counter++ is NOT thread-safe (read-modify-write)

AtomicInteger — CAS-based thread-safe operations

// All operations use LOCK CMPXCHG internally (x86) AtomicInteger counter = new AtomicInteger(0); counter.incrementAndGet(); // atomic i++ counter.addAndGet(5); // atomic add counter.compareAndSet(10, 20); // CAS: if 10, set to 20 counter.getAndUpdate(x -> x * 2); // atomic lambda update // For high-contention counters, prefer LongAdder (less CAS contention) LongAdder sum = new LongAdder(); sum.increment(); // updates per-thread cell → merge on sum()

VarHandle — Low-level fine-grained control (Java 9+)

// VarHandle gives access to different memory orderings VarHandle VH = MethodHandles.lookup().findVarHandle(MyClass.class, "field", int.class); // Relaxed — no ordering guarantee (just atomicity) VH.setOpaque(obj, 42); int v = (int) VH.getOpaque(obj); // Acquire/Release — for producer-consumer patterns VH.setRelease(obj, 42); // release store int v = (int) VH.getAcquire(obj); // acquire load // Sequential Consistency — full barrier (like volatile) VH.setVolatile(obj, 42); int v = (int) VH.getVolatile(obj);

LOCK-FREE PATTERNS
Building Lock-Free Algorithms with Atomics

Spinlock using CAS

// Lock-free spinlock (C++) std::atomic<bool> locked{false}; void lock() { bool expected = false; while (!locked.compare_exchange_weak( expected, true, std::memory_order_acquire, // acquire on success std::memory_order_relaxed)) // relaxed on failure { expected = false; while (locked.load(std::memory_order_relaxed)); // spin in cache } } void unlock() { locked.store(false, std::memory_order_release); // release }

Lock-Free Stack (Treiber Stack)

// Each push/pop uses CAS — no mutex needed struct Node { int data; Node* next; }; std::atomic<Node*> head{nullptr}; void push(int val) { Node* n = new Node{val, nullptr}; do { n->next = head.load(std::memory_order_relaxed); } while (!head.compare_exchange_weak( n->next, n, std::memory_order_release, std::memory_order_relaxed)); } // Problem: ABA — use hazard pointers or epoch-based reclamation for safe memory reclaim

Sequence Lock (Seqlock) — Linux Timekeeping

// Writers increment sequence (odd = writing), readers retry if odd atomic<unsigned> seq{0}; void write(int* data, int val) { seq.fetch_add(1, release); // start write (make seq odd) *data = val; seq.fetch_add(1, release); // end write (make seq even) } int read(int* data) { unsigned s1, s2; int val; do { s1 = seq.load(acquire); // read sequence if (s1 & 1) continue; // writer active — retry val = *data; s2 = seq.load(acquire); } while (s1 != s2); // retry if sequence changed during read return val; } // Readers NEVER block — writers use seq barrier, not mutex
FAILURE MODES
Common Failure Modes & Bugs
ABA Problem

CAS sees same value after A→B→A transition. Pointer has changed but CAS succeeds incorrectly. Fix: AtomicStampedReference, hazard pointers, epoch-based reclamation.

Volatile Compound Operations (Java)

volatile int i; i++ is NOT atomic — it's three operations (load, add, store). Use AtomicInteger for compound ops.

Missing Barrier on ARM/POWER

Code working on x86 (strong TSO model) silently fails on ARM (weak model) without explicit barriers. Always use std::atomic or language memory model — never raw assembly for cross-platform code.

Spurious CAS Failure (compare_exchange_weak)

compare_exchange_weak may fail spuriously on LL/SC architectures (ARM). Always wrap in a loop. Use compare_exchange_strong when spurious failures are unacceptable.

Atomic Operations Deep Reference

Why Atomicity Is Needed

Non-atomic increment: i++ Step 1: LOAD i into register Step 2: ADD 1 to register Step 3: STORE register to i Thread A: LOAD (i=0) Thread B: LOAD (i=0) ← interleaved here Thread A: ADD, STORE (i=1) Thread B: ADD, STORE (i=1) ← lost update! Expected: 2 Actual: 1 → DATA RACE

LL/SC vs CAS

// CAS (x86): if (mem == expected) { mem = new; return true; } Weakness: ABA — cannot detect A → B → A transition // LL/SC (ARM): LDREX r0, [addr] // Load-Linked — tags the address STREX r1, r2, [addr] // Store-Conditional — only succeeds if no other write since LDREX // LL/SC naturally avoids ABA — any write to addr (even back to A) fails the SC // LL/SC may fail spuriously → always in retry loop

Memory Barriers — All 4 Types

// 4 types of reordering to prevent: // LoadLoad — earlier load sees result of later load? // StoreStore — later store visible before earlier store? // LoadStore — load reordered after a store? // StoreLoad — store delayed past a subsequent load? // x86 barrier instructions: LFENCE → prevents LoadLoad reordering SFENCE → prevents StoreStore reordering MFENCE → prevents all 4 types (full barrier) PAUSE → spin-loop hint for hyperthreading efficiency // ARM barrier instructions: DMB ISH → Data Memory Barrier (Inner Shareable) — full barrier DSB ISH → Data Synchronization Barrier — stronger, drains pipeline ISB → Instruction Sync Barrier — flush pipeline (for self-modifying code)

MESI State Machine Transitions

State transitions for a cache line when Core 1 writes: Modified (M) ←── Core 1 writes (sole owner) │ │ Another core reads ▼ Shared (S) ←── Multiple cores have clean copy │ │ Core 1 writes (RFO) ▼ Exclusive (E) ←── Core 1 has clean exclusive copy │ │ Core 1 writes ▼ Modified (M) ──► on eviction ──► write back to memory │ │ Another core reads (bus snoop) ▼ Shared (S) Invalid (I): stale — must fetch from another cache or RAM

Java Memory Model — Happens-Before Detailed

// JMM defines visibility via "happens-before" (HB) relation // If A HB B → all of A's writes are visible to B Key HB rules: 1. Program Order: Each action HB next action in same thread 2. Thread Join: last action of thread HB join() return 6. Transitivity: if A HB B and B HB C → A HB C // The ONLY safe way to share data between threads: // 1. Use volatile (seq_cst) // 2. Use synchronized / locks // 3. Use AtomicXxx classes // 4. Thread.start() / Thread.join() boundaries // Anything else → data race → undefined behavior

C++ std::atomic Memory Orders — Full Reference

// memory_order_relaxed // → atomicity only; no ordering constraints // → use for: counters, statistics, flags where order doesn't matter std::atomic<int> count{0}; count.fetch_add(1, std::memory_order_relaxed); // memory_order_acquire (LOAD) // → no subsequent read/write can be reordered before this load // → establishes: "I will see everything before the paired release" bool ready = flag.load(std::memory_order_acquire); // memory_order_release (STORE) // → no prior read/write can be reordered after this store // → establishes: "all my prior work is visible to acquire loaders" flag.store(true, std::memory_order_release); // memory_order_acq_rel (RMW) // → combines acquire + release for read-modify-write operations // → used in: CAS for mutexes, exchange operations flag.compare_exchange_strong(expected, desired, std::memory_order_acq_rel); // memory_order_seq_cst // → total sequential order across ALL threads for ALL seq_cst ops // → most expensive → avoid in hot paths flag.store(true, std::memory_order_seq_cst); // default if not specified

Lock-Free MPSC Queue Sketch

// Multiple-Producer Single-Consumer queue (simplified) struct Node { int data; std::atomic<Node*> next{nullptr}; }; std::atomic<Node*> head{new Node{}}; // sentinel std::atomic<Node*> tail{head.load()}; // Producer (multiple threads — CAS on tail): void push(int val) { Node* n = new Node{val}; Node* old_tail; do { old_tail = tail.load(memory_order_acquire); } while (!tail.compare_exchange_weak(old_tail, n, memory_order_release, memory_order_relaxed)); old_tail->next.store(n, memory_order_release); } // Consumer (single thread — just reads head): int pop() { Node* h = head.load(memory_order_acquire); Node* next = h->next.load(memory_order_acquire); head.store(next, memory_order_release); return next->data; }
