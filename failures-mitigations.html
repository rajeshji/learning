Failure → Mitigation Strategies

Staff-level answer sheet · Detect → Mitigate → Prevent → Trade-off · 14 categories

Staff-Level Mental Model

Failure Occurs → Detect (How do we know?) → Mitigate (Recover) → Prevent (Next time) → Trade-off (What we sacrificed)

1. Infrastructure / Hardware Failures

Detect

Health checks · Heartbeats · Node monitoring

Mitigate

Replication · Auto failover · Redundant HW

Prevent

Multi-AZ / multi-region · RAID · Disk replication

Trade-off

Higher cost vs reliability

2. Network Failures

Detect

Latency metrics · Timeout monitoring · Packet loss alerts

Mitigate

Retries with backoff · Circuit breakers · Fallback paths

Prevent

Multi-network routing · Regional isolation

Trade-off

Retries can cause overload / retry storms

3. Application / Service Failures

Detect

Logs + metrics + alerts · Crash monitoring

Mitigate

Auto-restart (K8s) · Horizontal scaling · Circuit breaker for deps

Prevent

Load testing · Canary deployments · Memory profiling

Trade-off

Over-monitoring → alert fatigue

4. Data & Storage Failures

Detect

Checksums · Data validation · Audit logs

Mitigate

Replication · Backup & restore · Write-ahead logs

Prevent

Immutable logs · Strong consistency where needed

Trade-off

Strong consistency → higher latency

5. Distributed System Failures

Detect

Consensus health checks · Replica divergence monitoring

Mitigate

Leader election (Raft) · Quorum reads/writes · Conflict resolution

Prevent

Use proven consensus systems (etcd, ZooKeeper)

Trade-off

Consistency vs availability (CAP theorem)

6. Traffic & Load Failures

Detect

Traffic monitoring · Queue lag metrics · P99 latency

Mitigate

Auto-scaling · Load balancing · Rate limiting · Load shedding

Prevent

Capacity planning · Traffic shaping · Pre-scaling

Trade-off

Load shedding → some requests dropped

7. Concurrency & Race Conditions

Detect

Duplicate detection · Conflict logs · Integrity checks

Mitigate

Idempotency keys · Distributed locks · Optimistic concurrency

Prevent

Proper transaction design · CRDT for conflict-free data

Trade-off

Locks reduce throughput

8. Security Failures

Detect

Intrusion detection · Anomaly monitoring · Audit logs

Mitigate

Auth / authz · Rate limiting · WAF · Token revocation

Prevent

Encryption at rest/transit · Key rotation · Principle of least privilege

Trade-off

Strong security → higher latency + complexity

9. Dependency Failures

Detect

Dependency health checks · Error rate spikes

Mitigate

Circuit breakers · Fallback responses · Retry with backoff

Prevent

Decouple services · Cache critical data locally

Trade-off

Fallback → degraded / stale experience

10. Deployment & Configuration Failures

Detect

Deployment monitoring · Error rate spikes post-deploy

Mitigate

Rollback · Blue-green deployment · Canary releases

Prevent

Feature flags · Backward compatibility · Schema migration guards

Trade-off

Slower release cycles for safer deploys

11. Time & Scheduling Failures

Detect

Time-sync monitoring · Clock skew alerts · Job deadline tracking

Mitigate

Logical clocks (Lamport) · Retry delayed jobs · Graceful TTL handling

Prevent

NTP sync · Idempotent scheduling · Bounded clock drift (TrueTime)

Trade-off

Extra complexity for distributed time coordination

12. Human / Operational Failures

Detect

Audit logs · Change management alerts · Access monitoring

Mitigate

Rollback tools · Soft deletes · Access control enforcement

Prevent

Automation · Approval workflows · Runbook validation

Trade-off

More gates → slower operational velocity

13. Latency & Performance Failures

Detect

Latency histograms (P99) · Slow query logs · GC pause metrics

Mitigate

Caching · Query optimisation · Indexing · Connection pooling

Prevent

Load testing · Profiling in pre-prod · Continuous benchmarking

Trade-off

Cache → stale data risk

14. Cascading Failures — Most Dangerous

Detect

Retry spike metrics · Queue growth · Error rate chain reaction

Mitigate

Circuit breakers · Rate limiting · Bulkheads · Load shedding

Prevent

Service isolation · Timeout on all calls · Async decoupling

Trade-off

Partial system shutdown to save the whole

The Only Pattern You Need to Memorise

You don't need to remember 100 failures. You only need one pattern: retry → for transient failures (network, timeout) replicate → for hardware and data failures isolate → for cascading and dependency failures throttle → for load and traffic failures fallback → for dependency and deployment failures Everything maps to one of these five responses.
